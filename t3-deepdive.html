The memory wall

moving the math to where the data already is
325 papers · 27 read in full · 298 from the abstract

The Problem

Consider what it takes to multiply two numbers. Not the arithmetic — that is trivial, a fraction of a nanosecond on any modern chip. Consider getting the two numbers to the place where the multiply happens. Each number lives somewhere in memory, as a pattern of charge in a capacitor or the resistance of a transistor. To multiply them, a wire must carry that pattern from the memory cell to an arithmetic unit. The wire has length. Charging it takes energy and time. And there is only a finite number of such wires leaving the memory.

This is the whole problem, stated physically. An NVIDIA H100 GPU can perform 1,979 trillion 16-bit floating-point multiply-accumulate operations per second. But it draws its data from HBM — High Bandwidth Memory, a stack of DRAM dies bonded on top of the compute die — at 3.35 trillion bytes per second. A single 16-bit multiply-accumulate consumes two inputs, four bytes. So the memory can deliver at most 3.35 trillion / 4 = 838 billion operands' worth of work per second. The arithmetic units can consume more than twice that. The chip starves. Before it ever touches 43% of its rated compute, it runs out of things to compute *with*. This gap — arithmetic that outpaces the wires feeding it — is the memory wall, and it is the organizing constraint of nearly every paper in this corpus.

The wall is not a fixed height; it depends brutally on the workload. The relevant number is *arithmetic intensity*: how many arithmetic operations you do per byte you fetch. Multiply two large matrices together and each number you load gets reused across an entire row of outputs — high intensity, the chip runs near peak. But run the *decode* phase of a large language model, where the network generates one word at a time, and the intensity collapses. To produce a single next word, the model must read every parameter of the network exactly once and multiply each by one number. There is no reuse. Worse, it must also read the *KV cache* — a stored summary of every previous word in the conversation, one entry per word per layer per attention head — and compare the new word against all of them. For a 70-billion-parameter model at a 32,000-word context, that is over a hundred gigabytes of memory read to produce one word, with almost no arithmetic per byte. On this workload the H100 runs at roughly 20% of its rated compute, sometimes far less. One paper in this corpus measures exactly 21% compute utilization on Llama2-70B decoding. The expensive silicon sits idle, waiting for wires.

Two more facts sharpen the constraint. First, moving a byte costs far more energy than computing on it: reading an operand from off-chip DRAM burns on the order of a hundred times the energy of the multiply it feeds. So the memory wall is simultaneously an energy wall — data centers are power-limited, and most of the power goes to moving data, not transforming it. Second, capacity has its own wall. A 70-billion-parameter model in 16-bit precision is 140 gigabytes; an H100 holds 80. The model does not fit. You either split it across many GPUs (paying for interconnect and idle silicon) or you stream it from slower, larger memory (paying in bandwidth). Bandwidth, energy, and capacity form a three-way vise, and this research theme is the sustained effort to loosen it.

Why the Obvious Solution Does Not Work

The obvious answer is: make the memory faster. Add more wires. Widen the bus. This is exactly what the memory industry does, and it is not enough. The papers here show the frontier being pushed hard — a 42.5 Gb/s-per-pin GDDR7 DRAM at ISSCC 2025, an LPDDR5X chip crossing 12.7 Gb/s per pin with AC-coupled equalization to survive lossy channels — but each generation buys single-digit multiples while model sizes grow by orders of magnitude. The reason the wire count cannot simply grow is physical. Every wire off a memory chip needs a pin, a solder ball, a trace on the board. Chip perimeter is fixed by geometry, and signal integrity degrades as you push more bits per second down each wire. HBM already cheats by going vertical — stacking DRAM dies and connecting them with thousands of through-silicon vias straight down — but stacking traps heat: an ICCAD 2025 paper shows that adding HBM layers creates inter-die junctions with poor heat conductivity, forming hotspots that trigger *thermal throttling*, so the memory slows itself down to avoid cooking. You cannot win the bandwidth war by pushing bytes faster across a fixed boundary.

So the field splits along a deeper insight: if you cannot bring the data to the compute fast enough, move the compute to the data. And if you cannot do that cleanly, at least manage which data lives where, so the scarce fast bandwidth is spent only on bytes that matter. These two strategies — collapsing the memory-compute distance, and intelligently tiering the memory that remains — generate the four subthemes below. They are not alternatives; papers routinely combine them, and each creates new constraints for the others.

Subtheme 1: Processing-in-Memory — Doing the Arithmetic Where the Data Lives

What It Is

A DRAM chip is not a monolithic pool of bits. Internally it is a grid of *banks*, each bank a grid of *subarrays*, each subarray a matrix of cells whose rows are read out onto *sense amplifiers* thousands of bits wide. The bandwidth *inside* the chip — across those internal sense amplifiers — is enormous, far larger than the trickle that escapes through the external pins. Processing-in-memory (PIM) exploits this: bolt small arithmetic units directly onto the banks, and the data never has to leave the chip at all. The multiply happens millimeters from the cell instead of centimeters away across a starved bus. One paper measures the aggregate internal bandwidth of a rack of PIM-enabled GDDR6 chips at 512 terabytes per second — over a hundred times what those same chips could export through their pins.

The natural fit is exactly the workload that hurts most: matrix-vector multiplication, the operation at the heart of LLM decoding, where each weight is read once and touched once. There is no reuse to exploit, so the only lever is to stop paying the transport cost. PIM does precisely that. The catch is that a bank is not a general processor — it can host a small multiply-accumulate tree, maybe a lookup table, but not a flexible pipeline. So PIM is a scalpel, not a hammer: it wins overwhelmingly on the memory-bound kernels and does nothing for the compute-bound ones.

What the Research Community Is Doing

The most aggressive statement of the strategy is CENT ("PIM Is All You Need") at ASPLOS 2025, which builds a GPU-*free* LLM inference system: 32 CXL-attached devices, each holding 16 GDDR6-PIM chips with near-bank multiply-accumulate trees, delivering 2.3x the end-to-end throughput of four A100 GPUs at 2.9x lower energy on Llama2-70B, and 4.6x lower latency at batch size one. At the finer grain, AttenPIM (DAC 2025) recognizes that attention has *two* distinct matrix-vector shapes — scoring the new token against past keys, then blending past values — and gives each its own PIM mode, winning 1.13x–5.26x over uniform PIM baselines. PIMPAL (DAC 2025) replaces arithmetic entirely with in-DRAM lookup tables for edge devices, cutting area 40% while running 17.8x faster than prior lookup-based PIM. And CGO 2025's PIM-LLM shows the software side of the problem: a naive PIM deployment is throttled by the cost of shuttling operands from host to PIM, but a PIM-tuned tiled matrix-multiply library reaches 45.75x over the TVM baseline once that transfer is minimized.

Scaling PIM past a single die is its own research front. McPAL (DAC 2025) spreads unstructured sparse LLM weights across multiple HBM-PIM chiplets, routing the non-skipped multiplies through an in-memory butterfly network, reaching 1.57x–3.12x over an A100 at 10–36x the energy efficiency. SplitSync (DAC 2025) attacks a subtler cost: in bank-parallel PIM, every bank must first *activate* a row before it can compute, and that activation can take longer than the compute itself — so it lets bank *groups* run asynchronously to hide activation latency while staying synchronous inside a group to avoid extra accumulators, for 1.70x over conventional PIM. Even the instruction set gets attention: a DAC 2025 paper adds register-based addressing modes to in-DRAM PIM, cutting the control overhead of describing memory access patterns for 1.94x.

The Tradeoff

PIM trades generality for bandwidth. The arithmetic units it can fit near a bank are primitive, and the surrounding logic must not disturb the delicate analog timing of the DRAM array — WISEDRAM (DAC 2025) spends its whole design budget preserving standard DRAM read reliability while adding bitwise compute. Because PIM only helps memory-bound kernels, a PIM-only machine is lopsided: give it a compute-heavy phase (the *prefill* that ingests a long prompt) and it stalls exactly where a GPU would fly. This is why the pure-PIM systems remain research statements and why most of the corpus hedges toward heterogeneity, which is the next subtheme.

Subtheme 2: Heterogeneous Compute — Splitting Work Between Memory and a Real Processor

What It Is

If PIM is fast on memory-bound work and slow on compute-bound work, and a GPU is the reverse, the obvious architecture is to have both and route each piece of work to whichever engine suits it. The difficulty is that "memory-bound" versus "compute-bound" is not a fixed property of a kernel — it shifts at runtime with batch size, sequence length, and sampling strategy. A single attention operation can be bandwidth-limited for one request and compute-limited for another moments later. So heterogeneity is not just a hardware question (put a PIM unit next to a compute unit) but a scheduling question: decide, per operation, per instant, where it should run, and pay the cost of moving data across the boundary when you move it.

What the Research Community Is Doing

PAPI (ASPLOS 2025) makes the scheduling dynamic: it profiles each LLM-decoding kernel at runtime and remaps it between PIM units and GPU-like accelerators as its memory-versus-compute character shifts, rather than committing to a static assignment that is wrong half the time. PAISE (HPCA 2025) takes the more surgical route on real AMD MI100 hardware, offloading only the memory-bound attention layers to HBM-PIM while the GPU keeps the compute-bound layers, and reorders the KV-cache layout to exploit bank-level parallelism — cutting attention-layer time up to 48.3%. For Mixture-of-Experts models, where over 95% of the parameters sit in "expert" sublayers that are read sparsely, PIMoE (DAC 2025) splits work between an NPU and PIM with *throttle-aware* offloading that reacts to real-time throttling signals, and adds a near-memory data condenser to translate sparse layouts across the NPU/PIM boundary, for 4.5x over an A100.

The boundary itself is being redrawn physically. Stratum (MICRO 2025) stacks monolithic-3D DRAM with near-memory-processing logic via copper-to-copper hybrid bonding on a logic die, then tiers expert weights *inside* the stack by access speed, hitting up to 8.29x decoding throughput over a GPU baseline for MoE serving. A DAC 2025 near-memory processor uses 3D DRAM-to-logic hybrid bonding with a *centralized* controller (rather than one controller per bank, which wastes area) to reconfigure between the matrix-vector shape of decode and the matrix-matrix shape of prefill, for 2.9x over an NPU. And AsyncDIMM (HPCA 2025) solves a plumbing problem that blocks all of this: when both the host CPU and a near-memory accelerator want the same memory bus, they contend and can corrupt DRAM; AsyncDIMM adds a offload-schedule-return protocol that lets them share an unmodified bus safely, for 1.19x–1.92x.

The Tradeoff

Heterogeneity buys the best of both engines but pays in the seam between them. Every operation routed to PIM may need its operands re-laid-out first; every result may need to travel back. The scheduler that decides the routing is itself overhead, and a wrong decision is worse than no PIM at all. The physical integration — hybrid bonding, shared buses, near-memory controllers — is expensive and thermally constrained. The field is essentially betting that the seam can be made cheap enough that the win survives, and much of the cleverness in these papers is spent hiding the seam rather than doing the compute.

Subtheme 3: Spending Bandwidth Only on What Matters — KV Cache, Tiering, and Sparsity

What It Is

If you cannot widen the pipe, stop pushing junk through it. A large fraction of the memory traffic in modern inference is spent on data that barely affects the answer. In attention, most past tokens contribute almost nothing to the next word; in a memory hierarchy, most pages are cold; in a sparse weight matrix, most entries are zero. The strategy of this subtheme is to identify, cheaply and at runtime, which bytes are worth their bandwidth — and skip, evict, compress, or demote the rest. The hard part is that the identification must cost less than the traffic it saves, or the cure is worse than the disease.

What the Research Community Is Doing

The KV cache is the richest target because it grows without bound as a conversation lengthens. VEDA (DAC 2025) uses a voting scheme to evict unimportant key-value entries, shrinking the cache while a dataflow-flexible accelerator handles the resulting irregular shapes — turning an O(N) problem into O(1) per step. Sella (DAC 2025) predicts, using cluster-based associative arrays, which key-value pairs a query will actually correlate with, then fetches only those — a 66% reduction in off-chip memory access with under 1% accuracy loss and no retraining. UniCAIM (DAC 2025) goes further and fuses a *content-addressable memory* (hardware that finds matching entries in one step) with compute-in-memory on FeFET devices, doing both static and dynamic KV pruning in place for 8.2x–831x energy-delay improvement. A DAC 2025 accelerator predicts query-key correlation with a cluster-based associative array to selectively access the cache at all.

At the system level, the same "spend bandwidth on hot data" logic drives CXL memory tiering. CXL (Compute Express Link) lets a machine attach large pools of DRAM over a serial link, but that memory sits 140–410 nanoseconds further away than local DRAM — a range measured directly by the Melody characterization framework at ASPLOS 2025 across four real CXL devices. HybridTier (ASPLOS 2025) tracks both long-term access frequency and short-term "momentum" to keep genuinely hot pages in fast local DRAM and demote the rest to CXL, using probabilistic counters to keep the tracking cheap — 2.0x–7.8x less metadata overhead than prior tiering. M5 (ASPLOS 2025) pushes the access tracking into hardware inside the CXL controller, counting every 4KB page *and* every 64-byte word so it can migrate at sub-page granularity and avoid mistaking a warm page for a hot one, for 14% over the best CPU-driven scheme. On the DNN-accelerator side, SoMa (HPCA 2025) observes that once on-chip buffers are large enough to hold a whole layer, the remaining bandwidth pressure comes from *when* you prefetch and store across fused layers, and it schedules that communication for 2.11x and 37% less energy.

The Tradeoff

Skipping data is a bet that the skipped bytes did not matter, and the bet is probabilistic. Aggressive KV eviction can drop the one past token that turns out to be decisive; the papers guard this with accuracy budgets (under 1% loss) but the guard is workload-dependent and can fail on adversarial inputs. Tiering and prediction add tracking machinery — counters, associative arrays, hot/cold classifiers — that consume the very resources (SRAM, energy, latency) they are trying to save, so every design lives on a knife-edge where the metadata must stay an order of magnitude cheaper than the traffic. And sparsity makes memory access *irregular*, which fights the bandwidth-friendly sequential access patterns that DRAM is built for — several papers spend their hardware budget just re-regularizing the sparse traffic.

Subtheme 4: Emerging Memory as a Compute Substrate

What It Is

Everything above assumes the memory cell stores a bit and nothing more. But some device physics let the cell *compute*. In a resistive crossbar — a grid of wires with a programmable-resistance device (RRAM, PCM, or a magnetic tunnel junction) at each crossing — applying a voltage vector to the rows produces, by Ohm's law and Kirchhoff's current law, a current on each column equal to the dot product of the input voltages with the stored conductances. The entire matrix-vector multiply happens in one analog step, in the time it takes current to settle, with no data movement at all. This is compute-in-memory (CIM) in its purest form: the memory *is* the arithmetic unit. The prize is enormous energy efficiency — ISSCC 2025 macros in this corpus report 123.8 TOPS/W (YOCO, DAC 2025), 188.4 TOPS/W (a gain-cell CIM macro), and 60.81 TFLOPS/W for a diffusion-model accelerator — one to two orders of magnitude beyond digital GPUs.

The price is that analog is imprecise. The stored resistances drift and vary between devices; the summed current is corrupted by noise; and reading it back through an analog-to-digital converter is itself a major cost in area and energy. So the entire subtheme is a fight to get the efficiency of analog computation without letting its imprecision destroy the answer.

What the Research Community Is Doing

Much of the work is device- and circuit-level robustness engineering. CREST-CiM (DAC 2025) cross-couples two magnetic tunnel junctions per cell to store the +1/-1 weights of a binary network with an 8100:1 current ratio, making the difference between states easy to sense despite process variation, at 7.9% area overhead and near-software ResNet-18 accuracy. Guarder (DAC 2025) uses 3-transistor-2-RRAM cells for reliable multiply-accumulate despite RRAM's stochastic programming, and doubles the reliability circuit as a DNN IP-protection key. BiNeuroRAM (DAC 2025) cuts RRAM read power 14.7x–58.2x with a low-power sense amplifier so it can run spiking networks accurately. ISSCC 2025 shows the technology reaching integration: a monolithic MRAM-embedded microprocessor runs *end-to-end* DNN inference with 1.1 Mb of co-located weights and no external weight fetch — the whole network lives and computes in the memory.

The other half of the work pushes the imprecision problem up to the algorithm. SAGE (ICCAD 2025) reorders the weight and input channels of an LLM by statistical kurtosis so that the salient, hard-to-quantize values do the least damage to the analog signal-to-noise ratio — training-free. YOCO (DAC 2025) mixes charge-domain multiply with time-domain accumulation and pairs RRAM with SRAM to trade density against precision, reaching 8-bit sub-petaops-per-watt. A DAC 2025 embedded-DRAM design ("333-eDRAM") stacks three different transistor materials — IGZO for retention, carbon nanotube for drive current, silicon for peripherals — to escape the single-material tradeoff between density, speed, and leakage, for 5.15x energy-area-delay improvement.

The Tradeoff

CIM offers the best energy efficiency in the entire corpus and the worst precision guarantees. It excels at low-precision, error-tolerant workloads — binary and spiking networks, quantized inference — and struggles the moment full floating-point accuracy is required. The analog-to-digital converters that read the crossbar output can dominate area and energy, clawing back much of the promised win; several papers (OptiRange at ICCAD 2025) exist solely to optimize converter resolution. And the exotic devices — RRAM, FeFET, MRAM — are not yet manufacturable at the density and yield of standard DRAM, so CIM today lives mostly at the edge (always-on sensors, mobile) where its efficiency is decisive and its precision limits are tolerable, not in the datacenter where the memory wall bites hardest.

How the Pieces Fit Together

Read across the four subthemes and a single strategic logic appears. The memory wall cannot be climbed by any one move, because each move trades one scarce resource for another. Widening the external bus hits pins and heat. Moving compute into memory (PIM/CIM) recovers the huge internal bandwidth but sacrifices generality and, for analog, precision. Skipping data recovers bandwidth without new hardware but bets on the data being skippable and pays in irregularity. Tiering recovers capacity at the cost of latency and tracking overhead. The field is not choosing among these — it is stacking them, and the interesting engineering is in the interactions.

Those interactions are mostly frictions. Push compute into memory and you inherit memory's constraints: DRAM PIM must respect row-activation timing (hence SplitSync), preserve read reliability (hence WISEDRAM), and share the bus with the host (hence AsyncDIMM). Adopt sparsity to save bandwidth and you destroy the sequential access that DRAM and PIM both want, forcing butterfly networks and data condensers to re-regularize traffic. Stack memory in 3D to shorten the compute-data distance and you concentrate heat, throttling the very bandwidth you built the stack to gain. Each solution to the memory wall erects a smaller wall behind it, and a large fraction of these papers are really about the second wall.

Where are the bets? The dominant one, visible across ASPLOS, DAC, HPCA, and MICRO, is *heterogeneous, disaggregated, tiered* systems glued together by CXL and 3D hybrid bonding: keep a flexible compute engine, surround it with PIM for the memory-bound kernels, pool capacity over CXL, and tier aggressively so the fast bandwidth is spent only on hot data. This is a datacenter bet, and it is where the LLM-serving papers cluster. The second bet is analog CIM at the edge, where the energy win is decisive and low precision is acceptable — this is where ISSCC's chip-level results live. The two bets share a foundation of device and packaging innovation (GDDR7, HBM thermal management, monolithic-3D DRAM, hybrid bonding, new transistor materials) that neither could exist without, and which quietly determines how high the wall is in the first place.

What Remains Hard

  • Analog compute-in-memory delivers 100x the energy efficiency but cannot yet guarantee floating-point accuracy; no one has shown a purely analog CIM system that trains or serves a full-precision transformer without accuracy-recovering digital scaffolding that erodes the efficiency win.
  • KV-cache eviction and sparsity prediction bet that skipped tokens do not matter, but the accuracy guarantee is empirical and workload-dependent; there is no method that bounds the worst-case error of a pruned cache before running the input.
  • 3D stacking shortens the compute-data distance but concentrates heat into un-coolable inter-die junctions; thermal throttling now caps achievable HBM bandwidth, and no packaging or scheduling approach reliably extracts the full stacked bandwidth without thermal collapse.
  • PIM units are primitive by necessity and helpless on compute-bound phases like prompt prefill; a design that serves both prefill and decode near-optimally on the same silicon, without a second engine and an expensive seam between them, does not yet exist.
  • CXL memory pools trade capacity for a 140–410 ns latency penalty, but tiering systems still misclassify warm pages as hot and pay for migrations that do not repay; sub-page hot/cold tracking that is both precise and nearly free remains open.
  • Emerging non-volatile memories (RRAM, FeFET, MRAM) are individually promising but manufacturable only at densities and yields far below standard DRAM, so datacenter-scale CIM — where the memory wall is tallest — has no viable substrate today.
  • The scheduler that routes each operation to PIM, CIM, or a compute engine is now a first-class bottleneck: deciding correctly at runtime, as a kernel shifts between memory-bound and compute-bound within milliseconds, without the decision itself costing more than the routing saves, is unsolved.

the approachesHow the field actually tackles it

1.Keep the right data close: caches and smarter eviction

The oldest and most universal answer to the memory wall is the cache: a small, fast pocket of storage sitting right next to the math, holding a copy of the data most likely to be needed soon. Because it is small, it can only hold a tiny fraction of everything, so the machine is constantly making a brutal decision — when a new number arrives and the pocket is full, which old number do you throw out to make room? Get this right and the needed data is almost always already at hand; get it wrong and you keep evicting exactly the thing you were about to use, forcing expensive trips to the warehouse. This 'which to throw out' decision is called a replacement policy, and a surprising amount of hardware research is devoted to it.

The subtlety is that not all data is equal, and the standard policies pretend it is. A major insight running through this work is that instructions — the program's own recipe steps — are far more costly to lose than ordinary data, because when the chip cannot find its next instruction it simply freezes, unable to make any progress at all. Several efforts (isca-2025-060, micro-2025-054, micro-2025-116, hpca-2025-089) rebuild cache eviction to specifically protect instructions, or to tag each piece of data with how 'hot' (frequently reused) it is so the cache keeps the hot things and discards the cold. Others (isca-2025-081, micro-2025-093, hpca-2025-120) chase near-perfect eviction decisions, some even proving what the theoretically best possible policy would be and then approximating it cheaply. This matters enormously for the sprawling software that runs data centers, whose recipe is so large it constantly overflows the small nearby storage.

The tradeoff is that cleverer policies need more bookkeeping — extra little tables that themselves take up space and energy to maintain. The whole game is squeezing better guesses out of the least possible bookkeeping. A recurring finding is that a simple, well-tuned rule often matches an elaborate learned one, so the elegant designs are the ones that get most of the benefit for almost none of the overhead.

2.Fetch data before it is asked for: prefetching

If the commute is the problem, one fix is to start the commute early. Prefetching means predicting which numbers the program will want next and sending for them in advance, so they arrive on the fast nearby counter before the moment they are needed — hiding the long trip behind work the machine is already doing. When it works, the wait vanishes; the data is simply there. The engine that does this watches the stream of memory requests, spots a pattern (say, the program is marching through a list one item after another), and races ahead to grab what comes next.

The hard cases are where the pattern is not a simple march. Many important programs chase pointers — they read one number to find out where the next number lives, which they must read to find the one after that, a chain where each step depends on the last (hpca-2025-021, isca-2025-036, isca-2025-069). You cannot run ahead when you do not know where you are going until you arrive. A cluster of work attacks exactly this: some use the compiler (the tool that translates human-written programs into machine steps) to analyze the code ahead of time and leave hints about the coming access pattern (isca-2025-036, isca-2025-069, isca-2025-102), some profile the program on a practice run to learn its habits (isca-2025-069, isca-2025-102), and some feed the predictor richer clues about the timing and ordering of past accesses (hpca-2025-021, hpca-2025-045-adjacent efforts).

Prefetching's danger is the mirror image of its promise: a wrong guess is not free. Fetching data that is never used wastes the very memory bandwidth you were trying to conserve, and can shove genuinely useful data off the counter. So the mature designs spend as much effort on restraint as on aggression — filtering out low-confidence guesses (hpca-2025-087, hpca-2025-057), gating prefetches by how busy the memory system already is, and, in tiny battery-scavenging devices that may lose power at any instant, suppressing prefetches that would simply be lost before they are ever used (isca-2025-030, hpca-2025-028).

3.Build a ladder of memory: tiering across fast and slow pools

No single kind of memory is both big and fast and cheap — you get to pick two. Fast memory is expensive and small; cheap memory is large and slow. So instead of choosing, engineers stack them into tiers: a modest amount of fast memory close in, backed by a large amount of slower, cheaper memory farther out, backed by even slower storage beyond that. The trick is to keep the frequently-touched ('hot') data in the fast tier and let the rarely-touched ('cold') data settle into the slow tier — and to keep re-sorting as the program's attention shifts. Guess hotness well and the machine feels as fast as the expensive tier while costing as little as the cheap one.

A new plumbing standard called CXL (think of it as a fast, flexible expansion port that lets you bolt large pools of extra memory onto a machine, or even share memory across many machines) has made this tiering suddenly urgent and practical, and a large share of this theme is about managing it (hpca-2025-125, isca-2025-121, asplos-2025-125, asplos-2025-130, asplos-2025-087). The extra memory reached over this port is a little slower than the memory soldered right next to the processor — measured at a few hundred billionths of a second of added delay — so the whole question becomes: which pages of data are worth keeping in the fast local pool, and which can be exiled to the roomier CXL pool without anyone noticing? The answers range from tracking both long-term and momentary popularity of each page (hpca-2025-125), to letting the memory port's own controller precisely count accesses so the system stops mistaking merely-warm data for genuinely-hot data (asplos-2025-130), to letting a learning agent tune the migration strategy on the fly (isca-2025-121).

The tension here is that the sorting itself costs something. Moving a page from the slow tier to the fast tier takes time and bandwidth, and the bookkeeping to track what is hot takes memory of its own. Migrate too eagerly and you spend all your effort shuffling; migrate too lazily and hot data languishes in the slow tier. The best systems are the ones that track hotness cheaply and move data only when the move will clearly pay for itself.

4.Move the math to the data: processing in and near memory

This is the most radical rethink and the beating heart of the chapter's title. If hauling data to the processor is the whole expense, invert the arrangement: leave the data where it sits and place small arithmetic units inside the memory chips themselves, or right beside them. Then a number can be multiplied or added without ever making the long trip out to the main processor. There is a spectrum here. At one end, tiny compute units are placed near the memory banks (called processing-in-memory or near-memory processing); at the other, the memory cells themselves are coaxed into doing the arithmetic as a side effect of how they are read (called compute-in-memory). Both share one goal: keep the data still.

This reframing is a particularly good fit for modern AI, because generating text is mostly a torrent of simple multiply-and-add operations over an enormous pile of weights that must be read in full — exactly the case where the data movement dwarfs the computation. Several ambitious systems build entire AI-serving machines out of memory-with-math and skip the flexible general-purpose accelerator chip altogether (asplos-2025-051, micro-2025-057, micro-2025-113, hpca-2025-050, hpca-2025-077). One reports serving a large language model faster and at a fraction of the energy of a rack of conventional accelerators, precisely because its arithmetic lives inside the memory and the weights barely move (asplos-2025-051). Others target the specific memory-hungry steps — the running-notes lookup, the state updates of newer model designs — and offload just those to memory-side compute while a conventional chip handles the rest (hpca-2025-050, hpca-2025-077, micro-2025-117, micro-2025-119).

The cost of this approach is real and shapes every design. Memory chips are built for density and cheapness, not computation; there is very little room to add logic without either shrinking the memory or blowing the power and heat budget. So the work is a constant negotiation: keep the in-memory math units small and simple (asplos-2025-051, micro-2025-057 shares one unit between two memory banks to halve its footprint), decide which operations are worth doing in memory versus shipping out (asplos-2025-054, micro-2025-067), and rearrange data so the in-memory units are not starved or imbalanced (asplos-2025-102, hpca-2025-104). And because these chips must serve two masters — ordinary storage and now also computation — a whole sub-thread is about compilers and mapping tools that figure out how to lay a program across this strange hybrid substrate (isca-2025-074, isca-2025-096, isca-2025-098-adjacent, hpca-2025-102).

5.Do the filtering where the data lives: computing inside storage

The same 'move the math to the data' logic applies one tier further out, at the permanent storage drives — and there the payoff can be even larger, because those drives are the farthest away and the slowest to reach. The classic waste is this: to find the few records you actually want, a program drags every record across the slow link from the drive into the main processor, checks each one, and throws almost all of them away. The commute was spent hauling data that was immediately discarded. In-storage computing puts a small amount of logic inside the drive so the useless records are filtered out before they ever leave (asplos-2025-007, isca-2025-000, isca-2025-095, hpca-2025-091, micro-2025-118-adjacent). Only the survivors make the trip.

This is especially potent for two workloads that dominate this theme. One is databases and analytics, where a query often asks for a tiny, highly selective slice of an enormous table — pushing the 'does this row match?' test down into the drive can cut the data that crosses the link by orders of magnitude (isca-2025-000, isca-2025-095, isca-2025-051, asplos-2025-092). The other is the retrieval step that feeds modern AI systems: before answering, these systems search a giant library of documents for the few most relevant passages, and that search is a bandwidth-hungry hunt through huge tables of numbers. A cluster of work performs that nearest-match search inside the storage or memory itself, so the machine only pulls out the handful of passages it actually needs (isca-2025-020, isca-2025-076, isca-2025-091, isca-2025-072, isca-2025-066, asplos-2025-112).

The difficulty is that storage drives speak in coarse, rigid chunks and have their own quirky internal rules about how data can be written and erased, so teaching them to compute means carefully co-designing the drive's logic with the software that uses it (hpca-2025-091, isca-2025-051, micro-2025-059). And the filtering logic must be flexible enough to handle the many shapes real queries take, which is why several designs build a small, purpose-made instruction set so the host can ship arbitrary filtering rules down to the drive rather than hard-wiring a fixed few (isca-2025-051, asplos-2025-007).

6.Send fewer bits and skip the useless ones: compression and eliminating dead traffic

If you cannot make the wire faster, send less down it. Two complementary ideas fall under this banner. The first is compression: squeeze the numbers into fewer bits before they travel, then expand them at the far end, so the same wire effectively carries more useful information. The catch is that expanding compressed data takes work, and if that work is slow it eats the very time you saved — so the clever designs build extremely fast, parallel unpackers that can restore data at the pace the processor consumes it (isca-2025-021). For AI specifically, the model's weights and running notes can be shrunk dramatically, multiplying the effective size of the fast memory and cutting the traffic (isca-2025-021, micro-2025-103, which cheekily repurposes the video-compression hardware already sitting on graphics chips to compress AI data instead).

The second idea is subtler and almost philosophical: a large fraction of the data a computer moves is not useful at all. It writes back numbers that a program has already finished with and will never read again; it fetches memory that has not yet been filled with anything meaningful. This is 'dead' traffic — pure commute with no cargo. One line of work has the software (the compiler and the memory manager) tell the hardware which regions are dead so it can simply skip moving them, cutting a quarter of memory traffic in warehouse-scale systems for free (asplos-2025-015). Related efforts eliminate redundant copies entirely — deduplicating identical pages of memory (hpca-2025-115), or letting many machines share one copy of a process's state over the fast expansion port instead of each copying it (asplos-2025-014).

The underlying tradeoff is accuracy and complexity. Compression that discards a little precision (using 'smaller numbers' — fewer bits per value) saves the most but risks degrading the AI model's answers, so a delicate art has emerged around shrinking the unimportant values hard while protecting the critical few (isca-2025-021, isca-2025-109). And identifying dead or duplicate data requires cooperation across the software and hardware boundary, which only pays off in tightly integrated systems where one team controls the whole stack.

7.Tame the irregular and the crooked accesses

Everything above works best when memory is touched in tidy, predictable streams. But some of the most important workloads are the opposite: they touch memory in a scattered, unpredictable, jumping-around fashion. Graph analysis (following connections between people or web pages), recommendation systems, and sparse math (where most values are zero and only the scattered non-zeros matter) all leap around memory almost randomly. This is poison for the memory system, because memory is designed to deliver a fat chunk of neighboring data at once — and when you only want one number out of that chunk, you have hauled a whole crate to use a single item. The commute is paid in full but the cargo is almost entirely wasted.

A broad set of work attacks this crooked-access problem from several angles. Some reorganize the data itself so that things touched together sit together, restoring locality where none existed (isca-2025-016, hpca-2025-030, hpca-2025-106). Some build specialized fetch engines that gather the scattered specific numbers efficiently and reorder the requests so the memory can serve them with less waste — one such engine reorders thousands of scattered requests at once, giving it hundreds of times more visibility than the ordinary memory controller and reclaiming most of the wasted bandwidth (isca-2025-055, isca-2025-036, hpca-2025-079). And many push the scatter-gather work down into or near the memory, so the wasteful hauling never crosses the long wire (hpca-2025-079, isca-2025-056, micro-2025-092, asplos-2025-138).

AI's newer irregular workloads join this family too: graph neural networks (which learn over networks of connections) and the growing use of 'mixture of experts' models (which, for each word, wake up only a small, unpredictable subset of the model's parts) both create exactly this scattered-access headache (hpca-2025-070, hpca-2025-103, isca-2025-056, micro-2025-012, micro-2025-057). The through-line is that regularity is a resource: where the hardware cannot count on it, the software, the data layout, and sometimes new memory-side logic must manufacture it — because a memory system fed crooked accesses will waste most of its effort no matter how fast its wires are.

8.Make the address lookup itself faster: page tables and translation

There is a hidden tax on nearly every memory access that outsiders never see. Programs do not use the real, physical location of data; they use convenient made-up addresses, and the hardware must translate each made-up address into a real one before it can fetch anything. That translation is itself a lookup in a table that lives in memory — so a single data fetch can secretly require several memory fetches just to figure out where to go. To hide this, chips keep a tiny cache of recent translations close by; but when a program's data is spread across a vast range of addresses, that little cache overflows and the translations start missing, and suddenly every access drags a chain of extra memory trips behind it. This is a real and growing bottleneck, especially for the flexible, massively parallel chips used for AI (hpca-2025-053, isca-2025-035) and for the enormous, sprawling programs in data centers.

The responses are inventive. Some batch many translation lookups together so they can share work instead of each paying the full price (hpca-2025-053). One striking design notices that the address-translation table is shaped like a tree, and that graphics chips already contain specialized hardware for walking tree structures — built for rendering images — so it repurposes that idle image-rendering hardware to do address translations, gaining translation throughput almost for free (isca-2025-035). Others reduce the pressure at its source by keeping data in larger contiguous blocks so fewer translations are needed at all (hpca-2025-115), or attack the related problem on the instruction side where the recipe's own address lookups stall the machine (asplos-2025-025).

The reason this belongs in a memory chapter is that translation is memory movement in disguise: every translation miss is one or more extra trips to the warehouse, hidden underneath the trip you actually wanted to make. Speeding up the arithmetic does nothing for it; the only cures are the same family of cures as the rest of the chapter — cache the lookups better, predict them, batch them, or move them closer to where they resolve.

where it standsWhat's solved, what's open

The field has genuinely conquered the easy, regular cases. For programs that march predictably through memory, caches and prefetchers hide the commute so well that the memory wall barely shows — decades of refinement have wrung most of the waste out of these paths, and the remaining gains here are small, single-digit-percent tunings rather than breakthroughs. What is emphatically not solved is the hard core of the problem: the irregular, scattered, pointer-chasing accesses of graphs and sparse math, the address-translation tax on huge sprawling programs, and above all the sheer volume of data that modern AI must haul — colossal piles of weights and ever-growing running notes that no cache can hold and that dominate both time and energy. For these, the machine still spends most of its life waiting, and no clean general answer exists.

The most promising and least settled frontier is moving the math to the data — computing inside or beside memory and storage. In narrow, hand-tuned demonstrations it delivers spectacular wins, sometimes several-fold speedups at a fraction of the energy, precisely because it stops the data from moving at all. But it remains far from a drop-in solution: memory chips have brutally tight room for logic, the hardware and software must be co-designed together rather than mixed and matched, the programming tools are immature, and thorny practical issues loom underneath — reliability problems where densely packed memory cells disturb their neighbors (a hazard these compute-in-memory schemes can worsen), and the awkwardness of chips forced to serve as both storage and calculator at once. The honest summary is that the community has a rich menu of partial answers, each excellent in its niche, and no consensus on which will generalize. The one thing everyone now agrees on is the diagnosis: the bottleneck is the movement of data, not the doing of arithmetic — and for the first time in the history of computing, the entire field is reorganizing itself around that fact.

What it does

Databases that handle both individual record updates (transactions) and large-scale data analysis at the same time have always faced a painful dilemma: the best memory layout for transactions (storing data row by row) is the worst for analysis (which prefers column by column), and any compromise hurts at least one workload. PUSHtap breaks this deadlock by storing data just once in a clever two-dimensional layout that lets the CPU read rows efficiently while special compute units embedded inside the memory chips simultaneously read columns at high speed — achieving fast transactions, up-to-date analytics, and genuine isolation between the two, all from a single copy of the data.

The method, in detail

The idea. Modern RAM modules contain many memory devices arranged in parallel. When a CPU reads memory, it reaches across all devices at once, grabbing one piece of each row simultaneously — this is called interleaved access. PUSHtap exploits the fact that doing math inside the memory chips (processing-in-memory, or PIM) works in the opposite direction: each PIM unit can only touch data stored on its own device. By mapping database rows to the 'across devices' dimension and database columns to the 'within a device' dimension, the CPU naturally reads complete rows in one sweep, while PIM units each handle a slice of a column in parallel.

How it works. (1) Compact aligned format: Because database columns have different byte widths, naive alignment wastes space. PUSHtap groups columns of similar width into 'parts' using a bin-packing algorithm with a tunable threshold, padding as little as possible. This achieves around 97% PIM bandwidth efficiency and around 60% CPU bandwidth efficiency simultaneously. (2) Block-circulant placement: If a single popular column always lands on the same PIM unit, that unit becomes a hotspot. PUSHtap rotates which column goes to which PIM unit every 1,024 rows, spreading load evenly. (3) MVCC (multi-version concurrency control — the standard mechanism letting readers and writers coexist without blocking each other): Updates go to a delta region while the main data region stays intact. Before each analytical query, a compact bitmap (one bit per row saying 'visible or not') is broadcast to all devices so PIM units can skip stale rows without extra communication. Defragmentation — moving the freshest row versions back into the main region — is offloaded to PIM units when rows are wide enough to justify it, using a formula derived in the paper. (4) Hardware support: A scheduler and polling module are added to the memory controller so the CPU sends a single command to trigger all PIM units, rather than messaging each one individually; a two-phase load/compute execution model limits CPU blocking to at most 300 microseconds per batch.

The result. Against the standard multi-instance design (which keeps separate row-store and column-store copies and must periodically rebuild the column copy), PUSHtap delivers 3.4 times higher peak transaction throughput and 4.4 times higher concurrent analytics throughput — while keeping data always fresh.

What it does

Mobile phones have tiny vector math units (128 bits wide) because bigger ones cost too much chip area. This paper turns half of a phone's existing level-2 cache memory into a massively wider vector engine (8,192 parallel lanes) by reusing the cache's storage cells as arithmetic logic. The catch is that existing instruction-set extensions only think about data in one dimension, so the paper invents a new multi-dimensional instruction set that lets a single instruction grab data across four nested dimensions at once, making the engine 2.9x faster and 8.8x more energy-efficient than the commercial mobile vector unit.

The method, in detail

The idea. A phone's L2 cache is a large grid of SRAM (fast on-chip static memory) cells. Prior work showed you can repurpose those cells to do arithmetic: by activating two rows at once, the sense amplifiers (the circuits that read a cell's value) can compute bitwise logic and, through repeated bit-by-bit passes, full integer addition and multiplication. This gives you 8,192 parallel lanes operating one bit at a time — a technique called bit-serial computing. The problem is that existing vector instruction sets (RISC-V RVV and Arm SVE) describe data in a single flat dimension. Mobile kernels (image codecs, audio, ML layers) live in 2D to 4D arrays; using a 1D instruction set to load a 3D data structure requires many separate partial loads plus masking instructions to piece them together. With 8,192 lanes waiting idle during all that overhead, utilization was only 23%.

How it works. MVE (Multi-dimensional Vector ISA Extension) introduces load/store instructions that describe up to four nested dimensions, each with its own stride — zero for replication, one for sequential, a computed stride for row-major layout, or an arbitrary value stored in a control register. A single 'strided load' walks a 3D or 4D loop nest and fills all 8,192 lanes in one instruction. For irregular data (image rows scattered in memory), a 'random load' fetches an array of base pointers for the outermost dimension and then applies stride rules to the inner dimensions. Masked execution is also multi-dimensional: rather than marking each of 8,192 individual lanes, you set or clear one bit per outer-loop iteration, which the controller fans out to the right lane group automatically.

The key hardware piece. Inside the cache controller, a Transpose Memory Unit (TMU) receives data words from main memory and rotates them — data arrives horizontally (one word per clock) but must be stored vertically in the SRAM bitlines (one bit from each of many elements aligned in a column) so the bit-serial engine can operate on all elements in parallel. A crossbar routes each incoming data element to its correct bitline column.

The result. Across 44 benchmarks from 12 real mobile libraries, MVE delivers 2.9x speedup and 8.8x energy reduction compared to the phone's built-in Arm Neon SIMD unit, at only 3.6% extra chip area added to the core. Compared to a same-sized RISC-V RVV engine driving the same underlying bit-serial hardware, MVE raises utilization from 23% to 60% and improves performance 3.8x by eliminating the flood of setup and mask instructions.

The idea. The compaction step — where nodes are merged and their bookkeeping information (called TransferNodes) is handed to neighbors — dominates 48% of total runtime. The processor spends 54% of that time just waiting for data to arrive from RAM, and uses only 2.5% of the available memory bandwidth, meaning the memory bus is almost entirely idle.
