Kimi K3, from first principles · Session 04 of 07

The same work — done in parallel.

The last rung gave our model a memory it can correct in place — but it has to do that one word at a time, each step waiting on the one before it. On long text, that waiting makes training painfully slow. This rung changes nothing about the answer and everything about the speed: it reorganizes the very same work so a computer can do it in big parallel batches instead of a single-file line.

▶ We ran it · the headline

The one-at-a-time version and the batched version give the same answer (they differ by about 7e-07 — pure rounding). The batched version shortens the chain of steps that must wait for each other by about 32×, and ran 24× faster even on an ordinary computer.

In plain words · the problem, then the idea

The same bookkeeping, reorganized to run in parallel

The erase-then-write method is exactly right, but it has a punishing flaw: each word has to wait for the one before it to finish, so you can't speed things up by working on many words at once.

The problem. Imagine a workshop where each person can't start until the person before them hands over their piece — a single-file line where nobody moves until the slowest link finishes. Training a model means doing this across millions of words. A modern computer is built to do hundreds of things at once, but the one-at-a-time rule forbids it. The bookkeeping itself isn't slow; the waiting is. So training crawls.

The idea. Inside a small block of text — say 32 words — the bookkeeping can all happen at once; you don't have to finish word 1 before touching word 2 within the block. What must still be passed in order is only a short summary from the end of one block to the start of the next. So you do each block's work in one parallel burst and hand a summary forward. The long chain of 'wait for the previous word' becomes a short chain of 'wait for the previous block' — and the answer comes out identical.

The name, translated. Researchers call this working in chunks (a 'chunk-wise' method): split the text into fixed-size blocks, do all the careful memory work inside each block at once, and pass only a brief summary between them.

What it still can't do

The memory is still one fixed-size board. It can blend and correct a labelled fact, but it can't wipe itself clean when the topic changes completely — old facts will still bleed into a new chapter. Giving it a way to deliberately forget is the next rung.

The idea · careful work in blocks, a summary between them

Do the bookkeeping inside a block, pass a summary between blocks

Split the text into blocks of, say, a few dozen words. Inside a block, do the full careful bookkeeping among just those words — and because it's a small, self-contained group, a computer can do it all at once. Between blocks, fold the finished block into a short running summary and read that summary at the start of the next block. The only thing that still has to happen in order is block-to-block, so the chain of must-wait steps drops from one-per-word to one-per-block:

# for each block, computed in one parallel burst: corrections = this block's fixes, given the summary handed in inside = careful bookkeeping among the words in THIS block (all at once) carried-in = what everything before the block contributes, read from the summary output = inside + carried-in summary = summary + this block folded in # handed to the next block

The one clever step is working out a block's corrections in a single shot instead of word by word — a small, self-contained calculation we can run for every block at the same time. After that, only the summary hand-off from one block to the next stays a loop.

We ran it · the parallel win

The chain of must-wait steps shrinks with block size

The number that actually matters for training is how many steps must run one-after-another because each needs the result of the one before. Working in blocks cuts that chain from one-per-word to one-per-block — and even in plain Python on an ordinary computer, swapping the long word-by-word loop for a few block-sized batches ran several times faster:

The real win is the length of the must-wait chain — the steps that have to run one after another because each needs the result of the last. One-at-a-time has one link per word; in blocks it has one link per block (here about 32× fewer), with all the within-block work done in parallel. That shorter chain is why it trains fast — and it showed up even here: swapping the long word-by-word loop for a handful of block-sized batches ran 8–20× faster on an ordinary computer. In a real system the same idea runs on a purpose-built routine on the graphics chip, with blocks of about 64–128 words.

We ran it · why C is a knob

One fixed cost, plus a cost that grows with block size

The total work splits in two. One part is fixed — the running-summary bookkeeping — and doesn't care how big the blocks are. The other part is the careful within-block work, and it grows with the block size. So block size is a dial: tiny blocks do the least total work but in many small steps; a single block the size of the whole text is the old, expensive everything-compared-to-everything again:

The one-line takeaway

Re-scheduling the exact same calculation — not changing it — cut the chain of waiting from millions of words to dozens of blocks and ran 3 to 22 times faster, while the answer stayed true down to rounding noise.
