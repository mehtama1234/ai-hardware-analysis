Kimi K3, from first principles · The grand synthesis

Kimi K3 is a hardware paper that happens to produce language.

Read the architecture ladder one way and it's a story about memory and meaning. Read it the way this repository reads its conferences — ISCA, MICRO, HPCA, ASPLOS, ISSCC, DAC, SC — and every rung turns out to be a well-known move from computer-architecture research, applied to one model. This is the long version of that second reading: each of K3's choices traced back to the hardware limit it exists to dodge, with the numbers we measured ourselves as evidence, and the papers this corpus has already mined as the field it comes from.

Part I

The one wall everything is built against

For fifty years the central fact of computer architecture has been that arithmetic got cheap far faster than moving data got cheap.

Chips can multiply numbers at a staggering rate. What they cannot do is feed themselves at the same rate — pulling the numbers to multiply out of memory and pushing the results back lags further behind every generation. Architects named this the memory wall decades ago, and it has only grown taller. Most of what a modern accelerator's engineering budget buys is not more multipliers; it is ever more elaborate ways to avoid waiting on memory: deep cache hierarchies, high-bandwidth memory stacked on the die, keeping data on-chip as long as possible.

Generating text with a large model runs straight into that wall — and, crucially, on the wrong side of it. When a model produces one word, it must read a great many stored numbers (the model's own settings, and its memory of the conversation so far) and do comparatively little math with each one before it needs the next. It is nearly all fetching, barely any computing. So the speed of text generation is set almost entirely by how many bytes you have to haul out of memory per word — not by how fast the chip can multiply.

Hold that sentence, because it is the key to everything below. Kimi K3 looks, from a distance, like a collection of clever ideas about intelligence. Up close, nearly every one of those ideas is a way to haul fewer bytes per word, or to keep the bytes it does haul closer to the arithmetic, or to spread them across more machines. The intelligence is real. But the shape of the design is dictated by the wall.

Why this reframing is worth the trouble

Once you see the memory wall as the organizing constraint, K3 stops being a grab-bag of tricks and becomes a single, coherent argument — the same argument the hardware conferences have been making for a decade, now written in the language of a language model. The rest of this page is that argument, one axis at a time.

Part II

First principles: the roofline, and why generating text is a memory problem

Architects have a simple picture for "is this workload limited by math or by memory?" — the roofline. Plot, for any computation, how much arithmetic it does per byte it moves (call it the work-per-byte). If a computation does a lot of work per byte, the chip's multipliers are the bottleneck and you are "compute-bound." If it does little work per byte, memory is the bottleneck and you are "memory-bound" — the multipliers sit idle waiting for data, and buying faster multipliers changes nothing.

Training a model is compute-bound: you push huge batches of text through at once, reusing each stored number across many examples, so the work-per-byte is high. But generating text is the opposite. You produce one word at a time, and for that single word you must read essentially the entire model and the entire memory of the conversation — using each fetched number just once. The work-per-byte is dismal. Generation lives far down in the memory-bound corner of the roofline, and that is not a detail to optimize away; it is the defining fact of serving a model.

This is exactly the framing the accelerator community now designs around. In this repository's own corpus you can watch it become the explicit target of silicon:

From this corpus — the memory-bound framing, in silicon
  • ISSCCA 28nm 0.22μJ/Token Memory-Compute-Intensity-Aware CNN-Transformer Accelerator with Hybrid-Attention
  • ISCAHybrid SLC-MLC RRAM Mixed-Signal Processing-in-Memory Architecture for Transformer Acceleration
  • ICCADAccelStack: A Cost-Driven Analysis of 3D-Stacked LLM Accelerators

Notice what these are reaching for. A chip that is "memory-compute-intensity-aware" is one that knows some phases are memory-bound and schedules around it. "Processing-in-memory" and "3D-stacked" are attempts to move the arithmetic to the data instead of hauling the data to the arithmetic — because the haul is the cost. K3 attacks the same problem from the other side: instead of new silicon that moves bytes better, it is a model architecture designed to need fewer bytes moved. Same wall, two directions of assault.

Part III

The precision axis — shrinking every number

The most direct way to haul fewer bytes is to make each byte carry more. If the model's settings take fewer bits each, there is simply less to move — and less to store. This is the oldest lever in the book, and the hardware-arithmetic community (ISSCC especially) has spent years on the question of how few bits you can get away with.

K3-class models ship at roughly four bits per setting, using a format called MXFP4 — a tiny four-bit floating-point number, with small groups of them sharing one scale factor. We implemented that format for real and squeezed a million actual numbers with it (Session 9). The result is the precision axis made concrete:

The four-bit float was not more accurate than plain four-bit integers in our run (about 12% per-number drift versus 11%). Its scale factor is constrained to a power of two, which wastes a little range. It ships anyway — and that is the whole lesson of the precision axis. The four-bit float wins not on accuracy but because its power-of-two scale is almost free to apply in hardware and four-bit floats run natively on the tensor cores. The choice is made by the silicon, not the statistics.

That is the tell that this is a hardware story. A format is chosen not because it represents numbers best, but because it costs the least to move and multiply. The corpus is thick with the same reasoning — precision as a systems knob, not a math one:

Part IV

The bandwidth axis — the cache that must not grow

Shrinking the model is the easy half. The hard half is the conversation's own memory — and it is where K3's most important idea lives.

Recall the wall: generation is limited by bytes-per-word. The model's settings are a fixed cost you pay every word no matter what. But the other thing you must read every word is the memory of everything said so far — and in the original design that memory grows with every word. Sessions 1 and 2 measured it: a keep-every-word memory climbs to hundreds of megabytes and then gigabytes as a conversation lengthens, and all of it must be streamed off memory for each new word. On the roofline, this is the worst possible workload: enormous byte traffic, almost no arithmetic per byte.

This single quantity — the growing conversation memory (the "KV cache") — is the number-one reason long-context serving is expensive, and the corpus shows the field throwing everything at it: pruning it, compressing it, re-sharding it, building custom memory for it:

From this corpus — fighting the growing cache
  • DACUniCAIM: A Unified CAM/CIM Architecture with Static-Dynamic KV Cache Pruning for Efficient Long-context
  • DACDIAS: Distance-based Attention Sparsity for Ultra-Long-Sequence Transformer
  • MLSYSSeesaw: High-throughput LLM Inference via Model Re-sharding
  • SCSlimPipe: Memory-Thrifty and Efficient Pipeline Parallelism for Long-Context LLM Training

Those papers make the growing cache cheaper. K3's answer is more radical: make it stop growing at all. Its main memory (KDA — the fixed-size running summary built over Sessions 2 through 6) holds the whole conversation in a state whose size never changes, however long the text runs. So the bytes streamed per word for the conversation memory go from climbing-forever to flat. We watched this happen on a real GPU (Session 2):

The point, in roofline terms

KDA does not make the model "smarter about attention." It changes the workload's work-per-byte: a fixed state read with a matrix multiply has far better arithmetic intensity than gathering an ever-larger cache. K3 takes the worst-positioned workload on the roofline and drags it upward. The few full-recall layers it keeps (MLA) are themselves compressed so even they stream less. This is the bandwidth axis, and it is the heart of the machine.

Part V

The compute axis — do less by waking fewer

Having fought the byte traffic, there is still the arithmetic itself. A model's capacity — how much it can know — tends to scale with its number of settings, but running every setting for every word is expensive. The architecture community's long-standing answer is conditional computation: build a large machine but only switch on the part you need. In neural networks this is the mixture-of-experts — hundreds of specialist sub-networks, of which a router wakes only a few per word.

K3 has 898 experts and wakes 18 per word (Session 7): roughly 3.7% of the model runs for any given word. Capacity scales with the full count; cost scales with the woken few. This is structured sparsity — and the corpus is full of hardware built specifically to exploit exactly this pattern, because sparsity is only a win if the silicon can skip the sleeping parts without wasting the skip:

From this corpus — sparsity and experts as a hardware target
  • ICCADMoE-OPU: An FPGA Overlay Processor Leveraging Expert Parallelism for MoE-based LLMs
  • DACPIMoE: Towards Efficient MoE Transformer Deployment on NPU-PIM System through Throttle-Aware Tasking
  • SCCompression Error Sensitivity Analysis for Different Experts in MoE Model Inference
  • ICCADDANCE: Dual-Side Agile N:M Sparse Compressed Digital CiM Accelerator

But conditional computation is never quite free, and here the story takes its most interesting turn — because sparsity does not remove the bottleneck. It moves it.

Part VI

The bottleneck moves — from arithmetic to the network

Solve the compute problem and you inherit a communication problem. This is the frontier the conferences are actually on right now.

898 experts, even squeezed to four bits, are far too many to fit on one accelerator. So they are spread across many chips — a few experts per chip. But each word needs its own particular handful of experts, scattered across the machines. So every word triggers a burst of chips shipping pieces of the computation to each other to gather the right experts and scatter the results back. This collective shuffle (an "all-to-all") happens at every expert layer, and its cost is set by the interconnect between chips — the network — not by any chip's math.

This is why the newest and most expensive-looking work in the corpus is not about multipliers at all. It is about wires, links, and photons — moving the bottleneck's home from the compute die to the fabric between dies:

From this corpus — the bottleneck's new home is the network
  • SCScaling All-to-All Operations Across Emerging Many-Core Supercomputers
  • HotChipsUB-mesh: A New Interconnection Technology for Large AI SuperNode
  • HotChipsA UCIe Optical I/O Retimer Chiplet for AI Scale-up
  • ICCADWaferscale Silicon Photonics Systems: A Cost-Benefit Analysis and Optimization

And this is where our own MoE experiment (Session 7) turns out to be a systems result in disguise. We trained a router on lopsided demand and watched, without a balancing incentive, one expert swell to 4.2× its fair share of the traffic. On a single machine that is merely wasteful. Spread across chips it is fatal: a collective operation runs only as fast as its slowest participant, so one overloaded expert-chip stalls every other chip waiting for it — the classic straggler problem. The load-balancing nudge (which cut the busiest share to 2.9×) is not about model quality; it is about keeping the network's collective from stalling on a hot spot. Moonshot open-sourced a dedicated MoE communication library for exactly this reason.

The deep pattern

Each axis, solved, exposes the next. Shrinking precision and flattening the cache made the model fit and stream; sparsity made it compute little; and that pushed the cost onto the network. This staircase — compute bottleneck → memory bottleneck → communication bottleneck — is the exact trajectory the architecture field has walked, and K3 stands at the current top step.

Part VII

The memory hierarchy — fused kernels and the SRAM you never see

Underneath the whole model is a subtler version of the memory wall: even within a single chip there is a hierarchy — a tiny pool of very fast on-chip memory (SRAM) next to the multipliers, and the large, slower main memory (HBM) a long way off. Moving data between those two is itself a big share of the cost. The winning move, over and over, is to keep intermediate results in the fast pool and never write them out to the slow one.

The famous example is FlashAttention (Session 1's footnote): computing attention without ever building the full word-by-word comparison grid in main memory — it works through the grid in small tiles that fit in the fast pool, keeping only a running result. Same answer, a fraction of the data movement. K3's own fixed-summary memory ships as a similar hand-fused kernel (the DPLR chunkwise routine of Session 4), and its bounded activation (SiTU, Session 7) is noted to be about three times slower unless it is fused into one kernel — a detail that is meaningless as mathematics and decisive as engineering. The corpus treats this dataflow-and-fusion problem as first-class:

From this corpus — keeping data close to the arithmetic
  • ISCARAGO: Systematic Performance Optimization for Retrieval-Augmented Generation Serving
  • ICCADHRAMTran: A Hybrid-RAM Transformer Accelerator with Dynamic Sparsity Floating-Point CIM
  • DACAdora Compiler: End-to-End Optimization for High-Efficiency Dataflow Acceleration

The through-line: a computation is not just its arithmetic; it is where the arithmetic's inputs and outputs live. Two mathematically identical operations can differ by an order of magnitude in speed depending on whether their data stayed in the fast pool. K3's kernels are written to keep it there.

Part VIII

The training machine — exposing parallelism

Everything so far has been about serving. Training flips the roofline (it is compute-bound), but it introduces its own hardware constraint: an accelerator is a machine for doing thousands of things at once, and it starves if you hand it work that must be done strictly one step after another. The enemy in training is a long chain of dependent steps — the sequential scan.

K3's fixed-summary memory is, at heart, a running update — read the state, write the state, one word at a time — which is exactly the kind of strictly-sequential chain a parallel machine hates. Session 4 measured the fix: a chunked reformulation that computes the identical result but cuts the chain of must-wait steps from one-per-word to one-per-block (a 32× shorter chain), running 8–20× faster on an ordinary processor even before specialized hardware. This is the classic move of trading a little redundant arithmetic for a lot of exposed parallelism — spend more multiplies to shorten the dependency chain, because on this hardware idle multipliers are the real waste. Keeping those multipliers busy (the field calls the fraction of peak you actually achieve "utilization") is what the chunk size is tuned for.

Sequential and chunked forms agree to seven parts in ten million — the same function, re-scheduled purely to give the hardware something parallel to chew on. The architecture choice is invisible in the output and decisive in the wall-clock.

Part IX

The meta-principle: designing the model and the machine as one thing

Every axis above points at one idea, and it is the idea the field has been converging on for a decade.

For a long time the division of labor was clean: researchers designed models, engineers made them run. That division is gone. Each of K3's choices — four-bit floats, a non-growing memory, sparse experts, chunked updates, fused kernels — was made because of what the memory hierarchy, the tensor cores, and the interconnect can do cheaply. The model was shaped to the machine, and (through custom kernels and comm libraries) the machine was shaped to the model. K3's own report calls this algorithm–system co-design, and treats it not as an afterthought but as the reason the gains are real: about 2.5× more capability per unit of computing than the previous generation, from the combination — architecture and training and hardware together — rather than from raw size (Session 8).

This is precisely the direction the conferences in this corpus have turned. A decade ago a hardware paper accelerated a fixed model. Now the papers co-design: the accelerator assumes a sparse, low-precision, long-context workload, and the model assumes a memory-bound, communication-limited, tensor-core machine. They are writing to each other. K3 is one of the clearest artifacts of that conversation — which is exactly why it belongs in a repository that reads hardware conferences.

The claim, stated plainly

The 22,580× growth from GPT-2 to K3 is real but it is the least interesting thing about the model. What made it possible to build and to run is a stack of decisions, each one a known answer to a known hardware limit: the memory wall, the roofline, precision, bandwidth, sparsity, interconnect, the memory hierarchy, parallelism. Strip the language away and K3 reads as a systems paper.

Part X

Coda: one vector's journey through the machine

Follow a single word as the model generates the next one, and watch the hardware story unfold in order. The word arrives as a vector. To place it, the model reads its settings — four-bit floats (Part III), a quarter the bytes they would otherwise be, streamed from main memory. It consults its memory of the conversation — held in a fixed-size summary (Part IV) that is the same size now as ten thousand words ago, so the read is flat and cheap, kept mostly in the fast on-chip pool by a fused kernel (Part VII). It needs a few specialists, so a router wakes 18 of 898 experts (Part V), most of which live on other chips, triggering a quick all-to-all across the interconnect (Part VI) — balanced so no one chip stalls the rest. The chosen experts do their small, bounded computation and the result folds back into the running summary. One word out. Then the next.

At no point in that journey was raw multiplication the limit. Every step was shaped by a byte that had to move, a memory that had to fit, or a message that had to cross a wire. That is what it means to say the model is a hardware paper: its intelligence is genuine, but its form — every architectural choice on the ladder you just climbed — is the shape of a machine pushing against the memory wall.

The road from GPT-2 to Kimi K3 was a search for a way to remember cheaply and think sparsely — and "cheaply" and "sparsely" are not statements about mathematics. They are statements about hardware. Read that way, this whole lab has been a computer-architecture paper in disguise, and so has the model it describes.
