Kimi K3, from first principles · Bonus · the hardware bill

What it takes to actually run it.

The rest of the lab is about how the model thinks. This page is about what it costs to run — because a 2.8-trillion-setting model doesn't fit anywhere by default, and the tricks that make it servable are as much a part of the design as the memory tricks. We measure the two that matter most: squeezing every number down to 4 bits, and the memory math of holding a conversation.

The problem · it doesn't fit

5.6 terabytes, before you do anything

Each of the model's 2.8 trillion internal settings is normally a 16-bit number. That's 5.6 TB just to hold the model still — 70 of the top-end 80 GB accelerators, before a single word is generated. No one serves it that way. The first thing you do is shrink every number.

We ran it · 4-bit quantization

Squeeze each number to 4 bits — and measure what breaks

The modern squeeze is a tiny 4-bit float shared across small blocks (the format K3-class models use). Each number keeps only 4 bits, and every group of 32 shares one scale — about 4.25 bits per number, a 4× cut. The 4-bit values aren't evenly spaced; they cluster near zero, where most real numbers live:

representable magnitudes: 0.0 · 0.5 · 1.0 · 1.5 · 2.0 · 3.0 · 4.0 · 6.0

We implemented this for real, squeezed 1,000,000 actual number values with it, and measured how far the squeezed versions drift from the originals — against 16-bit, 8-bit, and plain 4-bit integers for comparison:

Stored the normal 16-bit way, the 2.8-trillion-setting model is 5.6 TB — it would take 70 top-end 80GB accelerators just to hold it. Squeezing each setting to ~4 bits cuts the model to 1.5 TB (19 accelerators), a ~4× drop, while the numbers stay 99.2% faithful to the originals. Honest surprise from our run: MXFP4 is NOT more accurate than plain 4-bit integers here (12.396% error vs 10.774%) — its power-of-two shared scale wastes a little range. MXFP4 wins for a different reason: that power-of-two scale is almost free to apply in hardware and 4-bit floats run natively on the tensor cores, so it's faster and cheaper to serve at the same size. (Per-weight error isn't end-task accuracy: real serving also keeps the few most sensitive parts at higher precision.)

The honest read

Our run found the 4-bit float is not more faithful than plain 4-bit integers — its power-of-two shared scale wastes a little range. It ships anyway because that scale is almost free to apply in hardware and 4-bit floats run natively on the chips, so at the same size it's faster and cheaper to serve. And per-number drift isn't the same as getting answers wrong: the errors are scattered and mostly wash out, and real systems keep the few most sensitive parts at higher precision.

The other bill · the conversation itself

Holding the conversation costs memory too

Shrinking the model is only half the bill. The other half is the running memory of the conversation so far — the very thing Sessions 1–2 measured. In the plain full-attention design that memory grows with every word and, on real hardware, we clocked it ballooning to hundreds of megabytes and then gigabytes as the context got long. That's memory that has to sit on the accelerator next to the model, and be re-read for every new word.

Why K3's memory design is a serving decision

This is the payoff of the whole ladder, seen from the machine room. K3 carries most of its context in the cheap fixed-size memory (Sessions 2–6), so the conversation's memory stops growing — the accelerator's room and bandwidth go to serving more users and longer chats instead of to an ever-bigger cache. The 4× squeeze frees room for the model; the fixed-size memory frees room for the conversation. Together they're what turns a 5.6 TB research artifact into something you can actually put behind an API.

The crowd, spread across machines

898 specialists don't fit on one chip either

Even squeezed, the specialists (Session 7's mixture-of-experts) are far too many for one accelerator, so they're spread across many — a few experts per chip. But each word needs a specific handful of them, scattered across the machines, so every word triggers a quick round of chips shipping pieces to each other to gather the right experts. That shuffle is a real cost, and it's why serving these models is as much a networking problem as a math one — and why the model and the machines it runs on (Session 8's bonus) have to be designed together.

The one-line takeaway

A 2.8-trillion-setting model is a hardware problem before it's an intelligence problem: shrink every number to 4 bits (5.6→1.49 TB), keep the conversation's memory from growing, and spread the specialists across machines — the same memory ideas from the ladder, now measured as the electricity bill.
