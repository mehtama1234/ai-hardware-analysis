MICRO 2025 — First Principles Essay

First-principles overview — the problem, the approaches, where it fits

What MICRO is

MICRO (IEEE/ACM International Symposium on Microarchitecture) is the home for researchers who study what happens inside a single processor core and the immediate structures around it—the pipeline, cache hierarchies, branch prediction, memory controllers, and the fine-grained mechanisms that govern how a processor actually executes instructions. Unlike systems conferences (OSDI, ASPLOS) that ask "how should we architect systems?", MICRO asks "how do we make a single chip execute instructions faster, more efficiently, and more securely?" The papers here are grounded in two questions: what hardware constraint or opportunity exists at the microarchitectural scale, and what mechanism (in silicon, or in the code that controls silicon) can exploit or relieve it? Researchers submit here when their contribution is about the internals of a core or the first-level memories and networks attached to it—not about operating systems, distributed systems, or algorithm design in the abstract.

The one problem this community is organized around

At the absolute bottom of the computing stack sits a tension: a processor must execute billions of instructions per second, yet the data those instructions need lives in slow DRAM—often 100–300 nanoseconds away. Between the core and main memory sits a hierarchy of increasingly large, increasingly slow caches, plus prediction structures that try to guess what code and data will be needed before the core even asks for them. Every megacycle, the core produces decisions: which instruction to fetch, whether a branch is likely taken, how to schedule dependent operations, whether to speculate ahead or wait for a result. Each decision trades off power, latency, and correctness.

The core constraint is that most data misses fundamentally cannot be fixed by the core alone. If a memory access takes 200 nanoseconds and the core runs at 3 GHz (0.33 nanoseconds per cycle), that's 600 cycles of idle time. No amount of instruction-level parallelism within the core itself can hide that latency. So the microarchitecture must be clever: it must predict which data will be needed, prefetch it into closer caches before the core asks for it, and reschedule other work to run while memory is in flight. It must also be efficient: adding a larger cache or a more aggressive prefetcher costs silicon area, power, and design complexity. Every byte of cache capacity and every prefetch request consumes power. The core must extract value from each transistor allocated to it.

A second tension underneath this is that modern workloads are wildly diverse: a single chip now runs LLM inference one moment and graph processing the next. LLM inference is bandwidth-hungry but has highly regular memory access patterns (matrix multiplications with known dimensions). Graph processing is irregular—it depends on the shape of data it hasn't seen yet. Database queries have their own patterns. Quantum control systems have different constraints entirely. Caches and prefetchers designed for one workload can actively hurt another.

Third, as silicon density has increased and chips have become targets for security attacks, a new problem has emerged: the microarchitectural side channel. Branch prediction states can leak information about victim code. DRAM row-activation patterns can reveal which addresses a program touched. Timing variations in cache and prefetch behavior can be observed by a co-located adversary. The microarchitecture that was designed for speed now has fingers in security, and mitigating timing attacks without destroying performance has become a core concern.

The main approaches in 2025

Rethinking memory hierarchy and data movement

The 2025 MICRO papers show a sustained pivot: instead of asking "how do we make the existing cache hierarchy faster?", researchers are asking "where should data live, and when should it move there?" This includes near-data processing (PIM), where compute moves close to DRAM rather than moving data out to the core. Stratum uses monolithic 3D-stacked DRAM with Cu-Cu hybrid bonding (1 µm pitch vs. 10 µm for conventional HBM TSVs) and places logic die on top, creating an in-memory tiering system that predicts which expert weights in a mixture-of-experts LLM will be hot and maps them to fast DRAM layers before each inference batch. Mono3D DRAM NMP System extends this pattern by tightly coupling memory and compute. The insight is that for LLM serving and other memory-bandwidth-limited workloads, the data-movement cost dominates, so architecture must collapse the distance between compute and storage.

Similarly, several papers attack the compression and layout of data in memory itself. Near-Core Decompression Accelerator embeds a decompression engine between L1 and HBM to decompress LLM weights on-the-fly, and Bit-Slice-Level Compute-Memory Co-Optimization redesigns arithmetic and memory layout in tandem for 4-bit LLM inference. These are not incremental cache tweaks—they are fundamental rethinks of what gets stored where and in what format.

Prefetching and scheduling as learned coordination problems

Classical prefetch strategies (next-line, stream detection) rely on fixed heuristics, but modern systems have too many competing memory streams. Micro-MAMA shows that multi-core prefetching is actually a multi-agent coordination problem: each core's prefetcher competes for shared memory bandwidth, and uncoordinated agents degrade system throughput and fairness. The paper uses hierarchical reinforcement learning—local bandit agents on each core, with a central supervisor that provides global bandwidth visibility and prevents individual agents from greedily claiming too much bandwidth. The result is 2.1% throughput and 10.4% fairness improvement over independently operating prefetchers.

Symbiotic Task-Seeded Prefetching and Scheduling treats prefetch and schedule as a joint optimization: if you know what task will run next (a known quantity in task-parallel systems like OpenMP), you can prefetch data for that task before it arrives, reducing cache misses and improving inter-task locality. The insight is that modern architectures have multiple levels of scheduling—OS scheduler, work-stealing runtime, in-core instruction scheduler—and microarchitecture can expose hooks into the OS and runtime to coordinate prefetching with actual scheduling decisions.

Specialization via ISA extension and heterogeneous cores

Rather than a single monolithic core, several papers argue for tightly coupled heterogeneous execution: a general-purpose core handles irregular control flow and setup, while specialized execution units handle regular compute. SMX (Heterogeneous ISA+Coprocessor for Sequence Alignment) adds instructions to handle variable-length sequences irregularly, while a 2D systolic-style coprocessor accelerates the parallel inner loop of dynamic programming. Closing CPU-to-ASIC Gap for Cryptographic Kernels shows that a minimal ISA extension (crypto instructions) plus targeted SIMD vectorization can eliminate the 100x gap between generic CPU and specialized crypto ASIC, on real Intel hardware.

Automated RISC-V Instruction-Subset Processor Generation inverts the problem: given a workload and a hardware budget, automatically generate a minimal processor that implements only the instructions actually needed. This is particularly powerful for extreme-edge devices where a full CPU is overkill.

Security by design in the execution engine

The MICRO community has moved past "security is an afterthought" and is now asking: how do we architect prediction structures, memory controllers, and speculation to be secure by default? CryptoBTB addresses branch target buffer timing attacks by decoupling the encryption of the BTB index from the critical path. The key insight is that you can encrypt asymmetrically—the BTB access itself doesn't need to know the plaintext index; only the hardware needs to maintain the invariant that the mapping is secret. By using a hierarchical exclusive BTB design, the paper recovers capacity lost in prior flat encrypted designs and achieves 4.27% overhead vs. 31.89% for the prior state-of-the-art.

Understanding and Mitigating Rowhammer Defense-Induced Covert Channels reveals that defenses themselves (PRAC and RFM) become attack vectors: the timing differences caused by preventive refresh actions are observable by a spy process and can leak information via bandwidth throttling. The paper demonstrates LeakyHammer, a covert channel achieving 39–48 Kbps capacity. Rather than patching symptoms, it suggests that future defenses must account for their own side effects.

Reverse-engineering and modeling as first-class research

With closed proprietary architectures dominating (NVIDIA GPUs, modern Intel), understanding actual behavior requires detective work. Reverse-Engineering and Modeling Modern NVIDIA GPU SM Microarchitecture uses public benchmarks and architectural induction to build accurate cycle-accurate models of NVIDIA SM execution, memory hierarchy, and warp scheduling—information NVIDIA doesn't publish. This is not academic curiosity; it is a prerequisite for understanding where accelerators are actually bottlenecked and designing compatible workloads. Similarly, ρHammer reverse-engineers Intel DRAM address mapping using structured pairwise timing measurements, recovering full bank functions in polynomial time without prior knowledge of bank bit layouts. The message is clear: if you can't see inside, measure the outside carefully enough to infer the inside.

Sparsity, quantization, and sub-byte computation

For LLM and CNN inference at scale, data-type and sparsity optimizations are now microarchitectural considerations. HiPACK solves the ARM SIMD incompatibility problem for sub-8-bit quantized convolutions using a Dual Interleaved Register mechanism that allows a single SIMD multiply to process two sub-8-bit data streams without width mismatch. Outlier-Aware MX Block Floating-Point for 4-Bit LLM Inference extends MX (a block FP format with shared exponent) to handle outlier magnitudes efficiently in 4-bit inference. Reconfigurable Sparse Accelerator with Distributed On-Chip Memory and Probabilistic Tiling Optimization for Sparse Tensor Algebra approach sparse workloads as a scheduling and data-layout problem, optimizing how sparse tensors are tiled and moved through hierarchy.

How it connects to the broader field

MICRO sits at the core production bottleneck. Systems conferences (OSDI, ASPLOS) design algorithms, OS kernel features, and distributed architectures—all of which eventually must run on hardware whose constraints MICRO discovers. Machine learning conferences (MLSys, NeurIPS) propose training and inference algorithms—but their efficiency ultimately depends on whether the chip can execute them efficiently. Architecture conferences (ISCA) study large-scale systems and heterogeneous clusters—but each node contains a microarchitecture that MICRO's work directly impacts.

The flow is generally downstream: MICRO produces understanding of what's actually fast and what's slow on real silicon. That informs systems design (e.g., if prefetching is coordination-limited, OSes should expose scheduling hints to hardware). That informs algorithm design (e.g., if sub-8-bit arithmetic is efficient on ARM, ML compilers should target it). Conversely, MICRO depends on ISCA to define chip-scale constraints (interconnect bandwidth, memory capacity), and on systems conferences to define the workloads that actually matter in practice.

What MICRO does not do is ask whether we should have built a chip at all—that is an economics and strategy question. It does not propose entirely new paradigms (like optical computing or quantum), though it does optimize within them (quantum control synchronization). It does not solve algorithmic problems—it assumes algorithms are given and asks how to run them fast.

What's open

The most conspicuous gap is that MICRO does not yet solve the microarchitecture for extreme heterogeneity at the core level. The 2025 papers show isolated examples (SMX adds a coprocessor; RISC-V generates minimal cores), but a principled framework for automatically co-designing ISA, prediction structures, and memory systems for a given workload set remains elusive. The MICRO community can design a good prefetcher for LLM inference or a good prefetcher for graph processing, but designing a single core that runs both well is still largely manual engineering.

Second, the security-performance tradeoff remains unresolved. Every paper that adds security (CryptoBTB, rowhammer defenses) incurs overhead. Whether that overhead can be eliminated—or whether it is fundamental—is unknown. MICRO papers propose specific mitigations, but a comprehensive theory of which secrets must be protected and at what cost is absent.

Third, the MICRO community is only beginning to operationalize the multicore coordination problem. Prefetching and scheduling are increasingly global optimization problems that touch OS, runtime, and hardware simultaneously. Current papers optimize one layer (hardware) with hints from another (OS). A unified framework for joint hardware-software optimization across many cores remains mostly unexplored.

Finally, the community has relatively little on power and thermal management at the core scale. Most papers optimize for throughput or latency; power is a secondary metric. For mobile, edge, and datacenter workloads under thermal constraints, a deeper integration of power, thermal, and microarchitectural choice is needed—though this is expensive to measure and simulate.
