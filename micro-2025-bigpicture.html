MICRO 2025 — Deep Dive

First-principles overview — the problem, the approaches, where it fits

What MICRO is and why it exists

MICRO—the International Symposium on Microarchitecture—is the venue where processor architects solve problems that live below the abstraction of Instruction Set Architecture (ISA). The conference exists because silicon is finite, power budgets are real, and the only way to squeeze more computation into a fixed die or energy envelope is to understand the mechanics of execution: how instructions travel through pipelines, where data waits to be fetched, when predictions fail and force costly rollbacks, and how billions of transistors can be organized to maximize throughput without burning out. MICRO papers answer this question: given a workload and a power/area budget, what is the minimal set of microarchitectural mechanisms that delivers performance?

The community is composed of processor designers at Intel, AMD, ARM, Nvidia, and dozens of fabless companies; researchers at universities who study the gap between what compilers think the hardware does and what the hardware actually does; and—increasingly—engineers building accelerators for machine learning, graph processing, and specialized workloads. The implicit contract is that every paper will disclose cycle-level behavior, silicon area/power tradeoffs, and measurable speedups on real benchmarks or cycle-accurate simulation, not aspirational models.

MICRO has historically been conservative about claims and generous about rigor. Papers are expected to reason about caches, coherence, pipeline latency, and memory systems with the precision of a physicist measuring radiation. The venue deliberately excludes papers that are primarily about instruction-level parallelism exploitation (those go to ISCA), algorithm optimization (those go to ASPLOS), or programming models (those go to PACT). MICRO is about the machine itself: the circuits, the scheduling logic, the memory hierarchy, and the control mechanisms that make a processor a processor.

The core constraint

The fundamental constraint that MICRO addresses is the memory wall: the exponential divergence between processor speed (doubling every 1.5–2 years historically) and DRAM latency (improving by only 6–8% per year). This creates a crisis in microarchitecture. A modern processor executes an instruction every nanosecond or faster, but fetching a cache line from main memory takes 100–300 nanoseconds—a drought of 100–300 instruction slots. During that time, the pipeline will stall unless the architect has already predicted which data is coming and prefetched it, or arranged the computation so that the processor keeps working on other tasks.

The memory wall manifests in three concrete ways. First, spatial locality pressure: accessing data that is physically near a previously accessed byte saves a round trip to DRAM because the entire cache line (64–256 bytes) arrives together. Processors cannot afford to waste cache lines. Second, temporal locality pressure: if data has been used recently, it should be kept in a small, fast cache (L1, L2, L3) rather than evicted to DRAM, because reusing it costs nanoseconds instead of hundreds of nanoseconds. If a program has poor temporal locality (a dataset larger than the L3 cache being scanned once), the cache becomes useless and the processor will stall. Third, instruction cache pressure: the same penalties apply to instructions. If a program's working set (the set of unique instructions needed in the next 100 million cycles) exceeds the instruction cache, the processor will fetch instructions from DRAM, stalling for hundreds of cycles.

Compounding these pressures are two secondary constraints: power density and speculative execution. Modern processors burn 50–150 watts in a space the size of a postage stamp. This creates a power/frequency ceiling: even if you can squeeze more computation into a pipeline stage, the resulting heat is unsustainable. Speculative execution—the technique of guessing which branch a program will take and executing instructions before the branch is resolved—buys enormous latency hiding but only if the guess is correct. If the processor speculates wrong (a misprediction), it must flush the pipeline, discard speculative work, and restart from the correct branch. This is devastating: each misprediction costs 10–30 cycles and stalls the memory system. Processors therefore invest enormous transistor budgets in branch predictors, cache hierarchies, and prefetchers to minimize mispredictions and memory stalls.

The 2025 MICRO corpus reveals that this constraint landscape has shifted. Accelerators (ASICs, FPGAs, GPUs) have shattered the assumption that "one general-purpose pipeline is sufficient." Now the constraint is not "how do I tolerate the memory wall in a single processor" but rather "how do I hide the memory wall across a heterogeneous system: CPU cores, GPUs, near-memory processors, and specialized dataflow engines." Papers at MICRO 2025 attack this by pushing computation toward data (processing-in-memory, in-SRAM compute), moving data intelligently (prefetching learned by reinforcement learning, dynamic scheduling across memory channels), and accepting that some computation should never use the general-purpose ISA at all (native sparse operations, native quantized operations, native quantum gates).

Themes and subthemes

Memory System Innovation: Architecture, Scheduling, and Near-Memory Processing

Papers in this cluster—25% of the corpus—attack the memory wall by restructuring how data flows from the processor to DRAM and back. Rather than hoping for spatial and temporal locality, these papers accept that memory access is inevitable and make it faster, cheaper, or simpler.

DRAM Organization and Read Disturbance

DRAM is built from capacitors (one bit per capacitor), and reading a capacitor to sense its value is destructive—the read drains charge and must be followed by a refresh to restore it. Modern DRAM exploits this by packing billions of capacitors into a single chip, but this density creates interference: reading one row of memory disturbs neighboring rows. This interference—called Rowhammer—has been weaponized in security exploits for over a decade. The 2025 work discovered a new disturbance phenomenon: reading along a column (vertically) causes different physical damage than reading across a row (horizontally). ColumnDisturb characterizes this column-based read disturbance, revealing that repeated column reads trigger bitflips that differ in pattern and severity from row-based Rowhammer. This opens new attack vectors and requires new defenses: physical memory allocation (e.g., isolating security-critical buffers into separate DRAM banks) and tighter refresh scheduling.

Related papers on Rowhammer defense explore a bitter irony: defending against Rowhammer causes new vulnerabilities. RowHammer Defense-Induced Timing Side and Covert Channels show that mitigations like targeted refresh create timing variations measurable by microarchitectural side-channel attacks. Conversely, Prefetch-Based RowHammer Revival demonstrates that prefetchers (originally designed to hide latency) can be repurposed as attack vectors: by forcing specific memory access patterns, an attacker can trigger Rowhammer without triggering defenses. The lesson is that defenses and attacks co-evolve: every mitigation introduces a new surface.

Dynamic Scheduling and Channel Management

High-bandwidth memory (HBM)—used in GPUs and accelerators—is organized into independent channels and banks, each capable of delivering a full-width word on each cycle if requests are well-distributed. If all requests go to the same bank, the architecture serializes and throughput collapses. HBM-Aware Dynamic Scheduling for Sparse Linear Algebra Acceleration (ChaSon) solves this by profiling the access patterns of sparse matrix operations (sparse-dense matrix multiply, SpGEMM, sparse tensor algebra) and dynamically rerouting rows between HBM channels to balance load. The paper shows that naive assignment of data to channels leaves 40–60% of bandwidth on the table for sparse workloads; adaptive scheduling recovers it.

Processing-in-Memory (PIM) and Near-Data Processing

The ultimate solution to the memory wall is to compute on data while it is still in memory, avoiding the round trip to the processor entirely. Processing-in-Memory Acceleration for Post-Transformer LLM Serving (Pimba) embeds compute (systolic arrays) in DRAM banks, placing simple dot-product engines at each bank. When a large language model (LLM) finishes its multi-head attention layers (the "transformer" block), it needs to apply a linear projection to each attention head's output—work that is highly regular (matrix-vector multiply). Moving this to the PIM eliminates data movement and discovers 1.2–1.7× speedup on LLM serving. The architecture uses interleaved bank sharing: requests from different compute stages (different layers of the LLM) are interleaved at the bank level, hiding latency within a bank.

Locality-Aware PIM-Host Cooperation for Graph Processing with Fine-Grained DRAM Column Access (FALA) pushes this further for graph workloads. Graph processing (traversing edges and aggregating node features) has poor spatial locality—accessing node 1, then node 1000, then node 500 in random order. Traditional prefetchers fail. FALA allows PIM units to execute column-range queries directly on DRAM: "fetch all edges originating from nodes 100–200"—a primitive that maps naturally to the column-oriented structure of DRAM and halves memory bandwidth compared to word-by-word access.

Compute-in-SRAM Characterization and Optimization for RAG (real-world RAG: retrieval-augmented generation) tests compute-in-memory on actual hardware (GSI-APU), a commercial system with 8 kB of in-SRAM compute capability. The paper measures how overhead (data marshaling, result serialization) affects real workloads and proposes compiler optimizations to amortize this overhead. Key finding: RAG workloads (dense retrieval + scoring) are a natural fit, but only if the kernel size is tuned to the SRAM capacity.

Decompression and DRAM Bandwidth Efficiency

LLMs are large. A 70B parameter model in 4-bit precision consumes ~35 GB of model weights. Loading this into GPU memory takes time; fetching it from CPU memory during inference compounds the bottleneck. Near-Core Decompression Accelerator for Compressed LLM Inference (DECA) places a small, dedicated decompressor (4–8 KB of silicon) between the L3 cache and the memory controller. Model weights are stored compressed (using lightweight algorithms like run-length encoding and dictionary compression). The decompressor intercepts memory requests for model weights and decompresses them on the fly, effectively increasing bandwidth by 2–3× without increasing DRAM pins or power. The roofline analysis shows the break-even point: if decompression latency exceeds 3–4 cycles, the benefit evaporates due to pipeline stalls.

Speculative Execution and Branch Prediction

Branch prediction—guessing whether a conditional jump will be taken—is a cornerstone of modern processors. A modern CPU executes one instruction per nanosecond but takes 15–30 cycles to resolve a branch (due to pipeline depth). Without prediction, the pipeline would drain and stall on every branch. With good prediction (>95% accuracy on real workloads), the pipeline stays full. However, prediction is a microarchitectural side channel: timing how long predictions take can leak information. Additionally, securing prediction logic adds latency and area, creating tension between performance and security.

Secure Branch Prediction

Secure Hierarchical BTB with Decoupled Low-Latency Index Encryption (CryptoBTB) redesigns the Branch Target Buffer (BTB)—a cache of branch outcomes and predicted targets—to resist both timing attacks and transient-execution attacks. Traditional BTBs use an unencrypted index, making them vulnerable to cache-based side channels. CryptoBTB encrypts the index using AES, but this is too slow for the critical path. The key insight is to decouple index encryption from result delivery: compute the encrypted index speculatively while simultaneously speeding up the unencrypted index for the most frequent case (L1 BTB hit), and use the encrypted index only if the L1 miss. This maintains prediction latency (1–2 cycles) while blocking timing channels. Silicon area increases by 8% due to the AES unit; latency is unchanged.

Microarchitectural Cost of In-Core Secure Speculation (ShadowBinding) measures the price of defending against Spectre and Meltdown attacks. These attacks exploit speculative execution: the processor guesses which branch to take, speculatively loads data from an attacker-controlled address, and if the guess is wrong, the load is annulled but its side effect (memory pollution in the L1 cache) remains, leaking secrets. Defenses include flushing the cache on misprediction (too expensive), or preventing speculative loads from reaching memory (cheaper). ShadowBinding shows that preventing speculative loads adds 4–12% latency to programs with high memory intensity and costs 5–15% energy. On programs dominated by arithmetic (e.g., scientific computing), the cost is near-zero because speculative loads are rare.

Reinforcement Learning for Prefetching

Traditional prefetchers use hand-crafted heuristics: if you access address X, prefetch X+64 (spatial locality). These are simple and fast but brittle—they fail on irregular access patterns (e.g., linked-list traversal, graph processing). Multi-Agent Reinforcement Learning for Multicore Prefetching (Micro-MAMA) trains independent RL agents—one per core—to learn prefetch policies from runtime access traces. Each agent observes recent accesses and decides which future addresses to prefetch. Agents are trained offline on representative workloads (SPEC2017, SPEC2006) and deployed on hardware. The approach discovers policies that adapt to workload characteristics: conservative (few prefetches, low memory overhead) for cache-friendly workloads, aggressive (many prefetches, high coverage) for cache-unfriendly workloads. Speedup over baseline prefetching: 5–12% on SPEC, 15–25% on graph and sparse workloads, with negligible hardware cost (a small neural network on-chip to evaluate prefetch decisions).

Sparse Workload Acceleration

Sparse workloads—where many matrix elements are zero and can be skipped—are abundant in machine learning (GNNs, recommendation systems), scientific computing (sparse linear algebra), and databases. Sparsity offers speedup (fewer operations) but creates challenges: the sparsity pattern is irregular, unpredictable, and data-dependent. A processor designed for dense operations (regular access patterns, high data reuse) performs poorly on sparse workloads.

Sparse Accelerator Architecture

Reconfigurable Sparse Accelerator with Distributed On-Chip Memory (Quartz) and Adaptive On-Chip Caching for Sparse Tensor Accelerators (SeaCache) tackle sparse-specific caching. Sparse kernels (e.g., SpGEMM—sparse matrix times sparse matrix) exhibit highly irregular reuse patterns. A traditional LRU (Least Recently Used) cache evicts the "oldest" entry, but for sparse workloads, reuse distance is skewed: a few entries are reused very frequently (hot), and most are reused once or never. Quartz and SeaCache propose adaptive replacement policies: estimate reuse probability on-the-fly and prioritize hot entries. SeaCache uses a learning-based predictor (trained on micro-benchmarks) to predict whether a load will be reused within the next 100 cycles; if yes, keep it; if no, evict it immediately. Result: 1.3–1.8× speedup on sparse tensor operations with the same cache size.

Spectral Clustering Row Reordering to Minimize SpGEMM Off-Chip Memory Traffic (Bootes) attacks a different angle: before running SpGEMM, reorder rows of the input matrices to improve cache locality. If matrix rows can be reordered so that rows often accessed together are physically adjacent, spatial locality improves. Bootes uses spectral clustering to identify clusters of rows with similar access patterns, then reorders rows within clusters. A 15–20% reduction in off-chip memory traffic yields 1.2–1.4× speedup.

Probabilistic Tiling and Sparse Tensor Algebra

Probabilistic Perspective on Tiling Sparse Tensor Algebra reframes tiling—partitioning a computation into cache-sized chunks—as a probabilistic optimization. Tiling dense tensor contractions (e.g., matrix multiply) is straightforward: divide the matrices into tiles of size M×K and K×N, multiply each pair of tiles, and accumulate. For sparse tensors, it is harder: tiles may have vastly different sparsity, and choosing tile sizes to balance load is combinatorial. The paper models tile sparsity as a random variable and optimizes tile sizes to minimize expected cache misses plus expected off-chip memory traffic. Speedup: 1.1–1.3× over fixed-size tiling on real sparse workloads from scientific computing.

FPGA-Based Sparse Acceleration

ML-Guided FPGA Reconfiguration for Adaptive SpGEMM Dataflow Selection (Misam) targets FPGAs (field-programmable gate arrays), which allow custom dataflow. SpGEMM can be implemented as systolic (row-by-row computation), outer-product (processing one input row at a time), or hybrid pipelines. Different sparsity patterns benefit from different dataflows. Misam trains a simple ML model (random forest) on a database of (sparsity pattern, matrix dimensions) → best dataflow mappings. At runtime, the FPGA is reconfigured dynamically to match the incoming matrix. Result: 1.2–1.5× speedup vs. fixed dataflow, with <1 ms reconfiguration overhead.

Automated Dataflow Compiler for Stream-Based LLM Acceleration on FPGAs (StreamTensor) extends this to LLM serving on FPGAs. Traditional dataflow accelerators (systolic arrays, spatial architectures) assume dense tensor operations with a fixed data layout. LLMs do not; layer shapes vary (attention has different dimensions than fully-connected layers), and batch sizes are dynamic. StreamTensor proposes a compiler that takes an LLM computation graph (a sequence of matrix multiplies, element-wise ops, etc.) and generates an FPGA bitstream that streams data through a network of operators rather than storing everything in on-chip buffers. A 70B parameter LLM on an Intel Stratix 10 FPGA achieves 10–15 tokens/sec, competitive with GPUs on serving latency (if not throughput).

Quantization and Sub-Bit Precision

Quantization—reducing the precision of a model's weights and activations from 32-bit floating-point to 8-bit integers or fewer—is a critical tool for deploying large models on edge devices and accelerators with limited memory and compute. MICRO 2025 covers both algorithmic advances (new quantization formats) and microarchitectural support (hardware for sub-bit operations).

Sub-8-Bit SIMD Convolution

HiPACK: Efficient Sub-8-Bit Direct Convolution with SIMD and Bitwise Management reduces CNN weights to 4–7 bits and activations to 4–6 bits, cutting model size in half or more. The challenge is that SIMD (Single Instruction Multiple Data) units in CPUs are designed for 8-bit, 16-bit, 32-bit, or 64-bit operations. Operating on 4-bit elements requires packing multiple elements into a single SIMD lane (e.g., four 4-bit elements into one 16-bit lane) and carefully managing carries and overflows during multiply-accumulate. HiPACK proposes dual interleaved registers: pack elements such that partial products from different lanes do not interfere. On AVX2 (a 256-bit SIMD unit), HiPACK achieves 2–3 TFLOPS (trillion floating-point operations per second) for quantized convolution—matching the peak throughput of an 8-bit SIMD engine, demonstrating that sub-8-bit precision need not sacrifice throughput if data layout is optimized.

MX Block Floating-Point

Outlier-Aware Extension of MX Block Floating-Point for 4-Bit LLM Inference (MX+) extends Microsoft's MX format (a compromise between floating-point and integer quantization: a block of values shares a common exponent, but each value has its own mantissa). Standard MX struggles with outliers (weight values much larger than the mean), which force the exponent high and waste precision on small values. MX+ adds a small lookup table (LUT) to identify and store outliers separately in higher precision, then apply MX to the remaining values. On Llama 2 70B, MX+ achieves 4-bit inference at 90% of the accuracy of 8-bit, vs. 78% for standard 4-bit quantization.

Quantized GEMM in Vector Architectures

Quantized GEMM Acceleration in Vector/SIMD Architectures (CAMP) proposes a new RISC-V vector extension specifically for quantized matrix multiplication. Traditional RISC-V vector units process elements one per cycle (or a few per cycle for longer vector widths). CAMP adds a specialized multiply-accumulate unit that takes quantized (8-bit) elements, computes full-precision products, and accumulates into an integer result. The unit pipelines to sustain one GEMM (matrix multiply) per cycle at 256-bit width, delivering 32 int8 GEMMs per cycle. Energy efficiency: 2–3 nanojoules per operation, competitive with GPU V100 at 1.2–1.5 nanojoules (GPUs are more efficient, but CAMP is more area-efficient and better suited for edge devices).

Dataflow Accelerators and LLM Serving

LLM serving—answering queries by running forward inference through a large language model—creates unique microarchitectural challenges. A 70B parameter model takes ~100 GB of memory; serving 1000 users concurrently requires batch sizes of 1000+, which taxes memory bandwidth. Papers in this cluster redesign the dataflow of LLM inference to reduce memory bandwidth, exploit parallelism, and hide latency.

End-to-End Fusion and Pipelining

End-to-End Transformer Layer Fusion and Pipelining via Einsum Cascades (TransFusion) observes that fusing operations (combining multiple kernels into one) reduces memory traffic: intermediate activations need not be written to memory and reloaded. A transformer layer consists of: input projection, multi-head attention (compute pairwise attention scores), attention head merge, output projection. Each operation is a matrix multiply (GEMM) or element-wise op. Traditional implementations call separate kernels, writing intermediates to memory. TransFusion fuses them into one kernel with cascading Einsum (Einstein summation, a notation for tensor contractions) operations. The architecture pipelines fused operations: while one part of the hardware sums attention heads (a reduction), other parts fetch the next attention scores. Result: 1.8–2.2× speedup vs. separated kernels on NVIDIA A100 GPU.

LLM-Based Cost Modeling for Dataflow Accelerators

LLM-Based Generalizable Cost Modeling for Dataflow Accelerators (LLMulator) trains an LLM to predict the execution time of dataflow accelerators (ASICs, NPUs, TPUs). Traditional cost modeling is hand-crafted: area experts encode heuristics (e.g., "if systolic array is memory-bound, latency = data_size / bandwidth"). This is brittle and does not generalize across accelerator architectures. LLMulator fine-tunes an LLM (e.g., GPT-2) on a corpus of (accelerator design, kernel code) → execution time pairs, teaching the model to predict latency as a function of hardware parameters and code structure. The model is 3–5× faster than cycle-accurate simulation and generalizes to new accelerators it was not explicitly trained on (transfer learning).

Bit-Slice Computing for LLM Acceleration

Bit-Slice-Level Compute-Memory Co-Optimization for LLM Inference (MCBP) exploits sparsity at the bit level: if many weight elements are zero or near-zero, they contribute few bits to the product. MCBP pipelines bit-slices through the compute unit in order of their frequency in the weight distribution: first process the most significant bits (which all weights have), then process middle bits (most weights have them), then least significant bits (fewer weights contribute). This skips many operations on zeros and near-zeros. On Llama 2, MCBP achieves 1.3–1.6× speedup vs. standard 8-bit inference with similar memory bandwidth.

Tensor Compression Using Video Codecs

Video Codecs Are Secretly Tensor Codecs (LLM.265) repurposes H.265 (HEVC) video codec hardware—common on GPUs—to compress LLM intermediate activations. Transformers generate large intermediate tensors (e.g., attention scores of shape batch × seq_len × seq_len for attention). These tensors are spatially correlated: adjacent elements are often similar. H.265 exploits spatial correlation using block prediction and entropy coding. By formatting transformer activations as images, LLM.265 compresses activation tensors by 2–4×, reducing memory bandwidth. The paper includes a trick: store compression metadata (prediction residuals, quantization parameters) alongside compressed data so the GPU can decompress incrementally.

Cache Replacement and Memory Hierarchy

Caches are the workhorse of modern processors, storing ~90% of memory accesses and delivering data with 3–30 cycles of latency instead of 100–300. However, cache replacement policy—deciding which line to evict when the cache is full—is a black art. LRU (evict the least recently used line) is simple and fast but suboptimal for many workloads.

Temperature-Aware Instruction Cache Replacement

Temperature-Based Re-Reference Interval Prediction for Instruction Caching (TRRIP) proposes a replacement policy aware of thermal effects. Modern CPUs have power-gating: if a component (e.g., a cache bank) is idle, it is powered down to save energy. When powered down, leakage current diminishes, and the component cools. If a hot component is re-powered, there is a startup transient (current surge, heat spike). TRRIP uses cache replacement to manage thermal state: prefer evicting lines from cool cache banks so that those banks stay powered down. Result: 15–20% reduction in peak temperature, enabling higher sustained clock frequency (no thermal throttling), yielding 8–12% throughput improvement.

Sliced LLC Replacement

Sliced-LLC-Aware Last-Level Cache Replacement Policy Design (Drishti) addresses a subtlety of many-core systems. The L3 cache (last-level cache) is physically sliced: each core has a slice, and cores' memory requests are hashed to slices (e.g., core 0 requests go to slice 0, core 1 requests go to slice 1). This reduces coherence traffic (each core's slice is private) but creates imbalance if some cores' access patterns are heavy-hitters. Drishti proposes slice-aware LRU: when evicting from a slice, predict whether the line will be reused by the core that owns the slice or by other cores. If other cores are likely to need it, keep it (it will be requested across the slicing boundary, which is cheap in modern coherence protocols). If only the owning core will use it, prefer evicting it. Result: 5–8% speedup on many-core workloads (16+cores).

Quantum Computing

MICRO has historically been skeptical of quantum computing, viewing it as speculative. However, with systems like IBM's quantum computers and specialized trapped-ion systems emerging, microarchitecture matters. Two papers address quantum-specific problems.

Distributed Quantum Control with Synchronization

Distributed Quantum Control Architecture with Zero-Overhead Synchronization (Distributed-HISQ) targets trapped-ion quantum computers, where qubits are ions suspended in electromagnetic traps. Unlike superconducting qubits (which are fabricated on a chip like transistors), trapped-ion qubits are controlled by external lasers and RF fields. Controlling many qubits requires precise timing: multiple control signals must be coordinated to the nanosecond. A distributed control architecture spreads control logic across multiple FPGAs or ASICs, but they must synchronize without overhead (latency, power). The paper proposes a time-stamped command architecture: each control command is tagged with a timestamp, and controllers execute commands at their designated time. Synchronization is implicit in timestamp matching; no explicit synchronization message is needed. Result: achieves sub-microsecond synchronization accuracy with <1% overhead.

Quantum Error Correction and Leakage Speculation

Accurate Leakage Speculation for Quantum Error Correction addresses quantum decoherence. Qubits lose their quantum state due to environmental noise, a process called decoherence. Modern quantum error correction codes (surface codes, stabilizer codes) protect against bit-flip errors (|0⟩→|1⟩) but not leakage errors: when a qubit leaks out of the computational subspace (e.g., a three-level system where |0⟩ and |1⟩ are the computational levels, but the qubit jumps to |2⟩). Leakage requires quicker detection and correction than bit-flip errors, but detection overhead is high. This paper proposes speculative leakage detection: given the control signals sent to a qubit, predict (classify) whether leakage has occurred with high probability. Use classical machine learning on a syndrome (measurement outcomes from neighboring qubits). This reduces detection latency from 100s of microseconds (full syndrome measurement) to microseconds (speculative classification + confirmation). On surface codes with 1000 qubits, leakage detection overhead drops from 30% to 8%.

Zone-Aware Trapped-Ion Circuit Compilation

Zone-Aware Quantum Circuit Compilation for Modular Trapped-Ion Systems (MUSS-TI) addresses an architectural constraint of modular trapped-ion systems: ions are organized into zones, and control signals from one zone to another have ~10μs latency (the time for an RF pulse to cross from one zone to another). Quantum circuit compilation traditionally ignores this latency, assuming all qubits are equally fast to interact. MUSS-TI proposes a compiler that maps qubits to zones to minimize cross-zone interactions. This is similar to task scheduling (placing tasks on cores to minimize communication), but for quantum gates. Result: 1.3–1.5× reduction in circuit depth, enabling higher qubit counts before decoherence limits.

Heterogeneous ISA and Coprocessor Architectures

Some workloads are so specialized that a general-purpose ISA is inefficient. Rather than extend the ISA endlessly (adding new instructions), architects can attach coprocessors that handle entire problem domains. Papers in this cluster propose heterogeneous designs combining general-purpose cores with specialized coprocessors.

Universal Sequence Alignment

Heterogeneous ISA+Coprocessor Architecture for Universal Sequence Alignment (SMX) targets genomics: aligning DNA sequences (comparing two strings to find similarities). Sequence alignment (e.g., Smith-Waterman algorithm) is a dynamic programming problem and compute-intensive but has irregular control flow (data-dependent loops). A general-purpose CPU handles control flow; an ASIC coprocessor handles the DP inner loop (element-wise comparisons and max operations). The coprocessor is microcoded: a small instruction set (10–20 operations) covers the DP recurrence. Area efficiency is high: 100K transistors for the DP engine (vs. millions for a general-purpose core) at 10× throughput/watt. Real-world result: aligning a 10 Gbp (gigabase-pair) human-genome fragment against a database of 1000 genomes completes in hours instead of days.

RISC-V Instruction-Subset Processors for Extreme Edge

Automated RISC-V Instruction-Subset Processor Generation for Flexible Extreme-Edge Electronics (Flexing RISC-V) targets ultra-low-power devices (smartwatch sensors, implanted biomedical devices). A full RISC-V processor (with all standard extensions) uses ~50K gates. Removing instructions you don't need saves area and power. The paper proposes a compiler: given a workload (e.g., signal processing for a wearable), analyze which RISC-V instructions are used, generate a minimal CPU that implements only those instructions, and synthesize the RTL. Result: 30–50% area reduction with no performance penalty (the removed instructions are not used anyway). On a wearable ECG processor, a 40-instruction subset (vs. 150 for full RISC-V) reduces area to 8K gates and power to <1 mW while maintaining 100 samples/sec.

Cryptographic Kernel Acceleration

Closing CPU-to-ASIC Performance Gap for Cryptographic Kernels via SIMD and Minimal ISA Extension shows that CPUs can approach ASIC performance for homomorphic encryption (FHE—fully homomorphic encryption, a cryptographic primitive for computing on encrypted data) if the ISA is extended with a single instruction: NTT (number-theoretic transform). FHE kernels spend 80% time in NTT, which is embarrassingly parallel (thousands of multiply-accumulate operations on independent data). A single RISC-V extension—a 64-lane, pipelined NTT unit—achieves 3–4× speedup and closes the gap to specialized ASICs, while remaining general-purpose enough for other workloads.

Networking, Pattern Matching, and Specialized Workloads

Some workloads are outside machine learning and scientific computing but demand microarchitectural innovation.

GPU Regex Matching

Interleaved Bitstream Execution for GPU Regex Pattern Matching (Interleaved Bitstream) accelerates regular expression matching on GPUs. Regex matching is traditionally sequential: scan the input string character by character, maintaining a state machine. GPUs are poor at sequential code (no branch prediction, limited instruction-level parallelism). Interleaved Bitstream reformulates regex as a bitwise operation: represent the state machine as a finite automaton and compute which states are reachable from the current states using bitwise operations on vectors of reachable states. By interleaving operations from multiple regex patterns (different users' queries), instruction-level parallelism increases. On NVIDIA H100, Interleaved Bitstream achieves 2–3× speedup vs. scalar GPU code (character-by-character state machine) and 5–10× speedup vs. a software library.

3D Gaussian Splatting SLAM

3D scene reconstruction in real time (SLAM—simultaneous localization and mapping) has exploded with the emergence of 3D Gaussian splatting (3DGS), a technique that represents a scene as a set of 3D Gaussians and renders them via splatting. Splatting requires rendering thousands of Gaussians per pixel, each with sorting and blending—expensive on CPUs. Two papers propose edge acceleration.

Real-Time 3D Gaussian Splatting SLAM via Multi-Level Redundancy Reduction (REACT3D) builds an ASIC that renders 3DGS at 30 FPS on a wearable device (edge camera). The architecture exploits redundancy: many Gaussians contribute negligibly to final pixel colors (far from the pixel, or transparent). REACT3D culls them before rendering (multi-level: spatial culling, then color-magnitude culling). Result: wearable SLAM at 30 FPS with <5 W power.

Algorithm-Hardware Co-Design for Real-Time 3D Gaussian Splatting SLAM on Edge (RTGS) goes further: instead of just culling Gaussians, retrain the model to use fewer Gaussians (algorithm redesign) and pair it with specialized rendering hardware. A 70% reduction in Gaussians + rendering accelerator delivers 1.2× real-time on wearable devices.

In-NAND Flash Computing

Inter-Bitline In-Flash Computation for Databases and MLC ECC (CrossBit) repurposes NAND flash controllers to compute directly on stored data. NAND flash is organized as a grid of cells, each storing a charge (representing one or more bits). Reading a cell involves applying a voltage and sensing current flow. Traditional reading is binary: does the cell state match the reference level? CrossBit extends this: sense not just binary but analog (actual current), which encodes the stored charge. Use a summer (analog addition circuit) to compute XOR and AND operations directly in the flash array by combining read currents from multiple cells. This enables in-situ computation: error-correcting codes (ECC) and database aggregations (COUNT, SUM) can run without moving data. Latency: reading 4 MB of data and computing an XOR-heavy ECC takes 100 ms instead of 200 ms (data movement). Energy: 50% reduction because the data path does not leave the flash.

Chiplet Architecture and Interconnect

Modern processors are built from chiplets—smaller dies (100–200 mm²) manufactured separately and assembled onto a substrate. Chiplets offer cost savings (yield improves if you test each chiplet independently) and technology flexibility (mix chiplets from different process nodes, e.g., older I/O chiplets on 14 nm, newer compute chiplets on 3 nm). But chiplets introduce latency and coherence challenges.

Locality-Aware Atomic Operations

Locality-Aware Atomic Memory Operation Execution on Chiplet Architectures (A. Delegato) optimizes atomic operations (lock-free synchronization primitives like compare-and-swap) on multi-chiplet systems. Atomics must preserve ordering: if thread A does an atomic store and thread B does an atomic load, B must see A's value. On a single die, this is simple (a bus or snoopy cache protocol ensures ordering). On chiplets, atomics are expensive: if A's atomic targets chiplet 1 and B's atomic targets chiplet 1 but B is on chiplet 2, B's request must traverse the chiplet-to-chiplet interconnect (20–50 cycles). A. Delegato proposes scheduling: the OS predicts which chiplet a thread will access (via profiling) and co-locates threads with their data. For threads that access the same atomic locations, pin them to the same chiplet. Result: 1.2–1.4× speedup on lock-heavy workloads (e.g., graph traversal with atomic updates).

Multi-Chiplet Simulation

Parallel Simulation Framework for Heterogeneous Multi-Chiplet Systems (LEGOSim) is a tool for simulating chiplet systems (many-core, heterogeneous—different chiplet types). Simulation is essential for design: does interconnect bandwidth bottleneck? Do cache hierarchies scale? LEGOSim partitions simulation into per-chiplet simulators (each running in parallel, one process per chiplet) and couples them via a synchronized, high-throughput interconnect model. Speedup vs. monolithic simulation: 50–100× on 16–32 chiplet systems, enabling design-space exploration.

Inference Optimization and Model Compression

Deploying trained models on resource-constrained devices requires careful optimization.

Test-Time Compute for LLM Reasoning

GPU-PIM Collaborative System for Test-Time-Compute LLM Reasoning (ORCHES) targets the emerging paradigm of test-time compute: spending more time (compute) during inference to improve quality. For example, an LLM can be asked to "think step-by-step" before answering, which involves generating many intermediate tokens. This is compute-bound. ORCHES proposes a collaborative GPU-PIM system: the GPU generates candidate tokens (parallel, using SIMD), and the PIM (near-memory processor) scores candidate continuations (evaluating likelihood of next tokens given a candidate). This overlaps GPU generation with PIM scoring, hiding latency. Result: 1.5–2× speedup on step-by-step reasoning benchmarks.

NPU Power Gating

Fine-Grained NPU Power Gating via Hardware-Software Co-Design (ReGate) addresses power efficiency of Neural Processing Units (NPUs). NPUs are specialized processors for neural network inference, prevalent in mobile devices. During inference, not all components are active: if processing a convolutional layer, systolic arrays are active but vector ALUs are idle; if processing a fully-connected layer, vector ALUs are active but systolic arrays may be idle. ReGate enables per-functional-unit power gating: idle units are clocked down (frequency reduces to nanosecond-scale), cutting leakage. Control is split: hardware detects idle units (no requests in 10 cycles), firmware (OS) confirms the idle prediction (checking if a new layer is coming soon). Result: 10–20% power reduction at 3–5% performance cost (brief latency for clock domain crossing when reactivating).

Synchronized CXL Memory Encryption

Adaptive Encryption for CXL Memory in Trusted Execution Environments (TEEs) addresses confidentiality of TEE data stored on CXL memory (composable memory, a disaggregated memory protocol allowing offboard memory). TEE data must be encrypted to prevent physical attacks (e.g., reading memory from a stolen CXL module). Encryption is symmetric (AES-256), so every read/write requires encrypt/decrypt. Naive encryption adds latency (AES is slow). The paper proposes adaptive encryption: if data is hot (accessed frequently), keep it in plaintext in a local buffer (smaller, encrypted on memory controller boundary); cold data goes encrypted to CXL. Hardware predicts which data is hot. Result: 5–10% latency overhead, acceptable for TEEs.

Security and Speculative Attacks

Security remains a cross-cutting concern. Beyond branch prediction and speculation, papers address side channels, covert channels, and defense mechanisms.

BTB Security

The Branch Target Buffer is a cache of (branch_address → target_address) mappings. If untrusted code can time BTB lookups, it can infer which branches a victim process executed, leaking secrets. CryptoBTB (discussed earlier) encrypts BTB indices to block timing channels. The key trade-off: encryption adds latency, so the design uses decoupled encryption—compute the encrypted index speculatively while simultaneously using a direct index for the fast path.

Rowhammer Defense as an Attack Surface

Multiple papers show that defenses enable new attacks. Rowhammer defenses (targeted refresh, memory isolation) have timing side effects that create covert channels: a process can modulate Rowhammer refresh activity and encode secrets into timing variation, leaking information to another process. Understanding and Mitigating Covert Channel and Side Channel Vulnerabilities Introduced by RowHammer Defenses catalogs these channels and proposes uniform refresh (always refresh at the same intervals, not just when Rowhammer is detected), eliminating timing variation. Performance cost: negligible.

Speculative Execution Cost

ShadowBinding measures the microarchitectural overhead of defenses against Spectre and Meltdown. These attacks exploit the fact that speculative loads can execute before branch resolution, and their side effects (cache pollution) leak secrets. Defenses prevent speculative loads from reaching uncached memory or clear the cache on misprediction. The paper shows that blocking speculative memory accesses (a line-level circuit preventing loads from leaving the L1 cache) has low cost on arithmetic-heavy workloads (2–3%) but high cost on memory-heavy workloads (10–15%), because legitimate speculative prefetches are also blocked.

Cross-cutting patterns

Two design philosophies recur across MICRO 2025's diverse papers. First, algorithm-hardware co-design: a single paper often proposes both a software algorithm and custom hardware. For example, 3D Gaussian splatting SLAM uses fewer Gaussians (algorithm) paired with culling hardware (architecture). Sparse accelerators use compiler-driven tiling (algorithm) paired with adaptive caching (hardware). Quantum circuit compilation uses routing-aware mapping (algorithm) paired with zone-aware gates (hardware). This contrasts with traditional microarchitecture, where the ISA is fixed and hardware designers optimize within its constraints. MICRO 2025 shows that the ISA itself is increasingly a design variable: add an NTT instruction for cryptography, add vector extensions for quantization, add a power-gating signal for NPUs.

Second, predictive adaptation: adaptive mechanisms (prefetchers, cache replacement, power gating) historically use simple heuristics ("evict LRU," "prefetch next line"). MICRO 2025 shifts to learned or speculative adaptation: reinforcement learning for prefetching (train offline, deploy online), temperature-aware replacement (predict thermal state), leakage speculation (predict quantum errors), and dynamic scheduling (profile access patterns, adapt to patterns). This reflects the community's acceptance that hand-crafted heuristics are too brittle; adaptive mechanisms must learn or predict.

How MICRO fits in the ecosystem

MICRO produces building blocks for systems that build on it. Papers at ISCA (Symposium on Computer Architecture) generalize MICRO's insights to full systems: MICRO designs caches, ISCA designs entire memory hierarchies. Papers at ASPLOS (Architectural Support for Programming Languages and Operating Systems) use MICRO's cache models and prefetching strategies to optimize compiler code generation and OS task placement. Papers at OSDI (Symposium on Operating Systems Design and Implementation) build on MICRO's security insights (speculative execution vulnerabilities, side channels) to harden kernels.

MICRO also depends on lower-level work: VLSI design (circuit-level optimization of caches, ALUs, multipliers), fabrication (process technology providing transistor counts and power budgets), and workload characterization (benchmarks that capture real-world behavior). Papers at DAC (Design Automation Conference) use MICRO designs as targets for hardware-software co-simulation and design-space exploration. Papers at ISCA also feed back into MICRO: if ISCA demonstrates that memory bandwidth is the bottleneck for a workload, MICRO's next round addresses it.

MICRO conspicuously does not cover programming models, high-level algorithm design, or cloud-scale systems. A paper on "how to write GPU kernels efficiently" (high-level) would not be at MICRO; a paper on "GPU kernel compiler generating efficient code" (low-level, targeting specific GPU microarchitecture) might be. A paper on "distributed training across 1000 GPUs" (systems) would not be at MICRO; a paper on "reducing all-reduce latency via novel interconnect topology" (microarchitecture) might be.

What is not yet solved

Despite 47 papers, significant gaps remain. First, software-defined microarchitecture: While papers propose adaptive replacement, learning-based prefetching, and dynamic scheduling, deployment requires custom hardware changes. The field is far from the vision of "microarchitecture as software"—where a designer uploads a new cache replacement policy or prefetch algorithm without re-taping the chip. The closest approach is FPGAs (some papers target FPGA-based accelerators), but FPGAs are 5–10× less area-efficient than ASICs.

Second, heterogeneous memory latency hiding: Papers achieve 1.2–2× speedup on specialized workloads, but the gap between these optimizations and the 100× speedup offered by ASICs for their target workload remains wide. The challenge is generality: a sparse accelerator is optimal for SpGEMM but poor for dense GEMM. A quantum control architecture is optimal for trapped-ion systems but useless for superconducting qubits. MICRO 2025 does not offer a unified framework for designing heterogeneous systems that adapt across qualitatively different workloads.

Third, reproducible profiling and design-space exploration: Many papers profile workloads (collect traces, measure cache misses, bandwidth) and then design hardware optimized for those traces. But workload behavior is volatile: a production deployment of an LLM serving system has different access patterns than a research benchmark. MICRO papers typically do not re-validate their designs on different workloads or production traces. This suggests that claimed speedups (1.2–1.5×) may not transfer to real deployments.

Fourth, security and performance co-optimization: Papers on speculative execution and Rowhammer defenses measure performance costs (4–15% latency or energy overhead for security), but papers on acceleration rarely consider threat models. A sparse accelerator might expose sparsity patterns (a side channel), or a quantum control architecture might expose timing information about qubit leakage. MICRO 2025 does not grapple with the tension between acceleration (expose structure for performance) and security (hide structure to prevent leakage).
