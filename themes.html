AI hardware 2025 · the field, visually

One constraint, ten answers

A chip does two jobs — arithmetic, and moving numbers between memory and the math. The arithmetic became nearly free; the moving did not. Every theme here is one way to move less data, move it a shorter distance, or move the compute to where the data already sits.

The one constraint: moving data, not doing arithmetic

Picture a brilliant accountant who adds any column instantly, but whose ledgers arrive one page at a time by a single courier. The accountant is never the bottleneck — the courier is. That is every chip today. Here is each community's answer, with the idea drawn out, then the problem and the approach in plain words.

Compression & honest evaluation

▸ shrink data before it travels

The problem. Building and running AI systems at the scale of real products means solving a grab-bag of practical problems that do not fit neatly into any one box: training models spread across dozens of machines without drowning in the time it takes those machines to share results, stopping the software that runs those models from swelling to a size that eats up memory, cutting the amount of bookkeeping data that training needs to hold in memory at once, making sure that performance measurements reported in research papers actually mean what they claim to mean, counting the carbon emitted not just by running chips but by building them in the first place, and squeezing large datasets so they travel and store faster. None of these is glamorous, but all of them quietly set a ceiling on how fast or how cheaply AI can actually move forward.

Why it bites. AI workloads bump up against two scarce resources that money cannot infinitely multiply: memory space and how fast data moves (bandwidth). Every source of waste — software libraries stuffed with code nobody uses, redundant bookkeeping data sitting in memory during training, slow result-sharing across machines on different continents, or raw data sent uncompressed — burns real time and real energy at scale.

The approach. The papers here attack this kind of hidden waste from many angles at once: stripping away software that is compiled but never actually called, replacing expensive per-weight training bookkeeping with a compact mathematical stand-in that reaches the same answer, redesigning how machines share training results so they do it far less often across slow long-distance links, squeezing numbers down at the hardware level so less data needs to travel, and replacing misleading summary statistics in research papers with ones that are mathematically sound. The common thread is finding and eliminating hidden waste — in software, in memory, in network round-trips, in how results are reported.

Attention & the KV-cache

▸ read the notes without hauling every page

The problem. Every time a language model produces one new word, it must re-read every prior word in the conversation. Those notes — the model's running notes, one entry per word per layer — grow without bound and must be loaded from memory chips on every single step. In long conversations or when handling many users at once, reading that memory takes far more time than the arithmetic needed to figure out the next word.

Why it bites. Modern GPU chips can do arithmetic ten to one hundred times faster than they can move data from memory chips. So as soon as the model's running notes grow too large to fit in fast on-chip memory, every step stalls waiting for data to arrive rather than actually doing math — a pure problem of bandwidth (how fast data moves), with no arithmetic shortcut available.

The approach. Papers in this theme attack the problem from three directions: reduce how much data must be stored (smaller numbers, skipping unimportant entries, smarter caching); reduce the cost of reading that data (doing math inside the memory, chips that sit closer to memory, better scheduling of reading); and reduce how often that data needs to be read at all (reusing shared starting passages, filtering progressively, smarter request ordering). A second cluster of papers improves the machinery around all of this — deciding which requests to handle first, splitting work between chips that are good at different things — so that memory is used efficiently and no chip sits idle.

Quantization & low precision

▸ fewer bits per number, same answer

The problem. A large AI model stores tens of billions of numbers. Every time the chip does any work, it must pull those numbers from memory chips across slow wires into the part of the chip that does math — and that wire journey is far slower and burns far more energy than the math itself. Using smaller, rounded numbers — say 4-bit numbers instead of 16-bit numbers — means the same wire can carry four times as much of the model per second, and the same memory chip can hold a model four times as large.

Why it bites. Bandwidth — how fast data moves — is a physical wall: the wires between memory chips and the math circuits can only carry a fixed number of bits per second, and that limit has grown far more slowly than model size. Using smaller numbers means more of the model fits in the small but fast on-chip memory, so the chip makes fewer slow round-trips out to the bigger but slower memory chips.

The approach. Researchers replace 16-bit or 32-bit numbers with compact codes — smaller integers or entries in a lookup table — then either retrain the model so it learns to live with the rounding, or redesign the chip's math circuits to work directly in the smaller format. The hard part is that not all numbers in a model matter equally: a handful of very large 'outlier' values carry a disproportionate share of information, and simply rounding them breaks accuracy badly. Most papers therefore pair a clever compression strategy (which finds or protects those outliers) with a matched piece of hardware (which knows how to operate in the smaller format without first converting everything back to the original size).

Memory hierarchy & near-data compute

▸ move the compute to where data sits

The problem. Modern AI models spend most of their time waiting for data to travel from memory chips to the processor, not actually doing math. When a model generates a single word, it must haul tens of gigabytes of stored numbers — its learned weights and the model's running notes — across a wire that can only move a fraction of that data per second. The processor sits idle most of the time, starved for numbers to work on.

Why it bites. The chips that do math have gotten dramatically faster over decades, but the wires connecting chips to memory have not kept pace — moving a byte still takes roughly the same time it did years ago. This gap between math speed and data-movement speed is called the memory wall, and AI workloads hit it especially hard because they read enormous tables of learned numbers and the model's running notes in patterns that defeat simple tricks for keeping data nearby.

The approach. The papers in this theme attack the memory wall from three directions: bringing the math closer to where data already lives (doing math inside the memory), smarter decisions about which data lives where and for how long (tiering, fetching data early, compressing, and smarter eviction), and restructuring how programs hand data between storage layers (computing near or inside the storage drive, using a fast link to extra memory, and tuning hardware and software together). Together they aim to cut the number of bytes that must cross any wire before useful work happens.

Interconnect & collectives

▸ the wires between chips are the bottleneck

The problem. When many chips work together to train or run an AI model, they must constantly send each other partial results and stay in sync — each chip finishes its piece of the math, then everyone has to swap numbers before the next step can begin. The wires that carry this traffic have a fixed, physically limited capacity. As models and clusters grow, the volume of data that must move between chips grows faster than those wires can handle, so expensive chips sit idle, waiting for numbers to arrive rather than doing useful work.

Why it bites. Physics sets hard limits: more wires cost more area and energy, and signals weaken over distance. You cannot simply add bandwidth the way you can add more math units. Meanwhile AI models keep growing, meaning more chips must share more data at once — the demand outpaces what physics cheaply allows.

The approach. Papers in this theme attack the bottleneck from three angles: reduce how much data needs to move at all (by sending only what matters, sending smaller numbers, or skipping unimportant values); move data more cleverly (by starting transfers early, matching the message pattern to the actual wiring, or letting chips share cached copies); and rebuild the wiring and switches themselves (new connection patterns, smarter switches that do useful work on data as it passes through, and dedicated fast links). The shared insight is that saving even one byte of traffic or one millisecond of idle time compounds across thousands of chips and billions of training steps.

Sparsity & mixture-of-experts

▸ skip the weights you don't need

The problem. Modern AI models do enormous amounts of multiplication, but most of the numbers they multiply together are zero or nearly zero and contribute almost nothing to the final answer. Doing that arithmetic anyway wastes energy and time. In a model made of specialists — where only a few specialist sub-networks handle each piece of text — the waste is even worse: at any moment, the vast majority of the model's stored numbers are sitting idle. The challenge is figuring out which work can be safely skipped, communicating that decision to the hardware fast enough, and actually avoiding the load-and-compute cycle for the parts that do not matter.

Why it bites. Bandwidth — how fast data moves — is the real constraint: pulling a number out of memory chips costs far more energy than doing arithmetic on it once it arrives. So the biggest win comes from never loading the useless zeros at all, not merely from skipping the multiply once a number is already on-chip.

The approach. The papers in this theme all exploit the same observation: at any moment, only a small fraction of a model's stored numbers are non-zero and worth computing with. They find that active fraction — sometimes at the level of individual bits, sometimes at the level of whole specialist sub-networks — and then redesign how data is laid out, how hardware is wired, or how work is scheduled so that the zero-valued or idle portions are never fetched, never routed, and never multiplied. Some papers remove useless numbers before the model is ever deployed; others decide what to skip on the fly while the model is answering a question; others reorganize where data lives so the active slice can be read in one fast burst rather than many scattered trips.

Compilation & hardware generation

▸ high-level model → generated silicon

The problem. Every AI model is a long list of math steps. Before those steps can run on a real chip, someone has to translate them into the precise, tiny instructions the chip actually obeys — which wires carry which numbers, in what order, with what groupings. Today that translation is done partly by hand and partly by tools that are too rigid to spot all the shortcuts. The result: chips spend a lot of time waiting around, and wiring up a brand-new chip design can take a team of experts many months.

Why it bites. A chip is fast but completely literal — it only does exactly what it is told, one tiny clock-tick at a time. The gap between 'multiply these two tables of numbers' and 'move these exact bytes to these exact wires in this exact order' is enormous. Bridging that gap well — finding the right groupings, orderings, and arrangements — is a puzzle with so many possible answers that no human team can solve it by hand at the scale modern AI demands.

The approach. The papers here all attack that translation gap from different angles, but share a common idea: build a richer middle-layer description of the computation — one that captures structure the final chip instructions do not — and then use that description to search for better translations automatically. Some use that middle layer to generate the chip's physical circuit directly; others use it to schedule operations more cleverly; others use a small AI model to predict which of thousands of possible translations will actually run fastest on real hardware.

Security & trust

▸ stay correct and safe when attacked

The problem. Every computer that handles sensitive work — a cloud server running your bank's code, an AI model processing private medical records, a phone storing your passwords — was designed to run fast, not to keep secrets. Speed-driven design choices, like letting the processor guess what instructions are coming next or sharing a memory bus between multiple users, leave physical fingerprints that an attacker can read without ever breaking any lock. The core problem is that the hardware itself leaks information through time, power draw, and the physical side-effects of its own normal operation. As AI workloads grow and more computation moves to shared cloud chips, the number of places where secrets can leak grows with it.

Why it bites. Modern hardware is fast because it reuses resources: the same storage cells, the same memory rows, the same prediction tables, the same memory bus slots get shared between programs, between virtual machines, and between users. That sharing is the physical root of nearly every attack in this section. If two users' data ever passes through the same transistor at overlapping times, the timing or electrical residue of that overlap can carry secret information out to a watching attacker.

The approach. Researchers attack the problem from three directions. First, they find and document the new leakage paths that sharing creates — discovering that even ordinary hardware features like a 'fetch data early' engine, a memory prediction table, or an idle power state can bleed secrets across security boundaries. Second, they build defenses that either eliminate the sharing (physically isolating resources by owner) or make the sharing timing-uniform so every user sees identical delays regardless of what the other user is doing. Third, they verify that proposed defenses actually hold up — using automated testing tools, mathematical proofs, and real chip measurements to close the gap between a security claim on paper and security in practice.

Reliability & correctness

▸ catch and recover from silent errors

The problem. AI systems and the chips running them can produce wrong answers without any warning. A worn-out transistor flips a single stored digit, a quantum bit loses its state in microseconds, two programs fight over the same piece of memory, or a server in a data center simply crashes — and in every case the system may keep running and report no error. It just quietly produces wrong results. The core difficulty is that we cannot stop and check every step in billions of operations per second. We either trust that the hardware worked, or we design in checks that catch a failure before a wrong answer spreads. As AI models grow larger and run across hundreds of chips at once, even one undetected error can silently ruin a weeks-long training run, a medical diagnosis, or a safety-critical decision.

Why it bites. Hardware is physical: transistors wear out over years, stray particles from space randomly flip stored bits, and manufacturing flaws sneak past quality checks. When a program runs across thousands of chips at once, the chance that something goes wrong at any one of them is much higher than for a single chip. And the sheer speed of modern computation — billions of steps per second — makes it impossible to recheck everything after the fact unless you plan for it from the start.

The approach. Researchers pursue three overlapping strategies. First, prove that a design is correct on paper before it ever runs — like checking a blueprint before pouring concrete. Second, watch for warning signs while the system runs and trace failures back to the faulty piece of hardware. Third, build in redundancy and graceful fallback so that when something does fail, the damage is contained rather than total. All three strategies share the same goal: shrink the gap between what the system is supposed to do and what it actually does.

Specialized accelerators

▸ custom silicon built for one job

The problem. Graphics chips were built to paint pixels on a screen, not to run AI models or protect secret data. Different kinds of work — computing on encrypted data without unlocking it, controlling a quantum computer, guiding a robot, or drawing a 3D scene — each need a very different rhythm of computation. Some tasks are deeply step-by-step; some can do millions of things at once; some spend most of their time moving numbers around rather than doing arithmetic on them. No single chip design handles all of these well. This theme asks: when the job is so different from standard AI training that a graphics chip is the wrong tool entirely, what chip should you use instead?

Why it bites. Each of these specialized tasks has a specific bottleneck that graphics chips are bad at. Computing on encrypted data without unlocking it inflates every number into a list thousands of entries long, so even simple addition floods the connection between the chip and its memory — long before the arithmetic units of the chip break a sweat. Quantum computers need classical electronics to send precise pulses and read results back in millionths of a second; ordinary server software is far too slow. Robotics and 3D mapping flip back and forth between large organized calculations and highly scattered memory reads that neither general-purpose nor graphics chips handle gracefully. The common thread: the bottleneck is always moving data, not doing arithmetic.

The approach. Researchers respond by designing chips, compilers, and algorithms together — each piece shaped to eliminate the specific data-movement bottleneck of its domain. Three patterns repeat across papers: (1) place the arithmetic unit physically next to the data it needs, so the data never has to travel far; (2) redesign the algorithm so it produces less data in the first place; (3) build a chip that can reshape its internal wiring to match an irregular workload, rather than forcing the workload to fit a rigid pipeline.
