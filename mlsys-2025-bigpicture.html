the shared fight

A chip can multiply faster than it can remember

Every one of the five venues starts from the same physical fact. It is the reason they exist in the same conversation at all.

A language model multiplies your words through an enormous grid of numbers to guess the next word — billions of times. Two resources decide the cost: arithmetic, which modern chips have in abundance, and memory — how much fits close to the chip and how fast numbers move in and out — which is scarce and has barely improved.

So the field's shared truth: AI is starved for data movement, not math. Every venue is closing that gap — just at a different depth.

In 2025 the workload even converged: LLM inference is the single most common workload at all five venues. What changed is that the fight moved down the stack — the same instinct, applied at whatever layer each community owns.

the words you need

Ten ideas, in plain words

The whole field runs on about ten concepts. Learn these and every paper below reads in plain English — no other background needed.

Math vs. memory

Running a model has two costs: doing the arithmetic (chips have tons of this) and fetching the numbers to do it on (slow and scarce). The whole field is about the second cost.

Bandwidththe real bottleneck

How fast you can move data — bytes per second. It's this, not how fast the chip can multiply, that actually limits AI. The chip mostly waits to be fed.

The model's running notesoften called the "KV cache"

As a model writes, it keeps a growing scratchpad of everything it has read so it needn't reread. It balloons with every word and every user, and it's the single biggest memory hog.

Reading vs. writing

Reading your prompt is one big burst of math that keeps the chip busy. Writing the answer is one word at a time, each needing a fresh trip through memory — so the chip mostly idles. Two different jobs.

Smaller numbers"quantization"

Store each number with fewer digits — round it off. There's less to move and it's cheaper to multiply, as long as the rounding doesn't wreck the answer.

Skipping"sparsity"

Most of the numbers barely change the result, so don't compute them. The catch: skipping is messy and irregular, and chips are fastest on tidy, regular work.

A model of specialists"mixture-of-experts"

Split one giant model into many smaller specialists; only a couple run for any given word. So the model is huge but cheap to run — most of it sits idle each step.

Flexible chip vs. hard-wired chipGPU vs. ASIC

A GPU can be programmed to do anything. An ASIC is etched to do exactly one job and nothing else — far faster and cheaper at that one job, useless at others.

Math inside the memory"processing-in-memory"

Instead of hauling numbers to the processor, put tiny math units inside the memory chips themselves, where data moves far faster. You compute where the data already lives.

Chips talking to chips"interconnect"

When hundreds of chips share one job, they must constantly swap partial results. The wiring between them — and the group-messages they send — can eat up to half the total time.

Theme 1 · 99 papers

LLM serving, attention & the model's growing notes

the problem

Every time a language model produces one new word, it must re-read every prior word in the conversation. Those notes — the model's running notes, one entry per word per layer — grow without bound and must be loaded from memory chips on every single step. In long conversations or when handling many users at once, reading that memory takes far more time than the arithmetic needed to figure out the next word.

the approach

Papers in this theme attack the problem from three directions: reduce how much data must be stored (smaller numbers, skipping unimportant entries, smarter caching); reduce the cost of reading that data (doing math inside the memory, chips that sit closer to memory, better scheduling of reading); and reduce how often that data needs to be read at all (reusing shared starting passages, filtering progressively, smarter request ordering). A second cluster of papers improves the machinery around all of this — deciding which requests to handle first, splitting work between chips that are good at different things — so that memory is used efficiently and no chip sits idle.

Why it matters — Modern GPU chips can do arithmetic ten to one hundred times faster than they can move data from memory chips. So as soon as the model's running notes grow too large to fit in fast on-chip memory, every step stalls waiting for data to arrive rather than actually doing math — a pure problem of bandwidth (how fast data moves), with no arithmetic shortcut available.

Making the core attention math faster on today's GPUs

When a model produces a new word, it scores every entry in the model's running notes against the new question, then blends those entries by score. This scoring-and-blending loop is the hottest, most repeated calculation in the whole system. These papers redesign the low-level GPU code that runs this loop, cutting idle processor time and wasted memory trips by rearranging how work is divided across the GPU's thousands of parallel math units.

Shrinking the model's running notes through compression and selective reading

The goal is to preserve model quality while dramatically cutting how many bytes travel between memory and the math units.

Using smaller numbers

the problem

A large AI model stores tens of billions of numbers. Every time the chip does any work, it must pull those numbers from memory chips across slow wires into the part of the chip that does math — and that wire journey is far slower and burns far more energy than the math itself. Using smaller, rounded numbers — say 4-bit numbers instead of 16-bit numbers — means the same wire can carry four times as much of the model per second, and the same memory chip can hold a model four times as large.

the approach

Researchers replace 16-bit or 32-bit numbers with compact codes — smaller integers or entries in a lookup table — then either retrain the model so it learns to live with the rounding, or redesign the chip's math circuits to work directly in the smaller format. The hard part is that not all numbers in a model matter equally: a handful of very large 'outlier' values carry a disproportionate share of information, and simply rounding them breaks accuracy badly. Most papers therefore pair a clever compression strategy (which finds or protects those outliers) with a matched piece of hardware (which knows how to operate in the smaller format without first converting everything back to the original size).

Why it matters — Bandwidth — how fast data moves — is a physical wall: the wires between memory chips and the math circuits can only carry a fixed number of bits per second, and that limit has grown far more slowly than model size. Using smaller numbers means more of the model fits in the small but fast on-chip memory, so the chip makes fewer slow round-trips out to the bigger but slower memory chips.

Making the number format itself smarter

Instead of forcing every stored weight or computed value into a fixed 4-bit or 8-bit slot, these papers design number formats that adjust to whatever range of values actually appears in a given part of the model. A standard fixed grid wastes most of its available codes on values that never show up; an adaptive format places its grid lines where values actually cluster, squeezing more accuracy out of the same number of bits.

The memory wall — moving compute to the data

the problem

Modern AI models spend most of their time waiting for data to travel from memory chips to the processor, not actually doing math. When a model generates a single word, it must haul tens of gigabytes of stored numbers — its learned weights and the model's running notes — across a wire that can only move a fraction of that data per second. The processor sits idle most of the time, starved for numbers to work on.

the approach

The papers in this theme attack the memory wall from three directions: bringing the math closer to where data already lives (doing math inside the memory), smarter decisions about which data lives where and for how long (tiering, fetching data early, compressing, and smarter eviction), and restructuring how programs hand data between storage layers (computing near or inside the storage drive, using a fast link to extra memory, and tuning hardware and software together). Together they aim to cut the number of bytes that must cross any wire before useful work happens.

Why it matters — The chips that do math have gotten dramatically faster over decades, but the wires connecting chips to memory have not kept pace — moving a byte still takes roughly the same time it did years ago. This gap between math speed and data-movement speed is called the memory wall, and AI workloads hit it especially hard because they read enormous tables of learned numbers and the model's running notes in patterns that defeat simple tricks for keeping data nearby.

Running math inside or right next to memory chips

Instead of shipping data from memory to a processor, these designs place small math units inside or immediately beside the memory chip itself. A memory chip's internal wiring carries far more data per second than any external wire, so doing even simple math there — multiplying rows of numbers by a single column, computing distances, adding things up — can eliminate most of the costly external data movement. This is what 'doing math inside the memory' means.

When chips must talk to chips

the problem

When many chips work together to train or run an AI model, they must constantly send each other partial results and stay in sync — each chip finishes its piece of the math, then everyone has to swap numbers before the next step can begin. The wires that carry this traffic have a fixed, physically limited capacity. As models and clusters grow, the volume of data that must move between chips grows faster than those wires can handle, so expensive chips sit idle, waiting for numbers to arrive rather than doing useful work.

the approach

Papers in this theme attack the bottleneck from three angles: reduce how much data needs to move at all (by sending only what matters, sending smaller numbers, or skipping unimportant values); move data more cleverly (by starting transfers early, matching the message pattern to the actual wiring, or letting chips share cached copies); and rebuild the wiring and switches themselves (new connection patterns, smarter switches that do useful work on data as it passes through, and dedicated fast links). The shared insight is that saving even one byte of traffic or one millisecond of idle time compounds across thousands of chips and billions of training steps.

Why it matters — Physics sets hard limits: more wires cost more area and energy, and signals weaken over distance. You cannot simply add bandwidth the way you can add more math units. Meanwhile AI models keep growing, meaning more chips must share more data at once — the demand outpaces what physics cheaply allows.

After a chip finishes its local arithmetic, it must send results to other chips before everyone can move on. If it simply waits, that waiting time is pure waste. The trick is to start sending early — breaking a large message into smaller pieces, sending the first piece while still computing the second, so the wiring and the math units are both kept busy at the same time. This requires a smart planner — a compiler or runtime — that knows exactly when each piece of data will be ready and schedules its delivery in advance.

Skipping the work that doesn't matter

the problem

Modern AI models do enormous amounts of multiplication, but most of the numbers they multiply together are zero or nearly zero and contribute almost nothing to the final answer. Doing that arithmetic anyway wastes energy and time. In a model made of specialists — where only a few specialist sub-networks handle each piece of text — the waste is even worse: at any moment, the vast majority of the model's stored numbers are sitting idle. The challenge is figuring out which work can be safely skipped, communicating that decision to the hardware fast enough, and actually avoiding the load-and-compute cycle for the parts that do not matter.

the approach

The papers in this theme all exploit the same observation: at any moment, only a small fraction of a model's stored numbers are non-zero and worth computing with. They find that active fraction — sometimes at the level of individual bits, sometimes at the level of whole specialist sub-networks — and then redesign how data is laid out, how hardware is wired, or how work is scheduled so that the zero-valued or idle portions are never fetched, never routed, and never multiplied. Some papers remove useless numbers before the model is ever deployed; others decide what to skip on the fly while the model is answering a question; others reorganize where data lives so the active slice can be read in one fast burst rather than many scattered trips.

Why it matters — Bandwidth — how fast data moves — is the real constraint: pulling a number out of memory chips costs far more energy than doing arithmetic on it once it arrives. So the biggest win comes from never loading the useless zeros at all, not merely from skipping the multiply once a number is already on-chip.

The engineering challenge is that routing decisions must be sent across machines, the right stored numbers must be fetched at the right moment, and the delay caused by chips talking to each other can dominate total time if not carefully hidden behind useful work.

the problem

Trusting the machine

the problem

Every computer that handles sensitive work — a cloud server running your bank's code, an AI model processing private medical records, a phone storing your passwords — was designed to run fast, not to keep secrets. Speed-driven design choices, like letting the processor guess what instructions are coming next or sharing a memory bus between multiple users, leave physical fingerprints that an attacker can read without ever breaking any lock. The core problem is that the hardware itself leaks information through time, power draw, and the physical side-effects of its own normal operation. As AI workloads grow and more computation moves to shared cloud chips, the number of places where secrets can leak grows with it.

the approach

Researchers attack the problem from three directions. First, they find and document the new leakage paths that sharing creates — discovering that even ordinary hardware features like a 'fetch data early' engine, a memory prediction table, or an idle power state can bleed secrets across security boundaries. Second, they build defenses that either eliminate the sharing (physically isolating resources by owner) or make the sharing timing-uniform so every user sees identical delays regardless of what the other user is doing. Third, they verify that proposed defenses actually hold up — using automated testing tools, mathematical proofs, and real chip measurements to close the gap between a security claim on paper and security in practice.

Why it matters — Modern hardware is fast because it reuses resources: the same storage cells, the same memory rows, the same prediction tables, the same memory bus slots get shared between programs, between virtual machines, and between users. That sharing is the physical root of nearly every attack in this section. If two users' data ever passes through the same transistor at overlapping times, the timing or electrical residue of that overlap can carry secret information out to a watching attacker.

Being sure it's actually correct

the problem

AI systems and the chips running them can produce wrong answers without any warning. A worn-out transistor flips a single digit, a quantum bit loses its state in microseconds, two programs fight over the same piece of memory, or a server in a data center simply crashes — and in every case the system may keep running and report no error. It just quietly produces wrong results. The core difficulty is that we cannot stop and check every step in billions of operations per second. We either trust that the hardware worked, or we design in checks that catch a failure before a wrong answer spreads. As AI models grow larger and run across hundreds of chips at once, even one undetected error can silently ruin a weeks-long training run, a medical diagnosis, or a safety-critical decision.

the approach

Researchers pursue three overlapping strategies. First, prove that a design is correct on paper before it ever runs — like checking a blueprint before pouring concrete. Second, watch for warning signs while the system runs and trace failures back to the faulty piece of hardware. Third, build in redundancy and graceful fallback so that when something does fail, the damage is contained rather than total. All three strategies share the same goal: shrink the gap between what the system is supposed to do and what it actually does.

Why it matters — Hardware is physical: transistors wear out over years, stray particles from space randomly flip stored bits, and manufacturing flaws sneak past quality checks. When a program runs across thousands of chips at once, the chance that something goes wrong at any one of them is much higher than for a single chip. Beyond the GPU

the problem

Graphics chips were built to paint pixels on a screen, not to run AI models or protect secret data. Different kinds of work — keeping data encrypted while computing on it, controlling a quantum computer, guiding a robot, or drawing a 3D scene — each need a very different rhythm of computation. Some tasks are deeply step-by-step; some can do millions of things at once; some spend most of their time moving numbers around rather than doing arithmetic on them. No single chip design handles all of these well. This theme asks: when the job is so different from standard AI training that a graphics chip is the wrong tool entirely, what chip should you use instead?

the approach

Researchers respond by designing chips, compilers, and algorithms together — each piece shaped to eliminate the specific data-movement bottleneck of its domain. Three patterns repeat across papers: (1) place the arithmetic unit physically next to the data it needs, so the data never has to travel far; (2) redesign the algorithm so it produces less data in the first place; (3) build a chip that can reshape its internal wiring to match an irregular workload, rather than forcing the workload to fit a rigid pipeline.

Why it matters — Each of these specialized tasks has a specific bottleneck that graphics chips are bad at. Computing on encrypted data inflates every number into a list thousands of entries long, so even simple addition floods the connection between the chip and its memory — long before the arithmetic parts of the chip break a sweat. Quantum computers need classical electronics to send precise pulses and read results back in millionths of a second; ordinary server software is far too slow. Robotics and 3D mapping flip back and forth between large organized calculations and highly scattered memory reads that neither general-purpose nor graphics chips handle gracefully. The common thread: the bottleneck is always moving data, not doing arithmetic.

Everything else that keeps it running

the problem

Building and running AI systems at the scale of real products means solving a grab-bag of practical problems that do not fit neatly into any one box: training models spread across dozens of machines without drowning in the time it takes those machines to share results, stopping the software that runs those models from swelling to a size that eats up memory, cutting the amount of bookkeeping data that training needs to hold in memory at once, making sure that performance measurements reported in research papers actually mean what they claim to mean, counting the carbon emitted not just by running chips but by building them in the first place, and squeezing large datasets so they travel and store faster. The papers here attack this kind of hidden waste from many angles at once: stripping away software that is compiled but never actually called, replacing expensive per-weight training bookkeeping with a compact mathematical stand-in that reaches the same answer, redesigning how machines share training results so they do it far less often across slow long-distance links, squeezing numbers down at the hardware level so less data needs to travel, and replacing misleading summary statistics in research papers with ones that are mathematically sound. stepping back

What the field agrees on — and argues about

Across 619 papers and five venues, a handful of shared instincts recur — and a handful of open fights.

Shared instincts

Stop separating software from hardware

Nobody optimizes "the algorithm" and "the chip" as separate layers anymore. The number format, the sparsity pattern, the data layout are fused straight into the silicon and its scheduling. Only the depth of the seam changes by venue.

Reading a prompt ≠ writing an answer

Over and over, the two halves of running a model are pulled apart and handled as different machines — because reading is heavy on math and writing is heavy on memory.

It's the memory, not the math

The explicit motivation almost everywhere. It holds so deeply that one paper measuring real compute-in-memory silicon found that even putting the math inside the memory can still leave you waiting on data movement.

Decide while running, don't hard-code

Fixed rules are the recurring villain. Adaptive skipping, deadline-aware scheduling, plans that reshape mid-flight — the field keeps replacing static heuristics with live decisions.

Open arguments

Reported speed vs. real speed

One MLSys paper is the field's conscience: it shows compression tricks that look great alone can vanish — or reverse — inside a real serving system under real load. Many accelerator papers, tested only in a simulator or one request at a time, quietly inherit this risk.

Flexible vs. fastest

The papers that build a general tool (a compiler, a chip generator, a programming model) trade a little peak speed for the ability to retarget. The papers that hand-build one accelerator get the peak but not the reach.

Cheaper vs. correct

"Near-lossless" is claimed nearly everywhere quantization or skipping appears, but the accuracy cost is negotiated, rarely eliminated — and rarely measured per-example rather than on average.

There's no shared yardstick

MLSys has a near-standard test bench (vLLM, FlashAttention, an A100/H100). The hardware venues have none — each subfield uses its own simulator — so speed numbers rarely compare even between two papers at the same conference, let alone across venues.
