the shared fight

A chip can multiply faster than it can remember

Every one of the five venues starts from the same physical fact. It is the reason they exist in the same conversation at all.

A language model multiplies your words through an enormous grid of numbers to guess the next word — billions of times. Two resources decide the cost: arithmetic, which modern chips have in abundance, and memory — how much fits close to the chip and how fast numbers move in and out — which is scarce and has barely improved.

So the field's shared truth: AI is starved for data movement, not math. Every venue is closing that gap — just at a different depth.

In 2025 the workload even converged: LLM inference is the single most common workload at all five venues. What changed is that the fight moved down the stack — the same instinct, applied at whatever layer each community owns.

Theme 1 · 99 papers

LLM serving, attention & the model's growing notes

the problem

Every time a language model generates one new word, it must re-read every word it has ever written or seen in the conversation. Those notes — called the KV cache (the model's running record of prior context, one compressed entry per token per layer) — grow without bound and must be loaded from memory on every single step. At long conversations or large batches, reading that memory takes far more time than the arithmetic needed to produce the next word.

the approach

Papers in this theme attack the bottleneck from three directions: reduce the amount of data that must be stored (compression, sparsity, smarter caching); reduce the cost of reading that data (in-storage compute, near-memory chips, better kernel scheduling); and reduce how often the data needs to be read at all (prefix reuse, progressive filtering, smarter scheduling). A secondary cluster of papers improves the surrounding serving infrastructure — schedulers, prefill/decode disaggregation, heterogeneous cluster routing — so that GPUs spend less idle time and the memory that does exist is used at peak efficiency.

Why it matters — Modern GPU chips can perform arithmetic ten to one hundred times faster than they can move data from memory. So as soon as the KV cache grows large relative to what fits in fast on-chip memory, every decode step stalls waiting for data rather than computing — a pure memory-bandwidth bottleneck with no arithmetic shortcut.

Making attention kernels faster on current GPUs

The attention operation itself — comparing each new query against every stored key-value pair to produce a weighted sum — is the hottest inner loop. These papers redesign the low-level GPU code (called kernels) that executes this loop, squeezing out idle processor time and memory round-trips through better tiling, quantization, and work distribution across the GPU's parallel cores.

Shrinking the KV cache through compression and sparsity

Rather than accepting that the full cache must exist and be read, these papers reduce either its size (quantization, low-rank projection) or the fraction that must be read per step (sparse attention, progressive filtering). Using smaller numbers

the problem

Modern AI models are enormous: a single large language model may store tens of billions of numbers, each occupying 16 or 32 bits of memory. Every time the chip runs a calculation it must move those numbers from storage into the compute units, and that movement is far slower and more energy-hungry than the arithmetic itself. Quantization is the practice of re-encoding each number using fewer bits — say 4 instead of 16 — so the same wire can carry more values per second and the same memory chip can hold a larger model.

the approach

Researchers replace high-precision numbers (32-bit or 16-bit floating point) with compact codes — integers, lookup-table indices, or custom small formats — then either retrain the model to absorb the rounding error, or design the chip arithmetic to match the new format directly. The hard part is that not all numbers in a model are equally important: a few extreme 'outlier' values carry disproportionate information and break naive compression. Most papers therefore pair a compression algorithm (which finds or avoids the outliers) with a matched hardware unit (which knows how to work in the compressed format without first converting back to the original).

Why it matters — Memory bandwidth is a physical bottleneck: the wires connecting storage to arithmetic circuits can only move a fixed number of bits per second, and that limit has grown far more slowly than model size. Shrinking each number means more of the model fits in fast on-chip memory and fewer trips are needed to slow off-chip storage.

Making the number format itself smarter

Instead of forcing every weight or activation into a fixed 4-bit or 8-bit integer, these papers design new numerical formats that adapt to the actual spread of values in a given layer or group of weights. The memory wall — moving compute to the data

the problem

Modern AI models—and many database, graph, and scientific workloads—spend most of their time waiting for data to travel from memory chips to the processor, not actually doing arithmetic. A large language model generating a single word must haul tens of gigabytes of stored numbers (its weights and its running conversation notes) across an electrical connection that can only move a fraction of that data per second. The processor sits idle for the vast majority of the time, starved for numbers to crunch.

the approach

The papers in this theme attack the memory wall from three directions: bringing the arithmetic closer to where data already lives (processing-in-memory and compute-in-memory), smarter management of which data lives where and for how long (tiering, prefetching, compression, and cache replacement), and restructuring how programs hand data between storage layers (near-storage computation, CXL-attached memory, and software-hardware co-design). Together they aim to cut the number of bytes that must cross any electrical boundary before useful work can happen.

Why it matters — Transistors on a compute chip have gotten dramatically faster over decades, but the wires connecting chips to memory have not kept pace—moving a byte still takes roughly the same time it did years ago. This gap between compute speed and data-movement speed is called the memory wall, and AI workloads hit it especially hard because they access enormous parameter tables and conversation-notes buffers with patterns that defeat simple caching strategies.

This is often called processing-in-memory (PIM) or near-memory processing (NMP).

When chips must talk to chips

the problem

When many chips work together to train or run an AI model, they must constantly share data — passing partial results, keeping copies of shared values in sync, and coordinating who does what next. The wires and switches that carry this traffic (the interconnect) have a fixed, physically limited capacity. As models and clusters grow, the volume of data that must move between chips grows faster than the capacity of those wires, turning the network into the primary bottleneck. The result is that expensive chips sit idle, waiting for data to arrive rather than doing arithmetic.

the approach

Papers in this theme attack the bottleneck from three angles: reduce how much data needs to move (compression, smarter partitioning, eliminating redundant transfers), move the data more efficiently (better routing, topology-matched algorithms, overlapping transfers with computation), and rethink the hardware fabric itself (new topologies, smarter switches that process data in-flight, and purpose-built physical layers). The common thread is that saving one byte of network traffic or one millisecond of idle time compounds across thousands of chips and billions of training steps.

Why it matters — Physics sets hard limits: more wires cost more area and power, and signals degrade over distance. You cannot simply add bandwidth the way you can add compute cores. Meanwhile, AI models keep growing, meaning more devices must share more data at once — the demand outpaces what physics cheaply allows.

Skipping the work that doesn't matter

the problem

Modern AI models do enormous amounts of arithmetic, but most of the numbers they multiply together are zero or nearly zero and contribute almost nothing to the final answer. Doing that arithmetic anyway wastes energy and time. For Mixture-of-Experts models — where a large network is divided into many specialized sub-networks called experts, and only a few experts process each piece of text — the waste is even more extreme: only a tiny fraction of the model's parameters do any work on any given input. The challenge is figuring out which work can be safely skipped, communicating that decision to the hardware fast enough, and actually avoiding the load-and-compute cycle for the parts that do not matter.

the approach

The papers in this theme exploit the observation that, at any moment, only a sparse subset of a model's values are non-zero and worth computing. They identify that sparse subset — sometimes at the level of individual bits, sometimes at the level of whole expert sub-networks — and then redesign data layout, hardware datapaths, or scheduling policies so that the zero-valued or dormant portions are never fetched, never routed, and never multiplied. The core technique varies: some papers prune weights before deployment, some dynamically skip computations at runtime, and some reorganize where data lives in memory so that the active subset can be read in one efficient burst rather than many scattered accesses.

Why it matters — Memory bandwidth is the real constraint: loading a number from memory costs far more energy than performing an arithmetic operation on it, so the biggest win comes from never loading the zeros at all, not merely from skipping the multiply once a number is already on-chip.

The engineering challenge is that routing decisions must be sent across machines, the right weights must be fetched at the right moment, and the communication delay between machines can dominate total time if not carefully hidden behind useful work.

Trusting the machine

the problem

Every computer that handles sensitive work — a cloud server running your bank's code, an AI model processing private medical records, a phone storing your passwords — is built from hardware that was designed to run fast, not to keep secrets. Speed-oriented design decisions, like letting the processor guess what instructions are coming next or sharing a memory bus between multiple users, leave physical fingerprints that an attacker can read without ever breaking any lock. The core problem is that the hardware itself leaks information through time, power draw, and physical side-effects of its own normal operation. As AI workloads grow and more computation moves to shared cloud chips, the attack surface — the number of places where secrets can leak — grows with it.

the approach

Researchers attack the problem from three directions. First, they find and document the new leakage paths that sharing creates — discovering that even mundane hardware features like a prefetch engine, a memory disambiguation table, or an idle power state can bleed secrets across security boundaries. Second, they build defenses that either eliminate the sharing (physically isolating resources by owner) or make the sharing timing-uniform (so every tenant sees identical delays regardless of what the other tenant is doing). Third, they verify that proposed defenses actually hold up — using automated testing tools, formal proofs, and real silicon measurements to close the gap between a security claim on paper and security in practice.

Why it matters — Modern hardware is fast because it reuses resources: the same cache lines, the same memory rows, the same branch-prediction tables, the same memory bus slots get shared between programs, between virtual machines, and between users. Sharing is the physical root of nearly every attack in this section — if two tenants' data ever passes through the same transistor at overlapping times, the timing or electrical residue of that overlap can carry secret information out.

Being sure it's actually correct

the problem

AI systems and the hardware running them can produce wrong answers silently — a misfiring transistor corrupts a number, a quantum bit decoheres, a parallel program deadlocks, or a cloud server crashes — and the system gives no warning. The fundamental challenge is that we cannot inspect every intermediate result; we must either trust that the hardware worked, or build in checks that catch failure before it propagates. As AI models grow larger and run on more hardware in parallel, a single undetected error in billions of operations per second can quietly corrupt a training run, a medical diagnosis, or a flight-control decision.

the approach

Researchers pursue three overlapping strategies: formally prove that a design is correct before it ever runs (mathematical verification); detect and attribute failures after they happen using runtime signals (operational monitoring); and build redundancy and graceful fallback into the system so that when something does fail, the effect is contained rather than catastrophic. Across all three strategies, the goal is the same — shrink the gap between what the system is supposed to do and what it actually does.

Why it matters — Hardware is physical: transistors age, cosmic rays flip bits, and manufacturing defects slip through testing. Software that runs across thousands of chips simultaneously multiplies the chances that something goes wrong, while the sheer speed of modern computation makes after-the-fact checking impractical without deliberate design.

Beyond the GPU

the problem

Graphics processors were designed to render pixels, not to run AI models or encrypt data. As AI, cryptography, robotics, and quantum computing each impose unique patterns of computation — some deeply sequential, some massively parallel, some dominated by memory traffic rather than arithmetic — a single chip architecture cannot serve all of them well. The research in this theme asks: when a workload is so different from neural-network training that a GPU is fundamentally the wrong tool, what chip should replace it? The answers span everything from silicon that computes directly on encrypted data, to chips that control quantum processors, to processors printed on flexible plastic that can bend around a wrist.

the approach

Researchers respond by designing chips, compilers, and algorithms that co-evolve together — hardware shaped to eliminate the specific data-movement bottleneck of one domain, paired with a compiler that generates code exploiting the hardware's unique capabilities. Three broad strategies recur: (1) place computation physically next to the data it needs, eliminating the wire between processor and memory; (2) redesign the algorithm so it produces less data in the first place; (3) build reconfigurable or programmable substrate that can reshape itself to the irregular workload pattern rather than forcing the workload into a rigid pipeline.

Why it matters — Every specialized domain has a distinct bottleneck that mismatches the GPU's strengths. Fully Homomorphic Encryption (FHE) — computing on data that remains encrypted end-to-end — inflates every number into a polynomial thousands of elements long, so even simple addition floods memory buses rather than stressing arithmetic cores. Quantum processors require nanosecond-precise classical control signals and low-latency feedback; standard server software stacks are too slow by orders of magnitude. Robotics and spatial-mapping algorithms alternate between dense matrix math and highly irregular pointer-chasing, which neither CPUs nor GPUs handle gracefully. The common thread is that each domain's bottleneck is data movement and timing, not raw multiply-accumulate throughput.

Quantum computer control and compilation

A quantum chip is useless without a fast classical controller that generates precise microwave or laser pulses, reads back measurement results in microseconds, and feeds the results back into the next gate operation. Classical software running on a general-purpose CPU is too slow for this feedback loop — quantum states decay in microseconds. Beyond control electronics, quantum programs need compilers that reduce the number of physical operations before the quantum state degrades. The papers here span both: hardware that closes the classical feedback loop fast enough, and algorithms that shrink circuit size before execution.

Quantum error correction hardware

Quantum information is fragile — stray electromagnetic fields flip qubits constantly. Quantum error correction (QEC) encodes one reliable 'logical qubit' in dozens or hundreds of physical qubits, running a continuous cycle of syndrome measurement (detecting errors without reading the data) and decoding (identifying what went wrong). The decoder must finish before the next error arrives — sub-microsecond on today's hardware — which rules out software running on a conventional CPU. These papers build purpose-built decoders and memory architectures that make fault-tolerant quantum computing physically realizable.

Everything else that keeps it running

the problem

Building and running AI systems at scale requires solving a wide set of infrastructure problems that do not fit neatly under any single hardware category: training models across many machines without choking on network bottlenecks, keeping the software that runs those models from ballooning in size, shrinking the memory needed to store optimizer state during training, making measurements of system performance honest and comparable, accounting for the carbon cost of building and running chips, and compressing the enormous datasets that feed these systems. Each of these is a distinct engineering challenge, yet all of them quietly limit how fast or how cheaply AI can actually progress. Together they form the unglamorous plumbing that determines whether the theoretically possible hardware improvements translate into real-world gains.

the approach

Researchers across these papers attack infrastructure inefficiency from multiple angles simultaneously: pruning away software that is never actually used, mathematically approximating expensive optimizer bookkeeping with cheaper surrogates, redesigning how gradient synchronization happens across slow wide-area network links, compressing raw data at wire speed so less bandwidth is needed in the first place, and replacing misleading aggregate performance statistics with ones that are mathematically correct. The common thread is finding and eliminating hidden waste — in software, in memory, in network round-trips, in how results are reported.

Why it matters — AI workloads are physically constrained by two scarce resources that money cannot infinitely buy: memory capacity and communication bandwidth. Every workaround that wastes either one — bloated software libraries, redundant optimizer state, slow data synchronization across continents, or uncompressed data streams — costs real time and energy at scale.

Shrinking memory used during model training

Training a large language model requires storing not just the model weights but also the optimizer's running statistics — numbers that track how each weight has been changing, used to set each weight's personal learning rate. For a 7-billion-parameter model these statistics alone occupy 28 gigabytes, crowding out space for data and forcing the use of more machines. The papers here find clever ways to store far less without changing what the training process actually learns.

mlsys-2025-059APOLLO — Replaces the full per-weight optimizer statistics with a compressed low-rank approximation, cutting optimizer memory from 28 GB to 1.6 GB for a 7B-parameter model while matching training quality; enables 3x higher throughput by fitting larger batches on the same hardware.

Training across slow or unreliable network links

Standard distributed training requires every machine to share its gradient updates with every other machine after every single training step, which works fine inside a data center on fast private cables but becomes a bottleneck when machines are in different cities or connected only by ordinary internet. The papers here redesign the synchronization pattern so that machines do many local steps before talking to each other, dramatically cutting how much data must cross the slow link.

mlsys-2025-036Photon — Lets geographically distributed clusters each train locally for many steps before synchronizing, reducing network traffic 500-fold for a 7B model and cutting total training wall-clock time 35% versus a centralized approach, while actually improving model quality.
mlsys-2025-045JaxPP — Extends the JAX machine-learning framework to support flexible pipeline parallelism schedules (where model layers are split across machines and data flows through them like an assembly line), enabling efficient multi-machine training across slower inter-node links.

Removing dead weight from machine-learning software

The software libraries that power GPU-based machine learning ship with enormous amounts of compiled code — kernels for dozens of GPU architectures, operations for every possible workload — but any given training run uses only a tiny fraction of it. This dead code consumes memory, slows down program loading, and wastes the scarce capacity of the GPU's own memory. The paper here builds a tool to identify what is actually used and strips out the rest.

mlsys-2025-054Negativa-ML — Intercepts the runtime calls that load GPU compute kernels to discover which ones any given workload actually uses, then permanently removes the rest from the library files; shrinks GPU code by up to 75% and cuts peak GPU memory use by up to 70%.

Compressing these numbers before storing or sending them buys back that bandwidth, but existing compressors force a choice between speed and compression ratio. The paper here closes that gap specifically for floating-point data on both CPUs and GPUs.

Accounting for the carbon cost of building and running hardware

The environmental cost of a chip comes from two places: the energy consumed while it runs (operational carbon) and the enormous industrial process that manufactured it (embodied carbon — the carbon baked into the chip before it ever turned on). These two costs trade off against each other in ways that are easy to ignore. Chips with more transistors are faster but cost more to fabricate; running fewer, larger chips longer saves manufacturing carbon but may use more electricity. The paper here builds a framework to optimize both costs together.

Researchers report speedups by averaging ratios across many benchmarks, but the standard averaging method (the geometric mean) is mathematically wrong for speedup ratios: it can declare one design faster than another even when the opposite is true in any single workload. Every paper here ultimately fights the same root constraint: the gap between how fast processors can compute and how fast data can move to feed them. Whether the fix is compressing data before it travels, eliminating optimizer state that occupies precious memory, synchronizing gradients less often across slow networks, or stripping unused code that crowds out working data — each solution reclaims bandwidth or capacity that arithmetic alone cannot create.

stepping back

What the field agrees on — and argues about

Across 619 papers and five venues, a handful of shared instincts recur — and a handful of open fights.

Shared instincts

Stop separating software from hardware

Nobody optimizes "the algorithm" and "the chip" as separate layers anymore. The number format, the sparsity pattern, the data layout are fused straight into the silicon and its scheduling. Only the depth of the seam changes by venue.

Reading a prompt ≠ writing an answer

Over and over, the two halves of running a model are pulled apart and handled as different machines — because reading is heavy on math and writing is heavy on memory.

It's the memory, not the math

The explicit motivation almost everywhere. It holds so deeply that one paper measuring real compute-in-memory silicon found that even putting the math inside the memory can still leave you waiting on data movement.

Decide while running, don't hard-code

Fixed rules are the recurring villain. Adaptive skipping, deadline-aware scheduling, plans that reshape mid-flight — the field keeps replacing static heuristics with live decisions.

Open arguments

Reported speed vs. real speed

One MLSys paper is the field's conscience: it shows compression tricks that look great alone can vanish — or reverse — inside a real serving system under real load. Many accelerator papers, tested only in a simulator or one request at a time, quietly inherit this risk.

Flexible vs. fastest

The papers that build a general tool (a compiler, a chip generator, a programming model) trade a little peak speed for the ability to retarget. The papers that hand-build one accelerator get the peak but not the reach.

Cheaper vs. correct

"Near-lossless" is claimed nearly everywhere quantization or skipping appears, but the accuracy cost is negotiated, rarely eliminated — and rarely measured per-example rather than on average.

There's no shared yardstick

MLSys has a near-standard test bench (vLLM, FlashAttention, an A100/H100). The hardware venues have none — each subfield uses its own simulator — so speed numbers rarely compare even between two papers at the same conference, let alone across venues.
