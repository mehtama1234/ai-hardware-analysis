Trusting the machine

attacks on chips, and the defenses
141 papers · 6 read in full · 135 from the abstract

the problemThe problem, in depth

Start with the one fact that everything in this chapter grows out of: a computer chip is not really a place where thinking happens. It is a place where numbers are moved. A chip has a tiny patch where arithmetic gets done, and a vast surrounding landscape where numbers wait, get shuttled around, and get parked for later. The arithmetic is nearly free. The moving is where all the time, all the heat, and — this is the part that matters here — all the leaking goes. Almost every attack and defense in this theme is a story about the moving of data, not the doing of arithmetic.

Why does moving data create a security problem at all? Because to move data efficiently, a chip cheats. It remembers where you looked last time so it can guess where you will look next. It keeps a private stash of recently-used numbers physically close to the arithmetic so it doesn't have to walk all the way out to the far memory. It starts doing work before it is even sure the work is needed, betting it can undo any mistake. Each of these cheats is a shortcut that makes the machine faster. And each shortcut leaves a mark. The private stash is warm where you touched it and cold where you didn't. The guess-machine is trained by what you did. The undo-a-mistake trick leaves footprints even for work that got thrown away. An attacker who cannot read your secret directly can instead watch these marks — how long something took, which shelf is warm, how the guessing behaves — and reconstruct the secret from its shadow. This is the family of "side channels": the machine keeps its promise never to hand your secret to a stranger, and then betrays you through how fast it runs.

Now layer on the physical reality of the far memory itself. The main memory of a computer is a warehouse of billions of microscopic buckets, each holding a tiny puddle of electric charge that means one or zero. To pack them densely — which is the whole point, since we want a lot of memory cheap — the buckets are jammed against each other in tight rows. They are so close that repeatedly slamming one row open and shut can jostle charge out of its neighbors, quietly flipping a one into a zero in a row you were never allowed to touch. This is Rowhammer, and it is not a software bug you can patch away. It is the price of physical density. It means an attacker running ordinary, permitted code in one corner of a shared machine can reach across a wall he is forbidden to cross and physically corrupt someone else's data — a co-tenant's, or the referee program that is supposed to keep tenants apart (asplos-2025-027, micro-2025-025). The wall between two programs is a legal fiction enforced on top of a slab of silicon that does not respect it.

This is why the problem is genuinely hard, and not just a matter of writing more careful code. The threats live below the level where software can see. A program has no way to ask "is my neighbor's memory physically adjacent to mine?" or "did the chip's guess-machine just learn something from me?" The abstractions that make computers usable — this is my memory, that is yours; my program runs in order, one step at a time — are polite lies told by the hardware. The real machine underneath is a churning, guessing, physically-crowded thing, and security means finding every place where the polite lie leaks and either sealing it or accepting a cost to hide it.

And the stakes have risen sharply because of how computing is now sold. We no longer each own our own machine. We rent slices of enormous shared machines in data centers, and a bank's data sits on the same physical chip as a stranger's. Worse, we now send our most valuable asset — a trained model, or the private data we feed it — to run on someone else's hardware and simply hope they don't peek. The whole business model of cloud computing and of running large AI models as a service rests on a promise: your secret is safe even on a machine you don't control and don't trust. That promise is exactly what this theme is about keeping. Several papers here are specifically about protecting the giant models and their private inputs — the running notes a language model keeps as it generates, the lookup tables that encode who a user is (asplos-2025-008, hpca-2025-004).

There is one more twist that makes this field feel like a hall of mirrors. Because the deepest threats are physical and cannot be wished away, the defenses themselves are physical machinery — extra counters, extra encryption, extra bookkeeping — bolted onto the memory path. And that machinery, being physical, moves data and takes time too. So the defenses acquire their own shadows. Several papers here show that the very shields built to stop one attack open a fresh timing side channel of their own, because the shield acts differently depending on what the victim is doing, and a watcher can read that difference (isca-2025-113, micro-2025-020, asplos-2025-095). Defending a computer, it turns out, is not like locking a door once. It is like trying to make a machine that never gives away, through any twitch of its behavior, what it is holding — while still running fast enough to be worth using.

the approachesHow the field actually tackles it

1.Stopping the neighbors from flipping your bits (Rowhammer defense)

This is the largest single cluster in the theme, and it tackles the most brutally physical problem: the memory chip's own density lets one row of storage disturb its neighbors. Since you cannot make the buckets less crowded without making memory more expensive, the defense is to catch the attack in the act. The core mechanism is counting. The memory keeps a tally of how many times each row has been slammed open, and when a row's count climbs suspiciously high, the memory sneaks in an extra refresh of the endangered neighbors — topping up their charge before it leaks away enough to flip. The whole art is doing this cheaply. A naive counter for every one of billions of rows would cost more than the memory it protects, so the papers compete on how to track the dangerous rows with almost no bookkeeping and almost no slowdown.

The field has converged on a few clever tricks. Some designs keep only a single "most-suspicious row so far" tag per memory bank instead of a whole table, which turns out to be provably enough (asplos-2025-113). Others move the counting off the critical path so it doesn't slow down every ordinary memory access (hpca-2025-015), or only count sometimes — rolling dice on each access and lowering the alarm threshold to compensate — so the common, benign case pays almost nothing (isca-2025-107). Others attack the scheduling of the protective refreshes: doing them one small sub-section of the chip at a time so the rest keeps serving requests (hpca-2025-072), or amortizing an expensive multi-bank stall across many rows at once (isca-2025-101). And one paper sidesteps the hardware entirely by having the software that hands out memory simply never place two distrusting programs in physically adjacent rows — if there is always a buffer row between enemies, a flip lands harmlessly in no-man's-land (micro-2025-090).

The recurring tension is security-versus-speed, and it is unusually sharp here because these defenses run on literally every memory access. A design that is airtight but adds even a few percent to every access is a tax on the entire machine forever. So the papers obsess over provable safety at near-zero average cost, and repeatedly discover that earlier "secure" designs had a hole an attacker could squeeze through (asplos-2025-113). Meanwhile the attack side keeps the pressure on, showing that as chips get denser the threshold for triggering a flip keeps dropping, and that supposedly-immune newest chips fall to a cleverer hammering technique after all (micro-2025-025).

2.Sealing the timing leaks (side-channel attacks and defenses)

This is the other giant cluster, and it is the purest expression of the theme's root idea. The machine never hands over your secret; it leaks the secret through how it behaves. The mechanism attackers exploit is always some shared, stateful shortcut the chip uses to go faster. The private stash of recently-used data (the cache) is the classic one: whatever the victim touched is now warm, and a watcher timing his own accesses can feel which shelves went warm and infer what the victim looked at. But the theme shows the leak is everywhere, not just in the cache. The guess-machine that predicts where memory accesses will go can be spied on and even actively poisoned (asplos-2025-056). The unit that decides whether two memory operations conflict leaks through balanced code that was supposed to be safe (asplos-2025-086). Even the chip's sleep states leak: how long a processor takes to wake up reveals what it was doing, and — remarkably — this can be read remotely over a network, with no shared machine at all (hpca-2025-046). Attackers also sharpen these leaks with tricks to slow the victim down at the exact right instant so faint signals become readable (asplos-2025-176), and exploit the pipeline flush that self-modifying code triggers as a loud, easy-to-read signal (asplos-2025-124).

The defenses fall into two philosophies. One is to make the shortcut behave identically no matter what the secret is — scrub the warm marks, or serve memory in fixed, secret-independent turns so an outsider learns nothing from timing (asplos-2025-098). The other is to scramble the mapping between what the victim does and what the attacker can observe, using cheap encryption so the attacker can no longer tell which shelf corresponds to which secret (micro-2025-014). A theme-wide lesson, stated plainly by several papers, is that hiding must be done without paying the full cost of the shortcut you are hiding — the fixed-turn memory schedule that leaks nothing also wastes bandwidth, so the trick is recovering that waste while staying blind to secrets (asplos-2025-098). And the darkest lesson is that defenses beget new channels: the anti-Rowhammer machinery, because it acts on the memory bus in a way that depends on the victim's activity, becomes a fresh timing channel of its own (isca-2025-113, micro-2025-020).

3.Taming the machine's habit of running ahead of itself (speculative execution)

Modern chips almost never wait. Rather than sit idle while they figure out whether a branch of code should run, they guess the answer and barrel ahead, quietly undoing the work if the guess was wrong. The undo restores the official state perfectly — but it does not scrub the private stash, the warm shelves, the trained guess-machine. So an attacker can trick the chip into speculatively touching a secret it was never allowed to touch, let the chip realize its mistake and roll back, and then read the secret out of the leftover warmth. This family, named Spectre and its relatives, is uniquely nasty because the leak comes from work the machine formally never did. You cannot find it by reading the program, because in the official story that code never ran.

The defenses cluster around a single idea: watch data that came from a secret and refuse to let it reach any shortcut that leaves an observable mark until the machine is certain the work is real and not a discarded guess. One approach tags secret-derived values and stalls any speculative memory access that would act on them, reusing tagging hardware the chip already has (isca-2025-037, isca-2025-038). Another, aimed at cryptographic code that is supposed to run in a fixed pattern anyway, throws out guessing entirely for those sensitive stretches and instead replays a pre-recorded, compressed script of exactly which way each branch goes — no guess, no leak, and because crypto code is so repetitive the script is tiny (isca-2025-039, isca-2025-041). A third builds a mathematically-proven compiler that rewrites sensitive code so no secret can ever flow into a leaking channel under any known variant of the trick, with the proof checked by machine (asplos-2025-104).

The unavoidable trade-off is that guessing is why the chip is fast, so any defense that curbs guessing risks giving back the speed. A key finding here is sobering: when researchers actually built these defenses down to the real circuits instead of estimating, the true cost was far higher than earlier papers claimed — over a third of performance on the fastest cores — because the security check itself sits on a timing-critical path (micro-2025-047). That gap between paper-estimate and silicon-reality is exactly why the theme also invests heavily in testing tools (asplos-2025-047, asplos-2025-159) that hunt for these leaks before a chip is built, since a speculation defense that quietly fails is worse than none.

4.Renting a machine you don't trust (confidential and trusted execution)

This approach answers the cloud's central dilemma head-on: you must run your secret computation on someone else's hardware, and you trust neither the owner nor the other tenants. The mechanism is to carve out a sealed enclave inside the chip — a region where the data is encrypted the instant it leaves the small trusted core and travels anywhere else, so that even the machine's owner, peering at the memory, sees only ciphertext. The chip can also prove to you remotely that the sealed region is genuine and unmodified before you send your secret in. This is the foundation under confidential computing, and the theme extends it in every direction: from the processor out to expansion memory (micro-2025-071), out to the network card so trust no longer has to route through the processor at all (asplos-2025-048), and — critically for AI — onto the flexible accelerator chips that actually run large models (asplos-2025-008).

The universal cost is encryption, and encryption is expensive precisely because it sits on the data-movement path this whole theme is about. Every number crossing the enclave wall must be scrambled or unscrambled, and that work stalls the very traffic that dominates a chip's time. The measured hit for running a large model inside an encrypted enclave can be crippling — cutting throughput by half or more (asplos-2025-008). So the papers here are almost all about hiding that cost. One overlaps the encryption with the computation and even guesses ahead of time which data the accelerator will demand next, encrypting it in advance so the scrambling never blocks the pipeline (asplos-2025-008). Another encrypts hot, frequently-touched pages with a faster scheme and only pays for the strong-but-slow scheme on cold pages, re-encrypting on the fly as access patterns shift (micro-2025-071).

It is worth being honest that the enclave is not a magic wall. Many of the side-channel and Rowhammer attacks elsewhere in this theme are demonstrated specifically breaching these enclaves — extracting keys through cache and contention timing even across the encryption boundary (asplos-2025-030), or reading enclave secrets through the memory-disambiguation unit (asplos-2025-086). Encryption hides the content of memory; it does not hide the pattern of access, and pattern is often enough. This is why the theme treats trusted execution not as a solved fortress but as one layer that must be combined with side-channel and access-pattern defenses to actually hold.

5.Building real walls between programs that share one machine (memory isolation and safety)

Even setting aside physical attacks, the plainest security problem is a program that reaches outside its assigned memory — by accident (a bug) or on purpose (an exploit) — and touches memory belonging to someone else. The classic wall is the coarse page boundary the operating system enforces, but it is both too coarse (it can't stop a program from corrupting its own data structures) and too expensive (crossing between isolated programs means a costly context switch). This cluster builds finer, cheaper walls. The recurring mechanism is to attach the permission to the pointer itself: instead of checking a separate table on every access, the chip carries the allowed bounds along with the address — sometimes literally tucked into unused bits of the 64-bit address (hpca-2025-051) — and the hardware rejects any access that steps outside them. This is the idea behind capability-based safety, extended here even to accelerator chips that know nothing about it, by inserting a small checking shim on their memory path (isca-2025-022).

A second family keeps many mutually-distrusting programs in a single shared memory space — which is fast, because nobody has to switch contexts — and enforces the walls with lightweight hardware tags or region colors that the chip checks on the fly. This lets a sandbox run untrusted code with almost none of the usual isolation overhead (asplos-2025-103), lets thousands of tiny cloud functions share one address space and still stay walled off from each other at nanosecond granularity (isca-2025-064), and lets a program protect its own most sensitive data from its own less-trusted parts by flipping a fast permission switch (hpca-2025-009). A third, heavier family — oblivious memory — hides not the content but the pattern of access itself, shuffling memory so that even a watcher who sees every address learns nothing about which one you actually cared about; the papers here fight its notorious cost by overlapping and pipelining the shuffling in dedicated hardware (hpca-2025-109) or by replacing a table lookup with a computation that has no revealing access pattern at all (hpca-2025-004).

The trade-off across this cluster is granularity-versus-cost. Fine-grained, per-object or per-pointer walls catch far more than coarse page walls, but only pay off if the check is nearly free — which is why so much of the work is about folding the check into existing hardware and keeping it off the critical timing path (isca-2025-022 reports about 1.4% overhead; hpca-2025-009 speculatively overlaps the permission switch). Oblivious memory sits at the expensive extreme: it offers the strongest hiding but historically at many-times slowdown, which is why its papers are pure engineering fights to make it affordable enough to use at all.

6.Finding the holes before the attacker does (verification, fuzzing, and testing)

The threats in this theme are subtle enough that no human can be sure a chip or its low-level software is free of them just by reading the design. So a whole line of work automates the hunt. The mechanism is to generate enormous numbers of adversarial test cases and watch for a leak or a crash, or to reason mathematically over all possible executions at once. On the software side, fuzzers bombard the operating system's core with malformed inputs to trip hidden bugs, and the papers here make the bombardment smarter — using a learned model to steer mutations toward unexplored code (asplos-2025-050), or using a large language model to write the detailed input specifications that a fuzzer needs and that humans normally hand-craft one painful call at a time (asplos-2025-163).

On the hardware side, the tools target exactly the invisible behaviors the rest of the theme worries about. Some generate targeted micro-tests that probe whether a speculation defense actually blocks every variant of the trick, giving designers feedback while the chip is still on the drawing board (asplos-2025-047). Others precisely set up the hidden internal state needed to trigger a speculative leak and then track whether any secret data reaches an observable channel (asplos-2025-159). Still others reason symbolically over a hardware design — exploring many execution paths mathematically rather than one at a time — and make it tractable by caching and reusing the results of equivalent sub-questions (asplos-2025-119). A related strand generates provably-correct low-level configuration code automatically, so that the error-prone hand-adaptation that so often introduces isolation-breaking bugs is replaced by correct-by-construction generation (asplos-2025-011).

The trade-off is coverage-versus-certainty. Fuzzing and testing can find real bugs fast but can never prove none remain; formal, symbolic reasoning can prove safety but drowns in the sheer number of paths a real design has. Much of the cleverness here is buying more of one without paying the full price of the other — a learned or LLM-guided fuzzer that explores more of the space, or a symbolic engine that reuses work to reach further before it chokes. The honest reason this cluster exists is the lesson from the speculation work: defenses that looked secure on paper turned out to have holes, so the field now treats automated, adversarial checking as a required step, not an optional one.

7.Poisoning the software the model is built from (the ML supply chain)

The newest and most distinct corner of the theme steps away from silicon entirely to a threat that rides the way modern AI is actually assembled. Nobody builds a large model from scratch; you stack it on a tower of borrowed software packages and pre-trained components downloaded from public repositories. Every borrowed piece is a place where an attacker can hide something, and the tower for AI is taller and less scrutinized than for ordinary software. The mechanism demonstrated here is chillingly quiet: a poisoned upstream package, at the moment it is loaded, reaches into the shared memory of the program and rewrites a core function of the AI library — swapping the model's forward behavior to plant a backdoor, or subtly altering a data-processing setting so the model quietly misbehaves, all without touching a single line of the victim's own code (mlsys-2025-005).

This matters because it evades everything the rest of the theme builds. There is no bit-flip, no timing leak, no boundary being crossed by force — the malicious change arrives through a door the developer opened voluntarily by trusting a dependency, and it manipulates the model's behavior rather than the operating system's security, so conventional detectors, which look for OS-level intrusions, never see it. The same paper pairs the attack demonstration with a large-scale study, using language models to sift through hundreds of thousands of public code discussions, and finds the uncomfortable truth that the AI community is no more security-aware than any other, despite this larger attack surface.

There is no clean defense offered here, and that is the point of including it: it marks the frontier where hardware security's hard-won lessons about untrusted components meet a software ecosystem that hasn't yet internalized them. The trade-off is the oldest one in security — the convenience of building on others' work versus the risk of trusting it — now playing out in an AI stack whose economic pull toward reuse is overwhelming.

where it standsWhat's solved, what's open

The mature core of this theme — Rowhammer counting and microarchitectural side channels — has reached a productive but unfinished equilibrium: defenses now offer provable safety at genuinely low average cost (fractions of a percent for the best Rowhammer trackers), yet every generation of denser memory lowers the threshold that must be defended, every new attack revives a channel thought dead, and defenses keep spawning fresh leaks of their own. It is a treadmill, not a finish line, and the field has accepted that. The honest gaps are sharpest where the theme meets modern AI. Confidential execution can seal a model's data behind encryption, but only by paying a heavy tax on the very data movement that dominates a large model's runtime, and the papers that shrink that tax do so by prediction and overlap rather than by removing it — so confidential AI inference is now feasible but still costly, and still porous to the access-pattern and timing attacks that encryption does not stop. Two things remain genuinely open. First, the reality-check problem: when secure-speculation defenses were finally built down to real circuits, their cost was far worse than a decade of paper estimates suggested, which means the community still cannot cheaply predict the true price of a defense before committing silicon to it. Second, the whole software supply chain beneath AI models is a wide-open surface with demonstrated attacks and no deployed defense, and no more security awareness than ordinary software despite a larger attack surface — the least solved and arguably most consequential gap in the theme.

MOAT: Securely Mitigating Rowhammer with Per-Row Activation Counters

What it does

Memory chips (specifically DDR5 RAM — the kind of main memory inside modern computers) are vulnerable to an attack called Rowhammer: an attacker can flip bits in a neighboring memory row by rapidly and repeatedly accessing an adjacent row, potentially corrupting data or escalating their own privileges. The new DDR5 standard introduced a framework called PRAC+ABO (Per-Row Activation Counting plus Alert-Back-Off) to defend against this, but it left the actual implementation to memory manufacturers, and the most obvious implementation (Panopticon) turns out to be insecure. This paper proves Panopticon can be broken with a 9x worse outcome than its advertised protection level, then designs MOAT, a provably secure replacement that uses only 7 bytes of storage per memory bank and causes only 0.28% slowdown on real workloads.

The method, in detail

The idea. Rowhammer works because rapidly activating a row of memory cells disturbs the electrical charge in physically adjacent rows, eventually flipping a bit. The threshold for causing a flip has dropped from 140,000 activations in 2014 to around 4,800 today and keeps falling. The new DDR5 framework addresses this by storing a counter next to each row that increments every time that row is accessed — a 'per-row activation counter' (PRAC). When a counter gets high enough, the memory chip sends an alert (ABO — Alert Back-Off) that tells the memory controller to stop sending requests so the chip can refresh neighboring rows.

Breaking Panopticon. Panopticon (the design that inspired PRAC+ABO) stores the addresses of rows that have hit the threshold in a small 8-entry queue per memory bank, but critically stores no counter information in the queue — only addresses. MOAT's authors discovered this is exploitable. The attack, called Jailbreak, works as follows: deliberately fill all 8 queue slots with different row addresses; then continuously hammer the most recently added row (the last one to be serviced, since the queue is first-in-first-out). That row accumulates activations the entire time the other 7 rows are being serviced, one by one. For a protection threshold of 128 activations, Jailbreak causes 1,152 activations on the attack row before it is mitigated — 9x the intended limit.

How MOAT works. The insight: if you can only mitigate one row per refresh period anyway (because refreshing a row's neighbors takes time), there is no need to track more than one candidate at a time. MOAT uses just two small registers per memory bank: a Current Tracked Address (CTA) register that always holds the row with the highest activation count seen since the last mitigation, and a Current Mitigated Address (CMA) register. When any row is accessed and its counter exceeds a first threshold (ETH, the Eligibility Threshold), it replaces the CTA only if its count is higher than whatever is already there. Because the CTA always tracks the current most-activated row with its counter value intact, an attacker cannot hide a row from the system by filling the queue with decoys — there is no queue to fill.

When a row's counter exceeds a second, higher threshold (ATH, the Alert Threshold), the chip sends an ABO alert and the row is immediately mitigated. A safe counter-reset mechanism copies the counters of boundary rows to 2-byte SRAM registers before resetting, preventing the attack of straddling a reset window.

The catch. The DDR5 specification requires at least 1-4 normal memory accesses between consecutive alerts (to avoid the memory channel being completely monopolized). An attacker can exploit these gaps using the Ratchet attack to push a row beyond ATH before it is mitigated. Analysis shows that with ATH=64 and current specifications, the true safe Rowhammer threshold MOAT can defend against is 99 activations.

The result. On 21 real workloads (SPEC and GAP benchmarks), MOAT with ATH=64 causes an average slowdown of only 0.28%, requires 7 bytes of on-chip storage per bank, and can safely protect against Rowhammer thresholds down to 99 activations.

SMaCk: Efficient Instruction Cache Attacks via Self-Modifying Code Conflicts

What it does

Modern x86 processors have a safety mechanism that detects when a running program overwrites its own instructions, then flushes the processor pipeline — a drastic slow-down that leaks measurable timing signals. This paper shows that an attacker sharing the same physical CPU core can exploit those timing signals to spy on a neighbour's private data, including encryption keys, with far better accuracy than classic cache-timing attacks. The authors also show how to detect the attacks using built-in hardware counters.

The method, in detail

The idea. When two programs share a CPU through hyper-threading (two virtual processors running on one physical core), they also share the pipeline — the assembly-line of stages that process instructions. If one program triggers a 'self-modifying code' (SMC) detection event, the hardware flushes that shared pipeline, stalling both programs for 235-425 extra cycles. An attacker in the sibling thread can measure that stall and learn whether the victim touched certain memory locations.

Why this is better than ordinary cache timing. Classic instruction-cache attacks distinguish a cache hit from a miss by a 1-2 cycle difference — so noisy as to be nearly useless without special high-resolution timers. The SMC flush adds hundreds of cycles of delay, making the signal crystal clear even on AMD chips whose timers only resolve to 20 cycles.

How the attacker probes. Prime+iProbe: the attacker fills chosen cache lines with do-nothing instructions (nops), then uses SMC-triggering instructions — flush, store, lock+increment, prefetch — as a probe. If the victim fetched one of those cache lines, the probe creates no flush (the line is gone), giving a low timing reading. If the line is still there, the flush fires and the timing spikes. This converts the victim's memory-access pattern into a timing waveform the attacker reads.

The key design choice. Finding that multiple x86 instructions — not just plain memory stores — trigger the SMC mechanism, and that the resulting timing gap (150-350 cycles) is large enough to distinguish reliably. The paper reverse-engineers exactly which instructions cause which hardware event counters to fire, confirming the mechanism on both Intel and AMD.

Case study results. Against a known-vulnerable implementation of RSA-2048 decryption in the Libgcrypt library, 10 measurement traces recover 70% of the private key — enough for a complete key recovery. A single trace against the OpenSSL secure-password protocol leaks 65-90% of the server's secret. A Spectre-style variant uses the instruction cache instead of the data cache, bypassing existing Spectre defenses.

Defense. Monitoring the hardware counter MACHINE_CLEARS.SMC detects the attack with 99.4% accuracy and only 0.85% false positives.

ρHammer: Reviving RowHammer Attacks on New Architectures via Prefetching

What it does

Modern computer memory chips (DRAM) have a hardware flaw called RowHammer: hammering the same memory row with rapid repeated reads can flip bits in neighboring rows, corrupting data or enabling attacks. On Intel's newest processors (12th and 14th generation, codenamed Alder Lake and Raptor Lake), the usual technique for doing this hammering — issuing ordinary memory-load instructions — has stopped working entirely. This paper presents rhoHammer, a new attack framework that revives RowHammer on these latest platforms by exploiting a different class of CPU instruction (prefetch hints) and carefully countering the processor's tendency to reorder those instructions.

The method, in detail

The idea. RowHammer requires hammering the same DRAM row thousands of times per refresh interval (roughly every 7.8 microseconds). To target the right rows, the attacker first must know the hidden internal address layout of the memory chip — which physical address maps to which DRAM bank and row. Then, the CPU must issue accesses to exactly those rows fast enough to flip bits before the memory controller refreshes them and recovers.

Step 1 — Reverse-engineering the memory map. The paper introduces a three-phase timing measurement algorithm (called Duet/Trios/Quartet) that uses a known side channel: when two consecutive accesses land in the same DRAM bank but different rows, the second access is noticeably slower because the first row must be precharged out of the row buffer first. By systematically issuing pairs and triples of addresses that differ in known bit positions and measuring whether a timing penalty appears, the algorithm deduces which bits of the physical address control which bank, without any prior knowledge of the chip's layout. This recovers the full mapping in about 4–9 seconds on all tested platforms — prior tools completely fail on the newer chips.

Step 2 — Prefetch-based hammering. Normal memory loads (the MOV instruction) stall the CPU pipeline while waiting for data to come back. Software prefetch instructions (PREFETCHT2/PREFETCHNTA) do not stall: the CPU just forwards the request and moves on immediately. This means prefetch instructions can issue far more memory requests per second — roughly doubling hammering throughput compared to loads.

Step 3 — Counter-speculation. Modern CPUs reorder instructions speculatively to run faster. That reordering scrambles the careful order that RowHammer patterns need. Prefetch instructions are especially vulnerable because CPU fence (barrier) instructions cannot order them. rhoHammer solves this with two tricks: (a) randomizing the control flow at runtime using unpredictable bit manipulations so the branch predictor cannot pre-execute loops in the wrong order, and (b) inserting tuned chains of NOP (do-nothing) instructions between prefetches — enough to fill the CPU's reorder buffer and force serialized execution, but not so many that throughput drops.

The result. On the newest Raptor Lake chips where load-based hammering produces zero bit flips, rhoHammer achieves a sustained rate of 2,291 bit flips per minute. On older Comet Lake chips it is 112x faster than the load-based baseline.

Supply-Chain Attacks in Machine Learning Frameworks

What it does

Machine learning projects like PyTorch and HuggingFace depend on hundreds of third-party Python packages, each of which is a potential back door into the application. This paper shows that a quietly corrupted helper package can silently rewrite parts of the AI system at runtime, injecting hidden behaviors, disabling safety checks, or leaking model weights — all without making any suspicious network calls or system requests that existing security tools would catch. A companion study then surveys half a million public discussions in top ML and non-ML open-source projects and finds that ML developers are no more security-conscious than general software developers, despite facing a uniquely larger threat surface.

The method, in detail

The attack. Python's design lets any imported package read and overwrite variables, functions, and classes that belong to every other package loaded in the same program. The authors exploit two mechanisms. First, global overwriting: a malicious helper package simply re-points well-known names — such as a model's forward function or an image-resize setting — at attacker-controlled replacements during its own startup. Because Python caches module objects globally, the replacement sticks even after the victim code imports the legitimate library again.
