# Punica: Multi-Tenant LoRA Serving

**Problem:** Serving multiple LoRA-fine-tuned model variants for different tenants requires inefficient memory and compute resources, as each tenant's adapted weights cannot easily share a single base model inference path without serialization overhead.

**Method:** Punica combines requests from different customers' LoRA adapters (lightweight customizations of a base model) into larger processing batches that run together. It stores the LoRA weights in high-bandwidth memory (the fastest available memory tier), eliminating the overhead of shuffling data between slower storage. When certain adapter combinations can't run in the same batch, dynamic scheduling (real-time reordering) intelligently groups compatible requests together while maintaining high throughput.

**Novelty:** Combining requests from different customers into shared processing batches lets them run the same base model computation together, even though each customer has different weight customizations, cutting per-request overhead.
