# Radius: Range-based Gradient Sparsity for Large Foundation Model Pre-training

**Venue:** MLSYS 2025 · **Subtheme:** Gradient Compression & Communication Reduction

## What It Does

In data-parallel LLM pre-training on 64+ GPUs, every training step requires synchronizing gradients (averaging across all workers) via allreduce collective communication. For a 2B parameter model, that's 8GB of data per step, times 1000+ steps per hour = huge communication overhead (40% of training time). Naive gradient sparsification using top-k (send only the largest 40% of gradients, discard the rest) requires allgather (each worker sends its top-k indices to all others) because different workers compute different top-k sets — scalability is O(n) with worker count. Radius makes a key empirical observation: after 15-20% of pre-training warm-up, the top-k gradient indices stabilize — the set of "important" gradient dimensions remains nearly identical across training steps for hours. This means **all workers can reuse the same top-k index set for T steps (default T=200)**, eliminating the need for expensive allgather. Instead of: (worker 0 computes top-k, worker 1 computes top-k, allgather indices) → allreduce values; Radius does: (compute dense allreduce on all gradients once every T steps to find new indices) → for next T steps, allreduce only top-k values using the same shared index mask. The catch: AdamW optimizer (nearly universal in LLM training) internally tracks per-gradient statistics; if gradients are zeroed before reaching the optimizer, AdamW diverges. Radius applies **gradient correction**: it computes the effective gradient update that AdamW would apply (accounting for momentum buffers and learning-rate schedules) before selecting which gradients to keep, ensuring index selection reflects true model importance. It also uses **error feedback**: accumulate non-top-k gradients in a local buffer, adding them back every T steps during re-sampling to prevent gradient leakage.

Data flow: Layer 0 computes gradients → apply gradient correction (simulate AdamW step) → compare against reused top-k mask → send only top-k values via allreduce → all workers receive same sparse gradient → apply AdamW with full state (momentum still tracks all dimensions, but only top-k receive updates) → accumulate non-top-k in error buffer → every T steps, full allreduce recomputes indices, error-feedback applies accumulated gradient → resume sparsification with new indices.

## The Key Result

On GPT-2.0B pre-training with 40% sparsity (send only top 60% of gradients) across 64 A100 GPUs: 21% per-step time reduction, 19% overall pre-training speedup, 89.69% communication volume reduction. At 128 GPUs with 40% sparsity, scaling efficiency is 42.5% versus 32.8% for dense allreduce (communication savings compound at scale). Downstream task performance on GLUE, SuperGLUE, LAMBADA is preserved (no accuracy degradation). 5.14% faster than PowerSGD baseline.

## Why This Approach

Gradient communication is the fundamental scalability bottleneck for distributed LLM pre-training. Tensor parallelism and pipeline parallelism help, but they are used in conjunction with data parallelism, and data-parallel gradient exchange still dominates. Dense allreduce is unavoidable (baseline). Naive top-k with allgather breaks down at 64+ workers because allgather cost grows linearly with worker count (NVLink/Slingshot fabric becomes saturated). Radius' insight — indices are temporally stable — is validated empirically across GPT models of various scales. This stability comes from the training dynamics: once model predictions stabilize (after warm-up), gradient distributions also stabilize, and the "important" dimensions (largest magnitudes) remain consistent. By reusing indices, Radius eliminates the O(n) allgather bottleneck and replaces it with a periodic full allreduce (amortized over T steps), which scales as O(log n) with tree reductions. The gradient correction mechanism ensures compatibility with AdamW (unlike naive top-k which just zeros non-top-k, corrupting optimizer state). This is essential because AdamW is the standard optimizer; a method that requires algorithm changes is not deployable. The alternative — higher bandwidth interconnects, more compression (PowerSGD low-rank) — does not achieve the scaling efficiency that Radius provides.

## What It Leaves Open

- Requires 15-20% warm-up training with full dense allreduce before sparsification activates; for very large models (70B+), warm-up cost is non-trivial (~25-30 hours on 128 GPUs).
- Very high sparsity (d=0.1, only top 10% gradients) causes training instability and divergence; practical limit around d=0.4 (60% gradient retention); no clear theoretical understanding of why or how to predict stability boundaries.
- Index resampling interval T is a hyperparameter (default T=200); no autotuning; suboptimal T causes either unnecessary communication (T too small) or gradient staleness (T too large).
- Evaluation limited to pure data-parallel training; integration with pipeline parallelism (Megatron-LM style) and tensor parallelism is open — gradient sparsification patterns differ in pipeline stages.
- Error feedback accumulation assumes bounded gradient magnitude; under extreme training dynamics (loss spikes, learning rate schedule changes), accumulated error could explode.
