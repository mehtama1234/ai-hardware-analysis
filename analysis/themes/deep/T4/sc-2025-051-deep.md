# Slicing Is All You Need: Towards A Universal One-Sided Algorithm for Distributed Matrix Multiplication

**Venue:** SC · **Subtheme:** Distributed Computation & Communication Scheduling

## What It Does

Distributed matrix multiplication is fragmented across incompatible algorithm families: 1D partitioning (split rows or columns) suits sparse models; 2D partitioning (checkerboard split of A and B) minimizes communication for dense matmul; 1.5D and 2.5D variants trade communication for memory. When a model requires a different partitioning strategy (e.g., switching from column-parallel tensor parallelism to row-parallel), existing frameworks require explicit data redistribution (allgather + scatter), which incurs communication overhead. This paper proposes a universal one-sided algorithm that dynamically computes any partitioning using index arithmetic. Instead of precomputing which rank holds which tile, the algorithm uses **slicing** — dynamic index-space calculation — to determine tile ownership on-the-fly. For example, to multiply a [M×K] matrix A partitioned row-wise across N workers with a [K×N] matrix B partitioned column-wise, each worker i computes C[i*M/N:(i+1)*M/N, j*N/N:(j+1)*N/N] by locally performing a sparse inner-loop that only touches the required A rows and B columns. The key mechanism is one-sided communication: instead of synchronizing all ranks at redistribution points, each rank independently issues RDMA reads/puts to fetch its required tiles from other ranks (PGAS style), overlapping communication with local computation. The implementation uses a high-level PGAS C++ framework with direct GPU-GPU communication via intra-node interconnects (NVLink, PCIe), avoiding host CPU marshaling.

Data flow: Worker 0 computes its tile of C → queries index-space mapping for which (A row, B column) pairs it needs → issues RDMA reads for A rows from workers 0-3 and B columns from workers 0-3 → while remote data arrives over NVLink, compute local contributions → aggregate partial results via one-sided put. This eliminates the synchronization barrier.

## The Key Result

Competitive with PyTorch DTensor optimization on distributed matrix multiplication across all partitioning strategies (1D, 2D, 1.5D, 2.5D). Achieves this using a single universal algorithm rather than separate specialized implementations per partitioning type. GPU-GPU direct communication reduces latency versus host-mediated redistribution.

## Why This Approach

Modern distributed AI systems require flexible parallelism: tensor parallelism may use 1D column-parallel on one layer, row-parallel on another, 2D on bottleneck layers. Traditional frameworks support either one partitioning statically (JAX pjit with hardcoded parallelism) or require explicit redistribution between changes. Redistribution is expensive: a [8K×8K] matrix reshuffle costs ~10GB of communication, serializing computation. Slicing's index-arithmetic approach avoids redistribution by computing the required tile set per rank on-demand. One-sided communication (RDMA/PGAS) is key because it avoids global synchronization; each rank independently fetches its data when ready, allowing stragglers to overlap computation. This is critical for heterogeneous clusters where ranks have variable compute speed. The universal algorithm design (not 1D, 2D, 1.5D, 2.5D variants) simplifies compiler logic and enables dynamic partitioning policy changes mid-training. The alternative — hand-tuned per-partitioning kernels or barrier-synchronized redistribution — does not provide this flexibility.

## What It Leaves Open

- Limited quantitative performance details; comparison mostly qualitative against PyTorch DTensor; exact speedup numbers on large-scale runs (128+ GPUs) not provided.
- Scalability to very large models (175B+ parameters) and how one-sided communication cost scales with model depth and width unclear.
- Interaction with batched matrix multiplication (matmul with batch dimension, common in attention) and mixed precision (FP8 quantization) not explored.
- Error handling for network failures or stragglers in one-sided communication not discussed; assumes reliable RDMA.
- Integration with gradient checkpointing and backward pass communication patterns (different slicing pattern for gradient computation) is open question.
