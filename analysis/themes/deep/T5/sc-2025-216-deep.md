# Sparsified Preconditioned Conjugate Gradient Solver on GPUs

**Venue:** SC · **Subtheme:** Preconditioner Sparsification for GPU Parallelism

## What It Does

Preconditioned iterative sparse linear solvers (used extensively in scientific computing for systems Ax=b) suffer from data dependencies across iterations that limit GPU parallelization. Preconditioners (like ILU factorization) reduce iteration count but introduce sequential dependencies: computing iteration k+1 requires results from iteration k, creating a dependency chain that prevents full GPU parallelization.

The SPCG (Sparsified Preconditioned Conjugate Gradient) solver intentionally sparsifies the preconditioner: instead of using a full preconditioner P (which is dense in dependency), it uses a sparser version P' with many small-magnitude elements removed. This reduction in connectivity reduces iteration dependencies while maintaining convergence (though requiring slightly more iterations). The sparsified preconditioner enables fine-grained parallelism on GPUs with many cores (2000+ CUDA cores).

Evaluated with ILU(0) (incomplete LU factorization with zero fill) and ILU(K) (K levels of fill-in) preconditioners on symmetric positive definite (SPD) matrices.

## The Key Result

On NVIDIA A100 GPUs, SPCG achieves 1.23x geometric mean speedup in the iterative phase with ILU(0) and 1.65x with ILU(K). End-to-end speedup: 1.68x with ILU(0) and 3.73x with ILU(K). These speedups come from reduced iteration dependencies enabling better GPU utilization despite additional iterations from sparsification.

## Why This Approach

Preconditioned conjugate gradient (PCG) solvers are backbone of large-scale scientific computing (CFD, structural mechanics, climate models) but are memory-bandwidth bound on GPUs. Preconditioners like ILU reduce iteration count dramatically (10-50x fewer iterations), but their sequential structure (forward/backward substitution in triangular solver) creates control dependencies that kill GPU parallelism. Naive GPU implementations serialize preconditioner application, leaving thousands of cores idle.

Sparsification breaks this bottleneck: by removing weak coupling (low-magnitude preconditioner entries), the dependency graph becomes sparser, enabling concurrent execution of more iterations. The cost is additional iterations (since preconditioner quality degrades slightly), but this trade is favorable on GPUs where iteration cost is low (matrix-vector multiply is memory-bandwidth limited anyway).

ILU(K) shows larger gains (3.73x) than ILU(0) (1.68x) because ILU(K) is denser initially, so sparsification removes more dependencies. ILU(0) is already sparse, limiting gain from sparsification.

## What It Leaves Open

- Evaluation limited to symmetric positive definite (SPD) matrices; behavior on general unsymmetric matrices (which require GMRES or BiCG instead of CG) not characterized. SPD systems are important but represent a subset of sparse linear solver use cases.
- Convergence analysis of sparsified preconditioners not rigorously provided; no formal bounds on iteration count increase as a function of sparsification level.
- Sparsification strategy (which entries to drop) is not detailed; sensitivity to sparsification threshold unknown. A heuristic threshold (drop entries below τ in magnitude) likely underlies the method, but robustness to different thresholds not shown.
- Scaling behavior beyond A100 (e.g., on H100 or multi-GPU systems) not explored; gains may diminish if network bandwidth becomes bottleneck instead of GPU compute.
- No comparison with other GPU-accelerated preconditioners (e.g., polynomial preconditioners, approximate inverse) or modern hardware-efficient alternatives (e.g., multigrid methods).
