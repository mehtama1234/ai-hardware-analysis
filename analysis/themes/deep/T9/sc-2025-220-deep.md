# Energy-aware performance portability with OpenMP dynamic variants

**Venue:** SC · **Subtheme:** Energy-Aware HPC Portability

## What It Does

This work extends OpenMP's dynamic variants mechanism with energy-aware runtime selection. OpenMP variants are alternative implementations of the same function (e.g., loop with different parallelization strategies). The runtime previously chose variants based on performance heuristics; this work adds energy profiling. The runtime profiles each variant's power consumption and execution time using RAPL (Intel/AMD), thermal sensors, and power meters. Online, the runtime solves a constrained optimization: select the variant that minimizes energy subject to meeting latency deadlines or thermal budgets.

Data path: workload → runtime profiler → power model (RAPL readings) → optimization solver → variant selection → execution. Constraints include thermal limits (e.g., "keep core <85°C") and deadline guarantees (e.g., "complete in <500 ms").

## The Key Result

Energy-aware selection reduces total energy consumption by 22–45% across HPC benchmarks (LULESH, AMG, HPCG) on Xeon Platinum and EPYC CPUs, compared to performance-only variant selection. On embedded systems (ARM Cortex-A72), energy savings reach 58% with marginal performance loss (<5%) under tight thermal budgets. Thermal headroom increased by 15°C in sustained workloads, extending device lifespan.

## Why This Approach

HPC systems are power-limited: data centers must fit within available power budgets (100–500 kW per rack). Embedded systems are thermally limited (passive cooling). Performance-only optimization ignores power, often selecting the fastest variant which is also the most power-hungry. Energy-aware selection exploits the Pareto frontier: some "slower" variants consume 40% less power, worth selecting if deadlines allow. This is critical for edge HPC (robotics, autonomous vehicles) where battery life and thermal constraints dominate.

## What It Leaves Open

- Profiling overhead: RAPL readings and solver cost ~10–50 ms per decision; unclear if this scales to sub-millisecond adaptive requirements
- Heterogeneous CPU/GPU systems: current profiling limited to CPU RAPL; GPU power estimation requires vendor-specific APIs not standardized
- Predictive models: static profiling assumes stable frequency/voltage; DVFS state changes invalidate models; dynamic re-profiling cost not analyzed
- Cross-platform generalization: energy models trained on Xeon do not transfer to EPYC or ARM; retraining burden high
- Integration with resource managers (Slurm, Kubernetes): global power/thermal constraints across nodes require distributed solving
