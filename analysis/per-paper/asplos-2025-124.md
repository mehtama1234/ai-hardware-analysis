# SMaCk: Efficient Instruction Cache Attacks via Self-Modifying Code Conflicts

**Venue:** ASPLOS  
**Authors:** Seonghun Son, Daniel Moghimi, Berk Gulmezoglu  
**Confidence:** high (full text)

## Problem
Self-modifying code (SMC) detection on x86 processors triggers pipeline flushes and machine clears shared between SMT sibling threads, creating measurable timing side channels on the L1 instruction cache with 150-350 cycle hit/miss differences — versus only 1-2 cycles for conventional L1i Prime+Probe attacks. These SMC-based timing channels have not been systematically exploited as a standalone information-leakage primitive.

## Motivation
Conventional L1i cache side-channel attacks suffer from low SNR because cache hit/miss timing differences are only 1-2 cycles; SMC pipeline flushes amplify this signal 100-350x, enabling more reliable cryptographic key extraction and covert channels.

## Method
The attack exploits the x86 SMC detection mechanism: when an instruction modifies a cache line already loaded in the L1i cache, the processor flushes the entire pipeline and serializes all sibling threads, adding 235-425 cycles of observable delay. The authors reverse engineer which x86 instructions trigger machine clears (clflush, clflushopt, store, lock+inc, prefetch, clwb) using hardware performance counters (MACHINE_CLEARS.SMC, CYCLE_ACTIVITY.STALLS_TOTAL, INSTRUCTION_CACHE_LINES_INVALIDATED). They construct Prime+iProbe and Flush+iReload covert channels using these instructions as L1i cache probes between SMT threads. For key extraction, the receiver primes L1i cache sets with nop-filled cache lines, then probes using SMC-creating instructions to detect evictions caused by the victim's instruction execution. A performance counter-based defense using machine_clears.smc detects attacks with 99.36% accuracy.

## Key Novelty
Systematic exploitation of the x86 SMC pipeline flush mechanism as a high-SNR side channel on the L1 instruction cache, enabling unprivileged SMT-thread attacks with 100-350x larger timing signal than prior L1i attacks.

## Contributions
- Systematic characterization of which x86 instructions trigger SMC detection and their timing profiles across Intel (Cascade Lake through Tiger Lake) and AMD (Ryzen 5, EPYC 7232P) microarchitectures
- Prime+iProbe and Flush+iReload L1i attack variants achieving up to 670 Kbit/s covert channel bandwidth with <1% error rate
- End-to-end cryptographic attacks: 2048-bit RSA key recovery in 10 traces and single-trace OpenSSL SRP server key extraction (65-90% bit leakage)
- ISpectre: Spectre-v1 variant using L1i cache encoding that bypasses data-cache Spectre defenses (up to 4105 B/s on AMD Ryzen 5)
- Performance counter-based dynamic detection with F-score 0.987 using machine_clears.smc counter

## Metrics
- Covert channel: up to 670 Kbit/s (Flush+iFlush/Flushopt), <1% error rate
- RSA key recovery: 70% bits in 10 traces (Prime+iFlush) vs. far more traces with Mastik
- SRP leakage: 65-90% bits in a single trace vs. 22-48% for Mastik PnP
- ISpectre throughput: up to 4105 B/s on AMD Ryzen 5 vs. 58.98 B/s for TLB-Evict+Prefetch
- Detection F-score: 0.987, FPR: 0.85%

## Baselines
- Mastik L1i Prime+Probe toolkit
- TLB-Evict+Prefetch (AMD prefetch attack)
- Lipp et al. AMD cache way predictor attack (0.66 B/s)

## Limitations
Attack requires SMT (hyper-threading) enabled; effectiveness varies across microarchitectures (AMD EPYC 7232P resists flush-based SMC conflicts); ~45% of SRP key bits unrecoverable per single trace due to sliding window ambiguity.
