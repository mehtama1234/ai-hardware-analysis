# SC-2025-255: Scabbard - CPU/GPU Unified Memory Race Detection

**First Tool for Cross-Device Data Race Detection in Heterogeneous Systems**

## Summary
Scabbard is the first tool to detect data races in CPU/GPU systems using Unified Heterogeneous Memory (UHM). By instrumenting both CPU and GPU code via LLVM passes and performing offline trace analysis, it closes a critical correctness gap in heterogeneous programming.

## Problem
AMD GPUs with Unified Heterogeneous Memory simplify heterogeneous programming by enabling transparent data sharing:
1. **Traditional Heterogeneous Model**:
   - CPU and GPU have separate memory spaces
   - Programmer explicitly copies data (CPU→GPU, GPU→CPU)
   - Error-prone but explicit

2. **UHM Model (AMD APU, MI series with UHM)**:
   - Single address space visible to both CPU and GPU
   - Automatic coherence maintained by hardware
   - Simpler programming model
   - **But introduces race condition risk**

3. **Correctness Gap**:
   - Existing CPU race detectors (TSan, Helgrind) miss GPU accesses
   - Existing GPU race detectors (GPU-specific tools) miss CPU accesses
   - **No tool detects cross-device races**
   - Example:
     ```c
     // CPU thread                    // GPU kernel
     data[i] = x;                     data[i]++;  // RACE!
     // Both modify same memory, no synchronization
     ```

## Approach
### Architecture Overview
**Two-Phase System**:
1. **Instrumentation Phase**: Mark memory accesses
2. **Analysis Phase**: Detect races offline

### Phase 1: Instrumentation via LLVM
**LLVM Pass Plugin**:
- Integrates into ROCm/HIP compilation pipeline
- Operates on LLVM IR (intermediate representation)
- Instruments both CPU and GPU code uniformly

**What Gets Instrumented**:
1. **Load Instructions**: Read from memory
   - Record: thread ID, variable address, timestamp
   - Add to trace buffer
2. **Store Instructions**: Write to memory
   - Record: thread ID, variable address, new value, timestamp
   - Add to trace buffer
3. **Synchronization Operations**: Barriers, atomics, locks
   - Record: type and location
   - Used to establish happens-before relationships

**Instrumentation Example**:
```llvm
// Original: store i32 10, i32* %ptr
// Instrumented:
call void @record_write(i32* %ptr, i32 10, i64 %thread_id, i64 %timestamp)
store i32 10, i32* %ptr
```

### Phase 2: Offline Trace Analysis
**Input**: Trace files from instrumented execution
- Contains all loads, stores, synchronization events
- Each event: address, value, thread, timestamp

**Analysis**:
1. Build dependency graph (happens-before from synchronizations)
2. For each pair of accesses to same address:
   - Check if they race (one is write, and no sync between)
   - If race found, report details
3. Generate race report (thread 1 access → thread 2 access)

**Race Detection Logic**:
```
For each address A:
  Get all accesses to A (loads and stores)
  For each pair (access1, access2):
    If one is write AND both not synchronized:
      Report race
```

### Unified Approach: Both CPU and GPU
**Key Innovation**: Single instrumentation framework handles both:
- CPU code: Standard LLVM instrumentation
- GPU code (HIP kernels): GPU-specific LLVM IR instrumentation
- Trace format: Unified (both device types write same format)

**Benefit**: Catches races between CPU and GPU (first time!)

## Scientific Significance

### The Correctness Problem
Data races in concurrent systems:
- **Behavior**: Non-deterministic (same input → different output)
- **Debugging**: Extremely difficult (Heisenbug - disappears when observed)
- **Scale**: Worse with more cores
- **Consequences**: Wrong scientific results (undetected)

Heterogeneous systems amplify this:
- More parallelism (more races possible)
- Harder to reason about (CPU+GPU model)
- Existing tools incomplete

### Why UHM Makes Races Likely
UHM simplifies programming, but enables subtle races:

**Example: Stencil Computation**
```c
// CPU initialization
for(int i = 0; i < N; i++)
    data[i] = initial_value;

// GPU kernel (runs asynchronously)
__global__ void stencil_kernel() {
    int i = blockIdx.x;
    data[i] = data[i-1] + data[i] + data[i+1];  // RACE with CPU!
}

stencil_kernel<<<blocks, threads>>>();
// CPU might still be writing while GPU reads!
```

The bug: Programmer forgot synchronization between CPU init and GPU kernel.

### Why Existing Tools Fail
- **TSan (ThreadSanitizer)**: CPU-only, doesn't see GPU accesses
- **GPU-specific Tools**: GPU-only, don't see CPU accesses
- **Manual Inspection**: Infeasible for large codebases

Scabbard bridges this gap.

## Implementation Challenges (Documented by Authors)
The authors position this as learning experience for future tool developers:

### 1. LLVM Compilation Pipeline
Challenge: Injecting passes in right place
- GPU code (HIP) compiled via separate pipeline
- Must add passes to both CPU and GPU LLVM IR paths
- Timing of injection critical (can't be too early/late)

### 2. Trace Format Design
Challenge: Single format for CPU and GPU events
- CPU events: Load, store from CPU thread
- GPU events: Load, store from GPU warp
- Need unified trace format for offline analysis
- Must handle different granularities (warp vs thread)

### 3. Performance: Avoiding Explosion
Challenge: Instrumentation explosion at scale
- Large GPU kernels can have 1B+ memory operations
- Tracing everything → gigabyte+ trace files
- Need sampling or buffering strategies
- Solution: Circular buffers, trace ring (keep recent events)

### 4. AMD ROCm Ecosystem
Challenge: Immature tooling infrastructure (vs NVIDIA/CUDA)
- Fewer examples of tool integration
- Less documentation for pass developers
- Community smaller (more difficulty getting help)
- Authors document workarounds learned

## Design Insights

### Why LLVM Is Right Choice
1. **Uniformity**: CPU and GPU both compile through LLVM IR
   - Shared IR representation
   - Same instrumentation framework
2. **Compiler Integration**: Part of normal build pipeline
   - Not post-hoc binary instrumentation
   - Better coverage and accuracy
3. **Platform Support**: Multiple GPUs via single framework

### Why Offline Analysis
**Online Analysis** (analyze during execution):
- Pro: Immediate feedback
- Con: 10-100x overhead (unacceptable)

**Offline Analysis** (analyze trace after):
- Pro: Low runtime overhead
- Con: Large trace files, post-processing time
- Trade-off: Better for scientific computing
