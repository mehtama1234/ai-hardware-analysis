# hpca-2025-091 — Reviving In-Storage Hardware Compression on ZNS SSDs through Host-SSD Collaboration

**Venue:** HPCA  
**Confidence:** low (abstract-only)

## Problem
Zoned Namespace (ZNS) SSDs cannot benefit from traditional host-transparent in-storage hardware compression because the ZNS interface's sequential write constraint makes it impossible to locate variable-length compressed chunks and reclaim the space freed by compression without exposing this information to the host.

## Motivation
ZNS SSDs are increasingly deployed in large-scale cloud storage for their performance and cost advantages, and enabling hardware compression on them would further improve storage density and cost-effectiveness, but the host-transparent approach fails on ZNS due to fundamental interface mismatches.

## Method
CCZNS splits the compression work between the SSD and host: the SSD hardware performs compression, then shares metadata about the compressed chunks (boundaries and offsets) with the host instead of hiding them. The host software (such as RocksDB with ZenFS) uses this information to track data locations and reclaim space freed by compression—responsibilities it already handles. This works around ZNS's sequential write constraint by letting the host work with variable-length chunks instead of having the SSD hide them.

## Key Novelty
CCZNS revives hardware compression on ZNS SSDs by separating compression (done by the SSD) from index management (done by the host) through a shared interface that exposes compression metadata.

## Contributions
- First analysis identifying why host-transparent compression fails on ZNS SSDs due to chunk location and space reclamation challenges
- CCZNS: a new host-SSD collaborative interface that decouples compression execution from address indexing
- Case study demonstrating CCZNS integration with RocksDB and ZenFS
- Experimental validation showing significant performance improvements over existing compression system solutions
