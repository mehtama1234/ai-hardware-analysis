# SC-2025-251: Portable BFS on Heterogeneous GPUs

**Unified SYCL Implementation Across NVIDIA, AMD, and Intel**

## Summary
This work presents efficient BFS implementations for heterogeneous GPU environments, demonstrating three load-balancing strategies that enable a single unified SYCL codebase to achieve competitive performance across NVIDIA A100, AMD MI300X, and Intel Max 1550 GPUs.

## Problem
Graph processing algorithms like BFS are critical for diverse applications (social networks, molecular dynamics, optimization). However:
1. **Load Balancing Challenge**: Sparse graphs create irregular workloads; some threads do much work, others little
2. **GPU-Specific Optimization**: NVIDIA, AMD, Intel GPUs have different characteristics (memory, execution model, cache)
3. **Portability vs Performance**: CUDA is efficient but NVIDIA-only; portable languages (OpenMP, HIP) often leave performance on table
4. **Multiple Codebases Required**: Typically need separate optimized implementations for each vendor
5. **Memory Access Patterns**: Poor locality on sparse graphs; L2 cache misses dominate

## Approach
### Load-Balancing Strategies
Three complementary techniques:

#### 1. Work-Group Localisation
**Goal**: Exploit spatial locality in graph structure
**Method**:
- Partition vertices into work-groups
- Threads within work-group cooperatively process local subgraph
- Use local/shared memory for frequently accessed neighbor lists
- Reduce global memory bandwidth

**Benefit**: Better cache behavior, reduced L2 misses

#### 2. Even Workload Distribution
**Goal**: Higher GPU occupancy through balanced load
**Method**:
- Analyze degree distribution of input graph
- Partition vertices to balance work (not just count)
- High-degree vertices distributed across thread blocks
- Prevent thread divergence and warp stalls

**Benefit**: Reduced tail latency, better occupancy

#### 3. Hybrid Strided-Access
**Goal**: Heuristic balancing combining multiple strategies
**Method**:
- Use strided memory access patterns where beneficial
- Adapt strategy to graph characteristics (density, regularity)
- Hybrid approach (switches strategies per phase)

**Benefit**: Adaptability to diverse graph structures

### Unified Codebase: SYCL
**Language**: Intel DPC++ (Data Parallel C++) - SYCL variant
**Advantages**:
- Single source code compiles to multiple backends (OpenCL, DPC++, Level Zero, Vulkan)
- Enables code reuse across GPU vendors
- Performance-portable (optimization portable, not just correctness)
- No #ifdefs or conditionals needed

**Compilation**:
- NVIDIA A100: Via SYCL-to-CUDA translation
- AMD MI300X: Direct SYCL support via oneAPI
- Intel Max 1550: Native support

## Key Contributions
1. **Novel Load-Balancing Strategies**: Three complementary techniques specifically for sparse graph processing
2. **Unified SYCL Implementation**: Single codebase for three GPU vendors
   - First to demonstrate competitive performance across all three
   - Reduces maintenance burden (one version, not three)
3. **Strong Performance Results**:
   - Peak: 153.27 billion graph traversals per second (GTEPS)
   - 8 NVIDIA A100 GPUs processing RMAT25-64 graph
   - Outperforms previous single-GPU CUDA implementations
4. **Scalability Validation**: Successfully handles very large graphs (RMAT scale 29 = 2^29 vertices ≈ 500M vertices)
5. **Real-World Validation**: Not just synthetic RMAT graphs; competitive on actual datasets

**GTEPS** = Billion Graph Traversals Per Second = 10^9 edges traversed per second
- Standard metric for graph algorithm benchmarking
- Higher is better

## Performance Portability Perspective
### The Portability Challenge
Traditional GPU programming:
- **CUDA** (NVIDIA): 
  - Highest performance
  - Most mature ecosystem
  - NVIDIA-only
- **HIP** (AMD):
  - Aimed at portability (translate CUDA to AMD)
  - Performance often lags CUDA
- **OpenMP** offload:
  - Standard, portable
  - Performance gaps vs vendor-specific
- **SYCL**:
  - Newest approach
  - Originally Intel-focused
  - Growing vendor support

- Competitive with CUDA on NVIDIA
- Native on AMD and Intel
- Single codebase

## Load Balancing Insights

### Why BFS is Hard on GPUs
Regular algorithms (matrix multiply, convolutions) have:
- Predictable workload distribution
- Cache-friendly access patterns
- High GPU occupancy

Sparse algorithms (BFS, sparse matrix-vector multiply) have:
- Irregular workload: high-degree vertices get all threads, low-degree vertices few
- Poor spatial locality: neighbors scattered in memory
- Warp divergence: some warps do real work, others diverge waiting
- Control flow divergence: some paths longer than others

### Load Balancing Solutions
1. **Degree-based partitioning**: Spread high-degree vertices → less divergence
2. **Work-group locality**: Exploit graph substructure (clusters, communities)
3. **Adaptive strategies**: Detect graph properties, switch algorithms

This work combines all three.

## Scalability Analysis

### 8-GPU Scaling
**Achieved**: 153.27 GTEPS
**If perfect scaling**: 8 × 19 = 152 GTEPS (almost matches!)
**Analysis**:
- Excellent scaling efficiency
- Multi-GPU communication overhead minimal (for BFS breadth-wise phase)
- GPU-GPU data transfer not dominant bottleneck

### RMAT Graph Scaling
Tested up to scale 29 (500M vertices):
- Demonstrates memory scalability
- Multi-GPU memory aggregation (8 × 40GB = 320GB possible)
- Important for real applications (social networks easily reach 1B+ nodes)

## Limitations
- **GPU Performance Breakdown**: Abstract emphasizes A100 results; MI300X and Max 1550 performance not detailed
  - How does work-group localisation work on different memory hierarchies?
  - Are speedups equal across vendors?
- **Real-World Dataset Analysis**: Limited detail on actual graph datasets
  - Natural graphs have different properties than RMAT
  - Clustering, degree distribution, community structure differ
- **Single Algorithm**: Only BFS evaluated
  - Generalization to other sparse algorithms (DFS, triangle counting) unclear
  - Load balancing principles may differ

## Broader Implications

### GPU Market Fragmentation
Industry increasingly sees three GPUs:
- NVIDIA A100/H100 (dominant, high cost)
- AMD MI300X (entering market, cost-competitive)
- Intel Max 1550 (emerging, niche adoption)

Single codebase supporting all three is strategic:
- Reduces vendor lock-in
- Enables price competition shopping
- Facilitates migration strategies

### Performance Portability Movement
This work exemplifies emerging approach:
- **Traditional**: Optimize for one target, pray others fast enough
- **Modern**: Design algorithms for portability, validate across targets
- **SYCL's role**: Enables modern approach at systems level

### Open Challenges
This work leaves open:
1. **Can load balancing strategies generalize?** (Other sparse algorithms)
2. **Is SYCL performance viable everywhere?** (Compiler maturity, optimization)
3. **Multi-GPU scaling bottlenecks?** (Network overhead at larger scales)
