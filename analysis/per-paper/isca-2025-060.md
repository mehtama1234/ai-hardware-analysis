# isca-2025-060 — Garibaldi: A Pairwise Instruction-Data Management for Enhancing Shared Last-Level Cache Performance in Server Workloads

**Venue:** ISCA  
**Confidence:** high (full text)

## Problem
Server workloads suffer from an "instruction victim" problem in the shared LLC: cold instruction cachelines are evicted by competing hot data cachelines, yet each instruction miss stalls the CPU frontend regardless of how much hot data is already resident in the LLC. Existing LLC management policies (Mockingjay, Hawkeye, DRRIP) optimize for data reuse distance and ignore the cost asymmetry between instruction and data misses.

## Motivation
Server workloads exhibit a many-to-few access pattern (many cold instruction lines each accessing a few hot data lines), which means that existing data-hotness-driven eviction policies systematically sacrifice instructions whose miss cost is highest, causing frontend stall cycles to dominate multi-core server CPI.

## Method
Garibaldi maintains a lookup table (16K entries, 194 KB) where each instruction address maps to the hotness of its associated data using a counter that maxes out at 63. At eviction time, it queries this table and protects instructions paired with hot data instead of following the standard eviction policy. When an instruction miss occurs, the system prefetches the related cold data. Every 100K accesses, it measures how often data misses follow instruction misses and adjusts the protection threshold.

## Key Novelty
Garibaldi is the first to measure the cost of instruction misses by the hotness of the data they trigger, using this connection to decide which instructions to protect and which data to prefetch.

## Contributions
1. Identification and analysis of the instruction victim problem in shared LLCs for server workloads, showing 95–99% instruction miss rates in the LLC even with advanced prefetching.
2. The Garibaldi pairwise instruction-data management scheme with selective instruction protection and pairwise data prefetch, adding only 194 KB overhead (0.6% of LLC capacity) for a 40-core system.
3. A dynamic threshold mechanism using coloring-based aging to adapt protection aggressiveness to workload characteristics without manual tuning.
4. Evaluation on 16 server workloads showing 13.2% geomean CPU speedup over LRU (6.1% over Mockingjay alone) with 10.4% energy reduction.

## Metrics
- **Speedup:** 13.2% geomean over LRU (6.1% over Mockingjay); up to 65.2% on verilator
- **Energy:** 10.4% reduction vs LRU; 5.0% below Mockingjay alone
- **Area:** 193.9 KB total storage for 40 cores (0.6% of 30 MB LLC)
- **Other:** 18% reduction in ifetch stall cycles

## Baselines
LRU, DRRIP, Hawkeye, Mockingjay

## Limitations
Garibaldi can slightly hurt performance in workloads where both instructions and data are cold (e.g., kafka), and its pair table requires 16K entries because instruction-data pairs do not share LLC sets, making set-sampling-based approaches inapplicable.
