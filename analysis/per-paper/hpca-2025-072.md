# AutoRFM: Scaling Low-Cost in-DRAM Trackers to Ultra-Low Rowhammer Thresholds

**Venue:** HPCA  
**Confidence:** low (abstract-only)

## Problem
In-DRAM Rowhammer mitigation using the DDR5 Refresh Management (RFM) command stalls the entire DRAM bank for 200-400ns per invocation; at ultra-low Rowhammer thresholds (sub-100), the required RFM frequency causes up to 33% performance slowdown with existing low-cost trackers such as MINT.

## Motivation
DRAM Rowhammer thresholds are decreasing with technology scaling, requiring more frequent mitigations, but the bank-stalling nature of RFM makes it prohibitively expensive at ultra-low thresholds.

## Method
AutoRFM prevents Rowhammer attacks by using DDR5's Refresh Management command to refresh one small memory section (a subarray) at a time, allowing other sections to continue handling requests. When a request arrives for the subarray being refreshed, the memory chip signals the processor to retry after about 200 nanoseconds. Randomized Memory Mapping prevents repeated targeting of the same subarray by shuffling which addresses map to which locations, and a Fractal Mitigation Algorithm handles sophisticated multi-step attacks like Half-Double without repeatedly refreshing the same subarray. Testing used SPEC, GAP, and stream workloads.

## Key Novelty
AutoRFM mitigates Rowhammer memory attacks by refreshing one small section (subarray) at a time, keeping all other sections active instead of stalling the entire memory bank.

## Contributions
- AutoRFM subarray-level transparent RFM mechanism avoiding bank-wide stalls during Rowhammer mitigation
- Randomized Memory Mapping to prevent repeated targeting of the same subarray
- Fractal Mitigation Algorithm for transitive (Half-Double) Rowhammer attacks
- Enables thresholds as low as 74 with average 3.1% slowdown vs 33% slowdown for bank-level RFM at threshold 100
