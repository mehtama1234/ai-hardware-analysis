# hpca-2025-095 — QPRAC: Towards Secure and Practical PRAC-based Rowhammer Mitigation using Priority Queues

**Venue:** HPCA  
**Confidence:** low (abstract-only)

## Problem
The JEDEC PRAC (Per Row Activation Counting) framework for DDR5 enables RowHammer mitigation via Alert Back-Off (ABO) signaling, but existing PRAC implementations (e.g., Panopticon) are either insecure when instantiated per JEDEC specification, or impractical (e.g., UPRAC) due to requiring oracle knowledge of the top-N most-activated rows.

## Motivation
DRAM RowHammer thresholds are shrinking with each technology generation, making scalable, secure, and low-overhead mitigations for future DDR5 and beyond chips critical for system security.

## Method
QPRAC builds a Priority-based Service Queue (PSQ—a queue ordering pending mitigation requests by row activation count, with most-accessed rows handled first) in the memory controller. It uses PRAC's per-row counters to prioritize which rows get protected, serving the most-activated rows immediately to prevent attackers from exploiting less-protected rows. To minimize performance impact, the design uses two tactics: it adds extra protections to Refresh Management (RFM—regular memory refresh cycles) at minimal cost, and it proactively drains the queue during standard DRAM refresh (REF) operations before emergency slowdowns (Alert Back-Off, or ABO) trigger.

## Key Novelty
A priority-based service queue (PSQ) that orders RowHammer mitigations by row activation count (how many times each row is accessed) within the PRAC/ABO framework, providing principled security while opportunistic and proactive refresh coordination reduces ABO-induced slowdowns to nearly zero.

## Contributions
- Security analysis showing Panopticon is insecure under JEDEC PRAC specification and UPRAC is impractical
- Priority-based Service Queue (PSQ) design for secure, scalable RowHammer mitigation via PRAC/ABO
- Co-design with opportunistic RFM mitigations and proactive REF-based mitigations to minimize performance overhead
- Secure mitigation scaling to RowHammer threshold as low as 71 with only 0.8% (0% with proactive) benign workload slowdown
