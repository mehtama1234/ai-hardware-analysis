# SC-2025-245: Scalable Hydrodynamics on Multiple FPGAs

**Energy-Efficient Alternative to GPU Acceleration for Stencil Computations**

## Summary
This paper demonstrates the viability of FPGAs for large-scale scientific computing by implementing scalable 2D and 3D hydrodynamics solvers on Intel Agilex 7 FPGAs. The work shows that despite lower throughput than GPUs, FPGAs achieve comparable energy efficiency while enabling customization for specific algorithms.

## Problem
Porting stencil-based hydrodynamic simulations from traditional CPU/GPU architectures to FPGAs poses several challenges:
1. **Algorithm Translation**: Stencil patterns must be adapted to FPGA's spatial compute model
2. **Memory Constraints**: FPGAs have limited on-chip memory compared to GPUs
3. **Throughput Trade-offs**: FPGA throughput is significantly lower than modern GPUs
4. **Scalability Questions**: Multi-FPGA systems have been less explored for HPC kernels
5. **Energy-Performance Trade-off**: Clear need to demonstrate FPGA viability for exascale

## Approach
### Architecture and Implementation
- **Platform**: Intel Agilex 7 FPGA cards with Intel oneAPI framework
- **Applications**: 2D and 3D hydrodynamics solvers
- **Scaling**: Demonstrated on single and dual FPGA systems

### Key Optimizations
1. **Memory-Centric Design**:
   - Exploit FPGA's large on-chip cache (compared to GPU shared memory size)
   - Minimize data streaming through careful data locality
   - Reuse data to reduce bandwidth requirements

2. **Domain Decomposition**:
   - Partition spatial domain across multiple FPGAs
   - Enable pipeline duplication within each FPGA
   - Reduce per-FPGA workload, increasing parallelism

3. **Computational Mapping**:
   - Custom hardware pipeline for stencil operations
   - Exploit spatial parallelism inherent in FPGA architecture
   - Minimize control flow overhead

## Key Contributions
1. **First Multi-FPGA Hydrodynamics Study**: Demonstrates FPGA scalability for scientific computing
2. **Memory Optimization Strategy**: Shows how FPGA's unique memory hierarchy can be advantaged
3. **Domain Decomposition for FPGAs**: Practical techniques for distributing stencil computations across cards
4. **Energy Efficiency Demonstration**: Comparable energy per flop to NVIDIA A100 despite throughput gap
5. **Heterogeneous System Insights**: Guidance for including FPGAs in next-generation HPC architectures

## Scientific Significance
### Energy Perspective
For exascale computing, energy consumption becomes a first-order constraint. If FPGAs can deliver equivalent energy efficiency to GPUs while enabling fine-grained customization, they become attractive for:
- Long-running scientific simulations where throughput is less critical
- Power-constrained deployments
- Domain-specific accelerators within heterogeneous systems

### Algorithm-Hardware Co-design
FPGAs enable customization not possible with fixed GPU architectures:
- Algorithm-specific memory hierarchies
- Custom dataflow patterns
- Reduced precision arithmetic (if applicable)
- Fine-grained parallelism exploited differently than GPU thread model

## Design Insights
1. **On-chip Memory is Precious**: FPGA design must aggressively exploit spatial locality
2. **Throughput vs Energy**: Lower throughput doesn't disqualify FPGAs if energy target matters
3. **Scalability Requires Careful Decomposition**: Domain decomposition critical for multi-FPGA (unlike multi-GPU where NCCL handles communication)
4. **Framework Matters**: Intel oneAPI abstracts FPGA complexity but specialized kernels may need HDL

## Broader Implications
This work challenges the GPU-dominance narrative in HPC by:
1. Showing FPGAs remain competitive on energy metrics
2. Demonstrating multi-FPGA scalability (previously uncertain)
3. Providing practical porting strategies for scientific codes
4. Opening FPGA as viable choice for exascale site planners

However, throughput gap vs GPUs means FPGAs suit:
- **Batch-oriented** simulations where latency doesn't matter
- **Energy-constrained** installations (data centers, edge)
- **Custom algorithms** where GPU template doesn't fit
