# SC-2025-253: Coupled Static-Dynamic MPI Correctness Tools

**Synergistic Accuracy and Performance Through Tool Integration**

## Summary
This work presents a coupled workflow combining static and dynamic MPI correctness tools. By forwarding static tool reports to dynamic tools and using selective instrumentation, the approach eliminates false positives, extends coverage to previously missed errors, and reduces runtime overhead by up to 10x.

## Problem
MPI (Message Passing Interface) programs are notoriously difficult to debug:
1. **Static Tools Limitations**:
   - Over-approximate (assume worst-case)
   - Produce false positives
   - Lack runtime context (value of variables)
   - Example: Assume `MPI_Send` might deadlock if no matching `MPI_Recv`

2. **Dynamic Tools Limitations**:
   - Under-approximate (only see executed paths)
   - Produce false negatives (miss errors in untaken branches)
   - High overhead (instrumentation costs 2-10x slowdown)
   - Can't afford to instrument everything
   - Example: Race detector only catches races in specific test runs

3. **Independence Problem**:
   - Tools run separately
   - No communication between them
   - Miss opportunity for synergy
   - Example: Static tool could guide dynamic tool where to look

## Approach
### Coupled Workflow Architecture
**Pipeline**:
1. **Static Analysis Phase**: Run static tools (CoVer, SPMD IR) on source code
2. **Exchange Format**: Static tools output findings in standard format
3. **Dynamic Tool Guidance**: Dynamic tool (MUST) reads static hints
4. **Selective Instrumentation**: Only instrument code flagged by static tool
5. **Dynamic Verification**: Dynamic tool confirms/refutes static findings
6. **Report Generation**: Combined results eliminate false positives, extend coverage

### Design Philosophy
**Key Insight**: Static and dynamic tools have complementary errors:
- **Static**: "This might be a race (but maybe not)"
- **Dynamic**: "I didn't see a race (but maybe it's in another code path)"
- **Combined**: "Static says it might happen; dynamic confirms if it does; otherwise it's a false positive"

### Generic Exchange Format
**Purpose**: Enable interoperability between static and dynamic tools
**Information Conveyed**:
- Location of potential errors (file, line)
- Error type/classification
- Context information
- Severity/confidence

**Benefit**: Tools from different vendors can interoperate (not locked to single tool)

### Selective Instrumentation
**Traditional Dynamic Tool**:
- Instrument entire program
- Catch all races
- But overhead 2-10x

**With Static Guidance**:
- Static tool flags ~1000 potential races
- Instrument only those ~1000 locations
- Miss anything outside those locations (acceptable tradeoff)
- Overhead now ~0.2x (10x reduction!)

## Key Contributions
1. **Coupled Workflow Design**: First framework for static-dynamic tool cooperation
2. **Generic Exchange Format**: Enables cross-tool interoperability
   - Not locked to specific tool pairs
   - Future tools can use same format
   - Standardization potential

3. **Proof of Concept**: Integration of three tools
   - CoVer (static analysis tool)
   - SPMD IR (static intermediate representation)
   - MUST (dynamic MPI correctness tool)
   - Focus: Detecting MPI local data races

4. **Results on Data Races**:
   - **False Positive Elimination**: Static tool findings verified by dynamic tool
     - Example: Static tool warns of race at line 42
     - Dynamic tool confirms: not reachable in practice (false positive)
   - **Coverage Extension**: Dynamic tool finds races missed by static alone
     - Example: Static tool misses race in complex pointer arithmetic
     - Dynamic tool catches it during execution
   - **Overhead Reduction**: Up to 10x (full vs selective instrumentation)

## Scientific Significance

### MPI Debugging Challenge
MPI programs notoriously hard to debug:
- Non-determinism (order of messages varies)
- Distributed state (hard to observe global state)
- Timing dependencies (race conditions)

Tools help, but each tool class has gaps.

### Data Race Focus
Local data races in MPI:
- **One-sided Operations (RMA)**:
  - Asynchronous access to remote memory
  - Easy to accidentally create races
  - Hard to detect (unlike message-passing, no synchronization points)
- **Shared Memory Regions**:
  - MPI-3 shared memory windows
  - Multiple ranks accessing same data
  - Race conditions if not carefully synchronized

Example:
```c
// rank 0                          // rank 1
MPI_Put(data, ...)                 data[0]++;  // RACE!
```

### Why This Problem Matters
Parallel debugging is bottleneck in HPC:
- Most time spent debugging, not coding
- Hard bugs take weeks to track down
- Unreproducibility common (Heisenbug)
- Better tools = faster science

## Design Insights

### Why Coupling Works
**Complementary Strengths**:
- Static: "Look at all possible paths"
- Dynamic: "Only path actually taken"
- Combined: "Show me paths static cares about"

**Overhead Trade-off**:
- Static: Cheap (offline) but over-approximate
- Dynamic: Expensive (runtime) but precise
- Combined: Cheap static phase guides expensive dynamic phase
- Result: Precision without full overhead

### Exchange Format Value
Historically, tools were monolithic:
- Static tool only works with static analyses
- Dynamic tool only with dynamic analyses
- No interoperability

Generic format enables:
- Mix-and-match tool combinations
- Vendor independence
- Standard adoption (LLVM, compiler infrastructure)

## Experimental Design

### Test Case: MPI Data Races
**Methodology**:
1. Take MPI programs (research codes, benchmarks)
2. Run static tools (CoVer, SPMD IR) → list potential races
3. Run dynamic tool (MUST) alone → detects subset of races
4. Run dynamic tool with static guidance → detects more races
5. Compare results

**Expected Outcomes**:
- Static tool has false positives (dynamic refutes)
- Dynamic tool has false negatives (static uncovers)
- Combined approach best of both

## Limitations
- **Single Bug Class**: Only data races studied
  - Deadlocks, type mismatches, other MPI errors not addressed
  - Generalization to other error types unclear
  - Coupled approach may work differently for deadlocks (less addressable by static)
- **Limited Tool Set**: Only three tools evaluated
  - Many other MPI correctness tools exist
  - Format proven on limited set
- **Exchange Format**: Details not provided in abstract
  - How expressive is format?
  - Can it represent all static findings?
  - Extensibility for new error types?
- **Scalability**: Not addressed
  - How many static warnings before dynamic tool overwhelmed?
  - Selectivity threshold unclear

This work suggests future direction:

Analogy: Unix philosophy (small tools, pipes, composition) vs monolithic Windows tools.

### Standardization

- **CII Foundation**: Could standardize format

### Practical Impact for Developers
Coupled approach benefits MPI developers:
1. Better bug detection (extends coverage)
2. Fewer false alarms (eliminates false positives)
3. Reasonable overhead (still usable on real code)
4. Flexible tool choice (not locked to specific tools)

## Design Considerations

### Why Not Just Use Dynamic Tools?
**Answer**: Overhead
- Full dynamic instrumentation 2-10x slowdown
- Scientific simulations cannot afford this cost
- Selective instrumentation based on static hints solves it

### Why Not Just Use Static Tools?
**Answer**: False positives
- Static over-approximation leads to many false alarms
- Developer must manually verify each one
- Dynamic tool eliminates false positives automatically
