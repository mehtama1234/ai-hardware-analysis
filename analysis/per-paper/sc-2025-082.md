# Weak Scaling of NVSHMEM Applied To Hashed Distributed Structured Data

**Venue:** SC 2025  
**Authors:** Davis, Johansen, Gao, Guzik

## Problem
Block-structured applications on GPUs often have sparse, irregular data distributions. Traditional MPI ghost-zone communication requires:
- Buffer packing/unpacking overhead
- CPU-centric synchronization points
- Complex neighbor indexing logic

This creates latency and scalability bottlenecks on GPU clusters.

## Approach
**HashBrick Library:**
1. **Brick-based data layout** – Aggregate sparse data into small regular bricks
2. **Hash-based neighbor indexing** – O(1) lookup of ghost brick locations without global index
3. **NVSHMEM one-sided communication** – GPU-GPU direct access to ghost bricks over NVLink
4. **No buffer packing** – Direct brick access eliminates serialization overhead

## Weak Scaling Results

### Performance Gain
| Communication Method | Wall-Clock Time |
|----------------------|-----------------|
| NVSHMEM (one-sided) | Baseline |
| MPI (two-sided) | 64-84% higher |

### Scaling Behavior
- **Computation time:** Constant (as intended in weak scaling)
- **Communication:** Scales well despite load imbalance
- **Efficiency correlation:** Ghost brick distribution variance correlates with scaling efficiency

## Hardware Target
- **NVIDIA GH200 cluster**
  - Grace CPU + Hopper GPU nodes
  - NVLink for intra-node communication
  - High-speed fabric for inter-node (Quantum2 InfiniBand implied)

## Benchmark Applications
1. **High-order CFD** – Real application
2. **Jacobi iteration** – Synthetic benchmark (worst-case stencil communication)

## Technical Insights

### Why NVSHMEM Wins
- **GPU-initiated communication** – No CPU round-trip latency
- **One-sided semantics** – Sender doesn't wait for receiver synchronization
- **Direct memory access** – Hashing enables direct targeting without coordination
- **Asynchronous progress** – NVLink copy engine overlaps computation

### Hash-based Indexing Design
```
Brick location = hash(brick_id) → direct address lookup
No global coordinate mapping required
Enables flexible, irregular distributions
O(1) lookup latency
```

## Limitations
- **GH200-specific** – Results may not generalize to other GPU clusters
- **Limited benchmarks** – Only two applications tested
- **Load imbalance partially characterized** – Variance correlates with efficiency but no load-balancing solution proposed
- **Weak scaling only** – No strong scaling analysis (important for latency-sensitive codes)
- **Two-node comparison** – Only MPI vs. NVSHMEM; no comparison with hybrid approaches

## Related Concepts
- One-sided communication (RMA, NVSHMEM)
- Sparse structured grids
- CFD on accelerators
- GPU-resident communication
- Hash-based data structures for HPC

## Significance
Demonstrates **substantial benefit of GPU-initiated, one-sided communication** for irregular applications, challenging traditional MPI + GPU model where CPU coordinates GPU communication.
