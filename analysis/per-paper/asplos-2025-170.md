# PUSHtap: PIM-based In-Memory HTAP with Unified Data Storage Format

**Venue:** ASPLOS  
**Confidence:** high (full text)

## Problem
HTAP systems cannot simultaneously achieve workload-specific optimization, performance isolation, and data freshness because OLTP demands row-store format while OLAP demands column-store format. Existing approaches (single format, multi-instance with rebuilding, or mixed delta-store) compromise at least one of these three goals.

## Motivation
PIM DRAM devices create a new access orthogonality—CPU interleaved access across devices (ADE, row-dimension) versus localized PIM access inside devices (IDE, column-dimension)—that can serve both OLTP and OLAP simultaneously in a single data instance without format replication or rebuilding.

## Method
PUSHtap maps HTAP rows to the CPU's interleaved ADE dimension and columns to the PIM's localized IDE dimension in a single-instance DRAM store. A compact aligned format uses a bin-packing algorithm with tunable threshold th to group similarly-sized columns into parts, minimizing zero-padding while preserving alignment for both CPU and PIM (achieving 97.4% PIM bandwidth at th=0.6 on CH-benchmark). Block-circulant placement rotates column-to-device mapping every 1024-row block, distributing each column evenly across all PIM units to eliminate hotspots and maximize parallelism. MVCC uses a data region and delta region; snapshots are encoded as per-device bitmaps written in parallel by CPU, and defragmentation is PIM-offloaded when row width exceeds a computed threshold (w > (BW_PIM + BW_CPU) / (2p * (BW_PIM - BW_CPU) * m)). A modified UPMEM-like memory controller adds a scheduler and polling module enabling fine-grained concurrent CPU/PIM access via a two-phase load/compute OLAP execution model that limits CPU blocking to 300 microseconds per load phase.

## Key Novelty
Exploiting the orthogonality of CPU interleaved (ADE) and PIM localized (IDE) access to implement a single unified data format that simultaneously serves OLTP and OLAP without format duplication or rebuilding.

## Contributions
- Unified HTAP data storage format: compact aligned format (bin-packing with threshold th) + block-circulant placement for co-optimized CPU and PIM bandwidth
- MVCC with bitmap-encoded snapshots (2.3% storage overhead) and PIM-accelerated defragmentation
- Memory controller extensions (scheduler + polling module) enabling fine-grained concurrent CPU/PIM access with two-phase OLAP execution
- 3.4x OLAP / 4.4x OLTP throughput improvement vs. multi-instance PIM-based HTAP on CH-benchmark (TPC-C + TPC-H)

## Metrics
- Speedup: 3.4x OLAP, 4.4x OLTP throughput vs. multi-instance PIM-based HTAP (MI); PUSHtap (HBM) 1.4x additional OLAP speedup at 8M transactions
- Other: PIM effective bandwidth 97.4% at th=0.6; snapshot bitmap overhead 2.3% storage; zero-padding 0.8%; memory controller synthesized at TSMC 90nm 2.4GHz

## Baselines
Multi-instance PIM-based HTAP (Polynesia-style, MI), row-store single format, column-store single format, ideal (zero MVCC overhead)

## Limitations
Block-circulant placement and key-column classification assume a relatively stable OLAP query workload; highly dynamic query patterns requiring frequent threshold adjustment are not fully addressed.
