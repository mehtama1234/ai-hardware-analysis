# RL4Sys: A Lightweight System-driven RL Framework for Drop-in Integration in System Optimization

**Venue:** SC 2025  
**Authors:** Dong, Rashid, Xu, Dai

## Problem
**RL for Systems Optimization:**
Reinforcement learning has succeeded in complex domains (games, robotics, autonomous driving), prompting exploration of RL for system optimization:
- Adaptive caching policies
- Dynamic scheduling algorithms
- Network routing optimization
- Energy-aware resource allocation

**Integration Barriers:**
- Existing frameworks (RLlib, Ray) designed for ML workloads, not systems
- Embedding RL in system software introduces:
  - Complex API integration
  - Significant runtime overhead (10-50%+)
  - Training latency interfering with system responsiveness
  - Unfamiliar abstractions to systems researchers

**Result:** RL rarely adopted in production systems despite theoretical promise.

## Approach
**RL4Sys: System-Focused RL Architecture**

### Design Principle
Minimize integration overhead by separating concerns:

### Client (Embedded in System)
- **Minimal instrumentation** – Record state-action-reward trajectories
- **Local policy inference** – Run cached policy (no server roundtrip latency)
- **Lightweight** – <6% runtime overhead

### Training Servers (Decoupled, Asynchronous)
- Execute RL training algorithms (PPO, DQN, etc.)
- Update policies asynchronously
- No blocking on original system

### Communication
- **Zero-copy gRPC** – Efficient trajectory/policy transfer
- **Adaptive batching** – Group trajectory updates to amortize communication

## Architecture Comparison

### Traditional (RLlib)
```
System → RLlib environment wrapper → ML framework → training
└─ Tight coupling, high overhead, blocking updates
```

### RL4Sys
```
System (policy inference) ←→ Server (async training)
       ↓
  Trajectory cache
       ↑
  gRPC zero-copy batching
└─ Loose coupling, minimal overhead, non-blocking
```

## Performance Results

### Overhead
| Metric | Value |
|--------|-------|
| Runtime overhead | <6% |
| Convergence | Matches RLlib |

### Throughput Comparison
- **220% higher throughput vs. RLlib** (environment-oriented settings)
- Interpretation: RL4Sys processes 3.2x as many environment steps per second
- "Environment-oriented" likely means: RL4Sys optimized for systems (many fast decisions), RLlib optimized for ML (fewer complex decisions)

## Technical Innovations

### Minimal Client Design
```python
# RL4Sys integration:
state = get_system_state()
action = policy_inference(state, cached_policy)
apply_action(action)
record_trajectory(state, action, reward)
```
No library initialization, no complex setup.

### Zero-Copy Communication
Trajectory format allows shared memory:
- Client writes trajectories to memory-mapped buffer
- Server reads without copying
- Reduces network overhead

### Adaptive Batching
- Accumulate trajectories locally
- Batch to server when threshold reached (or timeout)
- Reduces gRPC call overhead
- Adapts to system state (fewer calls when busy)

### Cached Policy Inference
- Policy stored locally on client
- Inference runs immediately (no server latency)
- Server updates policy asynchronously in background
- System sees benefits immediately from new policies

## Evaluation

### Convergence
- RL4Sys matches conventional frameworks
- Suggests algorithmic correctness despite lightweight design

### Throughput
- 220% improvement in environment-oriented settings
- Likely explains by:
  - Reduced communication overhead (zero-copy, batching)
  - Local inference (no server latency)
  - Asynchronous training (non-blocking updates)

### Runtime Overhead
- <6% for embedded client
- Acceptable for production systems
- Compared to RLlib's likely 10-50%+ overhead

## Limitations

### Scope Gaps
- "System optimization" undefined – which specific problems?

- Comparison only to RLlib (what about other lightweight RL frameworks?)
- Convergence speed not provided (just convergence confirmation)

### Algorithmic Questions
- How sensitive is convergence to stale policies (server lag)?
- What is policy update frequency?
- How does asynchronous training affect credit assignment?
- Gradient staleness impact not discussed

### Generalization
- Assumes fast system decisions (as opposed to slow simulation steps)
- Unclear if approach works for problems needing online learning (non-stationary environments)
- Hardware requirements for remote trainers not specified
