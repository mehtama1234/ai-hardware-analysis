# SC-2025-247: THAPI CXI Hardware Counter Sampling

**Exposing Hidden Network Performance Issues in HPC**

## Summary
This work extends the THAPI (Trace and Analyze Performance Information) framework with a hardware counter sampling plugin for Cassini/CXI network interfaces. This integration enables correlation of low-level NIC behavior (congestion, retries) with application-level events, revealing previously hidden network performance bottlenecks.

## Problem
HPC performance is fundamentally network-bound for many distributed applications. Current challenges:
1. **Blind Spots**: Existing tracing tools operate at application/MPI level, missing NIC-level events
2. **Hidden Congestion**: Network congestion and packet retries go undetected, manifesting only as latency jitter
3. **Diagnosis Gap**: Performance degradation appears as unexplained slowdowns without root cause visibility
4. **NIC Capabilities Unused**: Modern NICs provide rich hardware counters that remain underutilized
5. **Integration Challenge**: Adding NIC telemetry to existing frameworks requires careful design

## Approach
### Architecture
**THAPI Framework Extension**:
- THAPI is established HPC tracing infrastructure (used by Intel, ARM, etc.)
- Sampling plugin collects CXI hardware counters at configurable intervals
- Non-intrusive collection avoids overhead on critical path

**Data Integration**:
1. Hardware counter samples collected during execution
2. Converted to events in standard trace format
3. Merged with application trace via iprof tool
4. Visualized in Perfetto (Google's trace viewer)

### CXI Hardware Counters Tracked
Based on HPE Slingshot Cassini NIC capabilities:
- **Congestion Indicators**: Port queueing, backpressure
- **Packet Events**: Retransmissions, NAKs
- **Flow Control**: Credit stalls, rate limiting
- **Link Utilization**: Bandwidth per channel
- **Error Conditions**: Link errors, dropped packets

### Integration Pipeline
```
Application Execution
    ↓
CXI Sampling (periodic)
    ↓
Application Trace (THAPI)
    ↓
Trace Merging (iprof)
    ↓
Visualization (Perfetto)
    ↓
Root Cause Analysis
```

## Design Considerations

### Sampling vs Instrumentation
**Why Sampling?**
- Full instrumentation of every packet → prohibitive overhead
- Sampling captures statistical behavior with minimal cost
- Overhead tunable by sampling rate
- Natural for identifying hotspots (tail events still caught)

### Trace Format Standardization
- Integration with THAPI ensures compatibility
- Enables combination with other telemetry sources
- Facilitates tool interoperability

### Correlation with Application Events
Critical insight: NIC events only meaningful when correlated with application context. Example:
- "NIC shows packet retries" (isolated fact)
- "MPI_Reduce sees retries when rank X broadcasts, correlates with network congestion on link Y" (actionable insight)

## Limitations
- **Vendor-Specific**: Currently Cassini/CXI only (generalization to InfiniBand, Omni-Path unclear)
- **Overhead Not Quantified**: "Negligible" lacks specific numbers in abstract
- **Scalability**: Demonstrated at scale unclear (100s or 1000s of nodes?)
- **Counter Overflow**: Long-running application counter wraparound handling not discussed
- **Adaptive Sampling**: Whether sampling rate adapts to congestion level not mentioned

## Broader Implications
### Network Optimization Space
This work opens new optimization opportunities:
1. **Routing Improvements**: Can guide Slingshot routing algorithm tuning
2. **Congestion Control**: Feedback for dynamic flow control
3. **Application Tuning**: Guide rank placement and communication patterns
4. **Hardware Placement**: Information for topology-aware scheduling

### Democratizing Network Diagnosis
Previously, network troubleshooting required:
- NIC vendor expertise
- Specialized tools (ethtool, sysstat)
- Manual log analysis

Now integrated into standard HPC tracing → accessible to application developers

### Exascale Readiness
At exascale (millions of cores):
- Network behavior becomes dominant performance factor
- Deterministic debugging impossible (non-reproducible congestion)
- Statistical profiling essential (this work enables)
- Network becomes first-class performance resource (like CPU)
