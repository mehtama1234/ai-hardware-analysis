# SC-2025-249: Vector Databases on HPC Platforms

**Characterizing Qdrant Performance for LLM-Grounded Inference**

## Summary
This work presents the first empirical characterization of distributed vector database performance on an HPC supercomputer (Polaris). Using Qdrant with a realistic biological text workload, it evaluates insertion, indexing, and query performance at scale (up to 32 workers).

## Problem
Vector databases have become critical infrastructure for modern AI systems:
1. **RAG Pipelines**: Retrieval-augmented generation (RAG) grounding LLMs requires fast similarity search over large document collections
2. **Scale Mismatch**: Most vector DB benchmarks focus on consumer-scale (millions of vectors) while scientific computing demands larger scales (billions)
3. **HPC Blind Spot**: Traditional HPC platforms rarely host vector DBs; performance characteristics unknown
4. **Deployment Uncertainty**: No guidance on how vector DBs perform with scientific workloads on supercomputers
5. **ML-HPC Integration Gap**: Vector DBs exist in ML ecosystem; HPC systems in scientific computing; their intersection unexplored

## Approach
### Evaluation Framework
**Platform**: Polaris supercomputer (Argonne Leadership Computing Facility)
- High-performance network interconnect
- Distributed storage
- Typical HPC scheduling/resource management

**Workload**: Realistic biological dataset
- **Corpus**: BV-BRC (bacterial and viral research center) biological text
- **Embedding Model**: Qwen3-Embedding-4B
- **Scale**: peS2o corpus (scientific document embeddings)
- **Relevance**: Meaningful for scientific researchers using RAG

**System Under Test**: Qdrant
- Popular open-source vector database
- Supports distributed deployment
- Production-ready (used in industry)

### Measurements
1. **Insertion Latency**: Time to add vectors to index
   - Per-vector latency
   - Batch insertion performance
2. **Index Construction**: Time to build efficient search structures
   - ANN index (approximate nearest neighbor) construction
   - Optimization time
3. **Query Latency**: Time to answer similarity searches
   - Top-k nearest neighbor search
   - Latency percentiles (p50, p99, p99.9)

### Scaling Study
- Measured across 1 to 32 workers (Qdrant instances)
- Strong/weak scaling analysis
- Network communication overhead quantification

## Scientific Significance
### RAG for Science
Vector databases enable **Retrieval-Augmented Generation (RAG)**:
1. Query: "What's the latest on CRISPR off-target effects?"
2. System retrieves relevant papers from BV-BRC
3. LLM reads papers, generates response
4. Result: Grounded in recent literature (vs pure hallucination)

For scientific domains:
- Biology: Literature grounding for experimental design
- Physics: Cross-disciplinary connection discovery
- Materials Science: Finding similar compound systems
- Climate: Retrieving relevant simulation data

### Scale Challenge
Scientific domains work with massive corpora:
- **Pubmed**: 30+ million biomedical papers
- **arXiv**: 2+ million preprints
- **Protein DB**: Millions of structures
- **Climate Data**: Petabytes of simulations

Vector DBs must handle this scale while maintaining sub-second query latency.

## Performance Expectations
### Single Node
- Insertion: 1,000-10,000 vectors/sec (depends on vector dimensionality)
- Indexing: Minutes to hours (depending on size)
- Query: 10-100ms p50 latency

### Scaling (1→32 workers)
- **Linear scaling**: 32x throughput (ideal)
- **Sublinear scaling** (likely): 10-20x due to:
  - Network communication overhead
  - Coordination costs
  - Load imbalance

## Deployment Considerations

### Network Topology
HPC systems have structured networks (fat-tree, torus) unlike typical cloud. How does Qdrant's gossip protocol perform on HPC network topology?

### I/O and Storage
Vector DBs need persistent storage. How do HPC parallel file systems (Lustre, GPFS) perform as vector DB backends?

### Scheduling
HPC jobs have finite lifetime (typically hours to days). How do Qdrant's index maintenance and gossip protocols behave with frequent node turnover?

## Broader Implications
### ML-HPC Convergence
This work exemplifies growing convergence:
- **Traditional HPC**: Simulation, numerical computing
- **Modern ML**: Learning from data, inference
- **Intersection**: Using simulations to train, using models to optimize simulations

Vector DBs are a key technology enabling this convergence.

### Future Research Directions
1. **Vector DB Architecture for HPC**: Design vector DBs with HPC-aware optimizations
   - MPI-based communication (vs gossip)
   - Hierarchical indexing (vs flat)
   - Parallel file systems integration
2. **Scientific Workflow Integration**: Vector DBs as component of simulation pipelines
3. **Cost-Performance Tradeoffs**: When to use local vector DB vs cloud APIs
