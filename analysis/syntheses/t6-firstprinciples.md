# The Hundred-Fold Gap: Compilers as the Bridge Between Math and Silicon

## The Problem

Consider one of the most common operations in modern computing: multiplying two matrices. Take `C = A × B`, where each matrix is 4096 rows by 4096 columns of half-precision (16-bit) numbers. The arithmetic is fixed and knowable exactly. To compute every entry of `C`, you perform 4096 × 4096 × 4096 = 68.7 billion multiply-and-add pairs, or about 137 billion individual floating-point operations. An NVIDIA A100 GPU is rated at 312 trillion such operations per second on this datatype. Divide one by the other and the multiply should finish in 0.44 milliseconds.

Write the obvious three-nested-loop version — for each row, for each column, sum the products — and it will instead take somewhere between 10 and 50 milliseconds. That is 20 to 100 times slower than the chip is physically capable of. The arithmetic did not change. Every one of those 137 billion operations still happens. What changed is *where the numbers were* when the arithmetic units needed them, and *whether the arithmetic units had to wait*.

This gap is not a quirk of matrix multiply. It is the defining fact of modern hardware. A processor's arithmetic units can consume operands far faster than memory can deliver them. An A100 can do 312 trillion FP16 operations per second but read only about 2 trillion bytes per second from its main memory (HBM). If every operation needed a fresh operand from main memory, the chip would run at under one percent of its arithmetic peak. The only way to close the gap is to move a block of data close to the arithmetic units — into the small, fast on-chip memories (L2 cache, then per-block "shared memory," then registers) — and reuse it many times before evicting it. The naive loop reuses almost nothing; it streams the whole of `A` and `B` through the slowest memory over and over. The fast implementation tiles the computation so that a small square of `A` and a small square of `B`, once loaded into fast memory, produce a whole square of results before being discarded, and it arranges for the next tile to be arriving from main memory while the current tile is being multiplied.

There are thousands of legal ways to tile, order, fuse, and schedule this one operation, and the best choice depends on the exact sizes of every on-chip memory, the number of arithmetic units, their latency, and how many operations must be "in flight" to hide that latency. A human expert can hand-tune one kernel for one chip in days. But a modern neural network has thousands of distinct operations, deployed across GPUs, TPUs, NPUs, FPGAs, edge microcontrollers, and custom ASICs, each with different memory hierarchies. Hand-tuning does not scale. A compiler must automate the search from a high-level description of *what* to compute down to a specific, near-optimal sequence of machine instructions that says *how*. This theme — 204 papers across ASPLOS, CGO, SC, MICRO, HPCA, DAC, ICCAD and more — is the science of automating that descent, and the parallel problem of compiling not just programs onto chips but *chips themselves* out of high-level descriptions.

## Why the Obvious Solution Does Not Work

The obvious answer is: write the best kernel once, by hand, put it in a library, and call it forever. This is exactly what vendor libraries (cuBLAS, cuDNN, oneDNN) do, and for the handful of operations and shapes they cover, they are excellent. The trouble is that "the operation and its shape" is a moving target. A large language model serving requests does not know until runtime whether the next batch has 1 token or 2,000 tokens; the matrix dimensions change every request, and a kernel tuned for one shape can be several times too slow for another. New model architectures invent new operations that no library anticipated. New chips ship every year, and a chip with a differently-sized shared memory needs a different tiling. Custom accelerators — dataflow chips that stream tensors through fixed pipelines, compute-in-memory arrays, edge NPUs with tiny SRAM — have no hand-tuned library at all, because the hardware barely existed when the model was written.

So the field cannot rely on a fixed set of hand-written answers. It needs a *search* — an automated process that, given an operation, a shape, and a description of the target hardware, explores the space of legal implementations and finds a fast one. But the search space is astronomically large, evaluating a single candidate can require actually running it on hardware, and the "legal implementations" must be provably equivalent to the original math or the model produces wrong answers. Every subtheme below is a different attack on some part of this triangle: representing the space of legal transformations, searching it efficiently, and doing so late enough to know the runtime facts (shapes, values) that make specialization pay off.

## Subtheme 1: Multi-Level Intermediate Representations — Keeping Structure Alive Down the Stack

### What It Is
A compiler is a chain of translations. It starts with a high-level description — "multiply these two tensors, then add a bias, then apply an activation" — and ends with machine instructions that name specific registers and memory addresses. The classic mistake is to translate to a low-level, generic form too early. Once a tensor multiply has been shredded into a flat sea of scalar loads, adds, and stores, the compiler can no longer *see* that it was a matrix multiply, so it cannot apply the powerful tiling and reuse transformations that only make sense at the tensor level. An **intermediate representation (IR)** is the internal data structure the compiler manipulates between source and machine code. A **multi-level IR** keeps several representations alive at once — a tensor-graph level, a loop level, a scalar level — and lowers from one to the next only when the higher-level structure has been fully exploited. MLIR (Multi-Level IR), an infrastructure layered on LLVM, is the dominant vehicle: it lets each *dialect* (a domain-specific vocabulary of operations) coexist, so tensor operations, loop nests, and hardware-specific instructions can all be represented and progressively "lowered."

### What the Research Community Is Doing
At ASPLOS 2025, **Relax** attacks the specific pain of dynamic shapes in language models: it builds a single unified IR that holds computational graphs, loop-level tensor programs, and external library calls together, and threads *symbolic shape annotations* (the dimension is called `n`, not a fixed number) through the whole program so that optimizations survive even when the exact sizes are unknown until runtime — and the same IR lowers to GPUs, CPUs, NPUs, phones, and browsers. Also at ASPLOS 2025, **PartIR** treats the *parallelization* of a large model as a sequence of IR rewrites: each strategy (data parallelism, tensor/model parallelism, optimizer sharding) is a composable rewrite applied to the network's IR, so that arbitrary sharding schemes can be stacked, verified, and reasoned about predictably instead of being hand-woven into the model code. At MICRO 2025, **StreamTensor** introduces an "iterative tensor" (itensor) type into an MLIR pipeline that explicitly encodes the *order* in which a kernel streams its elements; this lets the compiler automatically fuse kernels that must be wired together through on-chip FIFOs on dataflow FPGAs, sizing those FIFOs to avoid deadlock — work that was previously done by hand. At CGO 2025, **xDSL** builds a lightweight "sidekick" MLIR-compatible framework that shares a textual IR format with production MLIR, so researchers can prototype new dialects without the engineering weight of the production compiler, then hand results back across the textual boundary. And SC 2025's **Mojo** carries this philosophy into a full language: an MLIR-based, CUDA-like syntax that compiles portable GPU kernels for the Python ecosystem, running competitively with hand-written CUDA on memory-bound stencil and streaming kernels across both NVIDIA H100 and AMD MI300A.

### The Tradeoff
Multi-level IR buys *structure preservation* — the compiler never loses sight of what the program means — and *portability*, because the same high-level dialect can lower to many backends. What it costs is enormous engineering surface: every dialect, every lowering pass, and every combination between them must be built and maintained, and the "lowering pipeline" becomes a research artifact in its own right. It also pushes hard problems downward rather than solving them: MLIR gives you the *place* to express a tiling decision, but not the decision itself. That decision is the search problem, which the next subthemes confront.

## Subtheme 2: Auto-Tuning and Cost Models — Searching a Space Too Big to Enumerate

### What It Is
Given the IR and the set of legal transformations, the compiler must *choose*: what tile size, what loop order, how much to unroll, how to map iterations onto the chip's parallel units. Each choice is a point in a **schedule space** that can contain millions to billions of legal configurations. The only ground-truth way to know which is fastest is to compile it and run it on the hardware — which takes seconds to minutes per candidate. Tuning a single operator this way can take hours; tuning a whole model, days. **Auto-tuning** is the automated search over this space, and its central bottleneck is evaluation cost. The field's response is the **cost model**: a cheap surrogate — analytical, or a learned neural network — that predicts a candidate's performance without running it, so the search can screen thousands of candidates and physically measure only a promising few.

### What the Research Community Is Doing
At ASPLOS 2025, **Pruner** confronts the fact that an accurate learned cost model is itself too slow to apply to every candidate: it uses a "draft-then-verify" scheme where a fast symbolic analyzer rapidly drafts a large candidate pool, and the expensive learned model only verifies the survivors — cutting tuning from the hours-to-days range. At CGO 2025, **IntelliGen** shrinks the search space by exploiting a *monotonic* property of memory optimization (improvements compound in a predictable direction), reaching 1.46–3.13× speedups on NVIDIA, 1.85–3.55× on AMD, and up to 16.9× on Cambricon accelerators. Also at CGO 2025, a coreset-based auto-tuner identifies "synergistic" pairs of compiler passes that jointly help, clusters benchmarks to learn which pass-set to apply to a new program, and delivers 13.9% code-size reduction in five seconds — attacking the classic phase-ordering problem where the *order* of optimization passes matters. At MICRO 2025, **LLMulator** rethinks the cost model itself: it fine-tunes a 1-billion-parameter language model (LLaMA-3.2-1B via LoRA) to predict accelerator performance, and — crucially — treats each performance number as a sequence of *digits* predicted categorically rather than as a single regression target, which lets it generalize to loop scales far outside its training range (12.2% mean error on unseen ASIC scenarios where prior methods exceeded 40%). SC 2025's constraint-driven **DynaChain** auto-tuner for the MT-3000 many-core processor uses "constraint dependency chains" to prune invalid schedules during search, matching expert-optimized GEMM libraries, and ICCAD 2025's MetaSchedule-based tuner for the RISC-V vector extension automatically searches loop tiling and vectorization to beat GCC by 46%.

### The Tradeoff
A cost model turns days of physical measurement into seconds of prediction — but only to the extent it is *accurate*, and accuracy is exactly what breaks down on the cases that matter most: new hardware, new operators, and input-dependent behavior the model never saw. An inaccurate cost model does not merely slow the search; it confidently steers it toward slow kernels. LLMulator's digit-wise encoding and Pruner's two-stage verification are both admissions of the same truth: you cannot fully trust the surrogate, so you must keep a cheap way to catch its mistakes. The deeper cost is generality: every cost model is trained or tuned for a slice of the hardware landscape, and the landscape keeps growing.

## Subtheme 3: Equality Saturation and Program Synthesis — Finding Transformations You Didn't Know to Look For

### What It Is
Ordinary compiler optimization is *destructive and greedy*: it applies a rewrite (say, `x*2 → x+x`), throws away the old form, and moves on. If a later rewrite would only have been profitable on the discarded form, the opportunity is lost forever — this is the phase-ordering problem. **Equality saturation** avoids the destruction. It records rewrites in an **e-graph** (equality graph), a compact data structure that represents *all* equivalent versions of a program at once: rather than replacing `x*2` with `x+x`, it notes that the two are equal and keeps both, along with everything derivable from either. After applying rewrites until the graph stops growing ("saturates"), the compiler runs an *extraction* step to pull out the single cheapest equivalent program according to a cost model. A related idea, **program synthesis**, goes further: instead of transforming a program, it *searches for a program from scratch* that provably matches a specification, which is how legacy code can be automatically "lifted" into a high-performance tensor DSL.

### What the Research Community Is Doing
The hard part of equality saturation is extraction: choosing the optimal program from an e-graph that may encode astronomically many is itself NP-hard, and exact methods are slow while fast heuristics are poor. At ASPLOS 2025, **SmoothE** reformulates extraction as a *continuous, differentiable* optimization — relaxing the discrete "pick this node or that node" choice into smooth real-valued weights so that gradient descent can solve it, and, unlike prior extractors, supporting arbitrary differentiable (non-linear) cost functions. The technique crosses cleanly into hardware design: at DAC 2025, **E-morphic** applies equality saturation to *logic synthesis*, exploring alternative circuit structures before technology mapping instead of committing to a single canonical form, and using simulated annealing for extraction to cut area 12.54% and delay 7.29% on the EPFL benchmark circuits. On the synthesis side, CGO 2025's **Tensorize** takes existing legacy code, symbolically traces it to derive a specification, automatically selects "sketches" (partial templates) from target tensor DSLs, and uses an algebraic solver to fill them in — producing correct-by-construction translations an order of magnitude faster than prior synthesis schemes and targeting GPUs, TPUs, and ASICs. CGO 2025 also shows the pattern in the small: automatic synthesis of *specialized hash functions* from example keys yields ~50× speedups on the hashing itself, and synthesis of sorting kernels.

### The Tradeoff
Equality saturation and synthesis find optima that greedy rewriting structurally cannot reach, and — in the synthesis case — come with correctness guarantees rather than mere hope. The price is scale. E-graphs can explode in size, and extraction is the recurring bottleneck (which is precisely why SmoothE and E-morphic each invent a new extraction method rather than a new rewrite). Synthesis has to bound its search or it never terminates; Tensorize's whole contribution is making the solving fast enough to apply to real code. These methods are powerful exactly where the search space has rich algebraic structure to exploit, and awkward where it does not.

## Subtheme 4: Just-in-Time Specialization — Compiling Late Enough to Know the Facts

### What It Is
Ahead-of-time (AOT) compilation happens before the program runs, when the compiler knows the code but not the data. Yet the facts that unlock the biggest speedups are often *runtime* facts: the actual matrix shape this request needs, the fact that a "variable" bound is always 3, the fact that an array is mostly zeros. **Just-in-time (JIT) compilation** defers final code generation until runtime, when those facts are known, and *specializes* the machine code to them — replacing a runtime-variable dimension with a constant the compiler can then optimize around, or generating a fast path for the common case. The bet is that the time spent compiling at runtime is repaid many times over by the faster code, which holds when the same specialized kernel runs many times.

### What the Research Community Is Doing
At CGO 2025, **Proteus** makes GPU JIT portable: it extracts language-agnostic LLVM IR from a kernel and recompiles it at runtime with user-annotated specialization points, hitting 2.8× over AOT on AMD and 1.78× on NVIDIA — and crucially, because it works at the LLVM IR level rather than in CUDA source, it is not tied to one vendor's toolchain. SC 2025's extension of the **RAJA** portability layer folds this same Proteus JIT into a production HPC abstraction, adding "dimension specialization" that replaces runtime dimension queries with compile-time constants for speedups from 1.2× to 23× on AMD MI250X. Specialization also drives value-based optimization: SC 2025's **ZeroSpec** uses profiling to find where zero values propagate through a program and builds specialized fast paths that skip the resulting redundant work (up to 1.31×), while ASPLOS 2025's **BitSpec** is a compiler-hardware co-design that *speculates* each variable's true bit-width — most 32-bit integers never use all 32 bits — emitting narrow instructions and relying on hardware to catch the rare overflow, for 9.9% average energy savings (up to 28.2%) on embedded devices. For the LLM case, where shapes genuinely change every request, SC 2025's **Helix** takes the opposite bet from JIT: rather than compile per-shape, it produces *shape-agnostic* code via hierarchical decomposition, cutting compilation time 174× while still delivering 2.26–3.29× execution speedups on unseen shapes. And SC 2025's **XaaS containers** push specialization to deployment time, shipping software as source or IR inside a container and compiling for the specific HPC machine only when it lands there.

### The Tradeoff
JIT specialization captures the single biggest lever the other subthemes cannot reach — runtime knowledge — but every specialization is a bet that the compile cost will be amortized. When shapes or values churn faster than kernels are reused, the JIT overhead becomes pure loss, which is exactly why Helix chooses shape-agnostic compilation for the volatile LLM regime and BitSpec needs a hardware safety net for its mispredictions. Specialization also multiplies the number of distinct code versions the runtime must manage, cache, and evict — trading compile-time simplicity for runtime complexity.

## How the Pieces Fit Together

Read across the corpus and one architecture repeats at every level: **represent the space of legal choices, predict the cost of a choice cheaply, then commit to a choice as late as you responsibly can.** Multi-level IR is the representation layer — it is what makes a tiling or fusion decision *expressible* without losing the structure that justifies it. Auto-tuning and cost models are the prediction layer — they make searching that space tractable by replacing measurement with estimation. Equality saturation is a bet that a richer, non-destructive representation lets you *reach better choices*, at the cost of a harder extraction search. And JIT specialization is the bet on *timing* — that the most valuable facts arrive at runtime and are worth deferring the final decision to capture. These are not four separate research programs so much as four pressure points on one pipeline, and they constrain each other directly: a more expressive IR enlarges the search space that the cost model must then cover; a more aggressive equality-saturation rewrite set makes extraction harder; late JIT specialization shrinks the AOT search space but adds runtime cost the cost model now has to account for.

The striking pattern in the 2025 corpus is that this same pipeline is being turned on *hardware itself*. The line between "compiling a program onto a chip" and "compiling a chip out of a description" has largely dissolved. HPCA's **LEGO** uses an affine-transformation IR — the polyhedral machinery invented for loop tiling — to automatically emit synthesizable RTL for spatial accelerators, beating the hand-tuned Gemmini baseline by 3.2× in performance and 2.4× in energy. ISCA's **Assassyn** compiles a single high-level program into *both* a fast simulator and RTL implementation, ending the duplicated-codebase problem. The equality-saturation, e-graph, and synthesis techniques that optimize tensor programs (SmoothE, Tensorize) are the same ones optimizing logic circuits (E-morphic) and routing qubits on neutral-atom quantum machines (HPCA's ZAC, which treats qubit movement as a reuse-and-scheduling compilation problem for a 22× fidelity gain). High-Level Synthesis — compiling C-like code into hardware — has become a dense sub-front of its own, with MICRO's OmniSim delivering 35.9× faster simulation of HLS designs and ICCAD's automated design-space exploration hitting 2.42× the frequency of AMD's commercial Vitis flow. The dominant strategy the corpus reveals is *unification*: build one IR-and-search machine general enough to target software kernels, dataflow accelerators, FPGAs, ASICs, and quantum hardware alike, and the current bets are placed on where that machine still fails — dynamic behavior, generalization to unseen targets, and trustworthy cost prediction.

The unifying force behind the bet is that the hardware landscape is fragmenting faster than humans can hand-tune it. Every new accelerator, every new model architecture, every new datatype multiplies the number of (operation, shape, target) triples that need a fast implementation, and the only economically viable response is a compiler general enough to absorb the new target and search its way to good code automatically. That is why so much of the effort goes into *representations that don't presuppose the hardware* (LEGO's affine relations, Relax's cross-level IR, StreamTensor's itensor) and *cost models that generalize past their training distribution* (LLMulator's digit-wise prediction). The field is, in effect, trying to build a compiler that can be pointed at a chip it has never seen.

## What Remains Hard

- **Cost models that generalize to unseen hardware and operators.** LLMulator's 12.2% error on new ASICs is impressive precisely because prior models exceed 40%; a cost model accurate on hardware it was never trained on remains unsolved, and it is the gating factor for auto-tuning any brand-new accelerator.
- **Compiling for genuinely dynamic shapes without per-shape retuning.** LLM serving produces a new matrix shape almost every request; Helix's shape-agnostic compilation and Relax's symbolic shapes are early answers, but closing the gap to per-shape-tuned performance while paying no per-shape compile cost is open.
- **E-graph extraction at scale.** Equality saturation reaches optima greedy compilers cannot, but every 2025 paper that uses it (SmoothE, E-morphic) had to invent a new extraction method because the discrete optimal-extraction problem still explodes; a fast, general, non-linear-cost extractor would unlock the technique broadly.
- **Verified composition of parallelization strategies.** PartIR makes data, tensor, and optimizer sharding composable and checkable, but proving that an arbitrary stack of sharding rewrites preserves the model's mathematical meaning across thousands of GPUs — rather than testing and hoping — is not yet routine.
- **Unifying the compile-time/runtime boundary.** JIT specialization wins when kernels are reused and loses when they churn; there is no principled way for a compiler to decide *automatically*, per kernel, how much to specialize versus how much to keep shape-agnostic, so the choice is still hand-tuned (BitSpec speculates and repairs; Helix refuses to specialize).
- **One IR for both software and silicon.** LEGO and Assassyn show a single representation can target software schedules and synthesizable RTL, but a compiler stack that lowers the *same* tensor program to a GPU kernel, an FPGA dataflow, and a custom ASIC — with a cost model that reasons across all three — does not yet exist end to end.
- **Correct-by-construction synthesis for real, messy code.** Tensorize lifts legacy code into tensor DSLs with correctness guarantees, but only for code its symbolic tracer can fully capture; extending provably-correct synthesis to programs with irregular control flow, pointers, and side effects is a wide-open frontier.
