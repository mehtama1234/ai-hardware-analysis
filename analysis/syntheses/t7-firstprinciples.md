# The Chip That Cannot Keep a Secret

## The Problem

Start with a fact that has nothing to do with cryptography: a transistor switching from 0 to 1 pulls charge off the power rail. A million transistors switching together pull a million times as much. If the number of transistors that flip depends on the data being processed — and it almost always does, because a byte with six 1-bits charges more capacitance than a byte with two — then the current a chip draws is a running commentary on what it is computing. Put a resistor in the power line, watch the voltage across it with an oscilloscope, and you are reading that commentary in real time. This is not a bug in any particular chip. It is a consequence of the fact that computation is physical, and physics conserves and radiates energy in ways that correlate with the bits being moved.

The same principle repeats across every physical channel a chip touches. Accessing data already sitting in the L1 cache takes about 4 cycles; a miss that goes to DRAM takes 200 or more. So the *time* a program takes leaks *which addresses* it touched, and which addresses it touched can encode a secret key — an AES table lookup indexed by a key byte lands in a cache set that an attacker sharing the machine can later probe. Switching current radiates an electromagnetic field an antenna can pick up from across a room. A processor's idle-state wake-up latency, visible only as network response jitter, tells a remote attacker whether the victim core was busy or asleep. Even the leakage current of a transistor shifts when a backside laser illuminates it, which is why an attacker with a laser can read out the state of an SRAM cell without touching a wire. Every one of these — power, timing, EM, thermal, photocurrent, contention on a shared bus — is a *side channel*: a path by which information about a secret escapes through a physical property the designer never intended to be an output.

The reason this theme exists as a distinct field, rather than a footnote in cryptography, is a brutal asymmetry. The mathematics of a cipher like AES can be provably secure — no known algorithm recovers the key from ciphertext alone in less than astronomical time. But the *implementation* of that cipher runs on silicon that leaks, and the leakage bypasses the mathematics entirely. An attacker who cannot break AES on paper can extract a full AES-128 key from an FPGA by collecting 25,000 to 78,000 power traces through a repurposed DSP block (LeakyDSP, DAC 2025), or recover an RSA-2048 key from an Intel SGX enclave by reading energy counters through an out-of-band management interface the in-band defenses never guarded (OOPS!, DAC 2025). The secret was never in the ciphertext. It was in the power trace, the cache timing, the branch history, the DRAM refresh schedule.

And the surface keeps widening because the hardware keeps sharing. Cloud economics demand that many tenants run on one physical machine — sharing the last-level cache, the memory controller, the DRAM chips, the power delivery network. Every shared resource is a potential channel between a victim and a co-resident attacker. Meanwhile the workloads themselves have become secrets worth stealing: a deployed neural network's architecture and weights are commercial IP, and the user inputs fed to it (a genome, a medical image, an embedding-table index that encodes which ad you clicked) are private data. So the field faces a moving target — more shared hardware, more valuable secrets, and a growing catalog of physical channels, each of which must be either closed or made to leak nothing meaningful.

## Why the Obvious Solution Does Not Work

The obvious answer is: encrypt everything and stop sharing. If data is encrypted in memory, a co-resident attacker who reads your DRAM sees noise. If the computation runs inside a hardware-isolated enclave, no other tenant can touch it. Both ideas are real and deployed — memory encryption ships in AMD SEV and Intel TDX, enclaves ship as Intel SGX and ARM TrustZone. The trouble is that neither closes the side channels, and both are expensive.

Encryption does not help when the leak is in *timing* or *power* rather than in the stored bytes. AMD SEV encrypts every guest VM's memory, and yet Reload+Reload (ASPLOS 2025) extracts a full AES-128 key across the SEV-SNP isolation boundary by timing cache-flush and memory-contention effects that encryption never touched — the ciphertext is opaque, but *when* the victim accesses it is not. Isolation does not help when the isolation mechanism itself has a physical signature: MDPeek (ASPLOS 2025) reads secrets out of an SGX enclave through the CPU's Memory Disambiguation Unit even when the enclave's code was carefully written to balance its branches, because the microarchitecture speculates in a data-dependent way beneath the level the software defense operates at. And the costs are savage: NVIDIA's H100 confidential mode cuts OPT-66B inference throughput by 88.2% because every byte crossing the trust boundary must be encrypted on the critical path (PipeLLM, ASPLOS 2025). Closing side channels by brute force — accessing every row of a table so no single access stands out — turns a cheap embedding lookup into a full-table scan. There is no single clean fix, which is exactly why the corpus splits into several distinct research fronts, each attacking a different physical channel with a different set of tradeoffs.

## Subtheme 1: Rowhammer and the DRAM That Betrays Its Neighbors

### What It Is

DRAM stores a bit as charge on a tiny capacitor. The cells are packed so densely that reading one row — which requires slamming its wordline high, an operation called an *activation* — disturbs the charge on physically adjacent rows through electromagnetic coupling and charge leakage. Activate a row tens of thousands of times before the neighboring rows get their periodic refresh, and enough charge bleeds away that a neighbor's bit flips from 1 to 0. This is *Rowhammer*. It is not a logical bug; it is the analog physics of a capacitor that is too small and too close to its neighbors. What makes it a *security* problem is that a bit flip respects no software boundary: the flipped bit might live in a page table entry, a cryptographic key, or a permission flag belonging to a different security domain — the operating system, the hypervisor, another tenant's VM. Flip the right bit and you rewrite privilege.

The physics has worsened with every process node. The number of activations needed to induce a flip — the *Rowhammer threshold* — has fallen from around 139,000 on early DDR3 to under 100, and the defenses now target thresholds in the sub-100 range. As the threshold drops, defenses must act more often, and acting more often is what makes them expensive.

### What the Research Community Is Doing

The dominant defensive idea is to *count* activations per row and refresh a row's neighbors before the count crosses the threshold. JEDEC standardized this as Per-Row Activation Counting (PRAC) for DDR5, but the naive form puts a counter increment on the critical path of every activation, costing about 10% performance on *all* workloads, benign or not. The 2025 corpus is largely a race to make PRAC cheap and provably secure at once. MoPAC (ISCA 2025) updates counters only *probabilistically* and lowers the mitigation threshold by the inverse of the sampling rate to preserve the security guarantee, cutting the overhead to 0.7%. Chronus (HPCA 2025) physically separates the counter array from the data array so counter updates run concurrently with data access, removing the latency penalty entirely. MOAT (ASPLOS 2025) replaces a prior insecure multi-entry queue with a single register that tracks only the highest-count row, achieving a provably secure dual-threshold design in 7 bytes of SRAM per bank with 0.28% slowdown. AutoRFM (HPCA 2025) drops the refresh-management stall from the whole bank to a single subarray, cutting slowdown from 33% to 3.1% at a threshold of 74. On the attack side, the field keeps proving the defenses porous: ρHammer (MICRO 2025) revives Rowhammer on 12th–14th-gen Intel chips — where ordinary load-based hammering produces *zero* flips — by using non-blocking software prefetch instructions to reach 187,000 flips/minute, a 112x speedup over the load baseline. HyperHammer (ASPLOS 2025) escapes KVM guest isolation to compromise the hypervisor itself.

### The Tradeoff

Every Rowhammer defense buys integrity by spending refreshes, and refreshes are stalls. The whole subfield is a search along a single curve: how much performance must you sacrifice to guarantee no flip at a given threshold? Worse, the defenses have become attack surfaces of their own. Because a preventive refresh blocks DRAM access in a way that depends on the victim's access pattern, the *mitigation* leaks. LeakyHammer (MICRO 2025) builds covert channels of 39–48.7 Kbps out of PRAC and refresh-management timing, and PRACLeak (ISCA 2025) extracts AES keys from the timing of the alert-back-off protocol. Fixing the integrity channel opened a timing channel — the recurring shape of this entire field.

## Subtheme 2: Microarchitectural Side Channels and Speculation

### What It Is

A modern CPU is fast because it does work before it knows the work is needed. It *speculates* past a branch it has not yet resolved, executing instructions on the predicted path; if the prediction was wrong, it discards the results and pretends nothing happened — *architecturally*. But *microarchitecturally*, the speculative work left traces: a cache line got loaded, a predictor got trained, a buffer got an entry. Those traces survive the rollback. Spectre and its descendants exploit exactly this: trick the processor into speculatively accessing a secret and leaking it into the cache, then read the secret out of the cache timing after the speculation is squashed. The secret was never *architecturally* read — the security check that would have blocked it was on the mispredicted path — yet it escaped. The root cause is that "constant-time" cryptographic code, written so its timing does not depend on secrets, assumes the processor executes the instructions in program order. Out-of-order speculation violates that assumption beneath the software's feet.

### What the Research Community Is Doing

The 2025 work splits into three moves: detect the leaky code, delay the leaky speculation, or replay a safe deterministic order. On detection, Teapot (CGO 2025) statically rewrites commercial binaries to run "speculation shadows" — a parallel path modeling speculative execution — and fuzzes to trigger Spectre gadgets 20x faster than prior binary tools; AMuLeT (ASPLOS 2025) generates litmus tests at *design time* so hardware architects can catch insecure speculation countermeasures before tape-out, and it rediscovered known holes in published defenses. On delay, SpecASan (ISCA 2025) repurposes ARM's Memory Tagging Extension: if a speculative load's pointer tag does not match the memory tag, the load stalls until speculation resolves, blocking the leak without disabling speculation wholesale. On deterministic replay, Cassandra (ISCA 2025) *disables* branch prediction inside constant-time crypto regions and instead records the known sequential control flow and replays it from a Branch Trace Unit — and because crypto control flow is deterministic, this actually runs 1.85% *faster* than the unsafe baseline. The Coq-verified type system in "Protecting Cryptographic Code Against Spectre-RSB" (ASPLOS 2025) proves a compiler transformation blocks *all* known Spectre variants, at under 2% overhead for most primitives and 5–7% for the post-quantum KEM Kyber. ShadowBinding (MICRO 2025) supplies the missing reality check: implementing the academic secure-speculation schemes STT and NDA as real RTL on a RISC-V out-of-order core costs 22–35% IPC — far more than the papers proposing them claimed.

### The Tradeoff

Speculation *is* the performance. Every defense that constrains it trades throughput for safety, and the honest RTL numbers (ShadowBinding's 35%) are much worse than the paper-level estimates. The field's escape from this bind is *selectivity*: protect only the code that touches secrets (crypto regions, tagged pointers) and let everything else speculate freely. But selectivity requires knowing which data is secret, which pushes complexity into the compiler and the type system — and any gap in that classification is a hole. Meanwhile the attackers keep finding channels nobody was guarding: MDPeek's Memory Disambiguation Unit, SMaCk's self-modifying-code pipeline flush (ASPLOS 2025, a 100–350x stronger L1i signal than prior attacks), CryptoBTB's branch-target-buffer leak. The defensive catalog is always one microarchitectural structure behind.

## Subtheme 3: Power, EM, and Optical Side Channels in Silicon

### What It Is

This is the physical layer of leakage — the one no amount of software constant-time discipline can touch, because it operates below the instruction set entirely. Correlation Power Analysis is the canonical attack: you hypothesize a key byte, predict how many bits would flip in the hardware for that hypothesis, and correlate your prediction against measured power traces; the correct hypothesis correlates, the wrong ones do not. The variants differ only in *how* you sense the power or field. An attacker might use an external probe, or — more insidiously in shared FPGAs — a circuit reprogrammed inside the same fabric to sense voltage droop, or an on-chip current sensor that was put there for power management. And at the extreme physical end sits optical probing: a laser fired at the backside of a chip modulates the reflected light in proportion to the voltage on a node, letting an attacker read out logic state directly, with near-100% success (the threat True-PolyTronik and the ISSCC laser-detection work confront).

### What the Research Community Is Doing

The attack papers show how little access is now required. AmpereBleed (DAC 2025) needs no crafted sensing circuit at all — it reads the ordinary INA226 current sensors already present on ARM-FPGA boards and fingerprints co-located DNN workloads with 99.7% accuracy. LeakyDSP (DAC 2025) turns idle DSP blocks into voltage sensors to pull an AES-128 key in 25,000–78,000 traces. The XGBoost-accelerator attack (DAC 2025) extracts decision-tree node features from an FPGA in 367,000 tests at 95.6% fingerprint accuracy; Energon (ICCAD 2025) reads GPU power and thermal fluctuations at *user* privilege to identify a transformer's model family (89%) and hyperparameters (100%). On defense, POLARIS (DAC 2025) uses explainable-AI to guide a masking model that obfuscates the power signature without hand-crafted attack expertise; TRANSPOSE (VLSID 2025) transforms RTL — duplicating and balancing sensitive registers, adding clock-gating — to flatten the power-secret correlation, validated by the Test Vector Leakage Assessment. Against optical attacks, ISSCC 2025's sensor-less laser-probing detector watches for the leakage-current *shift* a probing laser induces, catching near-100% of attacks for 4.35% area, and True-PolyTronik (VLSID 2025) builds logic from reconfigurable field-effect transistors that corrupt their own internal state when they detect the tell-tale power-supply modulation of a laser-logic-state-imaging attack. One counterintuitive result: approximate neural-network hardware (DAC 2025) turns out *harder* to attack, because the approximation noise raises the measurements-to-disclosure by 4–20x — inaccuracy as accidental armor.

### The Tradeoff

Physical-layer defenses cost physical-layer resources: area for masking logic and sensors, dynamic power for the balancing circuits, design effort to pass leakage assessment. And they are never complete — masking raises the number of traces an attacker needs, it does not drive it to infinity, so a patient attacker with enough traces still wins. The economics are the real defense: make the attack cost more traces, more time, more access than the secret is worth. But as sensing gets cheaper and attackers repurpose sensors already on the board (AmpereBleed, LeakyDSP), the attacker's cost keeps falling, and the defender must keep spending to stay ahead.

## Subtheme 4: Confidential Computing — Enclaves, Memory Encryption, and Private ML

### What It Is

When you cannot trust the machine your computation runs on — a cloud server, an edge device in someone else's hands — you want a region of hardware that even the operating system and hypervisor cannot peer into. That is a Trusted Execution Environment: a hardware-enforced enclave (Intel SGX, ARM TrustZone) or an encrypted VM (AMD SEV, Intel TDX, and RISC-V equivalents built on Physical Memory Protection). The hardware encrypts the enclave's memory, checks its integrity against a Merkle tree so tampering is detected, and attests cryptographically that the right code is running. The dream is *confidential computing*: run inference on a private genome or a proprietary model on rented hardware, and neither the cloud operator nor a co-tenant learns the data or the weights.

### What the Research Community Is Doing

The through-line is that the guarantee is real but the overhead is the enemy, and the overhead is worst exactly where the data is biggest — ML. PipeLLM (ASPLOS 2025) attacks the 88.2% throughput hit of H100 confidential mode by *speculatively* encrypting data before the GPU requests it, predicting KV-cache and token-generation access patterns to overlap encryption with compute, dropping the overhead below 19.6%. AIORE (MICRO 2025) makes CXL-expansion memory in a TEE cheaper by encrypting hot pages with fast parallelizable CTR mode and only cold pages with the mandated XTS mode, cutting security overhead 62.8%. FlexTEE (ICCAD 2025) and SeDA (DAC 2025) attack the Merkle-tree integrity-metadata traffic that throttles DNN accelerators, SeDA shaving 12%+ via bandwidth-aware encryption and tiling. For private ML specifically, GNNVault (DAC 2025) splits a graph neural network into a public backbone and a private "rectifier" held inside SGX, protecting both weights and graph topology at under 2% accuracy loss; Ensembler (DAC 2025) blunts model-inversion attacks that reconstruct a client's input from collaborative-inference gradients, improving reconstruction resistance (43.5% SSIM) for 4.8% overhead. ZION (DAC 2025) brings confidential VMs to commodity RISC-V at under 5% overhead. Azure's Secure Hardware Architecture (Hot Chips 2025) shows the production end: attestation, hardware key isolation, and cloud-specific threat models baked into shipping silicon. And the genome-alignment study (SC 2025) supplies the honest bill: AMD SEV+SME adds 20.9% overhead and halves effective memory bandwidth on a real BWA-MEM2 workload.

### The Tradeoff

A TEE moves the trust boundary inward — you now trust only the CPU vendor's silicon root of trust instead of the whole software stack — but it does not eliminate leakage across that boundary, which is why Subtheme 2's side channels keep puncturing SGX and SEV (MDPeek, Reload+Reload, OOPS!, ZenLeak). And confidentiality collides head-on with performance: encryption and integrity checking add latency to every memory access, and ML's appetite for memory bandwidth makes that latency hurt most. The 2025 strategy — speculate, tier the encryption by access frequency, optimize metadata locality — is fundamentally about hiding the cost behind computation the machine was doing anyway, the same pipelining instinct that made CPUs fast in the first place.

## How the Pieces Fit Together

The four subthemes are not four separate problems; they are four faces of one constraint — *computation leaves physical traces* — attacked at four layers of the stack. Rowhammer is the analog physics of the memory cell. Speculation channels are the physics of the pipeline. Power and optical channels are the physics of the transistor. Confidential computing is the attempt to wrap all of it in cryptography. And the defining pattern of the 2025 corpus is that these layers *interfere with each other*. A defense at one layer routinely opens a channel at another. PRAC and refresh management were built to stop Rowhammer (integrity), and they created timing side channels (confidentiality) — LeakyHammer and PRACLeak weaponized the very refreshes that MOAT and Chronus tuned for security. Memory encryption stops a co-tenant from reading your DRAM, but leaves the access *timing* wide open, which is how Reload+Reload beats SEV. Every point on the design space trades one physical channel for another; there is no configuration that closes them all.

Underneath, a single economic law governs the whole field: *make the attack cost more than the secret is worth.* Almost no defense in this corpus claims to make an attack impossible — they raise the measurements-to-disclosure by 4–20x (approximate NNs), cut attack success by 256x (CacheGuardian, ICCAD 2025), demand a million power traces instead of a thousand (the HDC accelerator attack, ICCAD 2025). Security here is quantitative, a moving equilibrium between the falling cost of attacks (attackers repurposing sensors already on the board, reviving Rowhammer with prefetch, reading energy counters out-of-band) and the rising cost of defenses. The bet the community is placing is *selectivity plus co-design*: do not pay the security tax uniformly — spend it only on the data that is actually secret (SpecASan's tagged loads, GNNVault's private rectifier, AIORE's hot pages, the Data Oblivious CPU's dual instruction paths), and design the defense jointly with the workload so its cost hides inside computation the machine was doing anyway (PipeLLM's speculative encryption, Cassandra's replay-instead-of-predict). The counter-bet, visible in the attack papers, is that selectivity is exactly where the holes are: any channel the classifier forgot to mark secret, any microarchitectural structure the taint tracker did not cover, is a way in.

The corpus also reveals *where* the field expects the next fights. Attacks are climbing the value chain from keys to models: Energon steals a transformer's architecture from GPU thermals, the XGBoost attack extracts trees, DeepPUFSCA breaks PUFs by fusing challenge-response and power data. The trust anchor is migrating off the CPU: TNIC (ASPLOS 2025) builds a formally verified root of trust in the NIC and beats CPU-centric TEEs by up to 6x, while FPGA-TrustZone and FPGA-CC push TEEs into reconfigurable fabric. And homomorphic encryption — the only approach that makes the leak *meaningless* by computing on ciphertext directly — is finally getting hardware that might make it usable: Orion (ASPLOS 2025) compiles arbitrary PyTorch CNNs to FHE and runs the first FHE ResNet-50 on ImageNet, Uranus (ICCAD 2025) accelerates private GNN inference 92x over software CKKS, and ISSCC 2025's MK-CKKS processor hits 30.4 GOPS/mW for multi-party computation. FHE is the field's long bet: if computing on encrypted data ever gets cheap enough, most of the side-channel problem dissolves, because there is nothing meaningful left to leak.

## What Remains Hard

- Rowhammer thresholds are falling below 100 activations while counter-based defenses still cost measurable performance at those thresholds; no design yet gives provable integrity at sub-50 thresholds without either a timing side channel or a slowdown that erases the benefit of the newer, denser DRAM.
- Every microarchitectural structure is a potential channel, and the defensive catalog is enumerated one structure at a time (MDU, BTB, RSB, self-modifying-code detection) — there is no general method to prove a *complete* core leaks nothing secret-dependent, only whack-a-mole against the structures already discovered.
- Secure-speculation schemes cost 22–35% IPC in honest RTL (ShadowBinding) versus the single-digit estimates in the proposing papers; closing that gap — real security at real, measured, single-digit overhead on a wide out-of-order core — is unsolved.
- Confidential ML inference on GPUs still pays double-digit throughput penalties even after speculative encryption (PipeLLM's <19.6%); driving TEE overhead for large-model serving toward the sub-5% seen for CPU workloads, given ML's bandwidth appetite, is open.
- Power and EM masking raises the attacker's trace count but never to infinity, and attackers keep finding *free* sensors already on the board (INA226 current monitors, DSP blocks, energy MSRs) — a masking scheme with a provable, workload-independent leakage bound at acceptable area is still missing.
- FHE has crossed into ResNet-50 and GNNs with hardware acceleration, but remains orders of magnitude off plaintext speed for transformer-scale inference; the bootstrap-noise budget and ciphertext-packing problem for attention layers has no efficient hardware mapping yet.
- Attacks now steal models, not just keys (transformer architecture from GPU thermals, decision trees from FPGA power), yet almost all defensive work still targets cryptographic-key leakage — protecting model IP and private inputs against physical-layer model-extraction is a largely unguarded frontier.
