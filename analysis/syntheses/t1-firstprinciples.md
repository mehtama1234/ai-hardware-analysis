# Every Token Must Read Every Other Token

## The Problem

A language model generates text one token at a time. A token is a chunk of text — roughly a word or a piece of one — represented inside the machine as a vector of numbers, a list of maybe 4,096 or 8,192 floating-point values. To decide what token comes next, the model does something specific and expensive: it takes the vector for the token it is currently producing and compares it against the vector of every token that came before. Each comparison is a dot product — multiply the two vectors element by element and sum the result — producing a single number that says "how relevant is that past token to this one." This is what "attention" means, mechanically. There is no metaphor hiding here. To emit one word, the model literally computes a relevance score against every word already in the conversation, then uses those scores to build a weighted average of the past.

Two numbers govern everything downstream. First, the past is stored as two vectors per token per layer — a "key" vector (what the token offers for matching) and a "value" vector (what the token contributes if matched). This store is called the KV cache. A "layer" here is one full round of attention-plus-transformation; a large model stacks 32, 64, or more of them, and every layer keeps its own separate KV cache. Second, the KV cache is re-read in full for every single token generated. When the model produces token number 100,000, it reads back the keys and values for all 99,999 prior tokens — across every layer, every attention head — computes 99,999 dot products per head, then throws none of it away because token 100,001 will need all of it again.

Put real numbers on it. A 70-billion-parameter model in 16-bit precision, serving a 32,000-token conversation, holds a KV cache of roughly 64 gigabytes. That is larger than the 40- or 80-gigabyte memory of the datacenter GPUs it runs on. DeepSeek-V3's team, reporting at ISCA 2025 (`isca-2025-130`), measured LLaMA-3.1-405B spending 516 kilobytes of KV cache *per token* — so a 128,000-token context costs 66 gigabytes for the cache alone, before you count the model weights. And the trend lines diverge: that same team noted high-bandwidth memory (HBM) capacity is growing under 50% per year while the memory footprint of frontier models grows over 1,000% per year. The hardware is falling behind the workload by more than an order of magnitude annually.

The consequence is that generation is not compute-bound; it is memory-bound. During the decode phase — producing tokens one at a time — the arithmetic units on a GPU sit mostly idle, waiting for the KV cache to stream in from memory. LAD's authors (`hpca-2025-092`) measured that beyond 2,048 tokens of context, re-reading the KV cache consumes over half of total inference time. The bottleneck is not that the machine cannot multiply fast enough. It is that the machine cannot move the numbers from memory to the multipliers fast enough. This single fact — that attention is a memory-movement problem wearing the costume of a compute problem — is why this entire research theme exists.

## Why the Obvious Solution Does Not Work

The obvious move is: buy more memory and more bandwidth. Stack more HBM on the GPU, widen the memory bus, and the problem goes away. It does not, for two reasons. First, HBM is physically and economically constrained — it sits on the same silicon interposer as the compute die, its capacity per package grows slowly (the sub-50%/year figure above), and it is the most expensive component on the board. You cannot buy your way out of a gap that widens 20-fold faster than the supply. Second, even with infinite memory, the *bandwidth* wall remains: reading 64 GB per generated token, at even 3 TB/s of HBM bandwidth, imposes a hard floor on latency that no amount of compute can lower. DeepSeek-V3's team put a ceiling on it — the theoretical upper bound for their model on H800 hardware is 67 tokens per second, dictated purely by how fast the interconnect and memory can move the cache.

So the field splits along the only axes that remain. If you cannot make the memory bigger or faster, you must (a) store less of it — compress or evict the KV cache; (b) read less of it — skip tokens that do not matter, via sparse attention; (c) read it more cleverly — fuse the computation so data never leaves fast on-chip memory; (d) move the reading closer to the data — do attention inside the memory or storage itself; or (e) generate more tokens per read — speculative decoding. Each of these is a distinct research community with its own conferences' worth of papers, and, critically, each one relieves one pressure while creating a new one somewhere else. That is why there is no single fix and instead a portfolio of partial ones.

## Subtheme 1: Shrinking and Evicting the KV Cache

### What It Is
The KV cache stores a key and a value vector for every past token. Two ways to make it smaller: store each number in fewer bits (quantization — instead of 16 bits per value, use 4 or 2), or store fewer tokens (eviction — decide some past tokens do not matter and delete their entries). A third, subtler route is to restructure *what* gets cached: if the model's architecture projects keys and values through a low-rank bottleneck, you cache the small bottleneck representation instead of the full vectors. All three trade fidelity or generality for bytes.

### What the Research Community Is Doing
DeepSeek-V3 (ISCA 2025, `isca-2025-130`) uses Multi-head Latent Attention, which compresses the per-token KV footprint from 516 KB (LLaMA-3.1-405B) down to 70 KB — a 7.4x reduction — by projecting keys and values into a shared low-rank latent space and caching only that. On the eviction side, ClusterKV (DAC 2025, `dac-2025-221`) rejects the common practice of permanently deleting tokens; instead it groups tokens into semantic clusters and recalls them at cluster granularity, holding a 1K–2K token budget for a 32K context while claiming negligible accuracy loss and delivering 2x lower latency and 2.5x higher throughput. TurboAttention (MLSys 2025, `mlsys-2025-025`) attacks the bit-width: it quantizes keys and values to INT4/INT2 with head-wise mixed precision — assigning 2-bit storage to the least important attention heads and 4-bit to the rest — and, crucially, runs the attention math directly on the quantized values rather than expanding back to 16-bit first, reaching up to 1.8x prefill and 1.7x decode speedup. KVO-LLM (DAC 2025, `dac-2025-176`) combines salient-token-aware quantization with pruning of both KV channels and tokens, co-designed with a multi-core accelerator, for 7.32x throughput and up to 8.38x energy efficiency.

But the most important paper here may be a skeptical one. "Rethinking Key-Value Cache Compression" (MLSys 2025, `mlsys-2025-007`) took four leading compression methods — KIVI, GEAR, StreamingLLM, H2O — and evaluated them not on toy benchmarks but under real serving stacks with FlashAttention and PagedAttention enabled. The result: the throughput advantage of compression *vanishes or goes negative* at batch sizes above 4 and cache lengths at or above 1,024 tokens. Worse, lossy compression made the model ramble — more than 20% of samples produced responses at least 1.5x longer, erasing the latency savings, and some individual samples degraded badly even when averages looked fine.

### The Tradeoff
Compression buys memory but spends accuracy, and the accuracy cost is not uniform — it hides in the tails, in specific samples and specific tasks, exactly where production systems get judged. Eviction is worse: once a token is gone, a later query that needed it cannot recover it, which is why the frontier is moving toward *recallable* schemes (ClusterKV) that compress-but-retain. And the `mlsys-2025-007` finding is a warning to the whole subtheme: a technique that looks like a win in isolation can be a loss once it composes with the fused kernels and paged memory that real servers already use.

## Subtheme 2: Reading Only the Tokens That Matter (Sparse Attention)

### What It Is
The premise of full attention — that every token must attend to every other — is empirically false most of the time. For any given query token, the vast majority of past tokens contribute near-zero weight after the softmax normalizes the scores. Sparse attention exploits this by computing dot products against only a chosen subset of past tokens. The subset can be *static* (fixed in advance — e.g., attend only to the most recent window plus a few "sink" tokens at the start) or *dynamic* (chosen per query at runtime based on which tokens look relevant). Static is cheap but rigid; dynamic is adaptive but costs work to decide what to skip.

### What the Research Community Is Doing
LServe (MLSys 2025, `mlsys-2025-047`) unifies both. It designates half of the attention heads as "streaming heads" that attend only to sink tokens plus a recent local window (a fixed Λ-shaped mask), while dynamically pruning KV pages hierarchically for the rest, all fused into a single CUDA kernel that handles both prefill and decode — yielding multiplicative speedups in both phases at 64K–512K token contexts without losing long-context accuracy on RULER and LongBench. SampleAttention (MLSys 2025, `mlsys-2025-060`) makes the sparsity fully adaptive per head and per input, driven by a runtime metric called Cumulative Residual Attention — the minimum fraction of attention probability mass a query must retain — and hits a 5.29x reduction in time-to-first-token at 1M-token context versus FlashAttention-2 while keeping over 99% of the full attention score. DIAS (DAC 2025, `dac-2025-023`) introduces distance-based irregular sparsity with approximate top-K selection via graph search, tested on Llama3-405B at 1M-token sequences with under 1% accuracy drop, and pairs it with a tree-structured processing-in-memory architecture for 75x speedup over prior LLM accelerators. H2EAL (ICCAD 2025, `iccad-2025-048`) observes that different heads have different sparsity patterns and co-designs a hybrid static/dynamic sparse scheme with a hybrid-bonding chip, reaching 5.2x–48.2x speedup and up to 73x energy efficiency at 0.87% average accuracy loss.

### The Tradeoff
Sparse attention's central risk is that "unimportant" is a prediction, and predictions fail. A token skipped because it looked irrelevant to the last few queries may be exactly the one a later query needs (the classic "needle in a haystack" retrieval failure). This is why the strongest work — SampleAttention's residual-mass metric, LServe's accuracy validation on multi-hop RULER — spends its effort proving the skipping is near-lossless on adversarial long-context benchmarks. Dynamic sparsity also has an overhead paradox: the computation to *decide* which tokens to skip can eat the savings from skipping them, which pushes designs toward coarse block-level rather than per-token decisions.

## Subtheme 3: Keeping the Data On-Chip (Fused Kernels)

### What It Is
A GPU has a memory hierarchy: slow, large HBM off to the side, and fast, tiny SRAM (registers and shared memory) next to the arithmetic units. A naive attention implementation computes the full score matrix, writes it to HBM, reads it back to normalize it with softmax, writes again, reads again to multiply by values — moving the same data across the slow boundary several times. A fused kernel (the FlashAttention lineage) restructures the math so a tile of the computation is loaded into SRAM once, and the scores, softmax, and value-weighting all happen there before the result is written out. The trick that makes this possible is that softmax can be computed incrementally, tile by tile, and the partial results merged — a property of the softmax rescaling operator that several papers exploit explicitly.

### What the Research Community Is Doing
LeanAttention (MLSys 2025, `mlsys-2025-037`) targets a specific failure of FlashAttention during decode: because decode processes one query token at a time, FlashAttention parallelizes only across batch and heads, leaving most of the GPU's streaming multiprocessors idle. LeanAttention proves the softmax rescaling operator is *associative*, which lets it chop the context dimension into fixed-size tiles and distribute them evenly across all compute units regardless of head or batch boundaries — reaching near-100% GPU occupancy and up to 2.53x speedup over FlashDecoding at 64K context. FlashInfer (MLSys 2025, `mlsys-2025-000`) attacks the fragmentation problem: real servers juggle ragged, paged, and tree-structured KV layouts, and every combination historically needed its own hand-written kernel. FlashInfer collapses them into one Block-Sparse Row format with a just-in-time compiler, cutting inter-token latency 29–69% versus compiler backends. FlexAttention (MLSys 2025, `mlsys-2025-015`) generalizes further, letting a researcher express any attention variant as two small Python functions (one that modifies scores, one that defines the mask) and compiling them into a fused Triton kernel — reaching under 1% paged-attention overhead versus 20–26% in vLLM. FastTree (MLSys 2025, `mlsys-2025-034`) exploits that many concurrent requests share a common prefix in a radix tree, converting per-query GEMV into batched GEMM to reuse the shared KV, for 2.2x system throughput. On the ASIC side, T-REX (ISSCC 2025, `isscc-2025-141`) reports that external memory access can dominate up to 81% of a transformer accelerator's energy, and by aggressively reusing data on-chip reaches 0.41–3.95 microjoules per token in 16nm silicon.

### The Tradeoff
Fusion is nearly free lunch on accuracy — FlexAttention and FlashInfer are numerically exact — which is why it is the most universally adopted technique. The cost is engineering surface area: every new attention variant, every new hardware generation, historically needed a new hand-tuned kernel, an O(variants × hardware) maintenance explosion. The recent work (FlexAttention, FlashInfer) is essentially a rebellion against that cost — trading hand-tuned peak performance for a compiler that generates good-enough kernels automatically. Fusion also does nothing about the fundamental *volume* of KV cache that must be read; it only ensures you read it once, not four times.

## Subtheme 4: Moving Attention to Where the Data Lives

### What It Is
If the bottleneck is moving the KV cache from memory to the compute units, one answer is to stop moving it — put small compute units inside or adjacent to the memory, so attention happens where the data already sits. This is near-data or in-memory processing (PIM). Variants: compute inside the DRAM (processing-in-memory), compute inside the SSD (in-storage), or bond a compute die face-to-face with a memory die (hybrid bonding) so the bandwidth between them is enormous. The physics motivation is direct: reading from a DRAM bank internally is far higher-bandwidth than shipping the bytes out over the pins and across the board to a GPU.

### What the Research Community Is Doing
Hybe (ISCA 2025, `isca-2025-080`) splits the two phases across two chips: the compute-heavy prefill runs on an H100 GPU, while the memory-bound decode is offloaded to lightweight NPUs provisioned with just enough compute to saturate their own HBM bandwidth, with partial KV tensors streamed to the NPU as they are produced — enabling million-token contexts that overflow GPU memory, at 2.1x speedup and 3.9x energy efficiency. InstAttention (HPCA 2025, `hpca-2025-068`) goes further down the hierarchy, executing the attention decode *inside* computational storage drives to exploit the SSD's internal NAND bandwidth and bypass the PCIe bottleneck entirely — 11.1x throughput over FlexGen for a 13B model. H2-LLM (ISCA 2025, `isca-2025-068`) and H2EAL (`iccad-2025-048`) both use hybrid bonding to stack high-capacity compute dies against DRAM, with H2-LLM reporting 2.72x geomean speedup over conventional in-die near-memory designs. Lincoln (HPCA 2025, `hpca-2025-083`) tackles consumer devices, repurposing the fast LPDDR interface to stream weights from Flash during prefill and doing near-Flash compute during decode, for up to 254x generation speedup over SSD-based systems. DIAS (`dac-2025-023`) and LP-Spec (ICCAD 2025, `iccad-2025-059`) build the sparse-attention and speculative logic directly into PIM banks. And MCBP (MICRO 2025, `micro-2025-096`) attacks all three bottlenecks — prefill GEMM, decode weight loading, KV loading — at bit-slice granularity, using content-addressable memory to find repeated bit patterns, for 9.43x speedup over an A100 at 22,740 GOPS/W.

### The Tradeoff
Near-data processing pays for its bandwidth win in inflexibility and cost. Compute placed inside DRAM or Flash is area-constrained and slow per unit — you get bandwidth but not much arithmetic — so these designs only help the memory-bound decode phase and can actively hurt the compute-bound prefill, which is why nearly every one of these papers is a *heterogeneous* design that keeps a real GPU or NPU for prefill and offloads only decode. Hybrid bonding and custom silicon also lock in a model shape at fabrication time; a change in attention architecture (say, a shift toward latent attention or SSM layers) can strand the hardware. These are bets that the workload will stay stable long enough to amortize a tape-out.

## Subtheme 5: Generating More Than One Token Per Pass (Speculative Decoding)

### What It Is
Autoregressive decoding is serial by construction: token N+1 depends on token N, so you cannot compute them in parallel, and each step pays the full cost of reading the entire KV cache. Speculative decoding breaks the serialism with a gamble. A small, fast "draft" model proposes several tokens ahead cheaply. Then the large "target" model verifies all of them in a single parallel forward pass — one KV-cache read instead of several. Tokens the target agrees with are accepted for free; the first disagreement is corrected and the rest discarded. If the draft is often right, you get multiple tokens per expensive pass. The catch is that acceptance rate is everything: a bad draft wastes both the draft compute and the verification.

### What the Research Community Is Doing
Smurfs (SC 2025, `sc-2025-386`) raises the acceptance rate by running several small draft models and taking a majority vote on their proposals, decoupling speculation from verification into a pipeline. SpecASR (DAC 2025, `dac-2025-354`) exploits a domain fact — in speech recognition the output is tightly constrained by the audio, so small and large models agree often — to adaptively size the draft and recycle prior drafts, reaching 3.04x–3.79x speedup with no accuracy loss. AASD (DAC 2025, `dac-2025-379`) targets multimodal models, generating drafts directly from the target model's own cached KV pairs via a "Target-Draft Attention" mechanism, for 2x speedup. SpecEE (ISCA 2025, `isca-2025-116`) composes speculation with early-exit: it uses a draft model to shrink the ~30,000-token vocabulary search space that an early-exit predictor must scan, cutting the predictor's overhead from 20%. And LP-Spec (ICCAD 2025, `iccad-2025-059`) builds a draft-token pruner into mobile PIM hardware, since speculation shifts the workload from memory-bound GEMV toward compute-bound GEMM — reaching 13.21x speedup and a 99.87x energy-delay-product improvement over mobile baselines.

### The Tradeoff
Speculative decoding converts a memory-bound problem into a compute-bound one — verifying K draft tokens in parallel does K times the arithmetic per pass but only one KV read. That is a good trade *when compute is idle*, which during decode it usually is. But it introduces new failure modes: rejected drafts are pure waste, and the acceptance rate depends on draft/target alignment that varies by task, which is why the recent work is all about raising or exploiting alignment (multi-model voting, domain conditioning, KV reuse). It also complicates the attention machinery — verifying a *tree* of candidate tokens rather than a linear sequence requires attention kernels that handle tree-structured masks, which is precisely why FlashInfer and FlexAttention invested in tree-attention support.

## How the Pieces Fit Together

The unifying observation across all 207 papers in this theme is a phase split. LLM inference has two stages with opposite hardware appetites: prefill (digesting the prompt) is compute-bound and parallel; decode (generating the answer) is memory-bandwidth-bound and serial. Almost every serious system now treats these as separate problems, and a large cluster of papers exists purely to manage the seam between them — WindServe (`isca-2025-034`) with stall-free cross-phase rescheduling for 4.28x TTFT improvement, Seesaw (`mlsys-2025-040`) re-sharding the model from tensor-parallel for prefill to pipeline-parallel for decode, gLLM (`sc-2025-018`) throttling prefill and decode tokens independently, LLMShare (`dac-2025-210`) doing design-space exploration to allocate different *hardware* to each phase, and Hybe (`isca-2025-080`) literally running the two phases on different chips. The phase split is the organizing principle of the whole field: once you accept that prefill wants FLOPs and decode wants bytes/second, every technique lands on one side or the other.

The techniques also compose, and their composition is where the real engineering lives. Sparse attention *reduces* the KV volume that fused kernels must read; quantization *shrinks* each entry so more fits in the SRAM tile; near-data processing *relocates* the read for whatever survives; speculative decoding *amortizes* the read across more output tokens. FlashInfer and FlexAttention exist precisely to make these stack — a single fused kernel that is simultaneously paged (for dynamic memory), block-sparse (for skipping), and tree-structured (for speculation). But composition is also where the field's warning lives: the `mlsys-2025-007` result showed that KV compression, which wins in isolation, can *lose* once PagedAttention and FlashAttention are already in the stack, because the fused kernels had already captured most of the available bandwidth. The bets that are being placed — and they are visible in the venue distribution, with MLSys dominating the algorithm/kernel work and ISCA/MICRO/HPCA/DAC/ICCAD dominating the silicon — are increasingly on *co-design*: MCBP, H2EAL, DIAS, and KVO-LLM all pair a specific attention-sparsity or KV-compression algorithm with a specific chip built to exploit exactly that pattern.

The deepest structural bet, though, is architectural. DeepSeek-V3's Multi-head Latent Attention and the arrival of hybrid Attention+SSM models — the target of Marconi (`mlsys-2025-004`), which had to invent an entirely new prefix-caching scheme because SSM layers update state in place and cannot be rolled back — signal that the field is not content to optimize the O(n²) attention it was handed. It is trying to change the exponent. A state-space model processes a sequence in linear time and constant memory per step, sidestepping the KV cache entirely; the price is a fixed-size recurrent state that cannot perfectly recall arbitrary past tokens the way full attention can. Hybrid models interleave a few full-attention layers (for exact recall) with many SSM layers (for cheap bulk processing), and that interleaving is the current frontier bet: keep just enough quadratic attention to stay accurate, and make everything else linear.

## What Remains Hard

- KV compression that provably preserves worst-case (not just average-case) accuracy under real serving stacks — the `mlsys-2025-007` finding that compression's benefit vanishes at batch>4 with PagedAttention enabled remains unaddressed, and no method yet guarantees the per-sample tail behavior that production requires.
- Dynamic sparse attention whose token-selection overhead is genuinely negligible at million-token contexts — current methods spend real compute deciding what to skip, and that cost grows with the very context length it is trying to tame.
- Prefix caching and state management for hybrid Attention+SSM models beyond exact-match reuse — Marconi enables it but the in-place-state-update problem means partial-prefix reuse remains far harder than for pure-attention models.
- A memory-hierarchy design that serves prefill (compute-bound) and decode (bandwidth-bound) well *without* physically separating them onto different chips, avoiding the KV-transfer overhead that phase-disaggregated systems spend most of their scheduling logic hiding.
- Quantized attention that runs softmax itself at low precision on tensor cores without dequantizing — TurboAttention started this, but 2-bit KV with maintained accuracy across diverse tasks (not just GSM8K/BBH averages) is unproven at scale.
- Co-designed accelerators that do not strand their silicon when the attention architecture shifts — a hybrid-bonded chip optimized for full-attention KV patterns may be worthless for latent-attention or SSM-heavy models, and no one has shown a reconfigurable near-data fabric that spans both.
- Speculative decoding with acceptance rates that stay high on genuinely hard, out-of-distribution generations — current gains lean on domain alignment (speech, multimodal) or multi-model voting, and the general-purpose long-form-reasoning case, where draft and target diverge most, is where speculation helps least.
