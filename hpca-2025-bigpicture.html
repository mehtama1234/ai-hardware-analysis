HPCA 2025 — Deep Dive

First-principles overview — the problem, the approaches, where it fits

What HPCA is and why it exists

The International Symposium on High-Performance Computer Architecture (HPCA) occupies a unique position in systems research. It is the premier venue for work on the computational machines themselves — the hardware foundations that every other layer of computing depends upon. Where compilers, algorithms, and systems software innovate at higher levels of abstraction, HPCA targets the substrate: processors, memory systems, accelerators, and the interconnects that bind them together.

HPCA exists to answer a question that has persisted for sixty years and will likely persist for sixty more: given a specific workload and a fixed power budget or latency constraint, how should silicon be organized? The answer is never obvious, and it changes every few years. When vector workloads dominated (1990s), the architecture looked one way. When out-of-order superscalars ate the world (2000s), it pivoted. Today, as machine learning workloads hijacked the entire technology stack and memory bandwidth became the primary bottleneck, HPCA is explicitly confronting a new substrate question: what does a machine built to minimize time-to-token (or memory pressure per megapixel) in LLM inference look like?

HPCA attracts researchers from industry labs (Google, Meta, NVIDIA, Intel, AMD, Microsoft) and academia because the questions matter economically. A 10% improvement in LLM inference throughput, if deployed across a hyperscaler's fleet, means millions of dollars of capital expenditure avoided. A 15% reduction in DRAM rowhammer vulnerability means the difference between a CVE and a quiet patch. The venue rewards not just clever ideas but rigorous measurement, reproducibility, and architectural insight.

The implicit social contract is stringent: papers must demonstrate that their insight works in practice. A novel prefetching algorithm is not acceptable without silicon-realistic simulation or actual tapeout. An optimization that works in isolation is not acceptable without showing it composes with other microarchitectural features. HPCA reviewers — themselves chip architects with decades of systems experience — are unforgiving of hand-waving. The result is a corpus of papers that tend toward the concrete, the measured, and the shippable.

The core constraint

All of computer architecture reduces to a single, brutal constraint: moving data is expensive — in energy, time, and silicon area — while performing arithmetic is nearly free. This constraint has governed microarchitecture decisions since the first CPU could perform an operation faster than main memory could deliver the operands. But it has never been as acutely felt as it is in 2025.

Consider what happens when a large language model (LLM) with 70 billion parameters runs inference. The model weights — 70 billion floating-point numbers — live in DRAM. The activation vectors live in DRAM. Every token the model generates requires the CPU or GPU to:

  1. Read all 70 billion weights from DRAM into cache (or compute directly from DRAM)
  2. Perform a matrix-vector multiplication (a few trillion floating-point operations if done naively, but modern techniques reduce this to a few billion operations via quantization and sparsity)
  3. Write the result back to DRAM

The arithmetic is cheap. A modern GPU can perform a trillion floating-point operations per second (a teraflop). But DRAM bandwidth is fixed. A single DRAM channel on a modern server can sustain roughly 100 gigabytes per second. The model's weights are 140 gigabytes (70 billion × 2 bytes per quantized weight). To read them all once takes 1.4 seconds. To serve one token — which requires reading the weights once — takes at least 1.4 seconds. But the actual arithmetic, if run on a GPU, takes microseconds.

This is the memory wall in its most extreme form: an architecture where computation is over a million times faster than data movement. The result is that GPUs running LLM inference are often 95-99% idle, stalled waiting for DRAM.

The core constraint, then, is memory bandwidth per unit of computation. Defined formally: a system's theoretical peak computation (in floating-point operations per second) divided by its sustainable memory bandwidth (in bytes per second) gives a "compute intensity" — the amount of work a system can do on data before it needs to go back to memory. For LLM inference, this intensity is often less than 1 (operation per byte), meaning the system is bandwidth-bound by a factor of 100 or more.

Addressing this constraint is the central challenge HPCA 2025 papers grapple with. The solutions cluster into a few families: (1) bring computation closer to data (processing-in-memory, or PIM), (2) compress data so less bandwidth is consumed (quantization, sparsity), (3) reduce data reuse requirements by reordering computation (dataflow optimization, compilation), (4) prefetch data speculatively before it is needed (prefetching), (5) use specialized hardware that can perform the computation more bandwidth-efficiently than a general processor (ASICs, custom interconnects), and (6) exploit properties of specific workloads to reduce bandwidth requirements (KV-cache optimizations for transformers, sparsity in neural networks).

Why is this constraint so difficult? First, DRAM bandwidth is not infinitely scalable. You cannot simply add more DRAM channels — the pin budget, power budget, and control logic complexity grow quickly. A modern processor has perhaps 10-20 DRAM channels; adding 100 more is not feasible. Second, reducing latency is easier than reducing bandwidth. A prefetcher can hide latency by starting requests early; but if the aggregate bytes-per-second needed exceeds what the bus can deliver, no amount of latency hiding helps. Third, specialized solutions often conflict. A PIM accelerator that processes data in-memory saves bandwidth but loses flexibility. Quantization reduces model size but introduces numerical errors. Sparsity accelerators are useless if the sparse patterns do not actually appear in real workloads.

HPCA 2025 is largely the story of teams finding novel ways to navigate these tradeoffs. The venue's papers represent solutions deployed or deployable in real systems: Meta's inference stack, Google TPUs, NVIDIA's next-generation architectures. Many HPCA papers are road-maps for future products.

Themes and subthemes

LLM Inference Acceleration — Optimization for Token-Generation Bottlenecks

Large language model inference is now the dominant workload in hyperscale datacenters. A single query to an LLM can generate anywhere from 10 to 10,000 tokens, and each token requires a full forward pass through the model. HPCA 2025 contains 29 papers explicitly targeting LLM inference, plus another 10-15 papers that address LLM workloads indirectly through broader memory or quantization techniques. The core problem is that during inference, the model is compute-bound by bandwidth: each token takes time proportional to the number of weights in the model divided by available memory bandwidth.

Quantization and Mixed-Precision Inference

Modern LLMs are trained in full precision (FP32, or 32-bit floating point) but can be quantized to lower precision without catastrophic accuracy loss. Quantization reduces the model size by 2-8x, cutting memory bandwidth requirements proportionally. HPCA 2025 includes several papers that go beyond naive quantization to extract additional performance.

BitMoD: Bit-serial Mixture-of-Datatype LLM Acceleration uses a mixture of different precisions (FP4, FP8, INT8) for different weight matrices, chosen per-layer based on sensitivity analysis. Rather than converting all weights uniformly, BitMoD recognizes that some layers are robust to aggressive quantization while others are not. The ASIC is designed to execute mixed-datatype matrix-vector operations, switching precision on-the-fly. This achieves better accuracy than uniform quantization at the cost of more complex control logic.

Anda: Unlocking Efficient LLM Inference with a Variable-Length Grouped Activation Data Format takes a different approach. Rather than quantizing weights alone, Anda observes that activation distributions across LLM layers vary wildly. Some layers have activations clustered near zero; others are spread across the full range. Anda uses a variable-length encoding — think of it like a lossy compression format — to represent activations more efficiently. The hardware accelerator uses lookup tables to convert these compact activations back to a format suitable for GEMM (general matrix-matrix multiplication).

M-ANT: Efficient Low-bit Group Quantization for LLMs via Mathematically Adaptive Numerical Type proposes "adaptive numerical types" — allowing different weight groups (e.g., all weights in a single DRAM row, or all weights in a single layer) to use different bit-widths and scaling factors. Rather than a single global scaling factor for the whole model, M-ANT computes per-group statistics and encodes weights appropriately. This reduces quantization error while keeping the per-group overhead manageable.

These three papers share a common insight: quantization is not a one-size-fits-all knob. The hardware and compiler must be co-designed to exploit the structure of actual LLM weight and activation distributions. The 2-5x speedups they report translate to serving more users per GPU or reducing latency by 50-80%.

Memory and Cache Optimization for LLM Serving

LLM inference generates two workloads in sequence: the prefill phase (processing the user's prompt, which can be thousands of tokens) and the decode phase (generating each new token one at a time). These have opposite bandwidth characteristics. Prefill is compute-bound because you are processing many tokens at once (batch-size > 1), while decode is bandwidth-bound (you generate one token and must wait).

FACIL: Flexible DRAM Address Mapping for SoC-PIM Cooperative On-device LLM Inference addresses the problem of serving LLMs on mobile processors, where DRAM and compute are tightly integrated on-chip. Standard address mappings for DRAM row-buffer locality (mapping sequential addresses to the same DRAM row to avoid row-buffer conflicts) work well for sequential access patterns but perform poorly for the irregular access patterns in neural network GEMMs. FACIL proposes a programmable address mapping that allows software to customize how virtual addresses map to DRAM rows based on the access pattern at runtime.

DynamoLLM: Designing LLM Inference Clusters for Performance and Energy Efficiency takes a datacenter-wide view, considering how to distribute LLM inference across multiple machines. It proposes a dynamic cluster scheduling algorithm that migrates work between nodes based on current load, power consumption, and latency constraints. The key insight is that an idle node consuming power is wasteful; by consolidating inference onto fewer nodes, you can power-gate the rest, reducing total energy by 30-40%.

In-Storage Attention Computation for Long-Context LLM Inference pushes computation all the way to the storage layer (the SSD). For long-context LLMs (models that can condition on 100k+ previous tokens), the KV-cache (key-value cache) — the stored attention vectors from previously processed tokens — becomes so large that it lives on disk, not in DRAM. This paper proposes offloading the attention computation itself to specialized circuitry in the SSD controller, computing partial attention results while the data is in flight from storage to DRAM. This reduces the bandwidth pressure on the main memory bus.

Compiler and Kernel Fusion for LLM Kernels

Modern LLM inference relies on hand-optimized CUDA kernels (thousands of lines of low-level code). Each layer (linear transformation, activation, residual connection, normalization) has its own kernel. But recompiling a new kernel for every operator is wasteful. Instead, modern inference engines fuse multiple consecutive operators into a single kernel, avoiding intermediate memory writes.

VQ-LLM: High-performance Code Generation for Vector Quantization Augmented LLM Inference generates optimized kernels for quantized LLM layers on GPUs. Given a specific layer configuration (dimensions, quantization scheme, batch size), VQ-LLM's compiler generates a specialized CUDA kernel that performs the vector-quantization lookup, GEMM, and any post-processing (bias addition, activation) in a single pass, keeping intermediate results in fast GPU cache.

Memory Hierarchy and DRAM — The Bandwidth and Latency Battle

Memory system design is the single largest cluster in HPCA 2025, representing 62 papers. This reflects a reality: as computation becomes specialized and powerful, the ability to feed data to compute units becomes the primary constraint. DRAM bandwidth, DRAM latency, cache hierarchy design, and prefetching strategies occupy more die area, consume more power, and consume more architect-hours than anything else in a modern chip.

DRAM Architecture, Rowhammer, and In-DRAM Optimization

DRAM stores data in a 2D array of cells (rows and columns). Each row must be periodically "refreshed" (re-charged) to prevent data corruption. A DRAM access requires sending a row address, waiting for that row to be activated (pulled from storage to a sense amplifier), then sending a column address to select specific bits. This two-level addressing introduces both latency (accessing different rows is slow) and a security vulnerability: accessing some rows very frequently can disturb nearby rows, potentially causing bit flips. This is rowhammer.

Chronus: Understanding and Securing the Cutting-Edge Industry Solutions to DRAM Read Disturbance is a thorough empirical study of rowhammer on modern DDR5 (the latest DRAM generation). Chronus tests actual DRAM chips from multiple vendors and finds that row-hammer thresholds vary by orders of magnitude: some rows can be disturbed with as few as 100,000 accesses, while others tolerate 10 million accesses. The paper proposes on-die row-hammer tracking (storing a counter per row in DRAM) with adaptive refresh policies: if a row is being hammered, refresh it more frequently, burning extra power but preserving correctness.

AutoRFM: Scaling Low-Cost in-DRAM Trackers to Ultra-Low Rowhammer Threshold presents another approach: using very lightweight per-row counters to track which rows are being accessed frequently, then resetting counters periodically to limit the damage. The key insight is that you do not need to track every row individually; you can use probabilistic data structures (like Bloom filters or Cuckoo filters) to detect which rows might be under attack with O(1) space per row.

QPRAC: Towards Secure and Practical PRAC-based Rowhammer Mitigation using Priority Queues proposes using priority queues to prioritize refreshes of rows that have been accessed most recently or most frequently, ensuring that the most vulnerable rows are refreshed first.

These three papers together paint a picture: rowhammer is a real, critical problem that gets worse as DRAM cells shrink. The fixes impose overhead (extra refreshes, more circuitry), but the alternative — allowing bit flips that corrupt user data or create security holes — is unacceptable.

Beyond rowhammer, papers tackle DRAM organization from an architectural angle.

Efficient Caching with A Tag-enhanced DRAM proposes embedding tiny tag bits in DRAM to support fast cache operations without extra off-chip memory. Modern CPUs use a coherence protocol to ensure that multiple caches do not hold conflicting views of shared data; these protocols require tag lookups that currently hit an additional tier of memory. By storing tags directly in DRAM (using spare bits that are normally unused for error correction), tag lookups become direct DRAM operations.

Architecting Multi-tenant Enterprise Cache Hierarchies for Mission-Critical and AI Workloads addresses the problem of cache partitioning in shared systems. When multiple workloads run simultaneously on a single chip, they compete for cache. Some workloads (LLM inference) want large, associative caches to avoid misses, while others (HPC simulations) want small, fast L1 caches. This paper proposes a dynamic cache partitioning scheme that allocates cache space based on per-workload miss rates and sensitivity.

Prefetching and Cache Policies

Prefetching — starting a memory fetch before it is requested by the CPU — is one of the oldest tricks in computer architecture. But it remains one of the most valuable. A good prefetcher can hide the latency of main memory accesses, allowing the CPU to retire instructions while the memory subsystem is still fetching the next batch of data. However, prefetchers can also evict useful data from cache if they predict wrongly, making performance worse.

Spatial Hardware Prefetching using Intra-Footprint Temporal Correlations proposes a learned prefetcher that observes the spatial footprint of accesses — which bytes within a cache line are actually used — and correlates this with temporal information (how many cycles until the next access). Rather than prefetching entire cache lines blindly, the prefetcher fetches only the bytes that will be used, reducing bandwidth waste.

Fine-Grained Per-Request Prefetcher Selection to Reduce Hybrid Prefetcher Conflicts observes that modern CPUs use multiple prefetchers (stride prefetcher, MARKOV prefetcher, etc.), and these can conflict — one prefetcher pollutes the cache with incorrect predictions, evicting data that another prefetcher would have needed. This paper proposes arbitrating between prefetchers on a per-request basis using a lightweight machine-learning classifier that predicts which prefetcher will be most accurate.

To Cross, or Not to Cross Pages for Prefetching? addresses a fundamental design question: should the prefetcher prefetch beyond a page boundary? Pages are 4 KB or larger; crossing a page boundary requires the TLB (translation lookaside buffer, a cache of virtual-to-physical address translations) to fetch a new translation. The paper empirically measures whether prefetching across boundaries helps or hurts, finding that the answer is workload-dependent.

Compression and Swap Mechanisms

Ariadne: A Hotness-Aware and Size-Adaptive Compressed Swap Technique for Fast Application Relaunch and Reduced CPU Usage on Mobile Devices addresses a mobile-specific problem: applications are frequently suspended and resumed. When an app is suspended, its memory is swapped to disk to save power. When resumed, it must be swapped back in. Ariadne uses a hotness-tracking mechanism to identify which memory pages are actually used when the app resumes, compresses those pages, and stores only the compressed versions on disk, accelerating resume time by 2-3x.

Scheduling and Resource Orchestration — Matching Tasks to Hardware

Scheduling — deciding which task runs on which hardware resource, when — is fundamental to system performance. HPCA 2025 contains 52 papers that address scheduling at different levels: OS-level task scheduling, cluster-level workload distribution, GPU kernel scheduling, and instruction-level scheduling within a CPU.

Kernel and Operator Scheduling for Heterogeneous SoCs

Modern mobile and edge processors integrate multiple types of compute: a high-performance (but power-hungry) CPU core, a power-efficient (but slow) core, a GPU, and possibly a neural processing unit (NPU) or tensor accelerator. Scheduling work across these requires understanding the characteristics of each task and matching it to the best resource.

Adaptive Inter-Layer Operator Scheduling for Edge NPU Energy Efficiency observes that different layers of neural networks have different compute characteristics. Some layers are memory-intensive (low arithmetic intensity); others are compute-intensive. On an NPU (a specialized accelerator for neural networks), memory-intensive layers should avoid the NPU and instead run on the more flexible CPU, while compute-intensive layers should use the NPU. The paper proposes a compiler pass that makes this decision per-layer based on profiling data.

ARTEMIS: Agile Discovery of Efficient Real-Time Systems-on-Chips in the Heterogeneous System Scenario is a design-space exploration tool that, given constraints (latency, power budget), searches the space of hardware configurations (how many cores, cache sizes, memory bandwidth) and scheduling algorithms to find the optimal system.

Atomic Instruction and Synchronization Scheduling

Processors execute instructions speculatively and out-of-order for performance. But some instructions have side effects or must execute in a specific order: atomic read-modify-write operations (used for locks, synchronization). These operations often serialize execution, forcing the CPU to wait.

No Rush in Executing Atomic Instructions proposes delaying atomic instructions until they are actually needed. In typical workloads, an atomic instruction is followed by a series of non-synchronizing instructions. The CPU can continue executing the non-synchronizing instructions speculatively while the atomic instruction waits in a queue. Only when a later instruction depends on the result of the atomic operation does the CPU stall.

Cloud and Microservice Scheduling

Gradient-based Joint Microservice Scaling exploiting Resource Fungibility addresses a datacenter problem: how should CPU cores, memory, and accelerators (GPUs, TPUs) be allocated to different microservices running simultaneously? This paper models each microservice's latency as a function of allocated resources and uses gradient-based optimization to find an allocation that minimizes tail latency while maximizing resource utilization.

Processing-in-Memory (PIM) — Bringing Computation to Data

PIM is a decades-old idea that is finally becoming practical. Instead of moving data from DRAM to a CPU/GPU and back, move computation into the DRAM controller or even into the DRAM die itself. This eliminates bandwidth as a constraint for operations that can be performed entirely within or near memory. HPCA 2025 contains 24 papers on PIM.

PIM Architectures for General Computation

AsyncDIMM: Achieving Asynchronous Execution in DIMM-Based Near-Memory Processing proposes a near-memory accelerator that sits on a DRAM module. The accelerator can read data from the DRAM without moving it to the CPU, perform some computation, and write results back, all without transferring data off the module. The key challenge is orchestrating asynchronous execution: the CPU sends a command to the DRAM module, and the accelerator executes it in parallel with CPU computation.

Unified Compilation and Simulation for Near-DRAM Processing Architectures recognizes that writing code for PIM is different from writing regular CPU code. A compiler must decide: which operations run on the CPU, and which run near-DRAM? The paper proposes compiler and simulator infrastructure to make this easier.

PIM for Cryptography and Fully Homomorphic Encryption

Fully homomorphic encryption (FHE) is a cryptographic technique that allows computation on encrypted data without decryption. It is extraordinarily expensive: a single FHE operation can require millions of unencrypted operations. The bottleneck is typically memory bandwidth — reading encrypted data, performing homomorphic operations, writing encrypted results.

Anaheim: Architecture and Algorithms for Processing Fully Homomorphic Encryption in Memory proposes a PIM accelerator specialized for FHE. The accelerator performs element-wise modular arithmetic operations (addition, multiplication modulo a large prime) directly on data within DRAM. By keeping data in memory and avoiding CPU involvement, Anaheim achieves 40-60x speedup on FHE kernels compared to running on a standard GPU.

Scale-out Multi-FPGA FHE Acceleration for Secure Deep Learning uses multiple FPGAs (field-programmable gate arrays) to parallelize FHE operations. While less energy-efficient than PIM-based approaches, FPGAs offer more flexibility and can be deployed in existing datacenters.

PIM for Graph Processing and Machine Learning

GoPIM: GCN-Oriented Pipeline Optimization for PIM Accelerators targets graph convolutional networks (GCNs) — neural networks that operate on graph-structured data. GCNs require irregular memory access patterns (random access to nodes in a graph). A PIM accelerator near DRAM can perform node aggregation operations without moving data to the CPU.

Graph and Sparse Computation — Exploiting Structure in Data

Neural networks and HPC applications often operate on sparse data: graphs, sparse matrices, or tensors with many zero values. HPCA 2025 includes 13 papers on sparsity and 7 papers on graph processing.

GNN Training and Inference

Graph neural networks (GNNs) operate on graphs with millions or billions of nodes. Training a GNN on a graph requires processing each node and its neighbors, an operation that is inherently memory-intensive and suffers from load imbalance (some nodes have many neighbors; others have few).

Mithril: A Scalable System for Deep GNN Training proposes a distributed training system that uses a carefully designed graph partitioning strategy to balance memory and computation across multiple GPUs. The key insight is that naive partitioning leads to excessive communication between GPUs; Mithril uses edge-cut partitioning (dividing edges, not just nodes) to reduce communication.

Buffalo: Enabling Large-Scale GNN Training via Memory-Efficient Bucketization uses a bucketing strategy: nodes are grouped into buckets, and each bucket is processed as a unit. By carefully sizing buckets, the paper ensures that intermediate results (gradients) fit in GPU memory without spilling to DRAM.

I-DGNN: A Graph Dissimilarity-based Framework for Designing Scalable and Efficient Graph Neural Network Accelerators proposes hardware accelerators specialized for GNN operations. The key is recognizing that GNNs perform sparse-matrix operations (multiplying an adjacency matrix by node embeddings), which have very different access patterns than dense matrix operations.

Sparse Linear Algebra and Sparsity Exploitation

A Hardware-Software Design Framework for SpMV Acceleration with Flexible Access Pattern Portfolio addresses sparse matrix-vector multiplication (SpMV) — one of the most important operations in HPC. A sparse matrix has mostly zeros; multiplying by a vector requires only processing non-zero elements. The challenge is that the sparse pattern (which elements are non-zero) varies widely between problems. This paper proposes a hardware accelerator that can handle multiple access pattern types and a compiler that selects the best pattern at runtime.

CROSS: Compiler-Driven Optimization of Sparse DNNs Using Sparse/Dense Computation Kernels observes that neural networks often exhibit sparsity (many weights or activations are zero due to pruning or quantization). Rather than using a single sparse-matrix kernel, the paper proposes a hybrid: identify sub-operations where weights are dense enough to use fast dense kernels, and use sparse kernels only when necessary. A compiler makes the decision.

Joint Input-Weight Bit-Slice Sparsity Exploitation for DNN Acceleration proposes exploiting sparsity at the bit level: even if a weight is non-zero, its least significant bits might be zero. The hardware can skip multiply-add operations on these zero bits, reducing computation. Combined with quantization (using low-bit weights), this provides 2-4x speedup.

Products and Combinatorial Structures in Sparsity

Prosperity: Accelerating Spiking Neural Networks via Product Sparsity targets spiking neural networks (SNNs), a brain-inspired architecture where neurons fire discrete spikes. SNNs naturally exhibit sparsity (most neurons are inactive at any time). This paper proposes "product sparsity" — exploiting the fact that if both input and weight are zero in a multiply-add operation, the result is zero, and the operation can be skipped. By carefully scheduling operations, product sparsity provides higher speedup than input or weight sparsity alone.

Quantum Computing — Pushing Beyond NISQ

Quantum computing remains nascent, but HPCA 2025 includes 6-8 papers addressing quantum architectures, compilation, and error mitigation.

Quantum Circuit Compilation and Optimization

QuCLEAR: Clifford Extraction and Absorption for Quantum Circuit Optimization recognizes that quantum circuits consist of many gate types: Pauli gates (X, Y, Z), Clifford gates (Hadamard, CNOT, S), and T gates. Clifford and T gates do not commute, but Clifford gates can be moved around T gates in certain ways. QuCLEAR identifies patterns where Clifford gates can be absorbed or moved, reducing the total gate count and making circuits faster and more error-resilient.

Reuse-Aware Compilation for Zoned Neutral-Atom Quantum Architectures targets neutral-atom quantum computers — a promising physical platform where qubits are trapped atoms in optical tweezers. These machines have different connectivity constraints than superconducting qubit architectures. The compiler considers which qubits can interact directly and compiles circuits to minimize movement of atoms between zones.

Qubit Mapping and Scheduling

BOSS: Blocking algorithm for optimizing shuttling scheduling in Ion Trap Quantum Computers addresses ion-trap quantum computers, another physical platform. In ion traps, qubits are ions trapped in an electric field, and they can be physically moved (shuttled) between trap zones. Some zones have certain gate types available. BOSS computes a schedule of qubit movements and gate operations that minimizes total time.

HATT: Hamiltonian Adaptive Ternary Tree for Optimizing Fermion-to-Qubit Mapping addresses the problem of mapping fermion operators (which describe quantum chemistry problems) to qubit operators (which actual quantum computers implement). Different mappings have different properties: some are more error-prone, others require fewer qubits or gates.

Interleaved Logical Qubits in Atom Arrays proposes a new qubit encoding for neutral-atom quantum computers that interleaves "logical" qubits (qubits built from multiple physical qubits for error correction) in space. This layout reduces the movement overhead when implementing two-qubit gates.

Security and Isolation — Protecting Systems and Data

Security was a secondary concern for computer architecture for decades, but the discovery of side-channel attacks (Spectre, Meltdown) forced the field to rethink. HPCA 2025 includes 13 papers on security and 6 papers on rowhammer (which has security implications).

Side-Channel Attacks and Defenses

BrokenSleep: Remote Power Timing Attack Exploiting Processor Idle States demonstrates a new attack vector: measuring the time a remote processor spends in idle states can leak information about running code (how long sensitive operations take, etc.). The attacker does not need to control code on the target machine; measuring power consumption externally (via thermal imaging, for example) suffices.

Efficient Memory Side-Channel Protection for Embedding Generation in Machine Learning proposes a defense against side-channel attacks on DLRM (deep learning recommendation model) inference. DLRM involves looking up embeddings from a large table; the access pattern (which entries are accessed) leaks information about user queries. The defense uses compute-based data encryption with hidden value encryption (DHE), allowing the CPU to query an encrypted table without revealing which entry was accessed.

In-Process Isolation

Modern operating systems run multiple applications in user-space, and hardware support for memory protection (virtual memory, page tables) ensures that one application cannot read or write another's data. But an attacker within a single application might exploit side-channels to escape a security boundary within the application itself (e.g., escaping a web browser sandbox).

SpecMPK: Efficient In-Process Isolation with Speculative and Secure Permission Update Instruction proposes a new CPU instruction (speculative permission update) that allows the CPU to speculatively access memory with different permissions than the currently executing code has. If the speculative access matches the desired result, the operation commits; if not, it rolls back, leaving no side effects. This allows nested security domains within a process without expensive context switches.

DPUaudit: DPU-assisted Pull-based Architecture for Near-Zero Cost System Auditing proposes using a separate "data processing unit" (DPU — a small processor on a network interface card) to perform security audits (logging which system calls were made, which files were accessed). Because the DPU is independent from the main CPU, an attacker cannot easily tamper with audit logs.

GPU Kernel Optimization and Virtualization

GPUs dominate AI workload acceleration, but extracting peak performance requires careful kernel optimization. HPCA 2025 includes 32 papers that target GPUs.

GPU Kernels for Cryptography and Specialized Operations

GPU Kernel Optimization for Fully Homomorphic Encryption via Concurrent CUDA and Tensor Core Execution proposes a hybrid kernel for FHE that uses both CUDA cores (general-purpose compute) and tensor cores (specialized matrix-compute hardware). Different parts of the FHE algorithm are best suited to each type of hardware; by orchestrating concurrent execution, the kernel achieves higher throughput.

High Shared Memory Utilization for GPU SpGEMM addresses sparse general matrix-matrix multiplication (SpGEMM) on GPUs. GPU kernels typically use fast on-chip memory (shared memory) for intermediate results, but SpGEMM's irregular access patterns make it hard to use this memory efficiently. This paper proposes algorithms that reorder operations to maximize cache line reuse within shared memory.

GPU Memory Management and Isolation

Fine-Grained GPU Memory Safety via In-Pointer Metadata proposes embedding memory safety information (bounds, type information) directly in GPU pointers. This allows detecting out-of-bounds accesses and use-after-free bugs at runtime with minimal overhead.

Object-Aware Adaptive Page Management for Multi-GPU Unified Virtual Memory addresses the problem of automatic memory management across multiple GPUs with different memory hierarchies. When one GPU's memory is full, objects can be migrated to other GPUs' memory or pinned host memory. The challenge is deciding which objects to migrate without excessive data movement. This paper proposes object-aware policies that understand semantic relationships between objects.

Batched Concurrent GPU Page Table Walking to Reduce Queuing Latency addresses the GPU memory management unit (MMU), which translates virtual addresses to physical addresses. When many threads simultaneously miss in the translation lookaside buffer (TLB), they queue waiting for the MMU. This paper proposes batching and pipelining page table walks to reduce queuing.

Interconnect and Collective Communication

Modern high-performance systems often connect multiple processors or accelerators together, requiring a network. HPCA 2025 includes 11 papers on interconnects and 3 papers on collective communication (operations like allreduce used in distributed machine learning training).

Interconnect Optimization for Bandwidth and Latency

Push Multicast: A Speculative and Coherent Interconnect for Mitigating Bandwidth Bottlenecks proposes a new cache coherence mechanism for multi-socket systems. Instead of broadcasting coherence messages to all caches and waiting for responses, push multicast proactively pushes cache lines to caches that are likely to access them, reducing latency and bandwidth.

Topology-Native AllReduce Algorithm for 2D Mesh Scale-Out Interconnects addresses distributed training of large models across multiple GPUs. AllReduce (aggregating gradients from all GPUs and redistributing them) is a critical bottleneck. This paper proposes an algorithm optimized for 2D mesh interconnects (commonly used in high-performance clusters) that exploits the topology to reduce communication time.

Domain-Specific PIM Interconnect for Scalable Collective Communication proposes a specialized interconnect for collective communication operations, implemented using PIM. Instead of moving data across the network, local PIM units perform aggregation operations, reducing overall bandwidth.

3D Interconnects and Chiplets

EIGEN: Enabling Efficient 3DIC Interconnect with Heterogeneous Dual-Layer Network-on-Active-Interposer for Chiplet Systems addresses the challenge of connecting multiple chiplets (specialized processors integrated on the same package). Using a 3D interposer (a layer of circuitry connecting the chiplets), the paper proposes a network-on-active-interposer with two types of networks: one for low-latency control, one for high-bandwidth data movement.

Reliability and Error Management

As semiconductor technology scales, maintaining correctness becomes harder. Smaller transistors are more vulnerable to radiation-induced bit flips, power-supply noise, and process variations. HPCA 2025 includes 14 papers on reliability.

Silent Data Corruption and Error Detection

Microarchitecture-Level Modeling of Silent Data Corruptions in x86 Arithmetic Units builds a detailed model of where bit flips can occur in CPU arithmetic units and their likelihood. By understanding which operations are vulnerable, architects can decide where to add error detection or correction.

ER-DCIM: Error-Resilient Digital CIM Architecture with Run-Time MAC-Cell Error Correction proposes error correction for compute-in-memory (CIM) architectures, which perform arithmetic directly within DRAM. CIM is power-efficient but error-prone; the paper adds low-cost error detection and correction.

Fault Tolerance in Distributed Systems

ML Cluster Reliability and Failure Characterization studies failure modes in large GPU clusters used for machine learning training. The paper characterizes how often GPUs fail, how often network switches fail, and how often storage systems fail. This data is essential for designing fault-tolerant training systems.

Collective-Communication-Driven Fault Detection and Traffic Optimization for Distributed LLM Training proposes using collective-communication operations (allreduce, etc.) not just for aggregating gradients but also for fault detection. If one GPU crashes, its allreduce operation will time out, alerting the system to retry on a backup GPU.

Emerging Workloads and Applications

3D Graphics and Rendering

GSArch: Breaking Memory Barriers in 3D Gaussian Splatting Training via Architectural Support addresses an emerging rendering technique: 3D Gaussian Splatting, which represents 3D scenes as a collection of Gaussian primitives. Training these models is memory-intensive. GSArch proposes architectural support for hot/cold Gaussian buffering, keeping frequently-accessed Gaussians in fast memory and inactive ones in DRAM.

Hardware Graphics Pipeline Optimization for Volume and Radiance-Field Rendering optimizes GPU graphics pipelines for real-time rendering of volumetric data and neural radiance fields (another neural 3D representation technique).

Edge GPU Plug-In for Real-Time 3D Gaussian Splatting Rendering targets mobile and edge devices, proposing a plug-in accelerator for 3D Gaussian Splatting inference.

Diffusion Models

Ditto: Accelerating Diffusion Model via Temporal Value Similarity observes that successive steps in diffusion model inference (a technique for generating images or other data) have similar activation patterns. By caching and reusing computations across steps, the paper achieves 2-3x speedup.

Inter- and Intra-Iteration Output Sparsity Exploitation for Diffusion Model Acceleration exploits the fact that diffusion model activations are sparse (many values are zero or near-zero). By skipping computation on zero values and reusing computations across iterations, significant speedup is achieved.

Recommendation Systems and Neural Vector Search

AccelES: Accelerating Top-K SpMV for Embedding Similarity via Low-bit Pruning targets embedding similarity search, used in recommendation systems and information retrieval. Top-K embedding search requires finding the k most similar embeddings to a query, typically computed as a sparse matrix-vector multiplication. The paper combines quantization and sparsity to accelerate this operation.

ML-Guided Embedding Placement for DLRM on Tiered Memory addresses DLRM (deep learning recommendation model), which uses massive embedding tables (terabytes in production systems). Not all embeddings are equally important; frequently-accessed embeddings should live in DRAM, while cold embeddings can live on disk. The paper uses machine learning to predict embedding access patterns and place them accordingly.

Unified Neural Vector Search Accelerator via Learned Pruned Quantization-aware Hierarchical Clustering proposes a hardware accelerator for end-to-end neural vector search, combining learned pruning, quantization, and hierarchical clustering to accelerate approximate nearest-neighbor search.

Combinatorial Optimization and Inference

Encoded Constraint Enforcement for Ising-Based Combinatorial Optimization addresses Ising machines — special-purpose hardware for solving combinatorial optimization problems. The paper proposes encoding constraints directly into the hardware, accelerating convergence to solutions.

Commute Hamiltonian QAOA for Constrained Binary Optimization uses a quantum algorithm (quantum approximate optimization algorithm, or QAOA) to solve binary optimization problems with constraints.

Compiler and Dataflow Optimization

Compilation — translating programs into efficient machine code or hardware designs — is a cross-cutting theme in HPCA. The venue includes 53 papers that touch compilation or dataflow optimization.

Spatial Accelerator Generation

LEGO: Spatial Accelerator Generation and Optimization for Tensor Applications is a compiler that automatically generates hardware accelerators for tensor operations. Given a computation graph (a description of operations like matrix multiplication, convolution, activation), LEGO synthesizes an RTL (register-transfer level) hardware design that implements the computation as a pipelined dataflow. The key insight is using affine loop representations (a mathematical formalism for loop nesting and transformations) to automatically derive hardware architectures.

DNN Compilation and Optimization

SoMa: Identifying, Exploring, and Understanding the DRAM Communication Scheduling Space for DNN Accelerators proposes a compiler that optimizes data movement in accelerators. Given a DNN computation graph and an accelerator architecture (with limited on-chip memory), the compiler decides when to read weights from DRAM, when to prefetch, and when to evict. By exploring the space of possible schedules, the compiler finds near-optimal solutions.

Adyna: Accelerating Dynamic Neural Networks with Adaptive Scheduling addresses dynamic neural networks (networks where computation depth varies based on input). At runtime, some paths through the network take fewer operations than others. Adyna's scheduler routes operations to available compute resources dynamically, balancing load.

Quantum Compilation

Quantum Circuit Compilation (a standalone paper, not part of a larger system) addresses the problem of compiling a high-level quantum algorithm specification to a low-level quantum machine instruction set. The compilation process must map high-level operations to available physical qubits and their supported gates, minimizing depth (total time) and width (number of qubits).

Power and Energy Efficiency

Energy efficiency matters everywhere: mobile devices have limited battery, datacenters face rising electricity costs, and high-performance systems generate enormous heat. HPCA 2025 includes 11 papers on power management and energy efficiency.

Energy-Aware Design Space Exploration

CORDOBA: Carbon-Efficient Optimization Framework for Computing Systems proposes optimizing not just for performance or power consumption alone, but for total carbon footprint including embodied carbon (carbon emitted manufacturing the hardware) and operational carbon (carbon from electricity consumption). The paper shows that optimizing for operational carbon alone can result in overprovisioned systems with high embodied carbon.

Architecting Space Microdatacenters: A System-level Approach addresses computing in space, where power is severely limited (power beamed to spacecraft from solar panels or wireless transmission). This paper proposes heterogeneous architectures with multiple processor types, carefully chosen to fit the power budget while meeting performance requirements.

Dynamic Power Management

DynamoLLM: Designing LLM Inference Clusters for Performance and Energy Efficiency (already mentioned in LLM section) uses dynamic cluster scheduling to consolidate inference onto fewer nodes, allowing power-gating of idle nodes.

Predictive GPU Frequency Scaling for Energy-Efficient LLM Inference Serving proposes adjusting GPU clock frequency dynamically based on predicted workload intensity. During prefill phases (where many tokens are processed together), the GPU can run at lower frequency; during decode phases (where one token is processed at a time), frequency can be lowered further, saving power.

Power-Failure-Aware Cache Dead Block Prediction for Intermittent Energy-Harvesting Systems addresses ultra-low-power systems that harvest energy from the environment (solar, RF, vibration). These systems intermittently lose power, so they must checkpoint critical state. This paper proposes predicting which cache blocks are "dead" (will not be accessed again), so they need not be checkpointed, reducing energy.

Cross-cutting patterns

Several design philosophies recur across HPCA 2025's seemingly diverse papers. The first is asymmetry as an optimization tool: instead of providing a single, symmetric solution (e.g., uniform precision, uniform memory hierarchy, uniform scheduling), architects build systems with multiple modes or types, choosing the best mode for each operation or phase. BitMoD uses mixed precision; FACIL allows programmable DRAM address mapping; Adyna schedules operations adaptively. This asymmetry adds complexity but extracts significant performance.

The second is co-design at every level: hardware and software must be designed together, not sequentially. A compiler cannot be separated from the hardware it targets; an accelerator cannot be separated from the algorithms it executes; a memory system cannot be separated from the workload's access patterns. Nearly every major paper in this corpus involves hardware-software co-design, sometimes spanning multiple layers (hardware, firmware, OS, compiler, runtime).

The third is measurement and characterization before optimization: HPCA papers overwhelmingly start with empirical analysis (e.g., Chronus's rowhammer characterization, ML Cluster's failure characterization, QuCLEAR's gate-count reduction). This reflects architectural culture: understanding the problem deeply before proposing a solution. The result is papers that feel grounded in reality, not theoretical speculation.

How HPCA fits in the ecosystem

HPCA produces architectural innovations that feed into products. Papers describing quantization techniques influence next-generation GPU architectures. PIM research shapes DRAM controller design. Rowhammer defense strategies become standards (many papers reference DRAM industry specifications). The venue is read by chip architects at major vendors and used to guide product roadmaps.

HPCA depends on advances in other fields: compilers provide the infrastructure for dataflow optimization; algorithms research (in ML and HPC) determines which operations must be fast; circuit design provides the building blocks (transistors, memory cells) that architects work with. HPCA sits at the convergence of these fields, synthesizing them into integrated systems.

What HPCA does not typically cover: operating systems scheduling (that is OSDI), networking protocols (that is SIGCOMM), machine learning algorithms (that is NeurIPS), or application-specific optimizations (those scatter across domain conferences). HPCA focuses specifically on the hardware mechanisms and instruction-set architectures that make systems fast.

What is not yet solved

The memory wall identified in Section 2 remains unsolved. Bandwidth and latency are still the primary bottlenecks, and the solutions remain incremental. PIM is promising but not yet ubiquitous — the largest AI inference systems still rely on moving data across PCIe buses. Prefetching remains imperfect; unpredictable access patterns still result in cache misses and memory stalls. This suggests a fundamental architectural rethinking may be needed, but the venue has not yet produced it.

A second gap is energy efficiency at the system level. HPCA 2025 includes papers on reducing power consumption, but few address the thermodynamics of large-scale inference. Cooling datacenter chips dissipating 300-500 watts requires significant infrastructure. Some papers (e.g., CORDOBA) point toward more holistic optimization, but this remains early-stage.

A third gap is reliability at scale. As models grow to trillions of parameters and training happens across thousands of GPUs, fault tolerance becomes critical. Yet hardware support for fault tolerance in HPCA 2025 remains limited. Checkpointing and redundancy (the standard approach) are crude tools; more sophisticated hardware mechanisms for fast recovery are needed.

Finally, the venue has produced only limited innovation on the algorithmic level — how should algorithms themselves be designed to be more "architecture-friendly"? Sparsity and quantization exploit structure in existing algorithms, but wholesale algorithm redesigns that embrace hardware constraints remain rare. This may reflect the reality that algorithm innovation (happening in ML conferences) and architecture innovation (happening in HPCA) have become separated, to the detriment of both.
