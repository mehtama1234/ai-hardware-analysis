Analog AI Master Review Path

This is the reading and build order for the combined analog in-memory AI system. Start with the Connected System Map, then use this page to inspect the detailed proof path across strategy pages, frontend/backend implementation, compiler and simulator plans, and the newer hardware evidence lab.

The One Question

Can a real model safely move some repeated matrix work into analog in-memory hardware, while digital logic keeps control of the places where small errors change the answer?

How To Read The System

Do not read these pages as a chip pitch. Read them as a chain of proof. The first object is the model graph. The graph is split into work that might tolerate analog error and work that should stay digital. The analog lab then asks how much error the tile creates. The model lab asks whether that error changes the answer. The digital controller decides when analog is allowed. RTL, synthesis, and OpenLane evidence ask whether that controller can become hardware. The frontend should only make the claim that this chain supports.

This is the standard for the rest of the pages: name the object, name the constraint, name the design move, show the evidence, and state the remaining failure mode.

The Claim Ladder

Evidence LevelWhat It MeansWhat It Cannot Claim
Local simulationThe model or analog assumption was tested in local code with recorded inputs and outputs.It cannot claim measured hardware behavior.
Model sensitivityThe same analog error was tested at different model locations to see where it changes choices.It cannot claim full pretrained-model quality.
RTL checkedThe digital rule was represented as Verilog and checked against generated cases.It cannot claim physical timing, routing, or power.
SynthesizedThe controller logic lowered into gates in the selected flow.It cannot claim final layout or manufacturability.
OpenLane routedThe selected digital block completed an educational physical-design flow under recorded constraints.It cannot claim signoff tapeout readiness.
Backend package importedThe old workbench can attach evidence to a model package and compute allowed or blocked claims.It cannot erase missing silicon, board, power, thermal, or reliability evidence.

Read In This Order

Combined Workflow

Shows the whole system as one path from customer model to frontend claim.

Consumes: old workbench pages, backend behavior, current-lab evidence, and cross-repo proof.

Produces: shared mental model for all other pages.

Supports: the two repos should be read as one workflow.

Refuses: treating a connected prototype loop as measured silicon proof.

2

Frontend Workbench

Shows the product surface where model fit, evidence, adapters, packages, claims, and hardware-lab evidence are reviewed.

Consumes: model package, backend placement, imported evidence, evidence audit, and claim readiness.

Produces: the user-facing review surface for imported analog, RTL, synthesis, and OpenLane evidence. Load package pkg-e931662a01293df2 to see the first connected hardware-lab evidence result.

Supports: narrow package claims backed by active evidence.

Refuses: hiding needs-review or blocked claims behind a single success badge.

3

Customer Intake

Defines the model, task, timing, power, environment, update, and safety facts needed before a claim is meaningful.

Consumes: user model, workload, device context, latency target, power target, update needs, and operating environment.

Produces: workload record.

Supports: judging analog fit against a real use case.

Refuses: chip claims detached from workload constraints.

4

Proof Ladder

Orders the proof steps from workload definition through final answer.

Consumes: workload record, proposed claim, and available evidence level.

Produces: step-by-step proof map.

Supports: moving from local simulation toward stronger evidence without skipping levels.

Refuses: calling simulation, RTL, layout, board measurement, and production signoff the same kind of proof.

5

Compiler Plan

Explains how model operators become analog candidates, digital-only regions, converter boundaries, and fallback points.

Consumes: model graph, operator roles, tensor movement, hardware target assumptions, and analog/digital constraints.

Produces: placement requirements.

Supports: a compiler handoff that names analog candidates and digital escape paths.

Refuses: claiming full compiler lowering from a placement sketch.

6

AIHWKIT Plan

Explains what analog simulation can and cannot prove for neural-network weights, noise, drift, and converters.

Consumes: candidate layers, weight ranges, noise/drift assumptions, converter assumptions, and model task metric.

Produces: simulator adapter requirements.

Supports: analog accuracy-risk experiments under stated assumptions.

Refuses: measured board behavior, measured power, or calibrated silicon accuracy.

7

Simulator Calibration

Explains how assumed analog behavior becomes stronger evidence only after comparison to better measurements.

Consumes: simulator output, local analog measurements, calibration target, and mismatch/drift assumptions.

Produces: calibration evidence levels.

Supports: ranking simulator trust by comparison to stronger observations.

Refuses: trusting a simulator because it has a precise-looking number.

8

Evidence Matrix

Defines which words are allowed for simulated, measured, RTL-verified, synthesized, routed, or blocked claims.

Consumes: proposed claim and evidence source type.

Produces: claim rulebook.

Supports: matching wording to proof level.

Refuses: overclaiming from incomplete or mismatched evidence.

9

Tapeout Risk

Names physical risks that still block production claims: ADC cost, heat, noise, process, chiplets, and layout.

Consumes: architecture assumptions, memory choice, converter costs, layout evidence, power estimates, and packaging needs.

Produces: physical-risk backlog.

Supports: deciding which physical risks still need evidence.

Refuses: production readiness without silicon, reliability, packaging, test, and signoff evidence.

10

Hardware Lab Bridge

Maps this workbench to concrete analog, RTL, synthesis, and OpenLane artifacts in the newer repo.

Consumes: old architecture requirements and new lab artifacts.

Produces: implemented-proof map.

Supports: seeing which architecture claims now have working artifacts.

Refuses: treating partial lab artifacts as full AIHWKIT, CrossSim, board, or silicon proof.

11

Combined Build Goal

States the actual development work needed to make both repos behave as one connected system.

Consumes: frontend, backend, hardware lab, evidence ledger, and proof reports.

Produces: build plan and acceptance criteria.

Supports: the current end-to-end development target.

Refuses: declaring the whole system done while page flow, measured board evidence, or claim boundaries remain incomplete.

12

Hardware Evidence Ledger

Lists each current proof artifact, what it proves, what it does not prove, and what should be imported into the backend.

Consumes: analog, RTL, synthesis, OpenLane, backend-import, and cross-repo proof artifacts.

Produces: evidence import source of truth.

Supports: explaining why C1, C4, and C5 are supported while C2 and C3 need review.

Refuses: turning local runtime and OpenLane estimates into measured board and power claims.

13

Board And Power Boundary

Defines what must be measured before latency and energy claims can be upgraded.

Consumes: runtime trace, board setup, meter setup, voltage/current samples, thermal setup, workload ID, and host-overhead rule.

Produces: measured-runtime and measured-energy evidence requirements.

Supports: the exact next experiment for C2 and C3.

Refuses: combining unrelated runtime and power estimates as measured evidence.

14

Page Flow Audit

Names which pages already carry the proof chain and which pages need richer handoffs.

Consumes: the current old and new page set.

Produces: rewrite batches for making the whole review path seamless.

Supports: planning page rewrites from actual gaps, not taste.

Refuses: adding pages that do not improve the evidence chain.

15

Current AIMC System State

Summarizes what is supported, what needs review, and what remains blocked in the current package.

Consumes: cross-repo proof, simulator status, residual-aware placement, backend claim readiness, and measured-evidence boundaries.

Produces: the short browser-reviewable current answer.

Supports: starting a review without reading every artifact first.

Refuses: treating supported local claims as production readiness.

16

Simulator To Placement Boundary

Explains why AIHWKIT and CrossSim payloads do not automatically become analog placement permission.

Consumes: simulator payload status, strict importer result, residual threshold, backend operator family, and source matching policy.

Produces: the rule for keeping a structural analog candidate analog-allowed.

Supports: bounded analog placement for matched fixed-weight MatMul rows.

Refuses: using simulator availability, threshold-fail output, or wrong-family evidence as placement proof.

17

Measured Runtime And Power Path

Explains exactly how latency and energy claims move from needs-review to supported.

Consumes: board runtime, meter trace, voltage/current samples, runtime trace ID, package, workload, board, run window, and host-overhead boundary.

Produces: the upgrade rule for C2 measured latency and C3 measured energy.

Supports: measured claims only for the exact synchronized run.

Refuses: combining local RTL timing, OpenLane estimates, or mismatched meter traces into measured energy.
