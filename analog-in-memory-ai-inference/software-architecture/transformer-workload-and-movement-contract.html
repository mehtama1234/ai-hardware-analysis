Define the workload before the chip

A transformer is not one workload. Prefill, decode, batch size, sequence length, cache state, and deadline change which bottleneck matters. The first practical translation of the conference themes is a workload contract and a movement ledger.

The hidden object: useful completed work

The chip does not produce matrix multiplications as the customer outcome. It produces tokens, classifications, actions, or control decisions. A matrix operation is useful only when its result survives the rest of the transformer and contributes to a correct completed request.

At first principles, a transformer step is a dependency graph: input tokens + weights + state → projections → attention → normalization/nonlinear transforms → MLP → residual state → logits → selected token. Every arrow can introduce time, energy, storage, quantization error, synchronization, or failure. The practical unit of optimization is a completed token under a declared operating condition.

Workload contract

Before mapping any operator, create a versioned record containing the model and weight hash, task, tokenizer, prefill/decode phase, batch and sequence shape, quality threshold, latency deadline, energy denominator, hardware profile, and fallback policy.

FieldQuestionFirst-slice value
ModelWhich weights and architecture are frozen?Three-block transformer MLP fixture, then a small token transformer.
TaskWhat is user-visible?Next-token logits and selected-token agreement with the digital baseline.
PhasePrefill, decode, or both?Separate prompt prefill from batch-1 decode.
QualityWhat error is allowed?Logit residual, top-k agreement, and task threshold.
DeadlineWhat latency boundary?Time-to-first-token and inter-token tail percentile.
EnergyWhat denominator?Energy per generated token including movement and conversion.
FailureWhat if analog is unsafe?Digital fallback with reason and cost.

Movement is a conservation problem

Each value has to be represented somewhere and transported across a boundary. Follow the value rather than only counting arithmetic:

weights → conductance/SRAM → array signal → ADC code → digital partial sum → SRAM → nonlinear/residual logic → logits

For every edge record tensor shape, precision, bytes read/written, number and resolution of conversions, synchronization, buffer residency, latency, energy, and whether the value is measured, simulated, or assumed.

Decision rule: if analog placement reduces MAC cost but increases conversion and movement cost enough to miss the token deadline or energy target, reject it.

KV cache is not an implementation detail

Weights may be fixed and suitable for an analog array, but keys and values are generated during execution and indexed by the current sequence. KV-cache capacity, bandwidth, layout, eviction, compression, and consistency are therefore part of the chip contract.

For the first attention experiment, keep KV-cache management digital and measure it explicitly. The analog question is narrower: can static projections reduce enough work without making the digital cache boundary dominant?

Practical outputs

  1. Freeze the MLP fixture contract.
  2. Add a token-level attention fixture with explicit prefill/decode modes.
  3. Generate a per-operator movement ledger.
  4. Measure the digital baseline with the same denominator used for hybrid.
  5. Record movement uncertainty instead of hiding it.
  6. Reject speedup claims that omit conversions, SRAM, cache, calibration, or fallback.

Refused claim

This chapter cannot claim that a matrix-level throughput estimate predicts token-level latency, or that a model with no KV-cache and decode accounting represents an LLM serving workload.
