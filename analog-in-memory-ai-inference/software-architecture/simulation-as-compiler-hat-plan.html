Simulation As The Compiler And Hardware-Aware Training

This page explains the idea in plain terms: before customers can trust an analog AI chip, the software must let them train and test models as if the chip already exists, including the chip's flaws.

The core question: can we make normal AI developers use the chip without asking them to understand analog circuits?

Claim boundary:

A simulator can show that a model survived stated assumptions. It does not prove the real chip works. Real proof still requires measured silicon, board logs, power data, temperature data, and task results.

What This Means

Digital chips usually try to do exact math. If the software asks for a multiply, the chip gives the same answer every time within the rules of the number format. That is why normal AI software can mostly ignore the physical details of the chip.

An analog in-memory chip is different. It stores numbers as physical states inside memory cells. It computes by letting electrical signals move through those cells. That can be much more power-efficient for matrix math, but the result is not perfectly exact.

The chip has physical behavior. Signals can be noisy. Stored weights can drift. A programmed value may not land exactly where the software wanted it. Wires can lose voltage. Temperature can change the answer. Converters between digital and analog values have limited precision.

So the software stack cannot pretend the chip is a normal digital calculator. It has to teach the model about the chip's behavior before the model is deployed.

Simulation as the compiler means the simulator is not just a research demo. It becomes part of the path from model to product. The simulator tells us whether the model can tolerate the real behavior of the chip, and the compiler uses that information when deciding what runs on analog arrays, what stays digital, and what needs calibration.

Why This Matters For Physical AI

Physical AI means AI that acts in the real world: robots, drones, factory equipment, smart cameras, smart home devices, and machines with sensors and motors.

These systems are hard because the world changes. A robot may grab a different object. A drone may fly in different light or wind. A factory arm may see a slightly different part. A smart device may need to respond locally without sending everything to the cloud.

Training only on real machines is usually too slow and expensive. The machine can wear out, break objects, damage itself, or create safety issues while learning. That is why robotics teams often train and test in simulation first.

A robotics simulator is like a controlled virtual world. It can contain the robot body, cameras, force sensors, objects, physics, lighting, and task rules. NVIDIA Isaac Sim is one example of a robotics simulation environment used for simulation, testing, synthetic data, and digital-twin workflows.

For our chip, the important move is this: the robot should not train against a perfect chip. It should train against a virtual version of our imperfect analog chip. Then the model learns to survive the kinds of imperfections it will see later on hardware.

The Three Jobs We Must Do

The strategy becomes practical only if we build three connected pieces. Each piece has a different job.

1. Build A Virtual Twin Of The Chip

This is the software model of the chip. It does not have to simulate every transistor at first. It does need to simulate the things that affect model accuracy and runtime behavior.

  • How many bits the inputs and outputs have.
  • How much programming error appears when writing weights.
  • How weights drift over time.
  • How much read noise appears during matrix multiplication.
  • How voltage loss changes large arrays.
  • How tile size limits split large layers.
  • How temperature changes the error profile.

The first version can be a Python simulator. Later versions should connect to AIHWKIT, CrossSim, circuit models, thermal models, and measured silicon data.

2. Make The Chip Hybrid

Analog arrays are attractive because matrix multiplication is a huge part of modern AI. But the whole AI model is not just matrix multiplication.

Some parts are better suited to analog arrays, especially repeated linear projections with mostly fixed weights. Other parts are better suited to digital logic, especially control flow, routing, normalization, Softmax, dynamic attention, scheduling, and exact bookkeeping.

So the product should not be presented as a pure analog chip that does everything. The safer design is a hybrid system: analog arrays for the heavy repeated math, digital blocks for the parts that need precision, flexibility, or fast decisions.

3. Build A Zero-Touch Translator

AI developers write models in tools like PyTorch or JAX. They do not want to manually program voltages, memory cells, DAC settings, ADC timing, calibration tables, or tile placement.

The compiler has to translate a normal model into a chip execution plan. It should decide which layers go to analog, which layers stay digital, how large matrices are split, how weights are programmed, how outputs are accumulated, and how calibration data is applied.

Zero-touch does not mean there is no complexity. It means the complexity is hidden behind the software stack, so a customer can use the chip without becoming a circuit designer.

What Hardware-Aware Training Does

Hardware-aware training is the practice of training the model while exposing it to hardware-like imperfections. Instead of training in a perfect digital world and discovering hardware failure later, we inject the expected analog behavior during training.

Think of it like training a driver in rain, glare, and rough roads before asking them to drive in the real world. The goal is not to make the road perfect. The goal is to make the driver less fragile.

In model terms, the training loop sees noisy weights, quantized inputs, quantized outputs, drifted conductance values, and noisy results. The optimizer then learns weights that still work when those small changes happen.

Normal Training

The model learns in a clean mathematical environment. That is useful, but it may produce weights that only work when computation is exact.

Hardware-Aware Training

The model learns while the training loop imitates the chip's errors. The final model may be less fragile when deployed to analog hardware.

This is common enough that real libraries exist for it. IBM AIHWKIT is an open-source Python/PyTorch toolkit for analog in-memory computing experiments. IBM also describes AIHWKIT-Lightning as a scalable hardware-aware training toolkit for larger models. Sandia CrossSim is a Python-based simulator focused on analog in-memory computing and crossbar accuracy effects.

A Simple PyTorch Example

The code below is not a production simulator. It is a teaching example. It shows the basic idea behind a hardware-aware layer: during the forward pass, we make the layer behave a little like imperfect analog hardware.

The important part is the direction of the idea, not the exact numbers. Real values must come from device measurements, circuit simulation, board tests, and calibrated tool models.

import torch
import torch.nn as nn
import torch.optim as optim


class SimpleAnalogLinear(nn.Module):
    def __init__(
        self,
        in_features,
        out_features,
        programming_noise=0.04,
        read_noise=0.02,
        drift_alpha=0.03,
        adc_bits=8,
    ):
        super().__init__()
        self.weight = nn.Parameter(torch.empty(out_features, in_features))
        self.bias = nn.Parameter(torch.zeros(out_features))
        self.programming_noise = programming_noise
        self.read_noise = read_noise
        self.drift_alpha = drift_alpha
        self.adc_bits = adc_bits
        nn.init.kaiming_uniform_(self.weight, a=5 ** 0.5)

    def quantize(self, x, bits):
        levels = (2 ** bits) - 1
        x_min = x.detach().min()
        x_max = x.detach().max()
        if torch.isclose(x_min, x_max):
            return x
        scaled = (x - x_min) / (x_max - x_min)
        rounded = torch.round(scaled * levels) / levels
        return rounded * (x_max - x_min) + x_min

    def forward(self, x, hours_after_programming=0.0):
        # DAC limit: the analog array receives a quantized input voltage.
        x = self.quantize(x, self.adc_bits)

        # Weight write error: the physical cell does not land exactly on target.
        if self.training:
            scale = self.weight.detach().abs().mean().clamp_min(1e-6)
            write_error = torch.randn_like(self.weight) * self.programming_noise * scale
            effective_weight = self.weight + write_error
        else:
            effective_weight = self.weight

        # Drift: stored conductance slowly moves over time.
        if hours_after_programming > 0:
            drift = (hours_after_programming + 1.0) ** (-self.drift_alpha)
            effective_weight = effective_weight * drift

        # Analog vector-matrix multiply.
        y = x.matmul(effective_weight.t()) + self.bias

        # Read noise: each analog execution has some transient error.
        if self.training:
            noise_scale = y.detach().std().clamp_min(1e-6)
            y = y + torch.randn_like(y) * self.read_noise * noise_scale

        # ADC limit: the output current is converted back to a digital number.
        return self.quantize(y, self.adc_bits)


class TinyClassifier(nn.Module):
    def __init__(self):
        super().__init__()
        self.net = nn.Sequential(
            SimpleAnalogLinear(10, 32),
            nn.ReLU(),
            SimpleAnalogLinear(32, 1),
            nn.Sigmoid(),
        )

    def forward(self, x, hours_after_programming=0.0):
        for layer in self.net:
            if isinstance(layer, SimpleAnalogLinear):
                x = layer(x, hours_after_programming)
            else:
                x = layer(x)
        return x


torch.manual_seed(7)
X = torch.randn(1000, 10)
y = ((X[:, 0] * X[:, 1]) > 0).float().unsqueeze(1)

model = TinyClassifier()
optimizer = optim.Adam(model.parameters(), lr=0.01)
loss_fn = nn.BCELoss()

model.train()
for _ in range(200):
    optimizer.zero_grad()
    prediction = model(X, hours_after_programming=0.0)
    loss = loss_fn(prediction, y)
    loss.backward()
    optimizer.step()

model.eval()
with torch.no_grad():
    fresh = model(X, hours_after_programming=0.0)
    old = model(X, hours_after_programming=1000.0)
    fresh_acc = ((fresh > 0.5) == y.bool()).float().mean().item()
    old_acc = ((old > 0.5) == y.bool()).float().mean().item()

print(f"Accuracy right after programming: {fresh_acc:.3f}")
print(f"Accuracy after simulated drift:  {old_acc:.3f}")

This example teaches the mechanism. It does not prove an analog chip is accurate. It also does not replace AIHWKIT, CrossSim, SPICE, thermal modeling, firmware logs, or silicon measurement.

The Real Workflow

The production workflow should look like a ladder. Each stage adds one stronger kind of proof.

  1. Start with a normal model. The customer brings a PyTorch, JAX, ONNX, or similar model.
  2. Classify the layers. The software identifies repeated matrix-heavy layers, dynamic layers, control logic, normalization, activation functions, and sensor preprocessing.
  3. Run hardware-aware training or fine-tuning. The model is trained or adjusted while simulated analog errors are injected.
  4. Run accuracy sweeps. The team tests many levels of noise, drift, quantization, temperature, tile mismatch, and write error.
  5. Map the model. The compiler decides which layers run on analog arrays, which layers run on digital blocks, and where memory movement happens.
  6. Estimate runtime and power. The stack predicts latency, energy, data movement, converter use, memory pressure, and thermal risk.
  7. Test in robot simulation. For robotics, the model is tested in a simulator with task metrics, not just generic model accuracy.
  8. Run on a board. When hardware exists, the same workload is run through real firmware, real drivers, and real I/O.
  9. Measure the result. The final answer needs measured task success, latency, power, temperature, update behavior, and failure cases.

Where The Tools Fit

Tool Area What It Helps With What It Does Not Prove
AIHWKIT / AIHWKIT-Lightning PyTorch-level analog layers, training with analog-like non-idealities, model robustness experiments. It does not prove our exact chip layout, board runtime, firmware, package thermals, or customer task success.
CrossSim Crossbar accuracy effects, array-level analog behavior, matrix-operation degradation from hardware assumptions. It does not replace a full SoC simulator, compiler, board test, or tape-out signoff flow.
Robot Simulators Testing robot tasks in a virtual environment before running on real hardware. They do not prove real-world safety or reliability unless matched against physical tests.
Compiler Stack Splitting the model, mapping layers, tiling matrices, scheduling analog and digital work, creating runtime packages. It does not prove the analog math is accurate unless connected to calibrated simulation and measured hardware.
Lab And Board Tools Measuring real latency, power, temperature, drift, calibration, firmware behavior, and task outputs. They usually do not explain all model-level failures unless tied back to simulator and compiler logs.

What Evidence We Need

For this strategy to be credible, each claim needs a matching artifact.

Virtual Twin Evidence

Simulator version, chip profile, noise parameters, drift assumptions, quantization settings, thermal assumptions, and raw run output.

Training Evidence

Before-and-after accuracy, task metric, robustness sweeps, failure thresholds, and comparison against a clean digital baseline.

Compiler Evidence

Layer placement, tile map, digital fallback list, memory movement estimate, runtime schedule, and unsupported operation list.

Hardware Evidence

Board logs, power measurements, temperature measurements, calibration logs, drift measurements, and real task results.

The final customer answer should be direct: this workload runs well, partly runs, or does not run well yet. Then we show the proof and the next missing measurement.

Important Corrections To The Pasted Example

  • A toy PyTorch script is useful for teaching, but it is not a high-fidelity chip model.
  • A result around 54% on a binary classification task is not strong evidence. It is close to weak baseline behavior unless the task is unusually imbalanced.
  • It is safer to say hardware-aware training may improve robustness, not that it automatically makes the model run flawlessly.
  • The real simulator must be calibrated from measured devices. Guessed noise numbers are only placeholders.
  • Simulation should guide the compiler and roadmap, but it cannot replace physical validation.
