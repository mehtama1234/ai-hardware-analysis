Analog Digital Execution Plan

This is the ordered build plan for the combined analog in-memory AI, digital control, EDA, backend, frontend, and evidence-review system. Each step names the object, the constraint, the development move, the evidence gate, the allowed claim, the claim that must stay blocked, and the next handoff.

One Goal

Make one review path where a model workload becomes a hardware claim only after every physical and software cost is visible. The path must count analog error, converter cost, digital fallback, memory movement, scheduler behavior, layout readiness, board runtime, power measurement, and task accuracy. If an item is only simulated, the claim must say simulated. If an item is measured, the package must show the board, meter, run window, and provenance.

Execution Batches

BatchObjectConstraintDevelopment MoveEvidence GateAllowed ClaimBlocked Claim
1. Workload contract One model, one task, one target device, one package ID. A chip can only be judged against a workload with accuracy, latency, power, update, memory, and environment limits. Make the intake form and package manifest require these limits before claim review. Frontend package view shows workload limits; backend package artifact stores them. This package evaluates this workload under these named limits. The architecture is generally good for all AI workloads.
2. Placement contract Model graph nodes, analog candidates, digital-required nodes, converter crossings, fallback points. Analog arrays help only where the operation, precision, tile size, and error tolerance fit. Deepen the placement artifact so every analog choice has a reason and every digital choice has a reason. hardware-placement.json plus backend endpoint and frontend panel. These graph regions are analog candidates and these regions must stay digital. The full model runs on analog hardware.
3. Analog simulator contract Analog tile output, residual error, ADC/DAC setting, drift, noise, wire drop, calibration profile. An analog multiply is not exact. The system needs to know how wrong it is and whether the task can tolerate that error. Attach AIHWKIT, CrossSim, SPICE, or calibrated simulator payloads through the strict tool evidence path. /evidence/validate-tool, /evidence/import-tool, and check_strict_evidence_api.py. This simulated or calibrated analog source supports this bounded analog-error claim. This is measured silicon accuracy.
4. Task-impact contract Task metric before and after analog error, quantization, and fallback. A small numeric error can be harmless or destructive depending on where it lands in the model. Connect simulator residuals to task accuracy checks and require pass/fail thresholds. task_accuracy.json, tolerance fields, dataset ID, record count, and frontend before/after claim preview. The task stayed inside this tolerance on this dataset or fixture. The model is accurate in deployment conditions.
5. Digital control contract Scheduler rows, governor rows, retry rules, fallback rules, RTL modules. The controller must protect the workload when analog output is too uncertain or too slow. Keep generating RTL traces from analog evidence and synthesize the control modules with Yosys. Generated CSV traces, generated Verilog include files, Yosys reports, and bridge check. The control rule has a checked RTL implementation path. The chip control plane is physically signed off.
6. Physical-flow contract OpenLane packages for controller blocks. RTL is still abstract until the flow can place, route, and report timing/area/power under a process setup. Turn OpenLane-ready packages into actual OpenLane run artifacts when host/container setup is stable. OpenLane config, constraints, pin order, routed results, timing report, area report, power report. This digital block has this educational physical-flow result. The full analog chip is tapeout-ready.
7. Board runtime contract Runtime trace for one workload on one board. Latency claims need repeated board runs and a clear host-overhead boundary. Import measured runtime only through the strict measured path. /evidence/validate-measured, board ID, board revision, runtime version, timestamps, p50, p95, repetition count. This board ran this workload with this measured latency distribution. The product meets all customer latency targets.
8. Power and thermal contract Power trace and temperature trace aligned to the runtime trace. Energy claims fail if the measured rail, meter, integration window, or host overhead is unclear. Import measured power only through the strict measured path. Meter name, measured rail, average power, peak power, power samples, temperature samples, integration window. This board used this measured power during this measured workload window. The analog system has proven broad power savings.
9. Final review package Manifest, artifacts, imported evidence, claim-readiness report, evidence brief. The final answer must not mix local, simulated, measured, and production evidence. Make the package view read like an audit: what exists, what it proves, what is missing, what cannot be said. Package archive, evidence audit, evidence brief, page contract audit, bridge check. The package proves only the claims marked supported by the current evidence. Any claim not tied to a named artifact.
