Benchmark Suite Plan

This page defines the repeatable workloads that prove where analog IMC is strong, partial, weak, or blocked.

Question: which concrete tests will show whether our analog strategy works?

Rule:

A benchmark suite must include bad-fit cases. A system that can only say yes is not credible.

Plain-Language Vocabulary

A benchmark is a repeatable test. It is a way to ask the same question the same way each time.

A strong-fit benchmark is a test where analog should plausibly help. A partial-fit benchmark is a test where analog helps only some parts. A bad-fit benchmark is a test where analog should probably lose or refuse the claim.

A digital baseline is the comparison system. It answers: how well would this workload run on a normal digital processor?

A tactile workload uses touch-like signals such as force, pressure, slip, vibration, or stretch. An event-vision workload uses a camera that reports brightness changes instead of normal video frames.

A VLA model is a vision-language-action model. It connects visual input, language/task instruction, and physical action. In this plan, we test only a small projection block first, not a full robot brain.

A benchmark suite is useful only if it can show both wins and losses. Otherwise it becomes a sales demo instead of an engineering tool.

Benchmark Set

Tactile Slip Detection

Measures local contact detection, false alarms, latency, and energy. Strong candidate for sensor-near analog.

Event-Vision Feature Extraction

Measures sparse high-rate vision feature generation and upstream data reduction.

Drone Perception Module

Measures sustained battery-limited inference under size, heat, and power constraints.

Industrial Anomaly Detection

Measures repeated fixed-weight inference with clear pass/fail and uptime metrics.

Small VLA Projection Block

Measures whether transformer linear projections map well while attention/control stays digital.

Known Bad Fit

Uses frequent updates, dynamic operations, vague metrics, or unsupported layers to test honest rejection.

Each Benchmark Must Include

  • model shape and layer list
  • sensor and input assumptions
  • task metric and pass/fail threshold
  • latency and power target
  • update frequency
  • analog simulation result
  • compiler mapping result
  • digital baseline comparison
  • safe claim and blocked claim

How A Benchmark Run Happens Practically

  1. Choose one benchmark scenario and one model.
  2. Run workload intake so the task, sensor, timing, power, and update assumptions are explicit.
  3. Split the model into analog candidates, digital-required parts, memory-heavy parts, and unsupported parts.
  4. Run analog simulation under named chip assumptions.
  5. Run or estimate the digital baseline.
  6. Compare task score, latency, energy, memory movement, and failure modes.
  7. Write the safe claim and the blocked claim.

Common Mistakes This Page Prevents

  • Using only easy benchmarks that make analog look good.
  • Benchmarking matrix multiplication but not the customer task.
  • Comparing against an unfair or weak digital baseline.
  • Ignoring bad-fit workloads.
  • Reporting accuracy without latency, power, update, and failure context.

Detailed Walkthrough

A benchmark suite is the bridge between strategy and proof. It prevents the company from saying "analog is good for Physical AI" without showing which physical task, which model, which metric, and which comparison.

Before The Benchmark

Choose a workload category and define the test. The benchmark is not valid until the success metric, input data, model, analog profile, digital baseline, timing target, and power target are written down.

During The Benchmark

Run the workload through the same pipeline every time: intake, partition, hardware profile, compiler map, analog simulation, digital baseline, task metric, and claim review. This consistency matters because otherwise one benchmark may be judged by accuracy while another is judged by power or speed.

After The Benchmark

The output should be a ranked result: strong fit, partial fit, bad fit, or unknown. It should also say why. A strong fit might be power and timing improvement with acceptable accuracy loss. A partial fit might be analog-friendly layers but too much digital overhead. A bad fit might require frequent full-model updates or unsupported operators.

What The User Should Conclude

A benchmark page should not only show winners. It should teach the boundary of the business. If analog wins only for fixed industrial sensing, that is still useful. If it fails for frequent-learning robotics, that is useful too because it prevents wasted silicon work.
