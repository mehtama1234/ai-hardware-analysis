Six-Gap End-To-End Goal

This page turns the six remaining gaps into one concrete product goal. It explains what needs to be built, why each part matters, what inputs it needs, what output it produces, and how we know it is done.

It uses the same connected-system contract as the rest of the workbench: object, constraint, design move, evidence, allowed claim, refused claim, and next handoff.

End-to-end goal: make the workbench able to answer whether a real customer workload is a credible analog IMC fit, what proof exists, what remains blocked, and what must be measured next.

Claim boundary:

This goal does not claim the chip works. It defines the software, simulator, compiler, measurement, and review system required before any chip-performance or Physical AI readiness claim becomes believable.

The Goal In One Sentence

Build a repeatable review workflow that starts with a customer workload and ends with a defensible answer: fit, partial fit, not fit, or unknown, with evidence attached and unsupported claims blocked.

The workflow should not be a pitch deck. It should be an operating system for deciding whether the analog chip deserves engineering, customer, and silicon investment for a specific workload.

What Success Looks Like

A customer uploads a model, describes the physical task, and receives a readable report showing analog fit, simulator risk, compiler mapping, latency budget, memory-update class, benchmark result, calibration status, and next measurements.

What Failure Looks Like

The system gives a broad score without saying which claim is supported, which evidence is missing, or why the workload may break on analog hardware.

Terms Before The Plan

Analog IMC means analog in-memory computing. The basic idea is to store model weights in memory-like cells and perform some math where the weights already live. This can reduce data movement, which is often a major source of power and delay.

Physical AI means AI connected to the physical world: sensors, machines, robots, drones, cameras, factory equipment, medical devices, infrastructure monitors, and other systems that observe real conditions and act or alert locally.

Matrix-heavy inference means the model spends much of its time multiplying large grids of numbers. Neural networks do this constantly. Analog arrays can be attractive here because the hardware physics can perform many multiply-and-add operations in parallel.

Sensor-near means the compute happens close to the sensor instead of sending all raw data to a large central processor. This matters when raw data is high-rate, power is limited, or a fast local reaction is needed.

Latency means delay. In Physical AI, the correct answer can still be useless if it arrives too late.

Calibration means measuring real hardware behavior and correcting the software model so it matches reality more closely.

Evidence means proof attached to a claim. A simulator, compiler output, board trace, power trace, thermal trace, and task result each prove different things.

ONNX, PyTorch, and JAX are common ways AI teams save, train, or exchange models. The customer may bring a model from any of these worlds, so the intake cannot assume one format.

ADC means analog-to-digital converter. It turns an analog electrical result into a digital number. DAC means digital-to-analog converter. It turns a digital number into an analog electrical input.

AFE means analog front end. It is the circuit near the sensor that receives real physical signals before they become clean digital data.

VLA means vision-language-action model. It is a model that can connect what it sees, what language says, and what action a robot or device should take.

RRAM, PCM, MRAM, FeRAM, and SRAM are memory families. The important question is not the acronym; it is whether the memory can store the model accurately, survive writes, avoid too much drift, and be manufactured at the right cost.

The End-To-End Flow

The six gaps should become one flow, not six disconnected documents.

  1. Intake: collect the model, task, physical setting, constraints, and success metric.
  2. Evidence Matrix: decide which claims are even allowed for this workload.
  3. Timing Budget: break the physical loop into sensor, compute, memory, safety, and output stages.
  4. Memory Decision: decide whether the workload is fixed-weight, low-update, adapter-update, or blocked for frequent updates.
  5. Benchmark Suite: run the workload against selected test cases and at least one bad-fit comparison.
  6. Simulator Calibration: replace guessed analog assumptions with measured or source-backed chip profiles as soon as evidence exists.

The final report should say what is proven, what is simulated, what is estimated, what failed, and what remains blocked.

The hybrid benchmarking pipeline explains how steps 1-7 happen practically when analog compute must work with digital helpers, memory, runtime software, sensors, and board measurements.

1. Customer Workload Intake

Open the detailed customer workload intake page.

This is the front door. If the intake is vague, every later answer is weak. The platform cannot judge analog fit from the model file alone because Physical AI depends on sensors, timing, power, environment, update behavior, and task success.

What We Need To Build

  • A guided intake form for model, task, sensors, physical system, environment, safety boundary, and deployment constraint.
  • A model import section for ONNX, PyTorch export, JAX export, or a placeholder model description when the model is not available yet.
  • A workload classification engine that labels the task as sensing-only, advisory, policy-level, reflex-level, safety-relevant, or not enough information.
  • A success-metric selector: accuracy, task completion, slip detection, false alarm rate, latency deadline, energy per inference, battery life, yield, or uptime.
  • A constraint checklist for latency, power, heat, size, memory, update frequency, calibration interval, and operating temperature.

Why It Matters

Analog IMC is not generally better for every model. It is strongest when the workload is matrix-heavy, repeated, sensor-near, power-limited, and has stable or rarely changing weights. Intake makes those assumptions explicit.

Inputs

  • Model file or model summary.
  • Sensor type and sample rate.
  • Task description and failure mode.
  • Latency target and worst-case timing requirement.
  • Power and thermal limits.
  • Update frequency and whether field adaptation is required.
  • Safety boundary and fallback owner.

Outputs

  • workload_intake.json
  • physical_context.json
  • success_metric.json
  • initial_claim_scope.json

Done means: the platform can explain what the workload is, why it might fit analog, and what claims are out of scope before running any simulator.

2. Evidence Matrix

Open the detailed evidence matrix page.

The evidence matrix is the rulebook. It prevents the platform from turning one weak result into a stronger claim than it supports.

What We Need To Build

  • A claim catalog: analog fit, model accuracy, compiler support, board runtime, power, thermal, update readiness, safety boundary, digital-twin readiness, production readiness.
  • A required-evidence table for each claim.
  • A claim-status engine: supported, partially supported, estimated, simulated, measured, blocked, or not applicable.
  • A warning system that says why a claim is blocked.
  • A reviewer view that shows safe wording and blocked wording side by side.

Why It Matters

Analog hardware strategy is full of tempting claims: huge energy savings, real-time robotics, adaptive Physical AI, and extreme-environment operation. The matrix keeps the company honest by tying every statement to evidence.

Read this table as a safety system for language. A claim is allowed only when the matching proof exists. If the proof is only a simulation, the claim must say simulation. If the proof is a board measurement, the claim can mention that measured board setup. If the proof is missing, the claim remains blocked.

Claim Minimum Evidence, In Plain Terms Still Blocked Until
Workload is an analog candidate. We know what the model does, how much repeated matrix math it has, how often weights change, what task score matters, and why the physical device cares about power or latency. Analog simulator risk is tested.
Model survives analog behavior. We run the model with analog-like errors such as lower precision, noise, drift, imperfect weight writing, temperature variation, and converter limits, and we record the assumptions. The simulator is calibrated against measured chip, device, board, or lab behavior.
Compiler can target the chip. We know which layers go to analog arrays, which stay digital, how large matrices are split, what data moves, and which operations are unsupported. The compiled package runs on a board or accurate full-system simulator.
Power advantage exists. We estimate or measure the whole system, including analog math, converters, digital helper logic, memory movement, host control, idle power, and workload duty cycle. Board-level power is measured.
Physical AI readiness exists. We test the full sense-think-act loop, the task result, the recovery behavior, the independent safety boundary, and whether updates are practical. Real hardware-in-the-loop or real task validation exists.

Outputs

  • evidence_matrix.json
  • claim_readiness.json
  • safe_claims.md
  • blocked_claims.md

Done means: every user-facing claim has a machine-checkable evidence requirement and blocked claims cannot pass by accident.

3. Timing And Latency Budget

Open the detailed timing and latency budget page.

Robotics and sensor-near Physical AI need timing discipline. A model can be accurate and still fail if the answer arrives too late.

What We Need To Build

  • A timing-budget form that separates sensor capture, analog front end, DAC, analog compute, ADC, digital VPU, memory movement, host control, safety filter, and output command.
  • A worst-case timing model, not only average latency.
  • A loop classifier: sensor front-end loop, reflex loop, policy loop, planning loop, safety override loop, adaptation loop.
  • A timing evidence importer for simulator output, firmware logs, board traces, oscilloscope captures, and system profiler output.
  • A visual timing report that shows which stage dominates and whether analog helps the full path.

Why It Matters

Analog VMM can be fast, but the full loop includes more than analog math. Converters, memory movement, digital logic, host control, firmware, and safety checks can erase the benefit. The timing budget shows where the real bottleneck is.

Path Question Evidence
Sensor path How fast does the physical signal become usable input? AFE logs, sensor specs, oscilloscope traces, board measurements.
Analog compute path How fast does the mapped matrix operation run? Simulator timing, compiler schedule, board timing.
Digital support path How much time do Softmax, LayerNorm, accumulation, routing, and safety checks take? Digital profiler, firmware trace, SoC simulator.
Safety path Can unsafe commands be blocked fast enough? Worst-case override timing and independent controller proof.

Outputs

  • latency_budget.json
  • loop_classification.json
  • timing_trace_summary.json
  • timing_bottlenecks.md

Done means: the platform can say whether analog helps the complete loop, not just one operation inside the loop.

4. Memory Technology Decision

Open the detailed memory technology decision page.

The memory choice decides whether the chip is mainly a fixed-weight inference engine, a low-update accelerator, an adapter-update system, or a credible adaptive Physical AI platform.

What We Need To Build

  • A comparison model for RRAM, PCM, MRAM, FeRAM, SRAM, and hybrid storage.
  • A workload-to-memory matcher that uses update frequency, retention, endurance, drift, write energy, write speed, density, temperature, and foundry availability.
  • A rewrite-risk report that says whether frequent field updates are practical.
  • A fallback architecture guide: fixed analog base weights plus digital/SRAM adapters when full analog rewrites are not practical.
  • A measured-memory-profile importer for future silicon or partner data.

Why It Matters

Analog IMC often looks best when weights are programmed once or rarely changed. Physical AI may need adaptation after deployment. If the memory writes are slow, energy-heavy, low-endurance, or hard to calibrate, the company should avoid broad adaptive claims.

Memory Question Why It Matters
How fast can weights be written? Determines whether field adaptation is realistic.
How much energy does writing use? Determines whether updates destroy the power advantage.
How many writes can the cell survive? Determines lifetime and warranty risk.
How much drift occurs? Determines calibration frequency and accuracy stability.
How dense is the memory? Determines model size and package cost.

Outputs

  • memory_technology_decision.json
  • update_readiness.json
  • rewrite_risk.md
  • memory_profile_import_template.json

Done means: the platform can explain which memory choice fits the workload and which update claims remain blocked.

5. Benchmark Suite

Open the detailed benchmark suite page.

The benchmark suite turns broad strategy into repeatable evidence. It should include strong-fit, partial-fit, and bad-fit workloads so the platform learns where analog really helps.

What We Need To Build

  • A small set of named benchmark scenarios with model shape, sensor assumptions, task metric, timing target, power target, and update class.
  • A repeatable runner that produces the same artifact fields for each benchmark.
  • A comparison baseline for digital execution.
  • A bad-fit benchmark that proves the system can say no.
  • A benchmark report that ranks workloads by analog fit, evidence strength, and next measurement need.

Recommended Benchmarks

Tactile Slip Detection

Sensor-near, high-rate, low-power reflex candidate. Measures slip detection, latency, false positives, and energy.

Event-Vision Feature Extraction

Tests sparse high-frequency visual signals and compact local feature generation.

Drone Perception Module

Tests sustained battery-limited inference with tight size, heat, and energy limits.

Industrial Anomaly Detection

Tests repeated fixed-weight sensing with clear pass/fail metrics and practical deployment value.

Small VLA Projection Block

Tests whether transformer linear layers can be useful analog candidates while attention and control stay digital.

Known Bad Fit

A workload with frequent full-weight updates, dynamic control, vague metrics, or heavy unsupported operators.

Outputs

  • benchmark_suite.json
  • benchmark_run_results.json
  • digital_baseline_comparison.json
  • benchmark_readiness_report.md

Done means: the platform can show examples where analog is promising, examples where it is partial, and examples where it should not be sold.

6. Simulator Calibration

Open the detailed simulator calibration page.

Early simulation uses assumptions. Real credibility starts when those assumptions are replaced by measured profiles.

What We Need To Build

  • A calibration profile schema for measured noise, drift, write error, IR drop, ADC/DAC behavior, tile mismatch, temperature behavior, and weak-cell behavior.
  • A tool for comparing simulator predictions against board or device measurements.
  • A fitting process that updates simulator parameters when measurements disagree.
  • A versioned chip-profile library so every result names the exact assumptions used.
  • A warning system that marks old or uncalibrated simulator results as weaker evidence.

Why It Matters

A simulator with guessed numbers can guide early design, but it cannot support strong product claims. The simulator becomes valuable when it is tied to measured device behavior and can explain where it is accurate or wrong.

Calibration Loop

  1. Run the model in the simulator with a named chip profile.
  2. Run a matching test on device, circuit simulation, board, or lab setup.
  3. Compare accuracy, latency, power, drift, and error patterns.
  4. Update the simulator parameters.
  5. Re-run the benchmark suite.
  6. Record which claims became stronger and which remain blocked.

Outputs

  • calibration_profile.json
  • simulator_vs_measurement.json
  • chip_profile_version.json
  • calibration_gap_report.md

Done means: simulator results clearly state whether they are hypothetical, source-backed, circuit-backed, board-backed, or measured-silicon-backed.

Acceptance Criteria

This goal is complete when the workbench can run a selected workload through the six-gap flow and produce a review package that is clear enough for engineering, customer, and investor review.

  1. The user can enter workload intake data without needing analog-chip expertise.
  2. The platform can classify the workload's Physical AI domain, loop type, update class, and safety relevance.
  3. The platform can produce an evidence matrix that blocks unsupported claims.
  4. The timing budget separates full-system latency from analog-core latency.
  5. The memory decision report explains update limits and safe update claims.
  6. The benchmark suite includes at least one strong-fit, one partial-fit, and one bad-fit workload.
  7. The simulator calibration report says whether assumptions are hypothetical, source-backed, circuit-backed, board-backed, or measured.
  8. The final answer uses plain language: fit, partial fit, not fit, or unknown.
  9. The exported review package includes raw evidence, normalized artifacts, claim status, and next work.

The result is not a promise that analog wins. The result is a disciplined machine for proving when analog wins.
