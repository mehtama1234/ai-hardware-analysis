chapter 05 · verification and claims

Prove the complete result

The final system needs more than a good circuit or a low simulated residual. It needs a chain of checkable translations from model intent to completed token, with every result labeled by what it can actually prove.

The hidden object: preservation across translations

At every boundary, representation can change. A tensor becomes quantized; a weight matrix becomes conductances; current becomes voltage; voltage becomes an ADC code; a code becomes a digital partial sum; a partial sum becomes a logit. Verification asks whether intended information survived each transformation.

model reference → graph import → quantized reference → placement → analog replay → recombination → RTL → extracted implementation → board trace → task output

Each equality has a different oracle. Passing one boundary does not imply that all later boundaries pass.

Acceptance gates

  1. Workload: model, weights, tokenizer, prompt set, phase, shape, and task metric fixed.
  2. Reference: digital baseline reproducible and archived.
  3. Mapping: every operator has placement, memory owner, precision, and fallback.
  4. Movement: bytes, conversions, synchronization, and KV-cache costs included.
  5. Analog: candidates have physical profiles and sensitivity results.
  6. Compiler: one schedule drives replay, cost, and runtime traces.
  7. Control: calibration, timeout, range, and fallback pass RTL checks.
  8. Physical: extracted/measured artifacts remain distinct from ideal models.
  9. Task: hybrid output meets quality threshold on held-out inputs.
  10. System: latency and energy use the same denominator as digital.
  11. Claim: package states supported, needs-review, and blocked claims.

Comparison protocol

Hybrid and digital must use the same model weights, tokenizer, inputs, sequence lengths, batch regimes, quality metric, host accounting, thermal condition, compilation budget, and stopping rule.

Failure examples are first-class results

Preserve operators rejected from analog placement, converter codes that fail, calibration profiles that fail held-out conditions, token cases where residuals change the selected output, thermal/supply cases that trigger fallback, schedules rejected because movement dominates, and mismatches between simulated, extracted, and measured behavior.

A good result is not one with no failures. It is one where failures are observable, classified, and connected to a design action.

End-to-end definition of done

  1. Digital baseline is reproducible.
  2. Hybrid plan is generated, not hand-waved.
  3. Movement and conversion costs are included.
  4. Analog eligibility is justified per operator.
  5. Physical constraints feed back into mapping.
  6. Calibration and fallback are executable.
  7. Token/task result is compared on held-out inputs.
  8. Latency and energy use a fair denominator.
  9. Failures and evidence limits are preserved.
  10. Final claim is narrower than or equal to evidence.
