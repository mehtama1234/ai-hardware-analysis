Plain-Language Primer

This section gives the reader enough background to understand the rest of the roadmap. It avoids treating terms as proof. A term explains what something is. Evidence proves whether it works for our chip.

Workload

A workload is the real job the customer wants to run. It is not only a model name. It includes the model, input data, required accuracy, response time, power budget, temperature range, update needs, and failure tolerance.

Why it matters: the same chip can be a good fit for one workload and a poor fit for another.

Analog In-Memory Compute

This means doing some math where the model weights are stored, instead of moving all weights into a separate processor for every calculation. The chip uses physical electrical behavior to do repeated matrix math.

Why it matters: moving less data can save energy, but the physical math can be affected by noise, heat, aging, and limited precision.

Hybrid Chip

A hybrid chip uses analog blocks for the parts they are good at and digital blocks for the parts that need exact control. Analog should handle repeated matrix-heavy work. Digital should handle changing decisions, control, scheduling, safety checks, and model steps that are hard to do reliably in analog.

Why it matters: the roadmap should not claim that the analog array runs the whole modern AI system by itself.

Compiler

The compiler is the translator. It takes a normal model and turns it into a plan for the chip. For this product, the compiler must decide what runs on analog, what stays digital, how big layers are split, how weights are placed, and what the board should run.

Why it matters: customers will not manually place weights on tiles, choose signal converter timing, or write low-level board commands.

ADC And DAC

A DAC turns a digital input number into an analog signal the array can use. An ADC turns the analog result back into a digital number. These blocks are necessary when digital software talks to analog compute.

Why it matters: these conversions take time and power. A fast analog array can still lose at the full-system level if conversion dominates the run.

Calibration

Calibration is the correction process for the real chip. It checks how the physical cells, tiles, voltages, and temperatures behave, then gives the runtime correction values and fallback rules.

Why it matters: an analog result is not trustworthy just because the digital model was accurate. The platform must show which calibration profile was used and what happens if calibration fails.

Board Proof

Board proof means a package actually ran on a physical lab board or prototype setup. A useful board result includes pass or fail, firmware version, board version, timing, failure reason, and the exact setup used.

Why it matters: simulator output can guide design, but it cannot replace measured hardware behavior.

Power And Thermal Proof

Power proof shows how much energy was used. Thermal proof shows how hot the chip or board became. The result must say whether it measured the whole board, the chip, one rail, or only a small block.

Why it matters: a chip can look efficient if the measurement ignores the host computer, memory movement, signal conversion, or cooling problem.

Transformer Or VLA Model

A transformer is a model family used in many modern AI systems. A VLA model uses vision, language, and action information to choose what a machine should do. These models often mix reusable matrix math with changing attention, normalization, memory movement, and control behavior.

Why it matters: the platform must show the split. Some parts may fit analog. Other parts should stay digital or remain blocked until proven.

Evidence Package

The evidence package is the saved record of what was tested, what was estimated, what was simulated, what ran on hardware, what failed, and what is still missing.

Why it matters: this prevents a demo from becoming an unsupported claim. The package should let a customer, investor, or engineer review the same facts later.

Rule for the whole page:

Plain explanations make the roadmap readable, but they do not prove the chip. Only the right evidence can move a claim from idea, to estimate, to simulation, to compiler proof, to board proof, to measured task proof.

Ecosystem Lens: Example Players To Evaluate

The roadmap should name the surrounding players because the chip will not become useful by itself. It needs sensors, simulators, model tools, board hosts, manufacturing paths, and early customer workloads. The names below are public examples to evaluate. They are not claimed partners, customers, integrations, endorsements, or proof that the chip works.

Tactile And Touch Sensors

Example players: GelSight, DIGIT / Digit 360, XELA Robotics, Pressure Profile Systems.

Why they matter: tactile workloads create force, pressure, slip, contact, and surface signals close to the robot hand or gripper. That is a natural place to test whether analog near-sensor compute lowers power or latency.

First proof: choose one task such as slip detection or contact classification, collect a real sensor stream, run the same task through a digital baseline and analog simulation, then measure whether the task score survives.

Do not claim: tactile compatibility or partnership until a real integration and measured result exists.

Event Vision And Fast Sensor Streams

Example players: Sony Semiconductor Solutions event-based vision sensors, Sony/Prophesee IMX636, Prophesee EVK cameras, Prophesee partner cameras such as CenturyArks.

Why they matter: event cameras send changes instead of full image frames. That can reduce useless data and support fast local perception if the chip can handle the interface and timing.

First proof: run obstacle, motion, gesture, or feature-extraction benchmarks on real event streams and include sensor capture, buffering, preprocessing, ADC/DAC, and host overhead.

Do not claim: direct analog ingest or sub-millisecond sensor response until the complete sensor path is measured.

Simulation And Digital Twins

Example players: NVIDIA Isaac Sim and Omniverse, MuJoCo, Gazebo, Synopsys Electronics Digital Twin, PTC Onshape-to-Isaac-Sim workflows.

Why they matter: robotics teams need to test policies, contact behavior, safety, and timing before they risk physical hardware. Our virtual chip model should plug into that loop so customers can see analog noise, drift, latency, and update limits early.

First proof: create a simulator adapter that calls the analog chip model during a task run and records task score, timing, failure cases, and chip assumptions.

Do not claim: real-world deployment proof from simulation unless the simulator profile has been calibrated against board and lab measurements.

Board And Edge-Compute Companions

Example players: NVIDIA Jetson, Qualcomm Dragonwing robotics processors, NXP i.MX processors, Lattice low-power FPGAs, common microcontroller and FPGA module vendors.

Why they matter: the analog chip needs digital control, firmware, I/O, power rails, safety override, logs, and a host system. These parts decide whether the full loop is actually fast and low power.

First proof: build a companion-board plan and measure sensor-to-answer timing, power, heat, firmware overhead, and fallback behavior on the same run.

Do not claim: analog replaces the host processor. The better claim is that analog helps selected matrix-heavy sections while digital logic handles control and safety.

Memory, Foundry, And Packaging Path

Example players: Weebit Nano ReRAM, GlobalFoundries 22FDX and embedded MRAM paths, Samsung Foundry, TSMC, memory-device university labs, packaging houses.

Why they matter: the memory choice controls weight capacity, precision, write speed, endurance, drift, retention, temperature behavior, and manufacturability.

First proof: measure a small array, fit simulator parameters to real device behavior, then decide whether the first workload should be fixed-weight, rare-update, adapter-update, or blocked for frequent learning.

Do not claim: manufacturable product readiness from a paper, process announcement, or single device result.

Compiler And Simulation Toolchain

Example players: IBM AIHWKIT, Sandia CrossSim, analog-mlir, SST/Golem, gem5-X / ALPINE-style system simulation, PyTorch, JAX/XLA.

Why they matter: customers should bring normal models. They should not manually program tile placement, analog voltages, converter schedules, weight writes, or calibration tables.

First proof: use existing tools where they fit, then add custom chip-target passes and adapters for our physical tile sizes, ADC/DAC rules, update rules, runtime commands, and evidence logs.

Do not claim: an open-source simulator proves our chip. It proves only the assumptions that were modeled.

Why This Roadmap Exists Now

The roadmap needs a market reason, not only an engineering reason. The larger shift is that AI is moving from chat screens and cloud servers into machines that see, touch, move, inspect, carry, sort, assemble, monitor, and act in the physical world. That shift changes what an inference chip must prove.

Trend 1: AI Is Moving Into Physical Systems

Physical AI means AI that works with real sensors, real timing, real power limits, real movement, and real failure modes. This includes robots, drones, vehicles, factory equipment, warehouse systems, smart cameras, tactile sensors, industrial inspection tools, medical devices, agriculture machines, and infrastructure monitors.

What this means for us: the chip cannot be judged only by one model benchmark. The platform must ask what physical system the model belongs to, what the system must sense, how quickly it must respond, how much power it can use, and what happens if it is wrong.

Trend 2: More Work Must Run On The Device

Cloud AI is powerful, but a physical device cannot always wait for the cloud. A robot hand, drone, vehicle, security sensor, or factory controller may need a local answer because the network is slow, unavailable, expensive, or not allowed for privacy and safety reasons.

What this means for us: the chip roadmap should focus on local inference where latency, power, heat, and sensor distance matter. The platform must show whether the analog chip improves the full local system, not just one math operation.

Trend 3: New Robot Models Are More Adaptive

New physical AI models are moving toward vision-language-action behavior. In simple terms, they take images, words, sensor readings, and body state, then produce actions. Some new on-device models are designed to adapt to new robot bodies, new sensors, and new tasks with a small amount of new data.

What this means for us: fixed-weight analog inference is not enough for every future workload. The roadmap must test whether weights can be updated, whether only small adapter layers can change, how much writing costs, and whether the chip remains reliable after updates.

Trend 4: Sensor Data Is Getting Larger And More Local

Physical systems are using more cameras, event sensors, force sensors, tactile skins, microphones, radar, lidar, temperature sensors, and vibration sensors. Sending all raw sensor data to a large processor can waste power and create delay.

What this means for us: the chip may be strongest near the sensor, where it can reduce data early or run low-power local inference. The platform must include the sensor path, preprocessing cost, synchronization, and sensor-to-answer latency instead of starting only at the model input tensor.

Trend 5: Simulation Is Becoming Part Of The Product

Physical systems are expensive and risky to test only in the real world. Companies increasingly train and test machines inside digital simulation before sending them to hardware. For our chip, this means the virtual chip model is not a side tool. It is part of how users decide whether the chip is usable.

What this means for us: the platform must connect model analysis, analog simulation, compiler mapping, system simulation, and board evidence into one review flow. A user should see what was simulated, what was measured, and what still needs real hardware proof.

Trend 6: Investors And Customers Want Proof, Not A Demo Story

Physical AI hardware takes more money, more time, and more integration work than software-only products. A good demo is not enough. Customers and investors need to know whether the same workflow can be repeated across models, boards, sensors, and workloads.

What this means for us: the workbench should become the proof system for the company. It should turn each roadmap claim into evidence, blocked reasons, required measurements, and safe wording.

Roadmap consequence:

These trends push us toward a hybrid analog/digital chip, a virtual chip model, a compiler path, sensor-aware workload review, weight-update readiness, board measurement, and an evidence archive. The end-to-end platform exists because the market is not only asking, "Is analog efficient?" It is asking, "Can this physical workload run on this chip with proof we can trust?"

Modification Playbook

This section turns the roadmap into a build checklist. Each item explains the plain meaning first, then says why we need it, what we can reuse, what we must build or modify, what the product should show, and what proof is required before the company can make a stronger claim.

1. Calibration And Chip Self-Checks

Plain meaning: the chip must check its own analog behavior before the platform trusts a result. Real analog cells do not all behave exactly the same, and their behavior can change with heat, voltage, use, and age.

Why we do it: without calibration, a good digital model can become a weak hardware result. The platform must know which correction profile was used and what happens if correction fails.

What we reuse: AIHWKIT, CrossSim, and internal simulators can help model noise, drift, limited precision, and weak cells before hardware is ready.

What we build or modify: silicon needs temperature monitors, voltage monitors, reference cells, tile health checks, and fallback behavior. The compiler and runtime need calibration profiles, weak-tile lists, correction values, recalibration commands, and failed-calibration handling.

What the product shows: calibration profile used, measured or assumed condition, missing calibration proof, drift risk, weak tiles, fallback status, and claim impact.

Proof required: a calibration trace from the board that includes pass or fail, correction values, weak tiles, temperature, voltage, failure behavior, and task result after calibration.

2. Tiling And Bit-Slicing

Plain meaning: large model layers must be split into physical pieces the chip can hold. If one model weight needs more precision than one analog cell can store, the compiler must spread that weight across multiple cells and combine the partial result.

Why we do it: a model may look good on paper but fail physically because it needs too many arrays, too many cells, too much memory movement, or too much converter work.

What we reuse: analog-mlir gives a starting point for converting supported layers into analog-style work. CrossSim can help estimate physical array risks.

What we build or modify: the compiler must know tile size, array count, cell precision, slice count, memory capacity, ADC/DAC placement, partial-result addition, and digital fallback rules.

What the product shows: tile plan, slice plan, physical fit, memory use, estimated latency, unsupported layers, and why a layer is too expensive or blocked.

Proof required: a compiler report that matches the target chip constraints, plus simulation or board evidence showing the mapped model still meets accuracy and runtime targets.

3. Transformer And VLA Partitioning

Plain meaning: modern robot and physical AI models mix different kinds of work. Some parts reuse stable weights and may fit analog arrays. Other parts make changing decisions, normalize values, handle actions, or enforce safety and should usually stay digital.

Why we do it: claiming that the analog chip runs the full model is risky if only the repeated matrix-heavy parts run on analog. The platform must show the split clearly.

What we reuse: analog-mlir layer extraction gives a starting idea for finding supported regions in a model graph.

What we build or modify: the compiler must scan transformer blocks, VLA action heads, sensor frontends, static projections, feed-forward layers, attention paths, Softmax, LayerNorm, safety/control boundaries, and unsupported operators.

What the product shows: analog candidates, digital-required parts, fallback parts, blocked parts, rewrite options, and the reason for every blocked region.

Proof required: mapping evidence, full-system runtime evidence, task accuracy evidence, and update or safety boundary evidence for the same model package.

4. ADC And DAC Scheduling

Plain meaning: digital software has to talk to analog arrays through signal converters. A DAC turns digital input numbers into analog signals. An ADC turns analog results back into digital numbers.

Why we do it: the analog math can be fast while the full system is slow because inputs, outputs, converters, memory, or the host computer become the bottleneck.

What we reuse: task graph ideas from analog-mlir, SST/Golem, ALPINE/gem5-X, and local estimators can help model system timing before the board exists.

What we build or modify: the compiler and runtime must schedule ADC sharing, DAC timing, column grouping, tile parallelism, memory movement, host dispatch, and digital accumulation.

Plain-English Foundation

This page should make sense even if the reader has never built a chip. These are the basic ideas used throughout the roadmap.

Analog Compute

Normal digital chips turn everything into exact 0s and 1s. Analog compute uses real electrical levels, like voltage and current, to do math. It can be very power-efficient for repeated math, but it is less exact.

Why it matters: we may save energy, but we must prove the model still gives the right answer.

In-Memory Computing

Most chips move data from memory to a processor, do math, then move the result back. In-memory computing does some math where the data is stored.

Why it matters: moving data costs energy. Doing math near memory can save power if the rest of the system does not add the energy back.

Analog Array

An analog array is a grid of tiny memory cells. Each cell stores a model weight as an electrical setting. When inputs pass through the grid, the grid naturally performs matrix math.

Why it matters: this is where the chip may be strongest, but the grid has size, precision, noise, and drift limits.

Digital Coprocessor

This is a normal digital helper block placed near the analog array. It handles steps that need exact logic, branching, sorting, control, or nonlinear math.

Why it matters: the chip should be hybrid because modern AI models contain work that analog arrays should not handle alone.

ADC And DAC

A DAC turns a digital number into an analog signal. An ADC turns an analog signal back into a digital number.

Why it matters: these translators can use power and time. If the model crosses back and forth too often, the analog benefit can disappear.

Compiler

A compiler is a translator. It takes a model written in normal software form and turns it into a plan the chip can run.

Why it matters: customers should not manually decide voltages, tile placement, memory movement, or chip commands.

Simulator

A simulator is a software test bench. It lets us test expected chip behavior before the real chip or board is ready.

Why it matters: simulation helps find problems early, but it is not the same as measured hardware proof.

Board Proof

Board proof means the model actually ran on a prototype board or lab setup and produced measured traces.

Why it matters: strong claims about speed, power, heat, and reliability need measured results, not only simulator output.

1. Virtual Chip Model

Each step turns one user question into one product result. The result must be written in complete sentences so the reader understands what happened and what still has not been proven.

1. Model Intake

The user learns whether the platform can open the model and understand its basic shape. The platform should show the model inputs, outputs, layers, operators, and size. This does not prove the chip can run the model. It only proves that the review can start from a real model file.

2. Analog Fit

The user learns which model parts may be good candidates for analog compute and which parts need digital compute. The platform should explain why each part was classified that way. This does not prove speed or power. It only creates the first analog/digital map.

3. Analog Accuracy

The user learns whether analog behavior such as noise, drift, limited precision, and imperfect weight writing may hurt the model answer. AIHWKIT and the local analog-error adapter can support this step. This is simulator or estimate evidence unless it is later backed by hardware.

4. Crossbar Layout

The user learns whether the physical memory grid could change the math. CrossSim can help test wire effects, read noise, bit slicing, programming error, and converter range. This does not prove the final chip. It tells us which layout assumptions are risky.

5. Hardware Cost

The user learns whether the workload seems realistic for the chip budget. The platform should show estimated area, memory use, energy, latency, and converter cost. NeuroSim or a local estimator can help, but measured silicon is needed before strong cost claims.

6. Compiler Mapping

The user learns whether normal model code can become a chip execution plan. The platform should show placement, tiling, bit-slicing needs, unsupported operators, and runtime target. Compiler mapping does not prove that the model keeps accuracy or saves power.

7. Transformer And VLA

The user learns which parts of modern robot or action models are analog candidates and which parts should stay digital. Static projection layers may be candidates. Changing attention, Softmax, LayerNorm, action timing, and safety logic usually need digital handling.

8. Full-System Runtime

The user learns whether CPU work, memory movement, signal conversion, and software overhead may erase the analog benefit. SST/Golem and ALPINE/gem5-X can support this in simulation. A real board trace is still needed for measured runtime claims.

9. Board Runtime

The user learns whether the model package actually ran on a prototype board or lab setup. The platform should show pass or fail, latency, timing variation, failure reason, firmware version, and board setup. Runtime alone does not prove energy or accuracy.

10. Power And Thermal

The user learns how much energy the run used and how hot the setup became. The platform should show which power lines were measured, what temperature was recorded, and whether the measurement covered the whole system or only one part of the chip.

11. Task Accuracy

The user learns whether the mapped model still solves the real task. The platform should compare the original model result with the mapped or hardware-run result using the task metric that matters for the workload. A speed result without task accuracy is incomplete.

12. Weight Updates

The user learns whether the chip can change model weights after deployment. The platform should separate fixed weights, rare updates, small adapter updates, and frequent local adaptation. Strong update claims need write energy, write time, endurance, retention, rollback, and post-update accuracy.

13. Sensor Path

The user learns what happens before the model input. The platform should show sensor capture, preprocessing, buffering, synchronization, latency, energy, and who owns that work. A chip-only claim is incomplete if the sensor path is ignored.

14. Final Answer

The user gets one direct answer: fit, proof, broken parts, safe claims, blocked claims, and next engineering work. The final answer must not upgrade estimates into measured proof. It should say exactly what can and cannot be claimed today.

How The Silicon Roadmap Fits

The silicon roadmap is useful only if the reader can see what it means for the product. This section translates the roadmap into plain decisions, proof requirements, and limits.

Build Software Before Silicon

The roadmap is right to start with software. We should not build a chip first and then discover that normal models cannot use it. The first product job is to build a virtual chip model, a model review flow, and evidence records so every later hardware decision has a clear test.

Use A Hybrid Chip

The roadmap is right that the chip should not be purely analog. Analog arrays are useful for repeated matrix math. Digital logic is still needed for changing decisions, exact control, software scheduling, model parts such as Softmax and LayerNorm, and safety-related behavior.

Build A Compiler

The roadmap is right that users should not manually program analog circuits. A customer should bring a normal model file. The compiler should split the model, place the analog-suitable parts, keep the digital parts digital, and produce a package that the simulator or board can run.

Account For Physical Effects

The roadmap is right to treat noise, drift, heat, signal conversion, and weight updates as core issues. These are not side details. They can decide whether the chip gives a real benefit or whether the low-power analog core is hidden by accuracy loss, conversion cost, update cost, or system overhead.

Use Careful Claim Language

We should not call the software model a perfect replica. It is a calibrated virtual chip model, and it is only as good as the measurements used to tune it. We should not call the chip unbeatable. We should say which selected workloads are supported by evidence and which workloads still need proof.

Keep Candidate Ideas Labeled

Memory choices such as STT-MRAM or FeRAM, package choices such as glass interposers, scheduling methods such as group-level parallelism, and analog filtering methods should stay labeled as candidate designs until the platform has simulation, compiler evidence, board evidence, or lab measurements for them.

Do Not Overclaim VLA Support

A robot or VLA model may contain some analog-friendly math, but that does not mean the whole model runs on analog. The product must show the split: what the analog array handles, what the digital coprocessor handles, what the CPU or controller handles, and what is still blocked.

Make Every Claim Pass Through Evidence

Every important claim should point to a proof level. A paper example is context. A local estimate is planning evidence. A simulator result is simulation evidence. A board trace is measured runtime evidence. A power trace is measured energy evidence. The platform must not let one kind of proof stand in for another.

1. Separate Analog And Digital Physically

Plain meaning: the chip has quiet analog areas and noisy digital areas. They cannot be placed carelessly next to each other.

Problem: fast digital logic switches on and off many times per second. That switching creates electrical disturbance. Sensitive analog arrays can pick up that disturbance and produce wrong math.

What changes in silicon: place analog and digital blocks apart, add protective isolation, protect the power lines that feed analog blocks, add quiet spacing around analog areas, and evaluate package choices that reduce electrical leakage between sections.

What changes in software: the simulator must include the chance that digital activity disturbs analog reads. The compiler should avoid scheduling noisy digital work at the same time as sensitive analog work when the chip allows that control.

What our platform shows: substrate-noise risk, isolation evidence, affected tiles, required measurements, and whether the claim is simulation-only or measured.

Board Integration In Everyday Terms

This is the path from "the compiler made a file" to "the chip actually ran something." It needs to be explained carefully because many roadmap words hide real lab work.

Board

A board is the physical test platform that holds the chip and lets a PC talk to it. Early boards are usually not pretty products. They are lab tools with connectors, test points, power inputs, and debug access.

Why the user cares: without a board result, we do not know whether the compiled model actually runs on hardware.

USB, Ethernet, PCIe, JTAG, And UART

These are common ways for a computer to talk to a test board. The right choice depends on whether the user needs a simple demo connection, a fast data path, or a low-level debug path for engineers.

USB: USB is often the easiest connection for an early lab demo because most computers support it and the setup is simple.

Ethernet: Ethernet is useful when the board sits on a network, in a shared lab rack, or in a remote test setup where several people or services need to reach it.

PCIe: PCIe is a high-speed connection often used by accelerator cards. It matters when the model sends a lot of data between the computer and the chip.

JTAG: JTAG is a low-level debug connection. Engineers use it when firmware, chip startup, register settings, or board bring-up are not working correctly.

UART: UART is a simple serial text connection. It is often used for early logs, status messages, and basic board bring-up before the full runtime path is stable.

Power Rails

A chip does not have one generic power input. Different parts of the chip may have separate power lines. These are called rails.

For example, the analog array, digital logic, memory, and input/output pins may each use a separate rail. Measuring these separately helps us see where the energy is really going.

Why the user cares: if we measure only the analog array rail, we may hide the real power used by the whole system.

Runtime Status

The board must report what happened during a run so the platform can separate a real result from a failed attempt. A status record should say whether the package loaded, weights were programmed, inference started, inference finished, or the run stopped early.

Important failure states include timeout, calibration failed, memory transfer failed, unsupported command, firmware mismatch, or chip did not respond.

Why the user cares: a failed run should not look like missing data or a successful estimate.

Debug Traces

A debug trace is a record of what happened step by step. It helps engineers find where the run broke.

Example: the PC sent the package, the board accepted it, the chip started layer 1, layer 2 fell back to digital, the run stopped at layer 3.

Why the user cares: the platform can explain failure instead of only saying "run failed."

Firmware Metadata

Firmware is the low-level software running on the board or chip controller. Metadata means the version and settings that describe that software.

Example: firmware version, board revision, driver version, clock speed, calibration profile, runtime mode.

Why the user cares: results are only meaningful if we know exactly what software and board setup produced them.

Latency, Jitter, Energy, And Temperature

Latency: latency means how long one run took from the start signal to the finished result. A low latency result matters when the chip is used in a robot, vehicle, sensor, or control system that must respond quickly.

Jitter: how much the timing changes from run to run. A robot may care about steady timing, not only average timing.

Energy: energy means how much electrical work was used during the run. A useful result should say whether it measured the whole board, the chip, or only one internal power rail.

Temperature: temperature means how hot the chip or board became during the run. This matters because heat can change analog behavior and can make a product harder to package or cool.

Why the user cares: these decide whether the chip is useful in a real device.

Synchronized Task Accuracy

This means the task result is tied to the same model package, same board run, same power trace, and same test setup.

Bad proof: power was measured on one run, accuracy was measured on a different setup, and the model package changed in between.

Good proof: this exact package ran on this exact board, used this much energy, reached this temperature, and produced this task result.

Concrete Compiler Changes

The compiler is the translator between a normal AI model and the chip. This section explains each compiler change without assuming the reader already knows compiler language. `analog-mlir` gives us useful starting ideas, but a real product needs our own chip target and our own evidence contract.

1. Layer Extraction

Plain meaning: first, the compiler must read the model and find the parts that look like good candidates for analog compute.

What we reuse: `analog-mlir` already has an idea called `analog-extract-layers`. It looks for supported layer-shaped regions such as linear layers and convolution layers.

What we add: our product needs to also find transformer blocks, VLA action heads, sensor frontends, unsupported operators, and reasons why something cannot run on analog.

What the user sees: a clear list of model parts: analog candidate, digital required, unsupported, or needs rewrite.

2. Analog Conversion

Plain meaning: after finding candidate layers, the compiler must turn them into a chip-style plan.

What we reuse: `analog-mlir` has `analog-convert-layers`, which turns supported model pieces into an analog execution form.

What we add: our chip has real limits: tile size, number of arrays, cell precision, ADC/DAC placement, memory capacity, and data movement. The compiler must include those limits instead of using a generic analog idea.

What the user sees: this layer fits, this layer needs many tiles, this layer needs bit-slicing, this layer is too expensive, or this layer falls back to digital.

3. Weight Isolation

Plain meaning: analog arrays are strongest when model weights are written once and reused many times.

What we reuse: `analog-mlir` has `analog-isolate-weights`, which separates persistent weights from changing runtime inputs.

What we add: Physical AI may need updates. We must mark which weights are fixed, which can be written later, whether only small adapter layers can change, how updates are written, and how rollback works if an update fails.

What the user sees: fixed-weight ready, periodic-update candidate, adapter-update candidate, or adaptive Physical AI blocked.

4. Task Graph

Plain meaning: a model run is not one step. It is a chain of analog work, digital work, memory movement, sensor work, and safety checks.

What we reuse: `analog-mlir` has `analog-assemble-task-graph`, which represents work as a runtime plan.

What we add: our plan must include digital coprocessor tasks, sensor preprocessing tasks, safety/control handoff, memory movement, calibration checks, failure paths, and fallback paths.

What the user sees: a map of what runs on analog, what runs on digital, what moves through memory, and where the system can fail.

5. Simulation Target

Plain meaning: before the real chip works, we still need a software place to test the compiler output.

What we reuse: `analog-lower-to-golem` sends compiler output toward Golem/SST simulation.

What we add: keep this path for simulation, but translate its output into our normal evidence format so the frontend can explain it plainly.

What the user sees: simulation-only compiler evidence. Useful, but not proof that the real board ran.

6. Real Chip Target

Plain meaning: the compiler eventually has to produce something our actual board and chip can load.

What we reuse: the general compiler shape and analog execution ideas from `analog-mlir`.

What we add: a new chip target path, runtime command generation, register writes, firmware interface, board package format, and error reporting.

What the user sees: chip target missing, chip target available, board package generated, or board package failed with a reason.

7. Calibration

Plain meaning: calibration is the chip's correction record. It tells the software how the real analog hardware differs from the ideal model.

What we reuse: existing simulators can help us think about drift, noise, and imperfect cells, but they cannot create the final correction record for our physical chip. The real calibration profile must come from our board, our chip, and our lab measurements.

What we add: the compiler and runtime need calibration tables, weak-tile lists, correction values, drift profiles, temperature profiles, voltage profiles, recalibration commands, and fallback rules. Each item has a job. The tables store corrections. The weak-tile list marks array regions that should be avoided. The profiles explain the physical condition being assumed. The commands rerun correction when needed. The fallback rules stop the system from pretending a bad calibrated run is valid.

What the user sees: the user should see the calibration profile used for the result, the condition it was tested under, the missing calibration proof, and the claim impact. If the model only worked with assumed calibration, the page should say that. If the model worked with measured calibration on a board, the page should say that too.

8. Scheduling

Plain meaning: the compiler must decide the order of work so the chip is not waiting on signal conversion, memory movement, or the host computer.

What we reuse: task graph concepts from the compiler pipeline.

What we add: ADC sharing rules, DAC timing rules, tile parallelism, column grouping, memory movement, host dispatch, and digital accumulation scheduling.

What the user sees: compute-limited, conversion-limited, memory-limited, host-limited, or balanced result.

How These Modifications Enter Our Roadmap

Each modification enters the roadmap in two stages. First we make the platform ask the right question and store the right evidence. Later we add the real simulator, compiler, board, or lab path that produces stronger proof.

Analog/Digital Isolation

This work checks whether noisy digital circuits can disturb sensitive analog math. Digital blocks switch quickly and can create electrical disturbance. Analog arrays can be affected by that disturbance because they compute with physical signals.

Now, the platform should add a roadmap gate that asks whether this risk has been modeled or measured. Later, the platform should import substrate-noise simulation and lab measurements from real switching workloads.

A strong claim needs measured noise while digital blocks are switching and analog arrays are computing. Without that measurement, the platform should treat this as a risk, not as solved hardware.

Heat And Drift

This work checks whether heat or time changes stored analog weights enough to hurt accuracy. In an analog chip, the model weights are physical states, so temperature and aging can move them away from the intended value.

Now, the package should record temperature and drift assumptions. Later, the platform should add thermal modeling, board temperature imports, and drift tests that run over a meaningful time period.

A strong claim needs a temperature trace plus task accuracy under the same tested heat and drift condition. It is not enough to show accuracy at room temperature and separately discuss heat as a theory.

Memory/Device Choice

This work chooses the physical memory type that matches the product promise. A chip designed for fixed weights has different needs from a chip that claims frequent updates or local adaptation.

Now, the frontend and package should show the assumed memory type and update pattern. Later, the platform should add device-specific simulation profiles and write tests for the selected memory behavior.

A strong claim needs write latency, write energy, endurance, retention, and variability data. Without those measurements, update claims should stay limited.

Tiling And Bit-Slicing

This work splits big model layers and high-precision weights into pieces the chip can physically store and compute. A model layer may be larger than one analog array, and one model weight may need several physical cells.

Now, the fit report should estimate tile count and slice count so the user sees the physical cost early. Later, the compiler should produce placement backed by the real chip limits.

A strong claim needs a compiler report that matches the target chip's tile size, precision, memory, and signal-converter limits. A generic layer count is not enough.

ADC/DAC Scheduling

This work checks whether signal conversion and memory movement erase the analog advantage. ADCs turn analog results into digital values. DACs turn digital inputs into analog signals. If these blocks become the bottleneck, fast analog math may not help the full system.

Now, the platform should show conversion work as a visible risk and cost. Later, the compiler and system simulator should show how converter timing, memory movement, and host dispatch are scheduled.

A strong claim needs a runtime trace showing converter timing, memory movement, and host overhead. A core-only speed number should not be used as a full-system speed claim.

Analog Filtering/Pruning

This work checks whether the chip can discard unimportant sensor data early without hurting the task. The idea is useful only if it saves energy and keeps the important signal.

Now, the platform should treat analog filtering as a candidate design option, not as a guaranteed chip feature. Later, the platform should add sensor-specific simulation and circuit evidence for the exact filtering method.

A strong claim needs measured power saving plus task accuracy after filtering. Saving power is not useful if the filtered model misses the thing the user needed to detect.

Transformer/VLA Split

This work separates repeated matrix math from changing attention, normalization, action, and control logic. Analog arrays may help with stable linear weights, but they usually should not be presented as running the whole modern robot model.

Now, the frontend and backend should produce a partition report that shows which model parts are analog candidates and which parts stay digital. Later, the compiler should turn that split into a real mapping for the analog arrays and digital coprocessor.

A strong claim needs mapping evidence, runtime evidence, and task evidence. Without all three, the platform should avoid saying the full VLA workload is ready.

Calibration Metadata

This work carries correction information for imperfect analog cells and changing physical conditions. Calibration tells the system how the real chip differs from the ideal math.

Now, the package should include calibration fields and claim rules that block strong statements when calibration evidence is missing. Later, the runtime should run calibration steps and attach board evidence to the package.

A strong claim needs a calibration trace and proof that the system handles calibration failure safely. The platform should show what happens if calibration fails instead of hiding the failure.

Weight Updates

This work proves whether the model can change after deployment without making the chip too slow, too power-hungry, or unreliable. A fixed-weight product and an adaptive Physical AI product are very different claims.

Now, the platform should show the update class and the missing proof. Later, it should add write tests, update tests, retention tests, rollback flow, and accuracy checks after the update.

A strong claim needs write cost, endurance, retention, rollback, and post-update accuracy. If those are missing, adaptive claims should stay blocked.

Board Integration

This work connects the PC, board, chip, lab instruments, backend, and frontend into one measured workflow. It is the path from a software package to a hardware result the user can review.

Now, the platform should add import contracts and demo traces so the frontend can show the shape of real evidence. Later, it should add a live board execution service that sends packages to a prototype board and collects results.

A strong claim needs board runtime, power trace, thermal trace, and task result from the same setup. Evidence from mismatched setups should stay separated.

Compiler And Runtime Direction

The compiler is the bridge between normal AI models and the physical chip. `analog-mlir` can help, but it is not a finished compiler for our chip. We should keep the Golem/SST path for simulation and add our own chip target beside it.

Reuse

We can reuse `analog-mlir` as a starting point for finding model layers, representing analog-style work, separating stable weights from changing inputs, and learning from the Golem/SST simulation path. This gives us compiler structure, but it does not give us a finished product compiler for our chip.

Modify

We need to add the parts that only our chip can define: the final chip target, physical tile sizes, bit-slicing rules, signal-converter scheduling, calibration data, weight-update data, runtime package format, board loader path, and clear error reporting when a model cannot be mapped.

Expose

The frontend should tell the user exactly where the compiler result stands. It should say whether the result is simulation-only, whether the real chip target is missing, whether a board-loadable package was generated, or whether the path is blocked with a specific reason.

External Toolkits In The Product

Toolkit names can sound abstract. In this platform, each toolkit is just a helper that answers one narrow question. No single toolkit proves the whole chip.

How To Read Toolkit Results

A toolkit result should be read as one piece of proof. It says something useful about one part of the chip story, such as accuracy risk, layout risk, compiler mapping, or system timing.

What The Platform Adds

The platform translates each toolkit result into plain language, stores it with the package, checks what claim it can support, and shows what evidence is still missing.

AIHWKIT

AIHWKIT is a Python and PyTorch toolkit for testing how analog hardware behavior may affect a neural network. It can help show whether noise, drift, limited converter precision, and imperfect weight programming may hurt the model. It does not prove board speed, board power, final silicon behavior, or production readiness.

AIHWKIT-Lightning

AIHWKIT-Lightning is the faster path for larger analog simulation sweeps. It helps when the model is too large for slow detailed experiments. It is still simulator evidence. It does not replace a real board run or a power measurement.

CrossSim

CrossSim helps test the physical memory grid. It can model risks from wire resistance, read noise, programming error, bit slicing, and converter range. It helps answer whether the array layout may damage accuracy. It does not prove the final packaged chip behaves the same way.

analog-mlir

analog-mlir is a compiler starting point. It can help identify model regions that look suitable for analog execution and can produce simulation-oriented runtime plans. It does not automatically produce code for our real chip. We need a chip-specific target before it becomes a deployment compiler.

SST/Golem

SST/Golem is a system simulation path. It helps test how a CPU or controller might send work to an analog accelerator, wait for results, and move data. It is useful before hardware is ready. It does not prove what a real board will measure.

ALPINE/gem5-X

ALPINE/gem5-X is a fuller computer-system simulator. It can include CPU behavior, memory behavior, operating-system effects, and accelerator calls. It helps find system bottlenecks. It does not prove real energy, heat, or production readiness.

NeuroSim

NeuroSim helps estimate chip-level cost such as area, latency, energy, and memory needs. It is useful for early hardware planning. It is not a measured silicon result, so its output must be shown as an estimate.

TxSim, XBTorch, And RxNN

These tools can help explore training behavior, update behavior, and memory-device behavior for crossbar-style hardware. They are useful when we need to understand write noise, drift, or memristor behavior. They do not prove write endurance, rollback, or retention unless those are measured.

Board, Power, Thermal, And Task Tools

These are the lab and product evidence sources. They show whether the package ran, how long it took, how much energy it used, how hot it got, and whether it solved the task. They prove only the setup that was actually tested.
