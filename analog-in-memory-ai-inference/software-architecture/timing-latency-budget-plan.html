Timing And Latency Budget Plan

This page defines how to measure whether analog compute helps the complete Physical AI loop, not just one matrix operation.

Question: does the full sensor-to-action path meet the timing deadline?

Rule:

Average analog-core latency is not enough. Robotics and safety claims need full-path and worst-case timing.

Plain-Language Vocabulary

Latency means delay. If a sensor sees something now but the system reacts too late, the AI may be correct and still fail the physical task.

A loop is the repeated path from sensing to action. A robot gripper may read force sensors, detect slip, choose a correction, and change motor force many times per second.

ADC means analog-to-digital converter. It turns a real electrical signal into a number. DAC means digital-to-analog converter. It turns a number into an electrical signal.

AFE means analog front end. It is the circuit that first touches the sensor signal, such as a force, voltage, current, pressure, or vibration signal.

VMM means vector-matrix multiplication. In plain terms, it is a common neural-network math operation where many input numbers are multiplied by many stored weight numbers and added together.

A safety override is an independent path that can stop or change an action if the learned policy suggests something unsafe.

Timing Stages

  1. Sensor capture.
  2. Analog front-end conditioning.
  3. Input conversion or direct analog ingest.
  4. Analog array computation.
  5. ADC output conversion.
  6. Digital accumulation and nonlinear operations.
  7. Memory movement and host scheduling.
  8. Safety filter check.
  9. Command output or upstream feature transfer.

How The Timing Budget Happens Practically

  1. Start with the task deadline. For example: "detect slip and react within 2 ms."
  2. Break the deadline into stages: sensor read, AFE, conversion, analog compute, digital compute, memory movement, safety check, and output.
  3. Put an estimate or measurement beside each stage.
  4. Mark the evidence level: guessed, source-backed, simulated, firmware-measured, board-measured, or lab-measured.
  5. Add the stages together for average timing and worst-case timing.
  6. Identify the bottleneck: the slowest or riskiest stage.
  7. Decide whether analog improves the complete loop or only one small part of it.

Common Mistakes This Page Prevents

  • Quoting only analog array speed while ignoring converters and digital support.
  • Using average latency when the safety case needs worst-case latency.
  • Forgetting memory movement and host runtime overhead.
  • Using one timing number for all Physical AI loops.
  • Claiming a reflex loop works before measuring the whole path.

Detailed Walkthrough

The timing budget should start from the physical consequence of being late. In a search engine, a late answer is annoying. In a robot hand, a late answer can mean the object already slipped. In a drone, it can mean the obstacle is too close. That is why the timing page must measure the whole path.

Before The Timing Budget

Start with the task metric and ask which deadline matters. There may be more than one. A tactile reflex may need a response in a few milliseconds. A higher-level policy may run every 20 or 50 milliseconds. A calibration update may happen over seconds or minutes.

During The Timing Budget

Each stage gets three values: target time, estimated or measured time, and evidence level. Evidence level matters because a guessed timing number should not be treated like a measured board trace.

After The Timing Budget

The output should identify the bottleneck. If analog compute is 0.1 ms but memory movement is 3 ms, then the analog core is not the current problem. If ADC conversion dominates, the hardware architecture needs converter or scheduling changes. If safety override is too slow, the workload cannot support safety claims yet.

What The User Should Conclude

The final timing answer should not be "the chip is fast." It should be more specific:

  • The full loop meets the deadline.
  • The analog core is fast but another stage dominates.
  • The loop only meets average timing, not worst-case timing.
  • The timing evidence is still estimated, so measured timing claims remain blocked.

Outputs And Done Criteria

  • loop_classification.json: loop type and timing criticality.
  • timing_bottlenecks.md: what stage dominates and what must be improved.

Done means the final answer can say whether analog improves the complete loop and whether any timing claim is still blocked.
