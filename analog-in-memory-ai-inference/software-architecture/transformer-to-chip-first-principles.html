Transformer To Chip

A practical engineering program for translating what the semiconductor conference themes teach us into a hybrid transformer inference system: selected fixed-weight work in analog memory, dynamic and safety-critical work in digital logic, and every claim tied to a measurable boundary.

The decision we are trying to make

We are not trying to prove that an entire large language model belongs in analog hardware. We are trying to decide, operator by operator and token phase by token phase, whether a particular transformer workload gets a better complete result from a hybrid implementation than from a fair digital baseline.

model + task + deadline + quality target
  -> operator and tensor inventory
  -> movement and conversion budget
  -> analog/digital/SRAM placement
  -> target-specific compiler schedule
  -> physical error and calibration model
  -> runtime governor and fallback
  -> token/task result
  -> latency, energy, reliability, and evidence claim
First-principles rule: an optimization is real only if it preserves the required output, under the stated operating conditions, at the complete-system boundary. A faster matrix multiply that adds expensive conversions, cache movement, calibration, or recovery can be a worse transformer implementation.

Our concrete vertical slice

The first implementation target is the existing three-block transformer-style MLP fixture, followed by an attention-shaped block and then a small token-level transformer workload.

deep-transformer-mlp-stack.onnx
  12 fixed-weight matrix multiplications -> analog candidates
  bias, nonlinearities, residuals, control -> digital
  activations, partial sums, calibration -> SRAM/digital support

attention-shaped block
  static Q/K/V/output projections -> conditional analog candidates
  score formation, scaling, Softmax, value selection -> digital
  KV-cache state -> SRAM/digital memory path

small token workload
  prefill and decode measured separately
  output quality and token deadline become the acceptance boundary

The current MLP and attention packages are useful software evidence. They are not measured silicon proof. The engineering task is to make their compiler, movement, physical, and evidence contracts agree.

Definition of practical success

  • Every transformer operator has a placement and reason.
  • Bytes, conversions, calibration, fallback, and KV-cache movement are counted.
  • Physical constraints can reject an otherwise attractive mapping.
  • The hybrid result preserves the digital baseline’s declared task output.
  • Latency and energy use the same denominator for digital and hybrid.
  • Claims identify simulation, circuit, layout, board, and blocked evidence.
Boundary: an operator residual, simulated TOPS/W estimate, or routed digital controller is not proof that a complete LLM runs efficiently on production analog silicon.

Allowed claim

This page can claim that the project has a concrete, staged engineering program connecting transformer workload definition, movement accounting, analog eligibility, compiler scheduling, physical constraints, runtime fallback, and evidence acceptance.

Refused claim

This page cannot claim that the complete transformer runs on analog silicon, that a software residual is measured hardware performance, or that the product is production-ready.
