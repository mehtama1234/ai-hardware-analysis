Plain Words Before The Details

This page should be readable even if the reader does not know chip design, machine learning, or compiler terms.

Workload The real job the user wants to run. It includes the model, the input data, the device, the speed target, the energy target, and the success metric.
Model The AI program. For example, a wake-word detector, image classifier, robot policy, sensor anomaly detector, or transformer model.
Analog Chip A chip that tries to do some AI math inside memory using physical electrical behavior. This can save energy, but only for the parts of the model that fit this style of compute.
Digital Fallback Parts of the model that cannot run well on the analog chip and must run on normal digital hardware instead. Too much fallback can erase the advantage.
Proof Evidence that supports a claim. A paper is weak proof for a customer workload. A measured board result is stronger. A task accuracy result is stronger still.
Breaks The reasons the claim is not ready. A break can be a missing measurement, unsupported model part, too much data movement, lost accuracy, high energy, or update risk.
Compiler Mapping A tool report that says which parts of the model can actually be placed on the analog chip and which parts must stay somewhere else.
Board Runtime A real measurement from a board or prototype that says how long the workload took to run and where time was spent.
Power And Thermal Measurements of energy use, peak power, and heat. These matter because low-power claims are not credible without measured energy and temperature behavior.
Task Accuracy The answer to: does the model still do the actual job correctly after it is changed, mapped, simulated, or run on hardware?
Transformer / VLA A transformer is a modern model style used in language, vision, and robotics. VLA means vision-language-action: a model that connects seeing, language-like reasoning, and action. These are harder for analog chips than simple fixed models.
Weight Update Changing the model after deployment. This matters for robots, personalized devices, and customer-specific models. Updating analog memory can be slow, costly, or wear out the device if not proven.

How The Platform Reaches The Answer

This is the missing flow. It shows what the user enters, what the platform checks, how the answer changes, and what comes out.

Demo workload

A robotics company wants to run a camera-and-touch model on an edge device. The model helps the robot decide what it is touching and what action to take next. The company wants lower power than a normal digital processor, but it also needs reliable accuracy and safe action handoff.

1
User enters the workload The user uploads the model and selects: robotics, camera plus touch input, low-power edge device, target latency, target energy, target accuracy, and chip profile. The platform now knows what job is being tested.
2
Platform reads the model It lists the model parts. Some parts are simple matrix math and may fit the analog chip. Some parts are control logic, normalization, attention, or custom operations and may need normal digital hardware.
3
Platform checks analog fit It asks: which parts can run inside analog memory, which parts need digital fallback, and how often data must move between the two. If data moves too often, the energy benefit may shrink.
4
Platform checks the tool evidence AIHWKIT or CrossSim can test analog accuracy risk. analog-mlir can test whether the model can be mapped to the chip path. Attention partitioning can test transformer hard parts. System simulators can test whether the rest of the computer slows things down.
5
Platform checks real measurements It looks for board runtime, power and heat data, and task accuracy. If these are missing, the platform does not allow strong claims. It says exactly which measurements are missing.
6
Platform checks update needs If the robot model must adapt after deployment, the platform asks whether the chip can safely update weights or small adapters. It looks for write speed, write energy, endurance, retention, rollback, and post-update accuracy.
7
Platform writes the answer For this demo, the answer is: partial fit. Some model parts look good for analog. Dynamic attention and control handoff need digital support. Board power, task accuracy, and update evidence are missing.
8
Platform gives the next work Run CrossSim for crossbar risk. Import analog-mlir mapping. Keep Softmax and control logic digital. Measure board latency and power. Run task accuracy after mapping. Measure update energy before any adaptive claim.

What Each User Actually Does With This

Investor Looks at one customer workload and asks: "Is this a real product path?" The platform shows whether the answer is backed by model analysis, simulator results, compiler mapping, board measurements, power data, and task accuracy. If those are missing, the investor sees the exact gaps.
Customer Uploads or shares a model and asks: "Will this work for my use case?" The platform shows which model parts fit the analog chip, which parts stay digital, what has been measured, and what proof is still needed before a pilot.
Founder Uses the result to decide what to build next. If many workloads fail because compiler placement is missing, build compiler support. If claims fail because power is not measured, prioritize board and power measurement. If robotics claims fail because weight updates are unproven, treat updates as a roadmap gate.
Engineer Gets a concrete work list. Example: run CrossSim for parasitics, import analog-mlir placement, keep Softmax digital, measure board latency, measure power, run task accuracy, and attach the results to the package.

What The Product Has To Show

1. The Direct Answer Example: "Partial fit. Good fixed-weight analog candidate. Not ready for adaptive Physical AI or production claims."
2. What Runs Where Shows analog layers, digital layers, fallback layers, unsupported layers, and where data moves between analog and digital hardware.
3. What Proof Exists Shows whether the proof is only a source, a local estimate, a simulator result, compiler output, board runtime, power trace, or task accuracy result.
4. What Breaks Names the blockers directly: unsupported ops, Softmax, dynamic attention, too much data movement, drift, missing compiler path, missing board data, or missing update proof.
5. What To Do Next Turns each blocker into work: run a simulator, connect a compiler, rewrite a model block, measure power, measure accuracy, or test weight updates.
6. What We Can Say Creates safe wording for customers and investors, plus a clear do-not-say list when proof is missing.

How Proof Changes The Answer

The same workload can move from "interesting idea" to "pilot ready" only when stronger proof is added.

1
Public paper or sourceThis means a paper, public benchmark, or outside example says something similar has worked before. It is useful background. It does not prove this user's model works on this chip.
2
Local estimateThis means our platform makes a first estimate from the model structure. It can say "this looks worth testing." It should not be used as a strong customer claim.
3
Analog simulator resultThis means a software tool tests what could happen when math is done with imperfect analog memory. It checks likely accuracy loss from noise, drift, converter limits, and crossbar effects.
4
Compiler mappingThis means a tool tries to place model parts onto the analog chip. It answers: "Can these layers actually get to the chip path, or are we only guessing?"
5
System simulationThis means a larger simulator checks the chip together with the processor, memory, and software around it. It catches cases where the analog core looks good but the full system is slow.
6
Board runtimeThis means the workload ran on a real board or prototype and the platform has the timing result. It answers: "How long did it actually take?"
7
Power and heat measurementThis means a real meter or lab setup measured energy, peak power, heat, and sometimes update energy. It answers: "Did it really save power?"
8
Task accuracy resultThis means the final mapped model was tested on the real task. It answers: "Did the model still solve the user's problem after all the chip changes?"

What Each External Tool Gives The User

AIHWKITPlain meaning: a software lab for testing analog AI behavior. User question: "If the chip math is noisy or drifts over time, will my model still work?" Output: a simulated accuracy-risk report. It cannot prove real board speed or real power.
AIHWKIT-LightningPlain meaning: a faster version for larger tests. User question: "Can we run this analog simulation on a larger model without waiting too long?" Output: faster large-model simulation. It is still not hardware proof.
CrossSimPlain meaning: a simulator for crossbar memory arrays, which are grid-like analog memory blocks. User question: "Will the physical layout of the memory hurt accuracy?" Output: risk from wire resistance, noise, bit slicing, ADC settings, and programming errors.
analog-mlirPlain meaning: a compiler path. A compiler turns a model into steps hardware can run. User question: "Can this model actually be prepared for the analog chip?" Output: mapped layers, digital fallbacks, unsupported parts, and compiler gaps.
Attention PartitionerPlain meaning: a checker for transformer hard parts. User question: "Which transformer parts fit analog, and which parts must stay digital?" Output: analog candidates, digital-required attention, Softmax and LayerNorm boundaries, and rewrite options.
SST/GolemPlain meaning: a system timing simulator. User question: "Even if the analog part is fast, will the rest of the computer slow it down?" Output: simulated bottlenecks from processor dispatch, memory movement, and synchronization.
ALPINE/gem5-XPlain meaning: a fuller computer-system simulator. User question: "What happens when the analog accelerator sits inside a full system with CPU, memory, and software?" Output: simulated system behavior before a board exists.
TxSim, XBTorch, RxNNPlain meaning: extra simulators for training, device behavior, and updates. User question: "Are model updates or memory-device behavior risky?" Output: early update and device-risk simulation. Real write energy and endurance still need lab measurement.
LIMCAPlain meaning: a design exploration helper. User question: "If this chip design is not enough, what should we try next?" Output: possible future memory-array or chip-block designs under power, area, and accuracy limits.
Board, Power, Task ServicesPlain meaning: real measurement feeds. User question: "What happened on real hardware, and did the task still work?" Output: measured latency, power, heat, and task accuracy. This is what unlocks stronger claims.

Detailed Toolkit Pages For Non-Technical Review

Each tool helps answer one part of the central question. None of them proves the whole product by itself. Our platform's job is to collect their results, explain them in plain words, and keep weak proof separate from strong proof.

AIHWKIT

AIHWKIT is a software test bench for analog AI chips. It lets us take a normal AI model and test what may happen when the model runs on imperfect analog memory instead of clean digital math.

Problem It Helps AnswerWill the model still be accurate if the chip has noise, drift, limited converter precision, and imperfect weight programming?
What The User Gives UsA model, a target task, expected accuracy, and chip assumptions such as converter precision, noise level, drift behavior, and update behavior.
What Comes BackA simulation result showing whether analog effects are likely to reduce accuracy, which layers are sensitive, and which chip settings matter most.
How It Changes Our AnswerIf the simulation is stable, the workload can move from "only a guess" to "simulator-supported candidate." If accuracy drops badly, the platform marks analog accuracy as a blocker.
What It Does Not ProveIt does not prove board speed, real power, real heat, manufacturing yield, or production readiness. It is software evidence, not hardware measurement.
Why It Matters To Our ProductIt gives the first serious check of whether analog physics could break the model before a customer or investor hears a stronger claim.

AIHWKIT-Lightning

AIHWKIT-Lightning is the faster version of AIHWKIT for larger models and larger test runs. It matters when a small simulator run is not enough to test the workload properly.

Problem It Helps AnswerCan we run enough analog simulation tests on a larger model without the test taking too long or using too much memory?
What The User Gives UsA larger model, a set of chip assumptions, and the test range they care about, such as drift levels, noise levels, and converter precision.
What Comes BackFaster simulation sweeps that show which settings look safe, which settings look risky, and where the model becomes fragile.
How It Changes Our AnswerIt helps the platform test bigger workloads instead of only toy examples. That makes the roadmap more credible for modern models.
What It Does Not ProveIt still does not prove real board behavior. A faster simulator is still a simulator.
Why It Matters To Our ProductIt supports bigger customer reviews where a normal simulation path may be too slow for useful iteration.

CrossSim

CrossSim helps test the analog memory grid itself. In simple terms, an analog chip often uses a grid of memory cells. Real wires and cells are imperfect, and those imperfections can change the math.

Problem It Helps AnswerWill the physical memory layout, wire resistance, read noise, programming error, bit slicing, or converter range hurt the final model result?
What The User Gives UsA model or math workload, array assumptions, precision settings, and the chip behavior we want to test.
What Comes BackAn accuracy-risk result tied to crossbar effects: how the memory grid, wires, and readout settings may change the answer.
How It Changes Our AnswerIt helps explain whether the model is only good in clean software or still looks good when placed near real analog memory behavior.
What It Does Not ProveIt does not prove the final chip has the same behavior. It also does not replace board power, board timing, or task testing.
Why It Matters To Our ProductIt lets our platform show a customer why the physical layout of analog memory is part of the answer, not a hidden detail.

analog-mlir

analog-mlir is a compiler path. A compiler is the part of the system that turns a model into instructions and placements the hardware can actually use.

Problem It Helps AnswerCan the model actually be prepared for analog execution, or are we only saying it looks compatible from a high level?
What The User Gives UsA model graph and target hardware rules: supported layers, array sizes, precision, memory limits, and digital fallback rules.
What Comes BackA placement-style report: which layers were found, which were converted, which weights were isolated, which steps stay digital, and which parts failed.
How It Changes Our AnswerCompiler evidence moves the workload from "looks like a fit" to "these exact parts have a path toward the chip."
What It Does Not ProveIt does not prove low power, board timing, thermal behavior, or final task accuracy. It proves mapping progress, not product performance.
Why It Matters To Our ProductWithout this layer, the platform cannot tell the difference between a real chip path and a slide-level compatibility claim.

Attention Partitioner

The attention partitioner is our product capability for transformer and VLA-style models. It separates model parts that may fit analog compute from parts that usually need digital hardware.

Problem It Helps AnswerWhich transformer parts can use analog matrix math, and which parts are hard because they change every input or require non-linear math?
What The User Gives UsA transformer, vision transformer, multimodal model, robot policy model, or VLA-adjacent model.
What Comes BackA split of static projection layers, feed-forward layers, dynamic attention, Softmax, LayerNorm, memory-heavy blocks, and rewrite options.
How It Changes Our AnswerIt prevents the platform from saying "transformer-ready" just because some matrix layers look good. It gives a more honest mixed analog/digital answer.
What It Does Not ProveIt does not prove the rewritten model is accurate, fast, or low power. Those need simulation, compiler mapping, board measurement, and task testing.
Why It Matters To Our ProductModern Physical AI claims often involve transformers or VLA-like systems. This feature keeps those claims specific and testable.

SST/Golem

SST/Golem is a system simulator. It helps test the analog accelerator together with a simulated processor and memory system before real hardware is available.

Problem It Helps AnswerEven if the analog core is fast, does the full system lose time moving data, waiting on the processor, or synchronizing work?
What The User Gives UsA mapped workload, processor assumptions, memory assumptions, accelerator dispatch rules, and timing targets.
What Comes BackSimulated timing evidence for processor dispatch, memory movement, synchronization, and analog accelerator calls.
How It Changes Our AnswerIt can show that the analog math is not the whole story. A workload may look good at the core level but still fail the full-system timing target.
What It Does Not ProveIt does not replace a real board. It is a stronger system estimate, not a real measured result.
Why It Matters To Our ProductIt helps our platform answer whether the whole device path is credible, not just whether one chip block is efficient.

ALPINE/gem5-X

ALPINE/gem5-X is a fuller computer-system simulator. It models analog acceleration inside a larger system with processors, memory, software, and operating-system behavior.

Problem It Helps AnswerWhat happens when the analog accelerator is not alone, but has to run inside a real computing stack?
What The User Gives UsA target workload, software runtime assumptions, processor and memory setup, and analog accelerator settings.
What Comes BackA full-system simulation result showing likely runtime behavior, memory effects, software overhead, and accelerator interaction.
How It Changes Our AnswerIt strengthens or weakens the system-readiness score before silicon or board proof exists.
What It Does Not ProveIt does not prove measured power, real thermal behavior, manufacturing readiness, or final customer-task accuracy.
Why It Matters To Our ProductIt helps investors and customers see whether the roadmap includes the full machine around the analog chip.

TxSim, XBTorch, And RxNN

These are additional simulation tools for training behavior, device behavior, and memory-update risk. They matter when the model may need to be changed or adapted after deployment.

Problem They Help AnswerHow risky are weight updates, write noise, device variation, conductance drift, and memristor behavior for this model?
What The User Gives UsA model, update pattern, memory-device assumptions, training or fine-tuning settings, and acceptable accuracy loss.
What Comes BackEarly evidence about update sensitivity, device variation risk, and whether the model looks fragile under changing analog memory behavior.
How They Change Our AnswerThey help decide whether a workload is fixed-weight only, occasional-update candidate, adapter-update candidate, or blocked for adaptive Physical AI.
What They Do Not ProveThey do not prove real write energy, real write time, real endurance, retention, rollback, or post-update board accuracy. Those need measurement.
Why They Matter To Our ProductThey support the weight-update gate so we do not confuse efficient fixed inference with real on-device adaptation.

LIMCA

LIMCA is a design exploration tool. It is useful when the current chip plan may not satisfy the workload and the team needs to explore future chip or memory-array choices.

Problem It Helps AnswerIf the current chip is not enough, what design directions could improve power, area, and accuracy?
What The User Gives UsDesign targets such as power limit, area limit, accuracy target, array choices, and possible circuit constraints.
What Comes BackCandidate design directions and simulation-backed options for future chip planning.
How It Changes Our AnswerIt moves a blocker into a roadmap item: what chip design change may be worth exploring next.
What It Does Not ProveIt does not prove the current workload runs on the current chip. It is future design planning evidence.
Why It Matters To Our ProductIt helps the founder and hardware team turn failed workload fit into a concrete design exploration path.

Board, Power, Thermal, And Task Services

These are not research simulators. They are measurement feeds from real hardware tests and real task tests. They provide the proof needed for stronger claims.

Problem They Help AnswerWhat actually happened when the workload ran on hardware, and did it still solve the user's real job?
What The User Gives UsA board run, power trace, temperature result, accuracy run, update test, calibration result, or lab report.
What Comes BackMeasured latency, measured energy, peak power, heat, task accuracy, update cost, calibration cost, and failure records.
How They Change Our AnswerThey can move a claim from simulated or estimated to measured. This is what investors and customers need for stronger confidence.
What They Do Not ProveOne board result does not automatically prove production readiness, reliability across all conditions, or every customer workload.
Why They Matter To Our ProductThey are the strongest evidence layer. The platform must make them easy to attach, review, and audit.

How This Source Material Is Relevant To Our Platform

The source is not just background research. It tells us what proof engines our product should connect to, what each engine can prove, and where our platform must prevent overclaiming.

Core Now: Analog Accuracy Risk AIHWKIT and CrossSim are directly relevant because our platform must answer whether analog chip behavior could hurt accuracy. They help test noise, drift, converter limits, programming error, wire resistance, and crossbar layout effects. In our product, their outputs become analog accuracy evidence, not final hardware proof.
Core Now: Compiler Mapping analog-mlir is directly relevant because our platform must show which model parts can actually be prepared for analog execution. Without compiler mapping, a model may only look good on paper. In our product, analog-mlir-style output becomes the model placement report: analog parts, digital parts, unsupported parts, and rewrite needs.
Core Now: System Reality Check SST/Golem and ALPINE/gem5-X are relevant because an analog core is only one part of a real device. The processor, memory, software, and data movement can reduce the benefit. In our product, these tools provide system simulation evidence before a board is available.
Core Now: Transformer And VLA Boundary The source explains why transformers are harder than simple models. Some projection layers may fit analog compute, but dynamic attention, Softmax, LayerNorm, and memory movement often need digital support or model changes. Our product must stop a user from claiming "VLA-ready" just because a few matrix layers map well.
Near-Term: Weight Update Risk TxSim, XBTorch, and RxNN-style tools matter because Physical AI systems may need updates after deployment. They can help model write noise, device behavior, and training/update risk. Our product still requires real write latency, write energy, endurance, retention, rollback, and post-update accuracy before stronger adaptive claims.
Near-Term: Architecture Planning LIMCA is relevant when the answer is: "the current chip shape is not enough." It can help explore future memory-array or chip-block designs under power, area, and accuracy limits. In our product, this belongs in roadmap planning, not customer workload proof.
Background Only: JAX Physics Examples RF-Squad is useful as an example of fast physics simulation using JAX. It is not an analog in-memory AI deployment tool for our first product. The lesson is that future simulators could use JAX-style acceleration, but we should not present RF-Squad as proof for an analog AI chip workload.
Our Platform's Job The toolkits are separate and technical. Our platform turns them into one answer: what fits, what proof exists, what breaks, what to test next, and what claim is safe. The value is not owning every simulator. The value is making their outputs understandable, comparable, and auditable.

Claim Boundaries

Safe To Say This workload has analog-friendly regions and a clear plan for what to test next.
Needs Review Simulation or compiler evidence exists, but board, power, or task evidence is incomplete.
Blocked Production readiness, adaptive Physical AI, or full VLA readiness cannot be claimed without stronger proof.
Do Not Claim Do not say analog is better just because one core operation is efficient. The full system must be counted.
