Evidence Matrix Plan

This page defines the rulebook that maps each claim to the evidence required to say it safely.

Question: what proof is required before we say a workload fits, runs, saves power, or is ready for Physical AI?

Rule:

A simulator result, compiler map, or demo page can support only the claim it actually proves. It must not unlock board, power, thermal, task, or production claims by accident.

Plain-Language Vocabulary

A claim is something the company says is true, such as "this workload is a good fit" or "this setup saves power."

Evidence is the proof behind that claim. Different claims need different evidence. A simulator result is useful, but it is not the same as a real board measurement.

A board trace is a record from actual hardware while it runs. A power trace is a measurement of energy use over time. A thermal trace is a measurement of temperature over time.

The evidence matrix is a rulebook: it tells the platform what a result is allowed to prove and what it is not allowed to prove.

Claim-To-Evidence Matrix

ClaimAllowed Evidence, ExplainedWhy This Evidence Is NeededSafe WordingBlocked Wording
Analog candidate Use customer intake, the model graph, layer density, tensor shapes, update class, and task metric. This means we first prove the workload has the kind of work analog is meant for: repeated matrix math, stable or rarely changed weights, clear success criteria, and a physical reason to care about power or latency. Without this, we may benchmark a workload that was never a good analog target. A model can be impressive and still be wrong for analog if most of its time is dynamic control, memory movement, unsupported operators, or frequent updates. This workload appears analog-friendly enough to test further. This chip will run the workload well.
Analog accuracy risk Use AIHWKIT, CrossSim, a local analog-error adapter, or a calibrated simulator. The evidence must include the raw configuration: precision, ADC/DAC settings, read noise, write error, drift, IR drop, temperature assumptions, tile mismatch, and the dataset or task used. Analog hardware is not exact. The model may lose accuracy when weights are noisy, values drift, or converters round signals. We need to see whether the model still works under the exact assumptions being tested. Under these stated analog assumptions, the model kept enough accuracy for this task. The real chip preserves accuracy.
Compiler support Use a layer split, tile map, bit-slicing plan if needed, digital fallback list, unsupported-operation list, memory movement estimate, and runtime schedule. This tells us how the model would actually be placed across analog arrays and digital helpers. A model that looks analog-friendly still may not fit the physical chip. Large matrices may need many tiles. Some layers may require digital logic. Some operators may be unsupported. The compiler evidence shows whether there is a real execution path. The compiler can map these layers and identifies the parts that stay digital or blocked. The board can execute the package successfully.
Latency fit Use a timing budget, simulator timing, firmware logs, board trace, or system simulator result. The timing must include the full path: sensor input, analog front end, DAC, analog compute, ADC, digital logic, memory movement, host/runtime overhead, safety check, and output. Analog compute can be fast but the complete loop may still be late. Robotics and sensor-near claims need worst-case timing, not just average analog-array speed. This estimated or measured full loop meets this stated deadline. Analog core speed proves robot timing.
Power fit Use a full-system power estimate or measured board power. The evidence must include analog array energy, ADC/DAC energy, digital helper energy, memory movement, host overhead, idle power, duty cycle, and thermal context. A single analog operation may be energy-efficient while the full system is not. Converters, data movement, and host control can consume enough power to reduce or remove the expected benefit. For this workload and setup, the estimated or measured system power meets the target. Analog gives a universal 100x power gain.
Adaptive readiness Use write latency, write energy, endurance, retention, drift after rewrite, recalibration time, rollback behavior, and post-update task accuracy. If using adapter updates, include which weights stay fixed and which small parts are allowed to change. Physical AI may need updates after deployment. Analog memory can be harder to rewrite than normal digital memory. Even high-endurance RRAM still needs proof that repeated analog weight writes remain accurate, affordable, and stable. This workload supports fixed weights, rare updates, or adapter updates under these measured or bounded limits. The chip supports all on-device learning.
Safety readiness Use a safety-boundary report, independent override path, worst-case override timing, fallback behavior, fault handling, and safety test results. The evidence must say whether analog inference is advisory, policy-level, safety-relevant, or safety-authoritative. A learned model should not be the only safety mechanism for a physical machine. If a robot, drone, or actuator can cause harm, an independent digital or control-system path must be able to block unsafe actions. The safety boundary is defined and this tested setup has an independent override path. The neural policy is safe because it ran once.
Production readiness Use repeated board results, calibrated simulator agreement, power and thermal measurements, task results, reliability testing, manufacturing/yield evidence, software/runtime stability, customer validation, and qualification plan. Production readiness is much stronger than a demo. It means the system works repeatedly, can be manufactured, can be supported, and has evidence under the target customer conditions. This tested configuration supports this limited customer claim with these attached measurements. The platform is commercially proven for all target markets.

How To Read One Row

Take the power row as an example. If the analog array alone uses very little energy, that is useful but incomplete. The full system still spends energy moving data, converting signals, running digital operations, keeping memory active, and coordinating the host processor.

So the evidence matrix allows a narrow claim from narrow proof:

Safe: the analog array estimate is low under this model.

But it blocks a broad claim until broader evidence exists:

Blocked: the full product saves power on the customer workload.

That broader claim needs full-system estimate first, then measured board power later.

Implementation Rules

  1. Each artifact must name its source, date, assumptions, and evidence level.
  2. Evidence levels must be explicit: hypothetical, source-backed, simulated, circuit-backed, board-backed, measured, or production.
  3. One evidence type cannot silently substitute for another.
  4. Blocked claims should explain the exact missing artifact.
  5. The review package should export both safe claims and blocked claims.
