Hybrid Analog-Digital Benchmarking Pipeline

This page explains how benchmarking actually happens when an analog chip must work with digital blocks, memory, software, sensors, and a host system.

Question: how do we practically test whether a workload runs better on a hybrid analog + digital system than on a normal digital baseline?

Rule:

Do not benchmark the analog array alone and call it workload performance. The real result is the complete path: input, analog compute, converters, digital helpers, memory movement, runtime, output, and task score.

Why This Must Be Hybrid

An analog in-memory compute array can be very good at repeated matrix math. But a real AI workload contains more than matrix math.

Modern models also contain normalization, Softmax, activation functions, attention control, memory movement, safety checks, sensor handling, buffering, and runtime scheduling. Many of those pieces are better handled by digital logic.

So the practical benchmark target is not:

analog array only

The practical benchmark target is:

sensor or model input
-> analog compute
-> ADC/DAC conversion
-> digital helper logic
-> memory movement
-> host/runtime control
-> output
-> task score

ADC means analog-to-digital converter. DAC means digital-to-analog converter. These matter because analog arrays still need to communicate with digital software and control systems.

Step 1: Split The Workload

Start by opening the model and listing what it actually does. The goal is to identify which parts are good analog candidates and which parts must stay digital.

Practical Work

  • Load the model file, usually ONNX, PyTorch export, JAX export, or another graph format.
  • Read the model graph and list every operation.
  • Mark linear layers, convolutions, and repeated matrix operations as analog candidates.
  • Mark Softmax, LayerNorm, dynamic attention, control flow, safety logic, and unsupported operators as digital or blocked.
  • Mark large reshape, buffer, token-cache, or memory-copy steps as system costs.

Step 2: Define The Hybrid Hardware Profile

Now describe the whole system being tested. If we only describe the analog core, the benchmark will miss the digital and physical costs that may dominate the result.

Practical Work

  • Write down analog tile size, such as 512 x 512.
  • Write down analog weight precision, such as 2-bit, 4-bit, or 8-bit effective weight storage.
  • Write down ADC and DAC precision, latency, and energy.
  • Write down what the digital helper can do: Softmax, LayerNorm, accumulation, control, safety, or scheduling.
  • Write down SRAM or buffer size. SRAM is fast digital memory used for temporary data.
  • Write down memory bandwidth, host processor role, power per block, and thermal limits.
analog tile: 512 x 512
weight precision: 4-bit effective
ADC: 8-bit, measured or estimated latency
DAC: 8-bit, measured or estimated latency
digital helper: Softmax, LayerNorm, accumulation, control
SRAM: 8 MB
target power: under 1 W
thermal limit: stated package and board limit

Output: hybrid_hardware_profile.json

Step 3: Compile Or Map The Model

This step matches the model to the hardware. It answers: where does each operation run, how is it split, and what does the runtime actually execute?

Practical Work

  • Take each analog candidate layer from Step 1.
  • Check whether it fits on one analog tile.
  • If it is too large, split it across several tiles.
  • Decide how partial outputs from multiple tiles are added back together.
  • Schedule when inputs are converted, when outputs are digitized, and when digital operations run.
  • Report unsupported operations instead of hiding them.

Example: a 2048 x 2048 matrix cannot fit on one 512 x 512 tile. It becomes 16 tile-sized chunks. The execution plan must say how those chunks run and how their results are combined.

Output: hybrid_execution_plan.json

Step 4: Run A Hybrid Simulator

Now simulate the whole system. This is where analog behavior and digital overhead meet.

Analog Side

Simulate lower precision, read noise, drift, imperfect weight writing, IR drop, tile mismatch, and ADC/DAC limits.

Digital Side

Simulate Softmax, LayerNorm, accumulation, memory movement, scheduling, unsupported operations, and host/runtime overhead.

The simulator should produce accuracy, latency, energy, memory movement, thermal risk, and failure notes.

Example result:
Analog matrix layers save energy.
ADC conversion and memory movement dominate latency.
Final task accuracy drops 4%.
Thermal risk is low.
Compiler fallback is required for Softmax and LayerNorm.

Output: hybrid_simulation_result.json

Step 5: Compare Against A Digital Baseline

A result is only meaningful if we compare it with a fair alternative. The baseline is the normal digital path the customer would use if our analog chip did not exist.

Practical Work

  • Use the same model or a clearly explained equivalent model.
  • Use the same input data and task metric.
  • Use the same latency, power, and accuracy targets.
  • Compare full-system results, not just core math speed.

Step 6: Run Workload-Specific Benchmarks

Generic matrix tests are not enough. We need workloads that resemble real customer jobs.

Tactile Slip Detection

Tests whether sensor-near analog compute can detect object slipping quickly and with low false alarms.

Event-Vision Feature Extraction

Tests whether high-rate visual change signals can be turned into compact useful features.

Drone Perception

Tests battery-limited perception where heat, size, and energy are tight.

Industrial Anomaly Detection

Tests fixed or rarely updated sensing with clear fault and false-alarm metrics.

Small VLA Projection Block

Tests the analog-friendly linear layers from a vision-language-action style model without claiming full robot-brain support.

Known Bad Fit

Tests whether the system honestly rejects workloads with frequent full-weight updates, vague metrics, or heavy unsupported operations.

Each benchmark should produce the same type of result: task score, partition, mapping, timing, power, failure reason, safe claim, and next measurement.

Output: benchmark_run_results.json

Step 7: Move From Simulation To Hardware

When a board or chip exists, the benchmark should not change shape. The evidence level changes. Estimates are replaced with measurements.

Practical Work

  • Run the same benchmark on the real board or prototype.
  • Capture board latency traces.
  • Capture power traces.
  • Capture temperature traces.
  • Capture calibration logs.
  • Compare real output against simulator output.
  • Update simulator assumptions when the board disagrees with the model.

Example: if simulation predicted 0.8 W but the board measures 1.4 W, the simulator profile must be corrected and old power claims must be weakened.

Output: measured_hardware_result.json
