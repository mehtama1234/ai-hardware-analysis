Research Backlog

The research backlog defines what to verify next, which source types are acceptable, and what each research pass is allowed to change in the roadmap.

Source StandardsDifferent claims need different proof

Product features need official documentation. Funding needs company, investor, or filing evidence. Chip performance needs measured results from our own setup.

Research PassesMarket, tools, compiler, silicon, board, sensors

Each pass starts with a concrete question, preferred source types, sample queries, affected package fields, and an owner.

Claim BoundaryResearch cannot become chip proof

Outside sources can change framing and priorities. They cannot unlock board, power, calibration, task, update, or production claims.

Reuse And Modification Map

The product should reuse outside tools where they answer a narrow question, then add our own chip-specific compiler, runtime, board, calibration, and claim layers.

ReuseKnown toolkits

ModifyChip-specific paths

OwnProduct contract

Action And Evidence Map

Future run and import controls should produce validated artifacts. Each action should say what proof level it can reach and which claims must still stay blocked.

RunAdapter actions

Model intake, analog fit, analog simulation, layout check, compiler mapping, runtime estimate, and final answer generation should each update one artifact.

ImportEvidence files

Board traces, power traces, thermal traces, calibration records, update reports, sensor reports, and task results should be validated before they affect claims.

BlockClaim protection

A passed action can only unlock the claim it actually supports. Board latency still cannot prove power, heat, or task accuracy.

Silicon To Board Proof Map

A chip feature becomes a product claim only after the board runs the same package, the lab measures the same run, calibration is tied to the same chip, and the task result still passes.

SiliconFeature exists

The chip needs analog tiles, monitors, health checks, fallback paths, write controls, and debug counters before hardware claims can start.

BoardFeature is reachable

The board must expose control links, power rails, status, firmware, and debug traces so software and lab tools can prove what happened.

LabRun is measured

Runtime, calibration, power, temperature, task accuracy, and fallback evidence must point to the same package and setup.

BoardBoard runtime trace

CalibrationCalibration trace

SensorsSensor path report
