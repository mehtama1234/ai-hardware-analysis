analog-mlir To Silicon Compiler Plan

This page explains, from first principles, why a research compiler like analog-mlir is useful but not enough to deploy neural networks on a real analog AI chip.

The main question: can analog-mlir translate a normal AI model into something our physical chip can run?

Short answer:

Not by itself. It can be a starting point, but real silicon needs chip-specific placement, scheduling, calibration, runtime packaging, and board validation.

The Compiler Decision In First Principles

An analog array is a physical shortcut for a specific kind of math: many stored weights are multiplied by changing inputs and summed. The shortcut is useful only if the surrounding system does not spend the saved energy and time on conversion, movement, calibration, and fallback. That makes compiler mapping a constraint problem.

The safe compiler claim is narrow: the compiler has produced a reviewable placement under stated constraints. The unsafe claim is broad: the model is now proven to run well on the chip. That later claim needs board runtime, power, thermal, task, and calibration evidence.

The Basic Problem

A trained AI model is a file full of math instructions and learned numbers. A physical chip cannot run that file directly.

Something has to translate the model into a plan the chip can execute.

model file
-> chip-specific execution plan
-> commands the hardware can actually perform

That translator is the compiler.

So the real question is not only whether the model has analog-friendly layers. The real question is whether the compiler can turn those layers into a physical plan for our chip.

What analog-mlir Gives Us

analog-mlir already has a useful research shape. It understands that a model has layers, that some layers can become analog operations, that weights need to be set up, and that execution needs a runtime plan.

1. Find model layers that look analog-friendly.
2. Convert those layers into an analog representation.
3. Separate weight setup from runtime execution.
4. Build a task graph.
5. Lower the analog work to a simulator target.
6. Emit runtime graph builders.
Why This Helps

It gives us a compiler structure to learn from: layer extraction, analog operations, weight handling, task graph assembly, and runtime lowering.

The Limit

The current target is a simulator-style runtime, not our future board and physical silicon.

Why That Is Not Enough

A simulator can pretend there is an analog array. A real chip has physical limits and failure modes.

Real Chip Facts The Compiler Must Know

  • How large each analog tile is.
  • How many tiles exist.
  • How much precision the memory cells support.
  • How ADCs and DACs are shared.
  • How much memory is available.
  • Which operations must stay digital.
  • How data moves between analog, digital, memory, and host logic.
  • What firmware commands the board accepts.
  • What calibration profile is tied to the chip.
  • Which tiles are weak or unavailable.

A useful product compiler cannot only say this layer is analog. It must say exactly where the layer goes, how it is split, how weights are loaded, how conversion happens, what stays digital, and what command package gets sent to the board.

The Five Compiler Problems

1. Replace The Simulator Target

Current research flow lowers to a simulator runtime. Our chip will need a real output format.

That output might be custom instructions, firmware calls, command packets, register writes, DMA descriptors, or a runtime package. We should not lock that too early.

Safe statement: we need a chip-specific backend.

Blocked statement: we already know the exact instruction format before the board/runtime interface exists.

2. Split The Model Into Analog And Digital Work

Analog compute is good at stored-weight multiply-add work. AI models also contain normalization, probabilities, reshaping, memory movement, control logic, and safety checks. Those may need digital compute.

analog candidate
digital required
fallback
unsupported
needs review

For transformers, fixed projection and feed-forward layers may be analog candidates. Softmax, LayerNorm, token movement, and dynamic attention often need digital or system handling. For VLA, sensor timing, action timing, control handoff, and safety logic also matter.

Safe statement: the compiler must classify model pieces by where they can actually run.

Blocked statement: the whole transformer or VLA model is analog-ready because some layers are matrix-heavy.

3. Fit The Model Onto Physical Tiles

A model layer can be larger than the physical analog tile. The compiler must split large layers into smaller pieces, place those pieces, and combine partial results.

model layer: 8192 x 8192
chip tile: 512 x 512

The layer cannot fit in one tile.
It must be split, placed, run, and recombined.

If the model needs more precision than one memory cell supports, the compiler may also split a weight across multiple cells or columns. That is bit-slicing.

Safe statement: the compiler must know tile size, precision limits, partial sums, memory limits, and conversion points.

Blocked statement: a logical analog layer automatically fits the physical chip.

4. Avoid The ADC Bottleneck

The analog array produces analog results. The rest of the system usually needs digital numbers. ADCs convert analog results back to digital.

ADCs cost area, power, and time. They may be shared by many columns. If the compiler schedules work poorly, the chip can spend too much time waiting for conversions.

Do not let expensive ADCs sit idle.
Do not force too much data through one shared ADC group.
Spread independent work across groups that can run in parallel.

Safe statement: ADC-aware scheduling is needed.

Blocked statement: a published speedup applies to our chip before we test it with our workload, tile size, ADC design, and compiler rules.

5. Use Calibration Data

Analog hardware is not perfectly identical everywhere. Two tiles may behave differently. A programmed weight may not land exactly. Temperature and voltage may shift behavior. Some tiles may be weak.

Calibration means measuring how the real chip behaves, storing correction data, and using that correction data when compiling or programming the model.

lab measures chip
-> calibration service writes profile
-> compiler consumes profile
-> runtime programs chip
-> board run checks output
-> task accuracy confirms result

Safe statement: calibration profiles should be first-class compiler inputs.

Blocked statement: calibration works until board output and task accuracy confirm it.

What We Should Build

Instead of saying we will simply hack analog-mlir, the clean roadmap is to keep the useful ideas and add our chip's physical truth.

1. Use analog-mlir as a reference compiler frontend.
2. Keep its useful front half where it finds analog-shaped layers.
3. Add a chip profile that describes our real hardware limits.
4. Add model partitioning.
5. Add physical placement.
6. Add ADC-aware scheduling.
7. Add a chip-specific backend.
8. Add calibration-profile input.
9. Add runtime package generation.
10. Add tests that block unsupported claims.
Early Version

A local placement estimator and compiler report that says what would map to analog, what stays digital, and what is blocked.

Later Version

A chip-specific compiler backend that generates board-loadable packages tied to calibration profiles and runtime traces.

What The Compiler Must Output

A product compiler should output more than compiled successfully. It should produce reviewable evidence.

  • Runtime package.
  • Weight programming plan.
  • Tile placement map.
  • Analog/digital split.
  • ADC/DAC schedule.
  • Memory movement plan.
  • Fallback plan.
  • Calibration profile used.
  • Debug trace configuration.
  • Claim boundary.

This output feeds the rest of the proof ladder. It should make board runtime, power measurement, task accuracy, and calibration checks easier to connect to the same package.

Claim Boundary

If this compiler work succeeds, we can make a narrow claim.

Safe claim: the model has a chip-specific compiler plan, selected layers were placed onto physical resources, and a runtime package was generated with clear analog, digital, fallback, and calibration records.

But this still does not prove the chip works as a product.

Blocked claims: the board ran it, the chip saved power, task accuracy passed, the package is thermally safe, the chip is production-ready, or the chip is VLA-ready.

Those require later proof: board runtime, power and thermal measurement, task accuracy, calibration and drift testing, update testing, and sensor-to-answer evidence.

Bottom Line

analog-mlir cannot directly deploy to commercial silicon unchanged.

It gives us a useful research compiler structure.

To make it useful for real silicon, we must add the chip's physical truth:
tile sizes, precision limits, ADC/DAC behavior, digital fallback,
runtime commands, calibration data, and board-package generation.
