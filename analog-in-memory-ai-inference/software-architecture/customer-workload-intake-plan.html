Customer Workload Intake Plan

This page defines the first real step: collect enough information about a customer workload to judge analog fit honestly.

Question: what must we know before saying whether this workload belongs on an analog IMC chip?

Rule:

Do not judge a Physical AI workload from the model file alone. The physical system, timing, power, updates, sensors, and task metric matter as much as the neural network graph.

How This Page Fits The Connected System

The Connected System Map starts with the workload because the same model can be useful, risky, or irrelevant depending on the physical job. This page turns a customer request into the structured object every later page consumes.

Plain-Language Vocabulary

A workload is the actual job the customer wants to run. It is not only the AI model. It includes the sensor data, the physical device, the speed target, the power limit, and the definition of success.

A model file is the saved neural network. It may say what math the AI performs, but it does not say whether the robot, drone, camera, or sensor system succeeds in the real world.

A task metric is the score that matters. For a gripper, it may be slip detection. For a drone, it may be obstacle detection per watt. For industrial monitoring, it may be false alarms and missed faults.

A safety boundary is the line between advice and authority. If the AI suggests an action, something else may still need to approve or block it before a motor moves.

ONNX, PyTorch, and JAX are common ways AI teams build or exchange model files. The intake should accept that customers may arrive from different software stacks.

Analog IMC means analog in-memory computing: storing model weights near the place where the chip performs some of the math, so less data has to move around.

What We Build

Guided Intake Form

Collect model, task, sensor, deployment, timing, power, update, environment, and safety details in one structured flow.

Workload Classifier

Classify the workload as sensing-only, advisory, policy-level, reflex-level, safety-relevant, or unclear.

Metric Selector

Force the user to choose the success metric: task completion, accuracy, false alarm rate, latency, energy, uptime, or another measurable target.

Missing-Info Gate

If a required input is missing, the system should say what is missing instead of guessing.

Fields To Collect

The intake should feel like a structured interview. The user should not need to know chip language. The form should ask practical questions and translate the answers into technical fields behind the scenes.

How The Intake Happens Practically

  1. The customer names the physical system: robot hand, drone, camera, machine sensor, wearable, or another device.
  2. The customer uploads a model or describes the model if the file is not ready.
  3. The system asks what input arrives from the real world and how fast it arrives.
  4. The customer chooses the task metric, such as slip detection, false alarm rate, missed fault rate, obstacle detection, or energy per inference.
  5. The customer states the timing and power limits.
  6. The customer states whether the model changes after deployment.
  7. The platform produces an initial scope: what can be analyzed now, what is missing, and which claims are blocked.

Concrete Example

Suppose a customer says: "We have a robot gripper and want to detect object slip from tactile sensors."

Common Mistakes This Page Prevents

  • Calling a workload "robotics" without naming the actual task.
  • Optimizing model accuracy while ignoring latency, power, and safety.
  • Assuming a model fits analog before checking layer types and update frequency.
  • Using a sensor-near story without knowing the sensor bandwidth or preprocessing.
  • Claiming adaptive Physical AI when the model needs frequent weight rewrites that are not proven.

Detailed Walkthrough

The intake should work like a technical interview with guardrails. The customer should not be asked, "Is your model analog-friendly?" Most customers cannot answer that. Instead, the platform asks practical questions and infers analog relevance from the answers.

Before The Intake

The customer usually arrives with one of three things: a finished model, a model architecture but no final weights, or only a product idea. The intake should support all three. A finished model gives the strongest analysis. A model architecture gives partial analysis. A product idea gives only early scoping.

During The Intake

The platform should ask questions in ordinary language. For example, instead of asking for "latency constraint," ask, "How quickly must the device react after the sensor changes?" Instead of asking for "update cadence," ask, "Will the model change after the product ships?"

After The Intake

The platform should produce a short first verdict. This is not the final answer. It is a scope statement: what we know, what we do not know, what can be tested next, and what claims are blocked.

Decision Logic

The intake should classify the workload before any deeper tool runs.

  • Promising: repeated matrix-heavy inference, stable weights, clear metric, tight power or latency, sensor-near input.
  • Partial: some analog-friendly layers exist, but important digital work, memory movement, or update needs may dominate.
  • Blocked: vague task, no metric, frequent full-model learning, unsupported model operators, or no timing/power target.
  • Unknown: not enough information to judge yet.

This early classification protects the rest of the system. It prevents a customer from spending time on compiler or simulator runs when the basic task definition is missing.

Output Artifacts

An artifact is a saved file that records what we learned. It matters because the same evidence can be reviewed later by engineers, customers, investors, or lab teams.

  • workload_intake.json: structured facts collected from the customer.
  • physical_context.json: sensor, environment, safety, and deployment constraints.
  • success_metric.json: the measurable target used to judge the result.
  • initial_claim_scope.json: claims allowed, blocked, or unknown before deeper evidence exists.

Done Criteria

  1. The user can complete intake without knowing analog circuit terms.
  2. The platform can explain why the workload might fit or might fail.
  3. Missing critical data blocks stronger claims.
  4. The intake output feeds the evidence matrix, timing budget, memory decision, benchmarks, and calibration flow.
