ASPLOS 2025 — Deep Dive

First-principles overview — the problem, the approaches, where it fits

What ASPLOS is and why it exists

The International Conference on Architectural Support for Programming Languages and Operating Systems (ASPLOS) exists to answer a single question: how do hardware architecture, operating system kernels, compilers, and runtimes depend on and enable each other? When a software system runs slowly or consumes too much energy, the problem rarely lives in one layer. A cache miss might be a microarchitecture problem, but it could also be a compiler issue (poor register allocation), an OS issue (wrong virtual memory policy), or a language runtime issue (bad data layout). ASPLOS is the venue where these dependencies are treated as first-class research objects.

ASPLOS attracts systems builders who believe that incremental improvement within a single layer is exhausted. These researchers ask: if I can change the hardware contract, what becomes simpler in the software? If I can change the memory layout, how does the CPU execute better? If I add a security instruction, how much complexity disappears from the kernel? The venue specializes in co-design—the deliberate construction of systems where hardware and software are engineered together, not separately.

Who submits to ASPLOS? Academic systems research teams, industry architects (Intel, AMD, ARM, Google, Meta, Microsoft), compiler writers, OS kernel teams, and security researchers. The implicit contract is that papers must address something that cannot be solved by just writing better software or just tweaking a compiler flag. They must explain a fundamental dependency or propose a new point in the design space that only exists when hardware and software are jointly optimized. Reviewers expect end-to-end results, measured systems, and honest accounting of trade-offs. Marketing claims are rejected; real numbers matter.

The 2025 edition includes 164 papers across six themes of equal urgency: large language model inference and training, database and datacenter systems, CPU and GPU microarchitecture, formal verification and security, memory system co-design, and compiler optimization. This is not a specialized ML conference, not an architecture-only conference, and not a systems-software-only conference—it is the intersection of all three, forced to coexist because no real computer can be built by picking one layer and ignoring the rest.

The core constraint

All computing happens under a constraint: energy and latency are inversely related. A processor can reduce latency—execute faster—by consuming more power, or reduce power by executing slower. That curve is fundamental physics and microarchitecture, not a negotiable trade-off. But modern systems are not free to explore that curve at will. They are constrained by two upstream demands that are orthogonal to the energy-latency curve: correctness under concurrency, and constant innovation in workload requirements.

Workload innovation is relentless. In 2024, large language models (LLMs) became production services, not research toys. A single inference request for GPT-4 or Llama 405B touches billions of parameters, engages multiple GPUs in parallel, and must return an answer in seconds because humans are waiting. The same year, database systems moved from static partitioning to elastic resource management—a cluster must decide moment-by-moment whether to allocate cores to OLTP (online transaction processing, latency-sensitive, short-running queries) or OLAP (analytic queries, throughput-sensitive, long-running scans). A neural network model must be trained not once per year but continuously, with dynamic hyperparameter sweeps and composition of multiple experts (Mixture of Experts, MoE) that changes the arithmetic entirely. These workloads did not exist when the CPU and GPU instruction sets were designed. The hardware is now constantly executing code it was never optimized for.

Correctness under concurrency is the second upstream demand. Multiple processes on a single machine, multiple machines in a cluster, and (increasingly) multiple layers of virtualization add complexity that hardware designers cannot hide. A cache line might be read-only (safe to replicate across CPU cores), written by exactly one core (safe to manage locally), or written by multiple cores concurrently (requires explicit synchronization). The OS kernel decides how memory translation works; the compiler decides how to partition computation across cores; the hardware must implement coherence to make all of this work. Any mismatch—hardware that doesn't support the memory model the OS assumes, or a compiler that doesn't understand the cache coherence semantics—produces a broken system.

What physically happens is this: every byte of data, every instruction, and every synchronization operation must flow through a memory system that has a fixed bandwidth. A CPU core might want to execute 10 instructions per cycle (modern CPUs support this), but if only 1 memory request per cycle can enter the memory bus, the core will stall. The memory bandwidth curve is architectural—it depends on physical features like pin count, clock speed, and the number of memory channels. You cannot outrun it with a faster CPU. You can only make better use of the bandwidth you have: prefetch data before you need it, compress data to use fewer bytes, move computation closer to data (near-data processing) to avoid long-distance transfers, or cache aggressively to reduce the number of requests. Each of these strategies has costs—prefetching burns power and can cause cache pollution; compression adds latency; moving computation changes how the software is written; caching requires storage area on the chip.

This is the core constraint that ASPLOS researchers live within: memory bandwidth is fixed, workloads are changing and diverse, correctness under concurrency is mandatory, and energy-latency are fundamentally coupled. No amount of algorithmic cleverness or language-level optimization can make this constraint disappear. Every paper in this venue is essentially a proposal for a new way to navigate this constraint: move the trade-off curve, add a new degree of freedom, or make a different point on the curve reachable than was reachable before.

Themes and subthemes

Theme 1: LLM Inference and Serving at Scale

LLM inference is the dominant workload in the 2025 ASPLOS corpus (37 papers, 23% of the venue). The problem is structural: modern LLMs have 10–400 billion parameters. Each inference request requires two phases: prefill (processing the user's input query, computing attention over all parameters), and decode (generating output tokens one at a time, each requiring a new pass through the model). Prefill is compute-bound and benefits from batching; decode is memory-bound because each token requires loading billions of parameters but doing very little computation per parameter. A single GPU has limited memory bandwidth, and filling all the parameter bytes from memory is the bottleneck.

Subtheme 1a: KV-Cache Scheduling and Memory Management

The key-value cache (KV-cache) is a data structure that stores precomputed attention keys and values during prefill, so the decode phase doesn't have to recompute them. In a batched serving system, multiple requests' KV-caches must coexist in GPU memory. The papers "Past-Future Scheduler for LLM Serving under SLA Guarantees," "Accelerating LLM Serving for Multi-turn Dialogues with Efficient KV-Cache Reuse," "Aqua: Network-Accelerated Memory Offloading for LLMs in Scale-Up GPU Datacenters," and "vAttention: Dynamic Memory Management for Serving LLMs with Advanced Adapters" all address the same core problem: given a fixed GPU memory size, which requests should be in GPU memory now, which should spill to CPU or network memory, and when should we evict them to make room for new requests?

Each paper proposes a different memory management strategy. "Past-Future" tracks patterns in request arrival and token generation to predict future memory demand. "Aqua" uses network-accelerated paging—when GPU memory is exhausted, the system pages KV-cache blocks over the network to other machines rather than to local disk, reducing latency. "vAttention" changes the data layout: instead of storing the full KV-cache as a dense tensor, it builds a sparse virtual-memory abstraction where cache blocks are addressed indirectly, allowing fragmentation and defragmentation without copying. The shared insight: memory layout and scheduling are coupled. The hardware (GPU memory subsystem) only works well with certain access patterns; the scheduler must understand those patterns and issue requests accordingly.

Subtheme 1b: Heterogeneous Device Scheduling

A single GPU is insufficient for large-scale LLM serving. "MoE-Lightning: High-Throughput MoE Inference on Memory-constrained GPUs," "Helix: Serving Large Language Models over Heterogeneous GPUs," "COMET: Towards Practical W4A4KV4 LLMs Serving," "Klotski: Efficient Mixture-of-Expert Inference via Expert-Aware Multi-Batch Scheduling," and "CPU-GPU-IO Pipeline for High-Throughput MoE Inference on Memory-Constrained GPUs" all deploy inference across multiple device types: GPUs (with good compute throughput but limited memory), CPUs (with larger memory but slower compute), and even smartNICs or processing-in-memory (PIM) devices. The scheduler must decide which layer (experts, attention heads, embedding tables) runs on which device, accounting for the bandwidth and latency of data movement between devices.

"MoE-Lightning" proposes expert-aware scheduling: different layers of the MoE model are pinned to the device where they fit best, and the scheduler predicts which experts will be needed and pre-transfers their state. "Klotski" batches multiple requests together and routes each batch's experts to the device with the most available memory, treating the heterogeneous system as a single logical device. "COMET" goes further: it uses mixed-precision quantization (4-bit weights, 4-bit activations, 4-bit KV-cache) to compress the model so more of it fits in GPU memory. All of these papers treat scheduling and data layout as inseparable—you cannot schedule without knowing where data lives, and you cannot place data without knowing what the scheduler will do.

Subtheme 1c: Processing-in-Memory (PIM) for LLM Inference

Four papers—"PIM Is All You Need: A CXL-Enabled GPU-Free System for Large Language Model Inference with Processing-in-Memory," "PAPI: Exploiting Dynamic Parallelism in Large Language Models with Processing-in-Memory," "PUSHtap: PIM-based In-Memory HTAP with Unified Data Storage," and "Affinity-based Optimizations for TFHE on Processing-in-DRAM"—propose pushing LLM inference into processing-in-memory (PIM) subsystems where the CPU or GPU doesn't pull data out to compute; instead, computation happens where the data sits, inside or adjacent to the memory array.

Why is PIM attractive for LLM inference? Because the bottleneck is not computation; it is memory bandwidth. Each token generation requires reading billions of parameters but only a few arithmetic operations per parameter. Traditional CPUs and GPUs have a high compute-to-memory ratio—designed to do a lot of work per byte fetched. PIM devices have a much lower compute-to-memory ratio; they are designed to do simple operations (matrix multiply, reduction) directly on data without moving it far. "PIM Is All You Need" shows that a system with CXL-connected PIM memory, no GPU, can serve LLM inference with better tail latency than a GPU system at lower cost. The trade-off: PIM devices are slower at individual operations but avoid the memory bandwidth cliff. This exemplifies the core constraint: by changing the hardware (adding PIM), the system becomes better at a specific workload (LLM decode) while potentially worse at others (training, where compute throughput matters more).

Theme 2: LLM Training and Distributed Parallelism

LLM training moves parameters around—pulling minibatches of training data, computing gradients through billions of parameters (backpropagation), and updating weights. With multiple GPUs, the system must partition the model across devices (model parallelism), partition the data across devices (data parallelism), or both. Communication happens between each training step (all-reduce operations to synchronize gradients across GPUs), and communication bandwidth becomes a bottleneck. Five papers directly address this: "Cascade: A Dependency-aware Efficient Training Framework for Temporal Graph Neural Networks," "PartIR: Composing SPMD Partitioning Strategies for Machine Learning," "GraphPipe: Improving Performance and Scalability of DNN Training with Graph-Topology-Aware Pipeline Parallelism," "Concerto: Automatic Communication Optimization and Scheduling for Large-Scale Distributed Training," and "FlexSP: Accelerating Large Language Model Training via Flexible Sequence Parallelism."

Subtheme 2a: Automatic Partitioning and Communication Scheduling

"PartIR" is a compiler framework that takes a distributed training specification (data parallelism, model parallelism, or pipeline parallelism) and automatically generates the communication schedule. Instead of hardcoding "after backward pass, do all-reduce," it infers the optimal communication strategy from the model's computational graph. "Concerto" goes further: it profiles communication patterns during training and dynamically adjusts the schedule to overlap communication with computation—while one layer is computing gradients, another layer is already sending its gradients to synchronize.

The key insight: training time is determined by the longest chain of dependencies (critical path). If layer A depends on gradients from layer B, which depends on layer C, all three must complete sequentially. But if layer C's gradients can be sent to other GPUs while layers A and B are still computing, the system has overlapped communication and computation, reducing overall time. This requires the compiler to understand both the hardware's communication capabilities (e.g., which GPUs can exchange data over which networks) and the algorithm's dependencies.

Subtheme 2b: Sparse Mixture of Experts Training

Traditional LLM training trains all parameters all the time. Mixture of Experts (MoE) models have multiple expert layers; each input token is routed to only 1–4 experts, not all experts. This reduces computation per token but introduces sparsity—some experts are busy, others idle. Two papers address this: "MoC-System: Efficient Fault Tolerance for Sparse Mixture-of-Experts Model Training" and "FSMoE: A Flexible and Scalable Training System for Sparse MoE LLMs." The problem: distributed training assumes all devices are busy all the time, so synchronization (waiting for all gradients before updating weights) makes sense. With MoE, devices are not busy equally—a device holding a rarely-routed expert will compute fewer gradients per step. "FSMoE" solves this by decoupling synchronization from computation: each device updates its local parameters independently, and only periodically synchronizes, reducing communication overhead.

Theme 3: Memory Systems and Tiering

A single GPU or CPU has a fixed memory size (8 GB to 640 GB). A single server might have 10 TB (terabytes) of DRAM (dynamic random-access memory), which is expensive, power-hungry, and requires physical space. Modern systems often add a lower-tier memory layer: Intel's CXL (Compute Express Link) protocol allows a server to connect to remote memory over a network interface, with memory-semantic operations (load, store, atomic) that work seamlessly. Five papers—"Adaptive CXL Memory Tiering with Dual-Signal Probabilistic Tracking," "Systematic CXL Memory Characterization and Performance Analysis at Scale," "M5: Mastering Page Migration and Memory Management for CXL-Enabled Systems," "CXL Controller Hardware Hot-Page and Hot-Word Tracking for Precise Tiered Memory Migration," and "Selective CXL Cache Coherence for OLTP"—characterize how to use tiered memory effectively.

The memory tiering problem: if you have GPU memory (small, fast, ~500 GB/s bandwidth), CPU memory (larger, slower, ~100 GB/s), and CXL memory (even larger, much slower, ~10 GB/s), which pages should live in which tier? "M5" proposes hardware-assisted page migration: the memory controller tracks which addresses are accessed most frequently (hot pages), and migrates them from slow to fast tiers automatically. "Systematic CXL" characterizes the latency and bandwidth of real CXL systems: latency is 300–500 ns (compared to 50 ns for local DRAM), but bandwidth can still reach 10 GB/s or more if requests are batched. The design implication: CXL memory is good for batch workloads (bulk data movement) but bad for latency-sensitive single-request access patterns.

Theme 4: Speculative Execution and CPU Security

Modern CPUs execute instructions speculatively: they guess what the next instruction will be, execute it, and roll back if the guess was wrong. This is fast—it hides the latency of branch resolution. But speculation creates a side channel: if you speculate on a secret value and access memory, the cache reflects which memory access happened, even though the speculative result was discarded. An attacker can infer the secret by measuring cache timing. This class of vulnerabilities—Spectre, Meltdown, MDS (Microarchitectural Data Sampling), Slam—has spawned an entire research area. Six papers address this: "PipeLLM: Fast and Confidential Large Language Model Services with Speculative Pipelined Encryption for Confidential LLM Serving on GPU TEEs," "Protecting Cryptographic Code Against Spectre-RSB," "RTL Verification for Secure Speculation Using Contract Sharding," "AMuLeT: Automated Design-Time Testing of Secure Speculation Countermeasures," "Snowplow: Effective Kernel Fuzzing with a Learned White-box Test Mutator," and "Tackling ML-based Dynamic Mispredictions using Statically Determined Security Properties."

Subtheme 4a: Speculative Execution Defenses

"Protecting Cryptographic Code Against Spectre-RSB" uses compiler support to prevent speculative execution from reaching cryptographic code paths that might leak keys. When the CPU mispredicts a branch, the compiler ensures that no secret-dependent memory access happens speculatively. This requires close coordination between the compiler (which knows which variables are secrets) and the CPU (which must honor branch predictions as being conditional).

"AMuLeT" and "Snowplow" take the opposite approach: instead of preventing speculation, they systematically test whether proposed defense mechanisms actually work. "AMuLeT" synthesizes test cases that exploit speculative execution; if a defense mechanism fails the test, it's broken. "Snowplow" uses machine learning to generate test cases (mutations of existing kernel code) that are likely to trigger transient execution bugs.

Subtheme 4b: Side-Channel Mitigation in Hardware

"RTL Verification" (Register Transfer Level—the hardware design language) proves that a CPU design is immune to certain side-channel attacks. This is not simulation; it is formal verification—a mathematical proof that no possible execution of the CPU can leak information through a side channel. The cost is substantial: verification tools are expensive, and they must abstract away low-level details, so they can't catch all attacks. But for high-security hardware (cryptographic accelerators, trusted execution environments), the insurance is worth it.

Theme 5: Compiler Optimization and Code Generation

Compilers bridge the gap between source code (written by humans in Python, C++, Rust) and machine code (executed by CPUs and GPUs). A good compiler can make code run 2–10× faster by reorganizing instructions, reordering memory accesses, and using specialized hardware instructions. Seven papers focus on compiler optimization; "Einsum Trees: An Abstraction for Optimizing the Execution of Tensor Expressions," "Faster Chaitin-like Register Allocation via Grammatical Decompositions," "SmoothE: Differentiable E-Graph Extraction," "Exo 2: Growing a Scheduling Language," "Target-Aware Implementation of Real Expressions," "Pruner: A Draft-then-Verify Exploration Mechanism to Accelerate Tensor Program Search," and "Mosaic: Exploiting Instruction-Level Parallelism on Deep Learning Accelerators" address different aspects.

Subtheme 5a: E-Graphs and Compiler Automation

"SmoothE: Differentiable E-Graph Extraction" and "Faster Chaitin-like Register Allocation" both use equality graphs (e-graphs)—a data structure that compactly represents multiple equivalent ways to compute the same result. Instead of committing to one code sequence, the compiler builds a graph with all options, then searches for the fastest option on the target hardware. "SmoothE" uses machine learning to predict which option is fastest; "Register Allocation" uses graph algorithms to solve register allocation (assigning variables to CPU registers vs. memory) optimally on machines where registers are limited.

Subtheme 5b: Tensor Compiler Abstractions

Deep learning models are written as sequences of tensor operations (matrix multiply, convolution, attention). A naive compiler translates each operation to a loop nest. But modern hardware benefits from kernel fusion: combining multiple operations into a single loop to avoid writing intermediate results to memory. "Einsum Trees," "Optimizing Deep Learning Inference Efficiency through Block Dependency Analysis," and "Relax: Composable Abstractions for End-to-End Dynamic Machine Learning" all propose new intermediate representations (IRs) for tensor programs that make fusion opportunities visible to the compiler.

Theme 6: Database and Datacenter Systems

Databases run on ASPLOS-relevant hardware: multi-socket servers with tens of cores, caches, and complex memory hierarchies. A single database query might touch millions of pages on disk, read thousands of cache lines into the CPU, and create contention with other queries on the same machine. Three papers—"Necro-reaper: Pruning away Dead Memory Traffic in Warehouse-Scale Computers," "Coach: Exploiting Temporal Patterns for All-Resource Oversubscription," and "Tela: A Temporal Load-Aware Cloud Virtual Disk Placement Strategy"—optimize database and analytics workloads on these systems.

"Necro-reaper" identifies memory accesses that are dead—data that is fetched into the CPU's cache but never used. By eliminating these wasted accesses (through profiling and compiler hints), it reduces memory bandwidth consumption and allows other queries to make progress. "Coach" profiles query workloads to identify patterns: if query A (a long-running scan) always happens at 9 AM, and query B (OLTP) is always heavy at 10 AM, the system can overcommit resources at 9 AM (run more scans) and scale back at 10 AM. This is a software-hardware co-design: the OS must support dynamic resource management, the hardware must provide performance counters that expose cache contention, and the compiler must generate code that the profiler can analyze.

Theme 7: Near-Data Processing and Accelerators

Moving data costs energy. Processing data in place—inside or adjacent to memory—can be more efficient than moving data to a CPU and back. Six papers explore this: "OS2G: A High-Performance DPU Offloading Architecture for GPU-based Deep Learning," "Hopps: Leveraging Sparsity to Accelerate Automata Processing," "ByteFS: System Support for (CXL-based) Memory-Semantic Solid-State Drives," "Accelerating Retrieval-Augmented Generation," "CIPHERMATCH: Accelerating Homomorphic Encryption-Based String Matching with Processing-in-Memory," and "pulse: Accelerating Distributed Pointer-Traversals on Disaggregated Memory."

A Data Processing Unit (DPU) or SmartNIC is a special-purpose processor in the I/O subsystem. Instead of the GPU fetching data from storage over the network, the DPU can preprocess the data locally (decompression, filtering) and send only the results to the GPU. This is attractive for deep learning inference on object storage: a user queries a database of images, the DPU filters and loads images matching the query, and sends them to the GPU for inference. "OS2G" measures the data transfer rate: 80% of time is spent on data movement, 20% on compute. By optimizing the DPU-to-GPU path (using NVIDIA's GPUDirect RDMA, which allows direct memory-to-memory transfer), "OS2G" reduces data movement time and improves throughput.

Theme 8: Formal Verification and Testing

Software bugs are expensive; security bugs are catastrophic. Formal verification is the process of using mathematical proofs to guarantee correctness. Five papers apply formal methods: "Robustness Verification for Checking Crash Consistency of NVM Filesystems," "Formalising CXL Cache Coherence," "Will We Ever have Truly Secure Operating Systems?," "ElasticMiter: Formally Verified Dataflow Circuit Rewrites," and "RTL Verification for Secure Speculation Using Contract Sharding."

"Formalising CXL Cache Coherence" takes the CXL protocol specification (a document describing how memory consistency works) and encodes it in a formal language (Coq, Isabelle, or TLA+). It then proves that any implementation following this protocol will be correct—two CPUs will never disagree about the value of a memory location, and memory updates will be visible in the right order. This proof is machine-checkable; no human reviewer needs to believe it; the computer verifies it. "ElasticMiter" formally verifies compiler rewrites—transformations that change code without changing behavior. For example, a + b + c can be rewritten as (a + b) + c or a + (b + c), but only if addition is associative (which it is not for floating-point due to rounding).

Theme 9: Virtualization and Container Orchestration

When multiple workloads share a single machine, each workload needs an isolated environment. Virtual machines (VMs) emulate a full computer (CPU, memory, I/O) in software; containers are lighter-weight and share the OS kernel but isolate filesystems and process trees. Managing resources across VMs or containers is a scheduling problem: how much CPU, memory, and I/O should each workload get? Three papers address this: "Cooperative Graceful Degradation in Containerized Clouds," "Concurrency-Informed Orchestration for Serverless Functions," and "Vela: A Virtualized LLM Training System with GPU Direct RoCE."

"Cooperative Graceful Degradation" proposes that when a machine is overloaded, applications should not be killed; instead, the OS should negotiate with each application about what to give up: reduce precision, use less memory, or extend latency. This requires hardware support (the OS must have a way to change an application's resource allocation on the fly) and runtime support (the application must be written to handle changing conditions).

Theme 10: Quantum Computing

Quantum computers solve certain problems exponentially faster than classical computers, but they are fragile. Quantum bits (qubits) decohere (lose their state) in microseconds. To run a long computation, errors must be corrected, requiring many physical qubits to encode a single logical qubit. Four papers address quantum computing: "HetEC: Architectures for Heterogeneous Quantum Error Correction Codes," "Realtime Scheduling for Quantum Error Correction Resource Management," "Unified ASIC Acceleration for Diverse Zero-Knowledge Proof Protocols," and "Optimizing Quantum Circuits, Fast and Slow."

"HetEC" proposes that error correction codes should be heterogeneous: different parts of the circuit use different codes optimized for different error types. The compiler must map high-level quantum algorithms (Shor's algorithm for factoring, quantum simulation) to these heterogeneous codes, accounting for the different latencies and fidelities of different codes. This is a compiler optimization problem: the algorithm is fixed, but the mapping to physical qubits is flexible.

Theme 11: Security and Cryptography

Modern systems must protect data from theft and manipulation. Encryption (converting plaintext to ciphertext using a key) is standard, but it has costs. Homomorphic encryption (HE) allows computation directly on encrypted data without decryption. This is powerful—a cloud service can operate on encrypted data and never see the plaintext—but it is also slow: a single addition on encrypted data is 1000× slower than on plaintext. Three papers address cryptography acceleration: "Orion: A Fully Homomorphic Encryption Framework for Deep Learning," "Cinnamon: A Framework for Scale-Out Encrypted AI," and "Practical Federated Recommendation Model Learning Using ORAM."

"Orion" builds a compiler and runtime for running neural network inference on encrypted data. The challenge: HE only supports certain operations (addition, multiplication, but not division or comparisons), and these operations are slow. "Orion" uses approximate computing—for some layers of the network, it is acceptable to use approximations that HE can efficiently compute (e.g., polynomial approximations to activation functions) rather than exact implementations.

Theme 12: Cache and Memory Optimizations

The CPU cache is a small, fast memory (L1: 32 KB, L2: 256 KB, L3: 20 MB) that holds recently accessed data. If an access hits the cache, it takes ~5 ns; if it misses, it takes ~100 ns to fetch from main memory. Reducing cache misses dramatically improves performance. Four papers address caching: "Instruction-Aware Cooperative TLB and Cache Replacement Policies," "OctoCache: Caching Voxels for Accelerating 3D Occupancy Mapping," "Treelet Accelerated Ray Tracing on GPUs," and "Hierarchical Prefetching: A Software-Hardware Instruction-Level Prefetch."

"Instruction-Aware TLB and Cache Replacement" proposes that the CPU should consider not just whether a cache line was recently used (traditional LRU, Least Recently Used policy), but whether the instruction that accessed it is likely to access it again. Some instructions (like those in a tight loop) have good temporal locality; others (like one-time initialization) do not. By tracking instruction patterns, the cache can make better eviction decisions—evicting lines that are unlikely to be reused, even if they were recently accessed.

Theme 13: Prefetching and Speculation

Prefetching is the inverse of caching: instead of waiting for a miss and then fetching, the hardware predicts future accesses and fetches them in advance, hiding latency. But prefetching can harm performance (cache pollution: fetched data displaces useful data) and can leak information (speculative prefetching creates a side channel). Two papers address prefetching: "ShadowLoad: Injecting State into Hardware Prefetchers" and "Instruction Prefetch via Shadow Branch Exposure."

"ShadowLoad" addresses a subtlety: current hardware prefetchers use heuristics (e.g., "if access A was followed by B, prefetch B next time we see A"). An attacker can pollute the prefetcher's history with specially-chosen memory accesses, causing it to prefetch attacker-chosen data and create a timing side channel. "ShadowLoad" proposes to inject the attacker's intended access pattern into the prefetcher, so it prefetches what an attacker wants, revealing the pattern (rather than hiding it under noise). This is a security-performance trade-off: prefetch effectiveness drops if the attacker cannot control the pattern.

Theme 14: IoT and Mobile Computing

Edge devices (smartphones, embedded systems, IoT devices) have limited power (battery) and memory (often megabytes, not gigabytes). Two papers address embedded systems: "Simplifying and Accelerating NOR Flash I/O Stack for RAM-Restricted Microcontrollers" and "Energy-aware Scheduling and Input Buffer Overflow Prevention for Energy-harvesting IoT Devices."

"NOR Flash" proposes a simplified I/O stack for microcontrollers. A traditional OS (Linux, macOS) has layers: filesystem, block device, disk driver, interrupts. On a microcontroller with 8 KB of RAM, these layers waste precious memory. "NOR Flash" combines all layers into one, directly mapping file operations to flash memory operations. This reduces code size and memory overhead, allowing more application code to fit.

Theme 15: Speculative Execution and Side-Channel Attacks

Speculative execution (executing instructions whose results might not be used) is a fundamental vulnerability: speculatively accessing memory leaves traces in the cache, which an attacker can observe. Five papers systematically exploit and defend against these attacks: "Reload+Reload: Exploiting Cache and Memory Contention Side Channel on AMD SEV-SNP," "SMaCk: Efficient Instruction Cache Attacks via Self-Modifying Code Conflict," "HyperHammer: Breaking Free from KVM-Enforced Isolation," "Controlled Preemption: Amplifying Side-Channel Attacks from L1 Instruction Cache," and "DejaVuzz: Disclosing Transient Execution Bugs with Dynamic Execution Analysis."

These papers expose vulnerabilities in virtualization and isolation mechanisms. "HyperHammer" shows that the rowhammer attack (by forcing DRAM rows to access repeatedly, causing bit flips in adjacent rows) can break out of KVM virtual machine isolation—a hypervisor supposed to enforce privacy is circumvented via a hardware vulnerability. The lesson: isolation must be enforced end-to-end, from CPU hardware to hypervisor; a break anywhere in the chain compromises the whole system.

Cross-cutting patterns

Several design patterns recur across all themes. The first is speculative scheduling: systems predict future behavior (which requests will arrive, which data will be accessed, which experts will be needed) and preemptively prepare (prefetch data, transfer model weights, reserve resources). This requires profiling (measuring past behavior), prediction (inferring future behavior from past), and adaptation (changing decisions as predictions prove wrong). Every major system in the corpus does this—LLM schedulers predict token generation patterns, database systems predict query load, and even CPUs prefetch based on historical access patterns.

The second is decoupling of concerns: instead of doing work synchronously (fetch data, process it, store result), systems do work asynchronously in stages. LLM serving decouples prefill and decode; training decouples gradient computation and parameter updates; storage systems decouple reads and writes. This requires new coordination mechanisms (queues, semaphores, memory barriers) but allows overlapping of stages—while stage A is producing results, stage B is already consuming them.

The third is approximate computing: trading exact correctness for speed. Neural networks are robust to noise, so quantization (rounding weights to low precision) or skipping layers (early exit for simple inputs) still produce correct answers most of the time. Floating-point arithmetic is inherently approximate (rounding errors accumulate), so approximate algorithms (iterative refinement, speculation) are just another point on the accuracy-speed curve.

How ASPLOS fits in the ecosystem

ASPLOS produces detailed systems blueprints that other researchers and engineers depend on. Papers showing how to co-design hardware and software for LLM inference have been adopted by cloud providers (AWS, Google Cloud, Azure) and system builders within weeks of publication. Work on memory tiering informs CXL specification evolution—the standard is updated based on measured performance of real systems. Formal verification results from ASPLOS have been incorporated into the CPU design processes of Intel and ARM, ensuring that new microarchitectures don't introduce new side channels.

What ASPLOS does not touch: most of the machine learning research (new neural network architectures, training algorithms, loss functions) happens at venues like ICML and NeurIPS, not ASPLOS. Pure algorithmic optimization (new sorting algorithms, matrix factorization) happens at venues like SODA and ESA. ASPLOS assumes the algorithm is fixed and asks: how can hardware and software co-design make it faster? Device physics (how to make transistors smaller, how to design memory cells) happens at venues like IEDM and ISSCC; ASPLOS assumes the device properties (latency, bandwidth, power) are fixed and designs systems around them.

What is not yet solved

Despite 164 papers, several critical problems remain unsolved. First, cache coherence is still hard. Modern systems use multiple CPUs, GPUs, specialized accelerators, and PIM devices. Each has a cache, and consistency is difficult. CXL standardizes cache coherence for CPUs and remote memory, but GPUs still use different coherence models, and PIM has no standard at all. A program running on a CPU-GPU system must carefully manage which data lives in which cache; there is no single coherence protocol that works efficiently for all workloads.

Second, dynamic workload adaptation remains ad-hoc. LLM serving systems predict request arrival and token generation patterns; database systems predict query load; training systems predict gradient sparsity. But each uses custom prediction logic. There is no general framework for "system adapts to workload characteristics." This means new systems must re-invent prediction and adaptation for each domain.

Third, security-performance trade-offs are not well-understood. Speculative execution is fast but introduces side channels. Encryption is necessary but slow. Formal verification is sound but expensive. Yet the corpus does not deeply compare these trade-offs quantitatively. When should a system tolerate a small security risk (e.g., timing side channels) to gain performance? When is the performance penalty of security acceptable? The community has not established principled guidelines.
