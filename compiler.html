How compilers
close the gap

Hardware mechanisms are half the story. The compiler is what makes them usable — translating high-level intent into efficient machine sequences. Each diagram below shows one transformation, exactly as it runs in the papers across CGO, ASPLOS, and MLSYS 2025.

00 · architecture

The IR bottleneck — and why MLIR uses many levels

Traditional compilers squeeze everything through one narrow IR (LLVM IR), losing domain structure. MLIR keeps multiple levels: a TensorFlow dialect, a linalg dialect, an affine dialect — each lowering progressively without discarding information that enables better optimization.

The bottleneck problem

A matrix multiply lowers to LLVM IR and looks like a generic loop — the tensor structure is gone. Passes that optimize tensors can't fire because they can't see tensors anymore.

What MLIR does

Multi-level IR keeps the tensor representation alive through Linalg → Affine → SCF, lowering one level at a time. Each stage can still see the structure the level above it understood.

01 · optimization

Equality saturation — hold all equivalent programs, extract the cheapest

A greedy optimizer commits to one rewrite at a time. If it picks wrong early, there's no recovery. An e-graph holds all equivalent forms simultaneously — then extracts the cheapest. DialEgg (CGO 2025) integrates Egglog directly into MLIR's pass pipeline.

Greedy optimizers get stuck

If you first apply a×4÷2 → a×2, you may miss that a<<1 is even cheaper. You committed before seeing the full picture.

E-class extraction

The e-graph grows until saturation (no new equivalences possible), then a cost-guided extraction picks the minimum-cost representative from each equivalence class.

02 · memory

Loop tiling — the same computation, in cache-friendly order

Row-major access sweeps across a large matrix, evicting each row before it's reused. Tiling restructures the loops into blocks that fit in L1: every element fetched is reused within the block before the next block starts. The arithmetic is identical; the cache behavior is not.

Why row-major misses

Matrix multiply accesses B column-by-column while iterating rows of A. Each B column access strides across memory — every element in a different cache line.

What tiling achieves

A tile of A and a tile of B both fit in L1. All C[i][j] updates for that tile complete before the tile evicts — converting cold misses to warm hits.

03 · parallelism

Vectorization — prove independence, then run 8 at once

A scalar loop executes one element per cycle. AVX2 can process 8 floats in a single instruction; AVX-512, 16. The vectorizer's job is to prove that N iterations have no data dependencies, then widen the loop — trading one 8-cycle scalar run for one 1-cycle SIMD instruction.

Dependency check

If a[i] depends on a[i-1], the loop can't be vectorized — the next iteration needs the previous result. Alias analysis determines whether memory accesses could overlap.

Remainder handling

If N isn't a multiple of 8, the vectorizer emits a scalar epilogue for the leftover elements, or uses a predicate mask to process a partial vector.

04 · security

ARM MTE — hardware memory tagging at ~5% overhead

Software bounds-checking adds 2–3× overhead. ARM MTE stores a 4-bit color tag in the top bits of every pointer AND in shadow memory beside each allocation. Every load/store hardware-checks the tags in parallel — at ~5% overhead. Cage (CGO 2025) uses MTE + PAC to make WebAssembly heaps safe with no software checks.

How the tag is stored

ARM's 64-bit address space has spare bits in the top byte (virtual addresses only use 48–52 bits). MTE repurposes 4 of those bits for the color tag — no change to pointer width.

Use-after-free detection

On free(), the allocator changes the shadow tag for that slot to a new random color. The stale pointer still holds the old tag. The next access finds a tag mismatch → hardware trap.

05 · code generation

Register allocation — assigning variables to fast slots

Variables that are alive at the same time cannot share a register — they interfere. The allocator builds an interference graph and finds a coloring: assign a register-color to each variable so no two interfering variables share one. When the graph needs more colors than registers exist, one variable spills to the stack.

The NP-hard part

Optimal register allocation (minimum spills) is NP-complete for general interference graphs. Every backend uses a greedy heuristic — Chaitin coloring or linear-scan — that gets close fast.

Spill cost

A spilled variable adds a store to memory on every write and a load on every read. In hot loops, spills dominate. The allocator weighs spill frequency against the cost of using a callee-saved register.

06 · runtime

JIT compilation — specialize for what actually runs

An AOT compiler must handle all inputs: any type, any device, any shape. A JIT watches the actual runtime calls, identifies the dominant path, and emits a specialized native stub for exactly those conditions — removing every branch for other paths. Proteus (CGO 2025) does this for GPU kernels at the LLVM IR level.

The trade-off

JIT adds startup latency (compilation time) before the fast path is available. Short-lived programs pay the cost without benefiting from it. PyPy and V8 use tiered JIT: first interpret, then JIT the hot functions.

Deoptimization

If a rare input arrives that violates the JIT's assumptions, the stub must deoptimize — fall back to the generic interpreter. Good JITs handle this without crashing.

07 · search

Synthesis as search — the compiler finds code it cannot write

Some optimal programs can only be found, not hand-coded. A sorting network for N elements has exponentially many orderings — the optimal one is discovered by A* over the program space, guided by a cost function, pruning provably suboptimal branches. Synthesis of Sorting Kernels (CGO 2025) finds networks competitive with hand-tuned and AlphaDev results without TPU clusters.

Why A* beats brute force

A* uses a heuristic to prune branches where the best possible completion already exceeds the cost of the current best solution. It finds the optimum without exhaustive enumeration.

Beyond sorting

The same approach finds optimal hash functions (Automatic Synthesis of Specialized Hash Functions, CGO 2025) and quantum circuits (ASDF) — anywhere the compiler can express cost and constraints.
